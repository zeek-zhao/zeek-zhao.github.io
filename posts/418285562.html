索引与执行计划

[!info] 本页概览
本文讲解 MySQL 索引原理（B+Tree）、索引类型、聚簇/二级索引、最左前缀、EXPLAIN 执行计划解读与索引失效场景，配可运行示例。

核心概念

  • 索引：帮助数据库高效获取数据的有序数据结构，本质是空间换时间。
  • B+Tree：InnoDB 默认索引结构，非叶子只存键、叶子存数据并串联，适合范围查询。
  • 聚簇索引：主键索引，叶子存整行数据；每表一个。
  • 二级索引（辅助索引）：叶子存主键值，回表查整行。
  • 回表：二级索引查到主键后再回聚簇索引取行；覆盖索引可避免。

[!note] 设计建议
组合索引把等值查询列放前面、范围查询列放后面；选择性高的列优先。

EXPLAIN 解读

列 含义 关注点
id 执行顺序 大 id 先执行
select_type SIMPLE/PRIMARY/SUBQUERY 避免 DEPENDENT SUBQUERY
table 表名/别名 多表时看顺序
type 访问类型 const > eq_ref > ref > range > index > ALL（全表扫描）
possible_keys 可能索引 —
key 实际索引 期望非 NULL
key_len 索引长度 越短越好
rows 估算扫描行 越小越好
Extra 附加信息 Using index（覆盖）/ Using filesort（需优化）

索引失效场景

覆盖索引与索引下推

常见坑

  1. 索引过多：每个索引都有写入代价，单表索引数控制在 5-8 个内。
  2. 低选择性列建索引：性别、状态这类列区分度差，收益低。
  3. 更新频繁列建索引：写放大；权衡读写比例。
  4. 大表加索引锁表：用 pt-online-schema-change 或 gh-ost 在线变更。
  5. EXPLAIN 显示走了索引但依然慢：关注 key_len/rows 是否过大，或回表严重。

最佳实践

  • 小表无需索引；中大型表为 WHERE/JOIN/ORDER BY 高频列建索引。
  • 用 EXPLAIN 验证每次慢 SQL 的优化效果。
  • 定期用 SHOW INDEX / information_schema 检查冗余索引。
  • 结合 07-SQL 优化 做系统化慢 SQL 治理。
