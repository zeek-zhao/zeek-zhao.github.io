DeviceTree 源码与内核实现

1. 引言：一份内核镜像如何支撑多种硬件平台¶

设备树解决的是一个很实际的问题：把硬件描述从内核代码里挪出去，同一份内核镜像就能跑在多种板子上。我最初是带着一个具体疑问去读这部分源码的——Bootloader 递过来的是一块扁平的二进制 DTB，内核怎么就把它变成能用 for_each_child_of_node 遍历的 device_node 树，最后还匹配上对应驱动？这篇就沿着 5.10 的 drivers/of/ 把这条链走一遍。

我一般先把 struct device_node 和 struct property 这两个结构体的字段记清楚。设备树所有 API 说到底都在操作它们，开头把这两个结构弄明白，后面读代码会省很多劲。

9.1 源码架构：从 DTB 到 platform_device 的一条主线¶

通过对Linux内核中设备树相关源码的分析，我们可以看出设备树实现的主要架构：

  1. DTB解析与初始化：

    • 早期启动阶段保存DTB地址
    • 解析基本配置信息（bootargs、内存等）
    • 展开DTB为内存中的树结构

  2. 设备树到平台设备的转换：

    • 识别可被转换的节点
    • 根据设备树信息创建平台设备
    • 设置设备的资源（内存、中断等）

  3. 设备与驱动的匹配：

    • 基于compatible属性的匹配机制
    • 多级匹配策略（driver_override > of_match > id_table > name）

  4. 设备树动态修改功能：

    • 覆盖机制允许运行时修改设备树
    • 变更集跟踪所有修改，支持撤销操作
    • 通知机制确保系统各部分感知变更

9.2 继续演进的方向：性能、功能、API 与跨架构¶

设备树源码实现仍在不断发展，主要方向包括：

  1. 性能优化：

    • 减少启动时间
    • 优化内存使用
    • 提高节点和属性查找效率

  2. 功能增强：

    • 完善覆盖机制
    • 增强热插拔支持
    • 提供更多动态配置能力

  3. 简化API：

    • 提供更易用的高级API
    • 统一不同子系统的设备树使用方式
    • 减少冗余代码

  4. 跨架构兼容性：

    • 统一ARM、RISC-V、PowerPC等架构的设备树处理
    • 支持更多硬件平台
