1. Bazel 的三个关键概念¶

Apollo 用 Bazel 做构建系统，关键概念有三个：

  • WORKSPACE：定义外部依赖
  • BUILD 文件：声明构建目标（cc_library、cc_binary、cc_test 等）与依赖关系
  • bazel-bin：构建产物目录，可安全删除重建

常用命令是 bazel build 编译、bazel test 跑测试、bazel clean 清理。增量编译时 Bazel 只重编变更的部分，能省不少时间。

2. 编译前先对三件事¶

  • 确认源码版本与 Docker 镜像版本匹配（10.0/11.0 建议 pin commit）
  • 检查磁盘空间（Bazel 缓存与产物占用大）与内存

3. 常用构建命令一览¶

目标 命令 说明
全量编译 ./apollo.sh build 编译全部模块，首次 30–60 分钟
指定模块 ./apollo.sh build --modules=cyber,common,dreamview,canbus 只编译指定模块
单个目标 bazel build //modules/perception:all Bazel 原生目标
并行加速 ./apollo.sh build -j$(nproc) 按核数并行
清理 bash scripts/apollo_clean.sh 清理构建缓存

构建产物位于 /apollo/bazel-bin，模块二进制与配置文件按目录组织，例如组件动态库路径形如 /apollo/bazel-bin/modules/example/libexample_component.so。

我一般先用 --modules 只编改过的模块，全量编译首次要 30–60 分钟，调试期耗不起这个时间。

6. 构建报错怎么解¶

问题 原因与解法
空间不足 清理 bazel 缓存或扩容
内存不足 限制并行度：bazel build --jobs=4
依赖缺失 检查 dev_start.sh 挂载与镜像版本是否匹配
编译中断 断点续编：重复执行原构建命令即可
分支切换后报错 外部依赖变更需清理重建：bash scripts/apollo_clean.sh

7. 缓存别乱清¶

  • 源码变更后缓存自动失效重编，正常开发无需手动清理
  • 频繁切换分支会导致缓存膨胀，建议定期清理
  • bazel-bin 产物目录可安全删除重建，不影响源码

8. 部署四步：构建到运行¶

部署分四个环节：

  1. 构建：产出模块二进制（bazel-bin 下的可执行文件与 .so）
  2. 打包：将二进制、配置文件与依赖环境制作成运行镜像或安装包
  3. 分发：部署到目标车辆计算平台（如 NVIDIA Orin）
  4. 运行：统一版本、环境变量与配置文件，通过启动脚本拉起

生产环境还需考虑日志收集、版本回滚与远程监控。

部署时务必统一三样：源码版本、镜像版本、配置文件。目标平台架构（x86/ARM Orin）不同时，要在对应架构上交叉编译或原生编译。10.0 起支持物理机直接安装与批量部署，不再强制以 Docker 为运行载体，适合车队级规模化分发。

9. 量产数据佐证¶

截至 2025 年 5 月，Apollo 已在全球部署超 1000 辆无人车、累计超 1100 万次出行服务、安全行驶超 1.7 亿公里；2025 年 1 月软件框架获 ASIL D 功能安全认证。这些量产数据说明当前构建与部署链路已达车规级标准。

代码示例与实现细节¶

操作步骤 / 使用流程¶

  1. 进容器：bash docker/scripts/dev_into.sh，参见 04-开发环境搭建-Docker。
  2. 确认 tag：git describe --tags，与主机构建版本一致。
  3. 全量或按需编译：首次全量 ./apollo.sh build，后续用 --modules 加速。
  4. 跑单测：bazel test //modules/... 确认核心模块通过。
  5. 起模块：用 mainboard -d <dag> 或 cyber_launch start <launch> 启动。
  6. 验数据：cyber_monitor 观察通道，cyber_recorder record 录制。
  7. 开可视化：./scripts/bootstrap.sh 后访问 DreamView，参见 14-调试与可视化工具-DreamView。
  8. 部署：将 bazel-bin 产物与 conf/dag 一并打包下发到目标机。

注意事项与常见坑¶

  1. 首次编译耗时长：全量编译可能 30-60 分钟，耐心等待，用 -j 加速。
  2. 内存不足：并行编译吃内存，内存小于 32GB 时降低 -j 值。
  3. BUILD 依赖缺失：新增 .cc 未在 deps 声明会链接失败，逐一补齐 deps。
  4. proto 生成失败：proto 文件路径写错或 import 未声明，检查 proto_library deps。
  5. linkshared 配置错：组件 so 必须 linkshared = True，否则 mainboard 加载失败。
  6. DAG 路径写错：module_library 指向不存在的 so，启动时报加载失败。
  7. 测试缓存假象：Bazel 会缓存测试结果，改代码后需 --nocache_test_results 强制重跑。
  8. 磁盘爆满：bazel 缓存很大，定期 bazel clean，但会牺牲增量编译速度。
  9. 中文社区反爬：知乎链接需登录，仅作延伸参考。
  10. 部署漏文件：只拷 so 不拷 conf/dag 会导致模块起不来，部署要打包完整。
