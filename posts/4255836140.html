13-RBAC权限控制

RBAC 用 ServiceAccount、Role 和 RoleBinding 控制谁能在集群里对哪些资源做什么操作。
📅 2026-11-07· 更新于 2026-11-07 · 579 字 · 约 2 分钟 ✍ zeek.zhao #指南#k8s

RBAC 权限控制

本篇接在 12-HPA自动伸缩 之后，把容量管稳了，最后得管权限：RBAC 回答的是「谁（主体）能对哪些资源（对象）做什么操作（动词）」。我的原则是默认不给权限，要用什么给什么。

三个对象决定谁能做什么¶

对象 作用域 作用
ServiceAccount 命名空间 集群内进程的身份
Role / ClusterRole 命名空间 / 集群 定义权限集合
RoleBinding / ClusterRoleBinding 命名空间 / 集群 把角色绑定到主体

先给进程一个身份¶

Role 里写清资源和动词¶

RoleBinding 把角色接到身份上¶

我一般绑完就顺手用 kubectl auth can-i 验一遍，比事后翻审计日志快得多。

跨命名空间用 ClusterRole¶

动词分读取写入两类¶

动词 含义
get / list / watch 读取
create / update / patch / delete 写入
* 全部
🔥最佳实践
  • 权限最小化：只给需要的资源与动词；
  • 应用 Pod 默认使用 default SA，应显式 serviceAccountName 指定专用 SA；
  • 生产常用 kubectl get clusterrolebinding cluster-admin -o yaml 审查管理员绑定。

我的习惯是 Pod 显式写 serviceAccountName，不用 default 那个兜底身份。

⚠️注意
RBAC 不替代网络隔离；Pod 间流量控制用 NetworkPolicy。

配 RBAC 就是三步：建 ServiceAccount、用 Role 收窄资源和动词、再用 RoleBinding 绑上；集群级权限换 ClusterRole，配完用 can-i 验证，网络隔离另交给 NetworkPolicy。
