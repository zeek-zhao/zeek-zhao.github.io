U-Boot源码结构与启动流程

说实话，U-Boot 这套源码我反复读过几遍，每回都能挖出之前漏掉的细节。它要干的活儿说白了就两件：把硬件初始化到位，再把内核搬进内存、把控制权交出去。我一般按「目录结构 → 两阶段启动 → 关键模块」这条线读，比顺着文件从头啃快得多。

一图看懂：源码按功能分区，启动分汇编与 C 两段职责衔接。

graph LR TOP[顶层目录 分区] --> ENTRY[入口 汇编阶段] ENTRY --> C[C 阶段 重定位初始化] C --> CMD[命令系统] C --> ENV[环境变量] C --> DM[驱动模型] C --> MM[内存管理]

一、源码按功能分区，先定位入口再顺着流程读¶

我一般先把顶层目录扫一遍，弄清哪块放架构相关代码、哪块放通用命令和驱动，再回头看启动链路，这样读起来不容易迷路。

1.1 先看顶层目录的功能分区¶

U-Boot的源码组织清晰，按照功能和架构进行分类。以U-Boot 2020.01版本为例，主要目录结构如下：

  • api/ API接口实现
  • arch/ 架构相关代码（arm、x86、mips等）
  • board/ 特定板级支持包
  • cmd/ 命令实现
  • common/ 通用功能代码
  • configs/ 各开发板配置文件
  • disk/ 磁盘分区处理代码
  • doc/ 文档
  • drivers/ 驱动程序
  • dts/ 设备树源文件
  • env/ 环境变量处理
  • examples/ 示例代码
  • fs/ 文件系统支持
  • include/ 头文件
  • lib/ 库函数
  • net/ 网络相关代码
  • post/ 上电自检代码
  • scripts/ 构建脚本
  • test/ 测试代码
  • tools/ 开发工具

1.2 主要模块及其关系¶

U-Boot源码模块间的关系可以概括为以下几点：

  1. 架构相关代码：位于arch/目录，根据不同CPU架构分类，如ARM、MIPS等
  2. 板级支持包：位于board/目录，包含特定开发板的初始化代码和配置
  3. 驱动程序：位于drivers/目录，提供硬件设备驱动
  4. 命令系统：位于cmd/目录，实现U-Boot命令行界面的各个命令
  5. 公共代码：位于common/和lib/目录，提供通用功能和库函数

这些模块通过清晰的接口相互协作，共同实现U-Boot的功能。

1.3 编译系统分析¶

U-Boot使用基于Kconfig的配置系统和Makefile构建系统：

  1. 配置系统：使用Kconfig定义配置选项，通过make xxx_defconfig应用预定义配置
  2. 构建系统：使用多层次Makefile结构，顶层Makefile负责全局控制，各目录下的Makefile负责本目录的编译

四、Legacy uImage 够用，多组件场景更该换 FIT¶

我倾向新项目直接用 FIT：它把内核、设备树、ramdisk 打成一个带校验的包，升级时不用再操心几个文件版本对不上。

U-Boot支持多种格式的内核映像，以适应不同平台的需求。

4.1 Legacy uImage 是带头部的单镜像格式¶

Legacy uImage是U-Boot传统的内核映像格式，它在普通内核二进制文件的基础上添加了一个64字节的头部。

4.1.1 uImage头部结构

头部包含的信息包括：

  • 魔数（Magic Number）：标识这是一个有效的uImage（0x27051956）
  • 头部CRC校验和：用于验证头部完整性
  • 时间戳：映像创建时间
  • 数据大小：映像数据的大小
  • 加载地址：内核加载到内存的地址
  • 入口点地址：内核开始执行的地址
  • 数据CRC校验和：用于验证数据完整性
  • 操作系统类型：如Linux、VxWorks等
  • CPU架构：如ARM、MIPS等
  • 映像类型：如内核映像、ramdisk等
  • 压缩类型：如gzip、bzip2等
  • 映像名称：描述性名称

4.1.2 创建uImage

U-Boot提供了mkimage工具来创建uImage：

参数说明：

  • -A：指定CPU架构（arm）
  • -O：指定操作系统（linux）
  • -T：指定映像类型（kernel）
  • -C：指定压缩方式（gzip）
  • -a：指定加载地址（0x20008000）
  • -e：指定入口地址（0x20008000）
  • -n：指定映像名称
  • -d：指定输入文件（zImage）
  • 最后一个参数是输出文件名（uImage）

4.1.3 U-Boot加载Legacy uImage的过程

当使用bootm命令加载uImage时，U-Boot会执行以下操作：

  1. 检查映像头部的魔数（ih_magic），确认这是一个有效的uImage
  2. 验证头部的CRC校验和（ih_hcrc）
  3. 验证数据的CRC校验和（ih_dcrc）
  4. 根据压缩类型（ih_comp）解压映像（如果需要）
  5. 将映像加载到指定的加载地址（ih_load）
  6. 跳转到入口点地址（ih_ep）开始执行

4.2 FIT 用设备树把多个组件打包校验¶

随着嵌入式系统的发展，传统的uImage已经不能满足复杂系统的需求，特别是在多设备树和安全启动方面。U-Boot开发了FIT（Flattened Image Tree）格式来解决这些问题。

4.2.1 FIT映像结构

FIT映像基于设备树（Device Tree）格式，通过ITS（Image Tree Source）文件定义，主要包含以下部分：

  1. images节点：存储多个二进制映像（内核、设备树、ramdisk等）
  2. configurations节点：定义不同的启动配置，通过引用images节点中的映像

八、安全启动靠逐级验签，信任根决定整条链¶

随着嵌入式系统安全重要性的提升，U-Boot也引入了安全启动机制。

8.1 安全启动就是逐级验签¶

安全启动的目标是确保只有授权的软件才能在设备上运行，通常包括以下步骤：

  1. 硬件根信任（例如ROM中的代码）
  2. 加密签名验证
  3. 链式信任传递

九、读源码的落点：先跑通启动流程，再按模块深入¶

要把 U-Boot 真正用起来，我建议的顺序是：先照着 start.S 把两阶段启动链路跑通，弄清栈和重定位在哪儿发生；再按你实际要改的部分，深入命令、环境变量或驱动模型其中一块。设备树和 FIT 映像这块改动风险最高，动手前先留一份能正常启动的旧镜像。
