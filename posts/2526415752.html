26-Cyber调度系统详解

任务注册进来之后怎么被执行，是 Cyber 实时性的核心。GPM 三层模型、协程状态机、两种调度策略和唤醒链路，顺着走一遍。
📅 2026-10-25· 更新于 2026-10-25 · 6769 字 · 约 17 分钟 ✍ zeek.zhao #概念#apollo

组件任务注册进调度器之后，到底是谁在什么时候跑它们？这就是调度系统回答的问题，也是 Cyber 实时性的核心。本篇接着 25-Cyber启动系统详解 往下，把 GPM 模型、协程状态机、两种调度策略和唤醒链路走一遍。数据到达怎么唤醒任务，另一半在 29-Cyber数据系统详解。

1. 用协程换可控性¶

1.1 G、P、M 各管什么¶

Cyber 调度器借鉴 Go 语言的 GPM 模型，把”任务怎么跑”拆成三个概念：

graph TD subgraph 每个 M 上运行一个 P M1[系统线程 M] --- P1[处理器 P] P1 --- Q1[协程队列] Q1 --- G1[CRoutine G1] Q1 --- G2[CRoutine G2] Q1 --- G3[CRoutine G3] end M2[系统线程 M] --- P2[处理器 P] P2 --- Q2[协程队列]
  • G（CRoutine）：待执行的轻量任务，调度基本单位
  • P（Processor）：协程执行环境，每个 P 绑定一个系统线程
  • M（Thread）：操作系统线程，真正被内核调度的实体

为什么选协程，理由有三条：

  1. 切换成本低。切换在用户态完成（Cyber 用汇编保存/恢复寄存器），不陷入内核，开销远小于线程切换。
  2. 调度可控。任务由框架调度而非内核，优先级和亲和性能精确控制。
  3. 资源高效。成百上千个协程复用少量线程，避免线程膨胀。

这套取舍我挺认：用一点实现复杂度，换来框架对优先级的完全掌控，对实时系统来说这笔账划算。

2.3 六个状态的流转¶

CRoutine 封装任务函数和调度元信息（id、name、priority、group_name、processor_id）。它的状态机是理解调度的关键：

stateDiagram-v2 [*] --> READY : 创建/入队 READY --> RUNNING : Processor 调度执行 RUNNING --> FINISHED : 函数执行完成 RUNNING --> DATA_WAIT : TryFetch 无数据 RUNNING --> IO_WAIT : 等待 IO RUNNING --> SLEEP : 主动休眠 RUNNING --> READY : Yield 让出 DATA_WAIT --> READY : 数据到达 SetUpdateFlag IO_WAIT --> READY : IO 就绪 SLEEP --> READY : 休眠结束 FINISHED --> [*] : 销毁

5. 几处值得看的实现¶

5.1 切换不进内核¶

Cyber 自带协程库（cyber/croutine/，基于 ucontext 思路以汇编重写）。切换时保存、恢复 callee 寄存器（x86-64 约 10 个寄存器 + 栈指针），全程没有系统调用。协程栈空间受控分配，单进程能轻松支撑数百协程。

5.2 三种并发手段¶

机制 实现 用途
原子操作 std::atomic 状态机、tick 计数
读写锁 自研 AtomicRWLock（读优先） id_cr_ 映射、优先级队列
条件变量 std::condition_variable Processor 空闲等待/唤醒

5.3 绑定核心为了缓存¶

Choreography 的本地队列让任务长期驻留同一核心。工作集持续留在 L1/L2 缓存，避免跨核 cache line 弹跳。”关键任务绑定处理器”这个配置的性能来源就在这儿。

5.4 SysMo 看谁卡住了¶

SysMo 线程周期性（默认 100ms）输出各 Processor 快照，是排查”哪个协程卡死”的第一工具：

还有个必须记住的约束：协程是协作式的。回调里跑一个 500ms 的阻塞计算，整个 Processor 线程都切不走。长耗时工作要么拆开 Yield，要么转 28-Cyber异步调用机制 的异步任务，再不然就独立进程。

6. 瓶颈在哪，怎么调¶

6.1 四类瓶颈¶

  1. 全局队列锁竞争：任务极多时 Classic 策略写锁争用上升 → 迁移到 Choreography
  2. 优先级倒置：低优先级协程持有高优先级任务所需锁 → 缩小临界区、用无锁结构
  3. 缓存颠簸：任务在核间漂移 → Choreography 绑定 + cpuset 隔离
  4. 协程饥饿：低优先级永无机会 → 分散到不同处理器/组

6.2 四条调优动作¶

  • 关键路径（控制）最高优先级 + 独占核；感知等计算任务按管线分组
  • processor_policy: SCHED_FIFO 仅用于真正关键的组，防止整机被实时线程占死
  • 用 SysMo 日志观察 processor:routine:执行时长 分布，超过周期预算的协程优先治理
  • 对比修改前后用 cyber_recorder 回放同一数据源，量化端到端延迟

Apollo 10.0 宣称系统整体资源使用降低 50%，单颗 NVIDIA Orin 就能支撑 L4。这个量级的降本，跟 Cyber 的调度和 IO 优化直接相关——更精细的优先级编排、更少的线程与切换、更深的零拷贝协同，是新版调度栈的演进主线。Cyber RT 从 3.5（2019）引入至今，GPM 模型和双策略的框架没变，但调度配置和核隔离已经是量产团队的必修课。

7. 两条主线串起整个调度¶

整个调度拆开看，是 GPM 三层模型加上协作式协程状态机，外面套两种策略：Classic 用全局队列，Choreography 做本地绑定；优先级和亲和性交给配置文件驱动。真正要盯住的是两条线：数据唤醒走 NotifyProcessor，往外接 29-Cyber数据系统详解；状态机靠 UpdateState 的原子语义，它划定了实时性保证的边界——这一点我建议动手前先读代码确认，别凭印象。异步任务池算是同一调度器上的另一类租户，见 28-Cyber异步调用机制。

1. 协程上下文切换时序¶

这段解决「Resume / Yield 到底保存恢复了什么」的问题：主协程保存自身上下文后切入子协程，子协程 Yield 时保存子上下文再回到主协程。

参数怎么调：协程栈空间受控分配，单进程可支撑数百协程；常见坑是协作式调度下在协程里跑阻塞调用，会把整个 Processor 线程卡住。

这段解决「Scheduler / Processor / CRoutine 三类之间什么关系」的问题：给出比正文更完整的类图，含两种 Context 的静态队列成员。

3. ChoreographyContext 的本地队列扫描¶

这段解决「绑定处理器后怎么从本地队列挑任务」的问题：持读锁遍历 cr_queue_，用 Acquire + UpdateState 双重确认协程就绪。

参数怎么调：本地队列按 id 有序，遍历顺序不再体现优先级，绑定任务间应靠处理器独占而非队列顺序保证；常见坑是同一处理器绑定了多个任务却期望优先级生效。

4. 配置层次结构¶

这段解决「调度配置文件里各字段的从属关系」的问题：全局配置 → 线程配置 → 调度策略 → 任务组 → 任务列表。

参数怎么调：从顶层 strategy 逐层核对到具体任务的 prio / processor；常见坑是只配了 processor 却忘了给组设置 SCHED_FIFO 与 processor_prio，实时性仍不达标。

5. 任务创建完整时序¶

这段解决「组件 CreateTask 后内部依次做了什么」的问题：创建协程 → 设置 id/name → DispatchTask → 设置优先级与组 → 注册唤醒回调。

6. SysMo 检查器主循环¶

这段解决「SysMo 怎么周期性触发调度快照」的问题：while 循环调用 CheckSchedStatus 后按 sysmo_interval_ms_ 等待。

参数怎么调：默认间隔 100ms，可在监控配置中调整；常见坑是间隔设得过小导致日志本身成为系统负载，尤其在高核数机器上。

7. 优先级倒置时序¶

这段解决「为什么低优先级任务会拖死高优先级任务」的问题：低优先级持锁，中优先级抢占，高优先级反而阻塞。

参数怎么调：缓解手段包括优先级继承协议、缩小临界区、无锁数据结构；常见坑是只提高高任务优先级却不处理锁，倒置依然存在。

8. 感知模块调度配置¶

这段解决「多路传感器任务如何分处理器」的问题：perception_group 把 Camera/Lidar/Radar 分别绑到 0/1/2 号处理器，processor_policy 取 SCHED_FIFO。

参数怎么调：相机处理通常计算最重，给最高 prio；常见坑是 cpuset 与系统中断核重叠，造成周期性卡顿，详见 16-感知模块-视觉感知。

9. 规划与控制模块调度配置¶

这段解决「关键实时任务怎么独占核」的问题：rt_critical 组用 1to1 亲和绑 12–15 核，Control / Planning 分别固定处理器。

参数怎么调：processor_prio 取 98 属高实时档，务必配合核隔离；常见坑是所有组都开 SCHED_FIFO，实时线程占满整机反而让系统失去响应，相关控制逻辑见 22-控制模块。

这段解决「调度策略未来如何按负载动态调整」的问题：监控 → 分析 → 生成策略 → 应用 → 再监控的闭环。

注意事项与常见坑¶

  1. 协程里跑阻塞调用：协作式调度下 500ms 阻塞会把整个 Processor 卡住，其他任务全部饿死；长耗时工作要 Yield 或转异步。
  2. 任务名与配置不一致：名称大小写或空格不符会静默落默认组，配置完全不生效，必须逐字核对。
  3. 同处理器绑定多任务却期望优先级：Choreography 本地队列按 id 遍历，绑定任务间不体现优先级，应靠独占处理器保证。
  4. 所有组都开 SCHED_FIFO：实时线程可占满整机，反而让系统失去响应；仅关键组使用实时策略。
  5. cpuset 与中断核重叠：网络/传感器中断落在任务核上会造成周期性延迟尖峰，需结合 /proc/interrupts 隔离。
  6. SysMo 间隔设得过小：监控日志本身成为负载，高核数机器上尤其明显，默认 100ms 通常够用。
  7. 优先级倒置未处理：只提高高任务优先级而不解决锁持有问题，倒置依旧；应缩小临界区或用无锁结构。
  8. 协程饥饿：低优先级任务长期无执行机会，Cyber 未实现动态优先级提升，需手工分散到不同处理器。
  9. 处理器编号越界：processor_id ≥ proc_num 会让任务误入全局队列，缓存亲和性失效而不自知。
  10. 忽略 cgroup 限制：容器/车机环境的 cgroup cpu quota 会压缩实际可用核数，配置里的 cpuset 不一定生效。
  11. 盲目切 Choreography：任务同质场景下本地绑定收益有限，反而增加配置复杂度，先用 SysMo 数据判断瓶颈。
  12. 回放数据不具代表性：调优前后对比必须用同一段典型场景数据，否则延迟数字没有可比性，测试方法见 54-自动驾驶测试方法。

调度的落地步骤¶

  1. 先用默认 sched.conf 跑通录制回放，采集基线延迟。
  2. 只改一个字段（policy 或 pool_size），对比 record 回放的调度延迟直方图。
  3. 确认无饥饿后再绑核；用 top -H 观察每个 worker 的 CPU。
  4. 把最终配置写入组件 conf，随 launch 文件一起版本化。
