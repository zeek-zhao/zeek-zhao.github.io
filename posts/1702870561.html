Linux时间子系统详解

时间子系统看起来铺天盖地，拆开其实就两件事：回答“现在几点”，以及“到点叫我”。我一般先把 clocksource 和 clockevent 的分工弄清楚，再看 timekeeping 和 timer，整条链路就顺了。

下面从秒的定义讲到用户空间接口，再往里走 timekeeping、POSIX clock/timer、tick、clocksource/clockevent，最后落到一个 ARM 的具体驱动实现。

一图看懂：时间子系统从 tick 到高精度定时器，向用户供取时与睡眠服务。

graph TD TK[Timekeeping 维护系统时钟] --> CLOCK[时钟源 clocksource] TK --> TIMER[定时器 hrtimer 动态 tick] API[用户接口] --> GET[取时 settime] API --> SLEEP[睡眠 nanosleep] API --> ALARM[alarm 与 POSIX timer] TIMER --> API

一、时间基准：秒的定义、闰秒与 epoch¶

1. 秒的两种定义与 Linux 的取舍¶

1.1 如何定义秒？

在定义秒这个术语时有两个标准：

  1. 以铯133的振荡频率来定义秒：这种基于物理属性的定义赋予秒一个恒定的时间长度。
  2. 依据地球自转和公转来定义秒：这符合人类习惯，即一天24小时，每小时60分钟，每分钟60秒。

对于Linux内核而言，它采用第一种定义，参考点(Linux epoch)是UTC时间。历史上，POSIX标准曾将时间参考点设定为1970年1月1日0点0分0秒(GMT)，后来修正为UTC时间。

1.2 如何处理闰秒(leap seconds)？

UTC时间与日常使用的日历时间有差异，因此产生了闰秒概念。为使UTC时间与日历时间保持一致，当误差累积到1秒时，会对UTC时间进行调整，即闰秒。

Linux内核虽然以UTC时间为epoch，但不考虑闰秒问题。对短时间段而言，UTC和GMT基本相同，大部分应用能正常工作。内核支持NTP协议，可以与外部时间服务器同步。

我一般先确认用哪个 clock：看墙上时间用 CLOCK_REALTIME，算耗时用 CLOCK_MONOTONIC，别拿 realtime 测间隔，NTP 一调就出错。

1.3 如何处理闰年

地球绕太阳公转的周期是365.2564天，因此需要特别处理闰年：

  • 每四年一个闰年(每年366天，其余为365天)
  • 每100年不设闰年(能被100整除的年份)
  • 每400年一个闰年(能被400整除的年份)

这样计算的结果是每400年少算了0.44天，精度已足够满足需求。

1.4 如何定义基准？

时间有绝对和相对概念。例如”1小时后吃饭”是相对时间，”1949年10月1日”是绝对时间。

系统需要定义一个epoch作为基准点，所有时间表示基于此基准点。Linux采用与Unix相同的epoch：1970年1月1日0点0分0秒(UTC)。NTP协议使用1900年1月1日0点0分0秒(UTC)作为基准点，GPS系统则使用1980年1月6日0点0分0秒(UTC)。

    • CONFIG_NO_HZ_IDLE：系统idle时停止周期性tick
    • CONFIG_NO_HZ_FULL：非idle状态也可以停止tick

  3. Timer模块配置:

    • CONFIG_HIGH_RES_TIMERS：高精度timer
    • CONFIG_TICK_ONESHOT：支持one-shot类型的tick device

三、用户接口：取时、睡眠与定时器三类服务¶

1. 取时间、设时间与时钟调整¶

1.1 秒级函数：time和stime

time返回当前时间点到Linux epoch的秒数，stime则设定此值。设定时间的进程必须有CAP_SYS_TIME权限。

1.2 微秒级函数：gettimeofday和settimeofday

这些函数工作原理与秒级函数类似，但精度提高到微秒级。在新POSIX标准中，这些接口被标为过时，推荐使用clock_gettime和clock_settime。

1.3 纳秒级函数：clock_gettime和clock_settime

这些函数支持不同类型的system clock：

  • CLOCK_REALTIME：真实世界的墙上时钟，可设定
  • CLOCK_MONOTONIC：单调递增的时钟，不可设定
  • CLOCK_MONOTONIC_RAW：不受NTP调整的本地晶振时钟
  • CLOCK_PROCESS_CPUTIME_ID：进程CPU时间
  • CLOCK_THREAD_CPUTIME_ID：线程CPU时间

1.4 系统时钟的调整

adjtime函数可以缓慢修正系统时钟，避免时间突变。

adjtimex实现了RFC 1305定义的更复杂时间调整算法。

2. 四种睡眠接口¶

2.1 秒级sleep：sleep

当前进程睡眠指定的秒数。如果被信号中断，返回值表示未睡眠的秒数。

2.2 微秒级sleep：usleep

概念与sleep类似，但精度为微秒。返回0表示成功，-1表示失败。

2.3 纳秒级sleep：nanosleep

nanosleep函数是推荐的睡眠接口，精度为纳秒。如果被信号打断，rem参数返回剩余时间。

2.4 高级sleep：clock_nanosleep

可基于不同的系统时钟进行睡眠，flags指定request参数是相对时间还是绝对时间。

3. alarm、interval timer 与 POSIX timer¶

3.1 alarm函数

在指定秒数后向进程发送SIGALRM信号，是最简单的timer接口。

3.2 Interval timer函数

每个进程支持3种timer，不同的timer定义了计时方式和发送的信号：

  • ITIMER_REAL：基于CLOCK_REALTIME，发送SIGALRM信号
  • ITIMER_VIRTUAL：仅计算进程用户空间代码执行时间，发送SIGVTALRM
  • ITIMER_PROF：计算进程总执行时间(包括内核代码)，发送SIGPROF

3.3 POSIX Timer函数

POSIX timer提供更灵活的timer服务：

POSIX timer允许更多的timer数量、多种通知方式和更高的精度。

我平时测耗时只用 clock_gettime，睡眠用 nanosleep；被信号打断时记得去看返回的剩余时间。

3. 何时切到 oneshot¶

Dynamic Tick模式的关键步骤：

  1. 系统初始化时以周期性tick模式启动
  2. 在timer软中断中检查是否可以切换到oneshot模式
  3. 切换到oneshot模式时，设置tick_device的event handler为hrtimer_interrupt
  4. 创建sched_timer来模拟周期性tick
  5. 系统进入idle时调用tick_nohz_idle_enter停止sched_timer
  6. 系统退出idle时调用tick_nohz_idle_exit恢复sched_timer

我一般把周期 tick 和 oneshot 当成同一套机制的两种模式，切换只在 timer 软中断里做一次。

4. 深度休眠时的全局广播¶

Tick Broadcast Framework解决的问题：当CPU进入深度休眠状态时，本地timer可能会被停止，无法正常工作。此时需要使用一个全局的timer来广播tick事件唤醒各个CPU。

工作原理：

  1. CPU进入idle前向broadcast framework注册需求
  2. Broadcast timer设置为所有请求中最早的超时时间
  3. Timer触发时，通过IPI向需要的CPU发送tick事件
  4. CPU退出idle后，重新启用本地timer
