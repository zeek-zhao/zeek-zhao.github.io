03-工程结构

发表于2026-10-24|Zephyr
|浏览量:

[!info] 本节目标
理解 Zephyr 仓库布局与工程组织方式。

1. 主仓库布局

zephyr 仓库按功能组织目录，kernel 存放内核源码，drivers 存放驱动，arch 存放架构代码，samples 存放示例，boards 存放板级定义，doc 存放文档。目录划分清晰，便于定位与贡献。

2. 应用工程结构

应用工程包含 CMakeLists.txt、prj.conf 与应用源码，可选 devicetree 覆盖与模块。构建系统自动集成应用与 Zephyr 源码，配置合并生成最终固件。工程结构规范支撑可维护开发。

3. 模块机制

模块是 Zephyr 扩展机制，通过 manifest 引入第三方组件。模块可包含驱动、库与应用代码，构建自动集成。模块化促进代码复用，生态组件以模块形式发布。

4. 板级定义

boards 目录定义板卡硬件配置，包含设备树文件、Kconfig 默认与文档。板级定义驱动构建与烧录配置，新板卡移植在此添加。板级目录结构规范，便于社区共享。

5. 示例与测试

samples 提供功能示例，tests 提供测试用例。示例演示 API 用法，测试验证功能正确。示例与测试是学习与贡献的入口，运行验证理解行为。

6. 构建产物

构建生成固件镜像、map 文件与配置输出。构建目录隔离源目录，清理重建方便。产物分析工具查看内存占用与符号，辅助优化与调试。

7. 实践建议

熟悉目录布局提升检索效率，阅读示例学习 API 用法。工程结构按规范组织，模块划分合理。文档记录自定义结构，团队协作统一约定。

8. 常见问题

理解工程结构时最常见的误区是把 zephyr 目录当作唯一的代码来源：实际开发中模块（module）机制允许把驱动、库与应用组织在独立仓库，通过 west manifest 统一管理。另一个易混点是 boards、soc 与 dts 目录的职责边界：boards 描述板级外设与配置，soc 描述芯片内核与平台，dts 存放设备树源文件与绑定。定位问题时先判断问题属于哪个层级，再进入对应目录检索，效率会高很多。新增文件时要注意 CMakeLists 与 Kconfig 的引用关系，文件放对了位置但没有加入构建系统，是编译期最常出现的”文件存在却不生效”现象。
