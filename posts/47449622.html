1. 概述¶

1.1 MCP 是什么¶

MCP（Model Context Protocol，模型上下文协议）是统一的开放标准，让 AI 应用通过 Tools / Resources / Prompts 三种原语与外部系统交互。Atlassian MCP 把 Jira 与 Confluence 的 REST API 包装成一组 MCP 工具，让 AI 助手直接用自然语言操作二者。

1.2 本次接入能做什么¶

  • 用 JQL 搜索 / 读取 Jira Issue，查项目、看板、Sprint、工作日志
  • 创建 / 更新 / 流转 / 评论 / 删除 Issue，管理 Epic 与链接
  • 用 CQL 搜索 / 读取 / 创建 / 更新 Confluence 页面与评论
  • 管理页面标签、附件、历史版本、权限与 Space 页面树
🔥典型场景
  • 「用 JQL 找出本周我名下所有未解决的 Bug」
  • 「把 PROJ-123 流转到 In Review 并加一条评论」
  • 「读取 Confluence 空间 ENG 的页面树，总结某页要点」
  • 「在 ENG 空间新建一页，内容来自这份草稿」

2. 方案原理¶

采用社区维护的 mcp-atlassian（GitHub：sooperset/mcp-atlassian，Python 包），以 stdio 方式在本机启动一个 MCP Server 进程，进程内部用 REST API + PAT 访问 Jira / Confluence。实例侧零改动、零插件、零重启。

flowchart LR A[WorkBuddy] -->|stdio| B["mcp-atlassian<br/>(D:/zeek/WorkBuddy/MCP/venv/Scripts/mcp-atlassian.exe)"] B -->|"REST API + Bearer PAT"| C["Jira<br/>issues.rollingwireless.com"] B -->|"REST API + Bearer PAT"| D["Confluence<br/>confluence.rollingwireless.com"]

一个进程同时暴露 Jira 与 Confluence 两套工具（实测 98 个），由环境变量决定连接哪套 / 哪台实例。

5. PAT 认证配置¶

5.1 在 Atlassian 侧生成 PAT¶

  1. 登录 Jira / Confluence → 右上角头像 → Profile → Personal Access Tokens
  2. 点击 Create token，命名（如 workbuddy-mcp），设置有效期
  3. 立即复制 token（生成后不可再次查看）
  4. 分别在 Jira、Confluence 各生成一个 PAT（两者不通用）

5.2 环境变量（Server/DC PAT 模式）¶

变量 必填 说明 示例
JIRA_URL 是 Jira 根地址（不带 /rest 等后缀） https://issues.rollingwireless.com
JIRA_PERSONAL_TOKEN 是 Jira 的 PAT（敏感） <jira-pat>
CONFLUENCE_URL 是 Confluence 根地址 https://confluence.rollingwireless.com
CONFLUENCE_PERSONAL_TOKEN 是 Confluence 的 PAT（敏感） <confluence-pat>
TOOLSETS 否 设为 all 暴露全部工具（推荐） all
JIRA_SSL_VERIFY / CONFLUENCE_SSL_VERIFY 否 自签证书时设 false true
⚠️关键：PAT 与系统严格对应
Jira 的 PAT 只能用于 Jira，Confluence 的 PAT 只能用于 Confluence。用错系统会返回 401，响应头会出现 WWW-Authenticate: OAuth realm=...；正确时响应头为 X-Seraph-LoginReason: OK。本次联调曾因两行 token 顺序颠倒而 401，纠正映射后即 200。
⚠️不要混用 Cloud 变量
Server/DC 用 *_PERSONAL_TOKEN；Cloud 才用 *_USERNAME + *_API_TOKEN。混用会导致认证失败。

6. 客户端配置（HTTP 常驻模式）¶

6.0 为什么最终不用 stdio（2026-10-30 故障根因）¶

最初按 stdio 接入，能连上但极不稳定，最终在 .workbuddy 这个 App 里每次必失败。日志给出的直接证据：

pidSpawned 有值、stderrChunks: 0 —— 进程起来了、没崩、没报错，只是 30 秒内没完成握手。逐步测下来根因是一条链：

测量项 结果 结论
python -c "pass" 576 ms 解释器本身正常
import fastmcp 2.5–4.8 s 单个包就极慢
import mcp_atlassian.servers.main 8.5–13 s 累计导入开销
遍历 site-packages（12,156 文件 / 158 MB） 118 s（1.3 MB/s） 小文件打开极慢
CPU 基准（1e7 次循环） 1.5 s 机器本身偏慢（正常约 0.3 s）

即：Windows Defender 实时扫描 + 慢盘 + 慢 CPU，使 Python 导入几百个模块要 9–13 秒，紧贴 WorkBuddy 的 30 秒 stdio 探活上限（normalizeTimeout 在应用层不可配）。平时勉强过，一旦机器有并发（另一个 WorkBuddy 实例、Electron 预热进程）就冲破 30 秒 → 连接失败。

📝顺带纠正一条早前的错误结论
之前曾判断「本版 WorkBuddy 不读全局 mcp.json」。这个判断是错的。实测 CODEBUDDY_MCP_CONFIG 环境变量里明确含
"atlassian-rw":{"type":"stdio",...,"_workbuddyMcpOrigin":"custom"}，daemon 日志也有 wb:mcp:connect arg="custom-mcp:atlassian-rw" —— 说明 mcp.json 的条目确实被注册并尝试连接了，只是卡在超时。mcp.json 里的条目会被导入连接器体系并带上 _workbuddyMcpOrigin: custom 标记。
🔥已排除的无效优化
  • 裁减工具集：TOOLSETS=all 8.5 s / default 7.0 s / 6 个精选集 11.1 s —— 无稳定收益，导入开销是固定的。
  • 换盘：C: 与 D: 在小文件延迟上无本质差异，瓶颈是杀软扫描而非磁盘型号。

结论：只要还是「每次连接都冷启动 Python」，就治不好。改为常驻 HTTP 服务后，冷启动只付一次，之后连接 0.35 秒完成。

📝结论边界（2026-11-06 补充）
上述「stdio 必超时」只针对重 Python 包。同机接入 jenkins-mcp-server@1.0.3（Node）实测冷启动 < 1 s，stdio 稳定可用，不需要改成 HTTP 常驻。接入新 MCP 时先量启动耗时再套用本结论，详见 04-Jenkins-MCP-连接与使用配置指南 §12.4。

6.2 启动服务¶

该脚本幂等（已在跑就直接返回），实际执行的是 start-mcp-http.cmd：

⚠️ALLOW_GLOBAL_CRED_FALLBACK=true 是 HTTP 模式的硬性前提
不加会一直 401，服务端日志为
UserTokenMiddleware: rejecting unauthenticated MCP request (no user identity and ALLOW_GLOBAL_CRED_FALLBACK is off)。
原因是 HTTP 模式默认按「每用户令牌」鉴权，本场景用的是全局凭据，必须显式放行回落。
⚠️.cmd 文件必须纯 ASCII
中文注释在 cmd.exe（GBK 解码）下会把脚本解析崩，报「此时不应有 XXX」。踩过一次。

6.5 开机自启¶

隐藏启动器已放入启动文件夹：

📝为什么用启动文件夹而不是计划任务
本机安全策略把 schtasks.exe、wscript.exe 列入工具黑名单，无法由 AI 侧创建计划任务。启动文件夹由 Windows 登录时自行拉起，不受影响。
代价：只在登录时启动。若重启了 WorkBuddy 但没重新登录，需手动双击一次 ensure-mcp-http.cmd。

10.1 速查表¶

10.3 本次接入踩坑全表（按代价排序）¶

# 坑 表现 正解
1 stdio 冷启动超 30 秒探活 连接器显示了但「连接失败」；日志 stdio-probe-failed elapsedMs:31568 改 HTTP 常驻（本节 6.0 有完整测量）
2 HTTP 模式缺 ALLOW_GLOBAL_CRED_FALLBACK 服务能起、端口在听，但请求一律 401 启动脚本加该环境变量

4 --path /mcp 在 Git Bash 里被 MSYS 转成 Windows 路径 服务打印的 URL 变成 http://127.0.0.1:9111D:/.../mcp 用 .cmd/cmd.exe 启动，或 MSYS_NO_PATHCONV=1
5 http_proxy 干扰本地探测 curl / httpx 打到 127.0.0.1:9111 返回 502 或连不上 探测时 NO_PROXY=127.0.0.1,localhost 或 curl --noproxy '*'
6 缺 "type": "stdio" 条目不进连接器列表（「没显示」） 每条 server 必须显式写 type
7 PAT 张冠李戴 两端 401 用 X-Seraph-LoginReason: OK 判定，逐端验证
8 安全策略拦 schtasks / wscript 无法由 AI 侧创建计划任务 改用启动文件夹；wscript 由用户手动双击即可
9 两个 App 混淆 改了配置却不生效 WorkBuddy.exe→.workbuddy；WorkBuddyAI.exe→.workbuddy-ai，别加错

10.2 分场景详解¶

场景一：401（最典型）

  • 检查 token 是否与系统匹配——Jira 的 PAT 在 Confluence 必 401，反之亦然
  • 用 curl 单独验证：/rest/api/2/myself（Jira）、/rest/api/user/current（Confluence）
  • 看响应头：X-Seraph-LoginReason: OK = 成功；WWW-Authenticate = 被拒

场景二：MCP Server 起不来

  • 手动前台运行 "...\mcp-atlassian.exe" 看报错
  • 核对 env 变量名：Server/DC 用 *_PERSONAL_TOKEN，勿用 Cloud 的 *_API_TOKEN

场景三：工具不全

  • 在 env 中加 "TOOLSETS": "all"，重启客户端
🔥万能调试法
先用 curl 确认 PAT 可用，再排查客户端配置，可快速二分定位问题。

11. 安全注意事项¶

⚠️最高优先级
  1. PAT 即密码：权限与账号一致，泄露等于账号泄露
  2. 仅生成时可见：Atlassian 不再次展示 PAT，丢失只能删除重建
  3. 禁止入库 / 入文档 / 入聊天：真实 PAT 仅存于本地 start-mcp-http.cmd，文档一律占位符
  4. 最小权限：如只需只读，可在生成 PAT 时限定范围
  5. 定时轮换：PAT 有有效期，到期前重新生成并更新启动脚本
  6. 本机安全：start-mcp-http.cmd 含明文 PAT，注意设备与文件权限；改为 HTTP 模式后 mcp.json 里只剩一个 URL，已不含令牌
  7. 端口只绑 127.0.0.1：常驻服务无鉴权，绝不可改成 --host 0.0.0.0，否则同网段任何人都能以你的身份访问 Jira/Confluence
📋PAT 泄露应急流程
  1. 登录 Jira / Confluence → Profile → Personal Access Tokens
  2. 撤销（Revoke） 泄露的 token
  3. 重新生成新 token
  4. 更新 start-mcp-http.cmd 中对应值并重启服务（stop-mcp-http.cmd → ensure-mcp-http.cmd）
  5. 排查泄露途径（聊天 / 仓库历史 / 截图），防再次发生
