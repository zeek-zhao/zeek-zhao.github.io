Systemd服务配置与管理

写 systemd 服务单元，我一开始也是照着网上模板抄，能跑就完事，直到有次改完 ExecStart 忘了 daemon-reload，服务死活不生效，排查了小半天。后来才明白，systemd 配置是一套很规整的声明式语言，把单元结构、依赖关系、资源限制这几块吃透，绝大多数服务问题自己就能定位。

这篇按单元文件结构、依赖与激活、安全隔离到排障的顺序，把配置要点和能直接复用的实例串一遍，需要哪块查哪块。

1. 核心认知：声明式配置取代 SysV 脚本¶

我接手别人的服务时，第一件事就是 systemctl cat 看实际加载了哪个文件，再决定改 /etc 还是加 drop-in。

1.1 什么是Systemd服务配置¶

Systemd是现代Linux系统使用的初始化系统和系统管理守护进程，负责在系统启动过程中初始化系统，并管理系统运行过程中的各种服务。服务配置是Systemd的核心功能之一，它通过统一的配置文件格式（称为Unit文件）来定义和管理系统中的各种服务。

Systemd服务配置的主要目标是：

  • 提供统一、标准化的服务定义方式
  • 管理服务之间的依赖关系
  • 控制服务的启动、停止和重启
  • 设置服务的运行环境和资源限制
  • 提供安全隔离机制

1.2 与传统SysV Init的对比¶

传统的SysV Init系统使用Shell脚本来启动和停止服务，而Systemd使用声明式配置文件，这带来了许多优势：

特性 SysV Init Systemd
配置格式 Shell脚本 声明式配置文件
依赖管理 通过命名约定（S01，K01等） 显式声明依赖关系
并行启动 不支持 支持服务并行启动
按需启动 不支持 支持（Socket、D-Bus等）
资源控制 有限 全面（通过cgroups）
服务状态追踪 简单的PID文件 完整的进程跟踪
安全隔离 不支持 支持（namespaces等）

1.3 Systemd服务配置的位置¶

Systemd的Unit文件存储在以下目录中，按优先级从高到低排列：

  1. /etc/systemd/system/ - 系统管理员创建的本地配置，优先级最高
  2. /run/systemd/system/ - 运行时创建的文件，优先级中等
  3. /usr/lib/systemd/system/ - 软件包安装的Unit文件，优先级最低

当同名Unit文件存在于多个目录时，Systemd会使用优先级最高的文件。这种分层结构允许系统管理员覆盖默认配置而不需要直接修改原始文件。

1.4 配置覆盖机制¶

Systemd提供了两种主要的配置覆盖机制：

  1. 完全覆盖：在较高优先级目录中创建同名文件
  2. 片段覆盖：创建以下格式的目录和文件：
    • /etc/systemd/system/unit.service.d/override.conf
    • 这种方式允许只修改部分配置，而不需要复制整个Unit文件

2.2 通用语法规则¶

Systemd配置文件遵循以下语法规则：

  1. 注释以#或;开头
  2. 以[Section]方式定义段
  3. 使用Key=Value格式定义配置项
  4. 多个值可以用空格分隔，也可以重复键名
  5. 字符串值不需要引号
  6. 布尔值可以使用yes/no、true/false、1/0表示
  7. 时间值支持多种单位：s（秒）、m（分）、h（时）等

2.3 Unit段详解¶

[Unit]段包含不特定于任何单元类型的通用信息和依赖关系，主要配置选项包括：

选项 描述
Description 对单元的简短描述，显示在systemctl status输出中
Documentation 文档URL列表，可以是man手册、网页或文本文件
Requires 强依赖关系，如果列出的单元未激活，则当前单元也不会启动
Wants 弱依赖关系，如果列出的单元未激活，不会影响当前单元
After 定义启动顺序，确保当前单元在列出的单元之后启动
Before 定义启动顺序，确保当前单元在列出的单元之前启动
Conflicts 定义冲突关系，如果列出的单元已激活，当前单元将不会激活
ConditionPathExists 仅在指定路径存在时才启动单元
ConditionPathIsDirectory 仅在指定路径是目录时才启动单元
ConditionPathIsSymbolicLink 仅在指定路径是符号链接时才启动单元
ConditionPathIsMountPoint 仅在指定路径是挂载点时才启动单元
ConditionPathIsReadWrite 仅在指定路径可读写时才启动单元
ConditionDirectoryNotEmpty 仅在指定目录非空时才启动单元
ConditionFileNotEmpty 仅在指定文件非空时才启动单元
ConditionKernelCommandLine 仅在内核命令行包含指定字符串时才启动单元
ConditionSecurity 仅在特定安全模块激活时才启动单元
AssertPathExists 与Condition相同，但在条件不满足时会导致启动失败

4. 依赖管理：强弱依赖决定故障传播¶

踩过的坑是把 Wants 当 Requires 用，依赖挂了服务还傻跑，结果数据写了一半。

4.1 理解服务依赖类型¶

Systemd提供了多种依赖类型，以满足不同的服务关系需求：

  1. 基本依赖类型：

    • Requires：强依赖，如果依赖的单元启动失败，当前单元也会失败
    • Wants：弱依赖，依赖的单元启动失败不会影响当前单元
    • Requisite：先决条件，依赖的单元必须已经成功激活，否则当前单元立即失败
    • BindsTo：类似Requires，但依赖单元停止时，当前单元也会停止
    • PartOf：当依赖单元停止或重启时，当前单元也会停止或重启
    • Conflicts：冲突关系，不能与指定单元同时激活

  2. 顺序依赖：

    • After：当前单元在指定单元之后启动
    • Before：当前单元在指定单元之前启动

4.2 配置服务依赖关系¶

依赖配置既可以在单元文件中定义，也可以通过特殊目录实现。在单元文件中，依赖关系通常在[Unit]段中定义：

除了在单元文件中定义，systemd还支持通过目录方式定义依赖关系：

  • <unit>.requires/：等同于Requires
  • <unit>.wants/：等同于Wants

例如，创建/etc/systemd/system/multi-user.target.wants/myservice.service软链接的效果等同于在myservice.service的[Install]段中添加WantedBy=multi-user.target。

4.3 故障处理与依赖传播¶

依赖类型决定了故障的传播行为：

  • Requires：如果A requires B，当B失败时，A也会停止
  • Wants：如果A wants B，当B失败时，A不受影响
  • BindsTo：如果A binds to B，当B停止或崩溃时，A也会立即停止
  • PartOf：如果A is part of B，当B停止或重启时，A也会停止或重启

9. 设计原则：单一职责与声明式优先¶

我坚持一个服务只做一件事，拆开来重启互不影响，排障时也容易定位。

9.1 服务设计原则¶

设计高质量Systemd服务应遵循以下原则：

  1. 单一职责原则：每个服务只做一件事，做好这件事
  2. 声明式配置：尽可能使用声明式配置而非复杂的脚本
  3. 明确依赖关系：显式声明所有依赖，不要依赖隐式行为
  4. 优雅启动和停止：实现正确的进程启动/停止机制
  5. 合理的重启策略：根据服务性质选择适当的重启策略
  6. 安全第一：应用最小权限原则，启用所有合适的安全隔离
  7. 资源控制：设置适当的资源限制，防止单个服务影响系统

9.2 性能优化策略¶

优化服务性能的策略：

  1. 优化启动顺序：

    • 使用systemd-analyze blame和systemd-analyze critical-chain识别启动瓶颈
    • 减少不必要的依赖
    • 使用socket和path激活替代立即启动

  2. 优化服务配置：

    • 使用Type=notify代替Type=forking提高启动效率
    • 优化TimeoutStartSec和TimeoutStopSec
    • 使用ExecStartPre进行并行预处理

  3. 资源分配优化：

    • 为关键服务提供更多资源（CPU权重、内存）
    • 为后台服务设置较低的资源优先级
    • 使用OOMScoreAdjust调整OOM killer的行为

  4. 减少磁盘I/O：

    • 使用PrivateTmp=yes减少临时文件I/O
    • 调整IOSchedulingClass和IOSchedulingPriority

9.3 服务配置的标准化¶

建立服务配置标准化实践：

  1. 一致的命名约定：

    • 使用描述性名称
    • 对相关服务使用一致的前缀
    • 使用标准化的实例参数

  2. 结构化布局：

    • 按功能分组配置选项
    • 保持[Unit]、[Service]和[Install]部分的逻辑顺序
    • 使用注释分隔主要配置块

  3. 文档化：

    • 使用Description和Documentation选项
    • 注释关键配置选项
    • 记录依赖关系和必要条件

  4. 版本控制：

    • 将服务配置纳入配置管理系统
    • 记录所有更改和原因
    • 使用统一的部署流程
