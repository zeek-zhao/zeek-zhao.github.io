43-常见问题排查

发表于2026-10-25|apollo
|浏览量:

[!info] 本节目标
掌握 Apollo 问题排查的系统方法论：按数据流分层排查的思路、环境/模块/数据三层常见问题速查表、日志与 Cyber 工具的使用，以及预防性维护的实践建议。

1. 排查方法论

按数据流分层排查：先环境后模块，先数据后算法。核心三问：

  1. 消息是否存在？（话题有没有输出）
  2. 频率是否正常？（更新率是否达标）
  3. 内容是否合理？（数值是否在预期范围）

多数”算法问题”其实是”数据问题”：算法表现异常时，九成原因在上游数据或配置。坚持数据流视角，避免直接钻进算法代码。

2. 常见问题速查表

现象 可能原因 排查方法
容器启动失败 镜像/驱动问题 检查 Docker 与 NVIDIA Docker 安装，看 docker logs
编译失败 依赖缺失/磁盘空间 清理空间，检查依赖，重试编译
模块不启动 配置错误/依赖模块未启动 查看 launch 文件依赖顺序与模块日志
无话题数据 驱动/网络/回放路径 cyber_channel list / cyber_monitor 确认话题
话题频率异常 硬件负载/调度问题 检查 CPU 占用与线程配置
感知结果异常 标定偏差/模型/参数 核对传感器标定与感知配置
规划不输出 上游数据异常 沿数据流逐级检查（见第 4 节实例）
控制抖动 参数/延迟/上游轨迹跳变 检查控制增益与上游轨迹连续性

3. 日志与工具

3.1 日志查看

日志包含错误与警告信息，模块启动失败、配置加载错误、数据异常通常都会留痕。日志级别（DEBUG/INFO/WARN/ERROR/FATAL）可通过配置调整，排查时建议开启 INFO 以上。

3.2 Cyber 工具

3.3 可视化排查

DreamView 是最直观的排查工具：感知框缺失说明感知或上游数据问题；框正常但轨迹异常则聚焦规划与预测；轨迹正常但车不动则聚焦控制与底盘链路。用可视化先做问题域的二分，再进日志细查。

4. 数据流排查实例

以”规划无输出”为例演示完整排查过程：

  1. 确认话题存在：cyber_channel list | grep planning，确认规划话题是否注册
  2. 检查输入频率：cyber_channel hz /apollo/localization/pose，定位输入是否正常
  3. 检查数据内容：cyber_monitor 查看定位位姿是否跳变、感知障碍物列表是否异常（空列表或离谱坐标）
  4. 查看规划日志：在 planning.INFO 中搜索拒绝生成轨迹的原因（如 “no valid path”、”reference line missing”）
  5. 定位根因：常见根因包括 Routing 未下发、地图加载失败、车辆配置与地图不匹配

逐级缩小问题范围，避免盲目修改代码。

5. 排查建议

  • 先复现再定位：稳定复现的问题才可高效定位，不稳定的先找复现条件
  • 保留现场数据：回放文件（record）与日志是分析依据，问题复现时立即录制
  • 单模块隔离测试：用回放数据单独喂某个模块，排除上下游干扰
  • 参考官方文档与社区：多数常见问题已有现成答案

6. 问题记录与升级

排查过程应记录现象、环境、复现步骤与日志，形成问题报告。常见问题优先在官方文档与社区搜索，未解决可提交 GitHub Issue，附上日志与脱敏数据。规范的问题记录有助于社区协作解决，也是团队知识沉淀的资产——建议维护团队内部 FAQ，按模块归类。

7. 预防性维护

减少问题的根本方法是预防性维护：

  1. 定期检查环境依赖与版本一致性
  2. 监控资源使用（CPU/内存/磁盘），异常增长提前预警
  3. 跟踪版本变更，升级前阅读 Release Notes
  4. 建立自动化测试与发布前回归验证
  5. 变更后观察运行状态，确认无回归再放量

预防性维护投入产出比高，可显著降低现场故障率；与文档沉淀配合，形成团队的知识资产。

[!tip]
排查效率的最大变量是对数据流拓扑的熟悉程度。建议结合 42-实战：搭建Demo自动驾驶演示 的演示环境，亲手画一张自己系统的数据流图（驱动 → 感知 → 预测 → 规划 → 控制），排查时对照检查点逐个验证，效率远高于无序尝试。
