16-RPMSG核间通信与开发流程

异构多核板子上，A 核跑 Linux、M 核跑 RTOS 是再常见不过的搭配，两边怎么传数据是我每次 bring-up 都要先想清楚的事。
📅 2026-11-05· 更新于 2026-11-05 · 2599 字 · 约 7 分钟 ✍ zeek.zhao #Linux#实战

RPMSG详解

异构多核板子上，A 核跑 Linux、M 核跑 RTOS 是再常见不过的搭配，两边怎么传数据是我每次 bring-up 都要先想清楚的事。这篇把 RPMSG 从原理到落地捋了一遍。

1. RPMSG 是异构多核之间的标准消息接口¶

1.1 它到底是什么¶

RPMSG(Remote Processor Messaging)是一种用于异构多处理系统(AMP, Asymmetric Multiprocessing)中核与核之间进行通信的标准二进制接口。在现代SoC设计中，异构多核架构越来越常见，如ARM大小核、CPU+DSP、CPU+GPU等组合，RPMSG提供了这些不同架构处理器间的通信机制。

我看这类 IPC 方案时，习惯先确认它是不是要跨不同操作系统——这正是 RPMSG 派上用场的地方。

1.2 它和 RPC 的分工¶

RPMSG作为一种IPC(Inter-Processor Communication)技术，可以成为RPC(Remote Procedure Call)的底层传输实现。RPC需要解决两大问题：

  1. 数据的序列化与反序列化
  2. 数据的传递方法

在异构多核系统中，由于不同核心可能运行不同操作系统，传统的TCP/IP通信不适用，此时RPMSG提供了高效的数据传递机制。

2. AMP 系统：主从核各跑各的系统、靠 IPC 连起来¶

flowchart TD subgraph SoC["System on Chip (SoC)"] A[ARM Cortex-A Core] --> |主处理器|OS1[Linux/Android] M[ARM Cortex-M Core] --> |从处理器|OS2[RTOS] D[DSP] --> |专用处理器|OS3[专用系统] end A <--> |RPMSG| M A <--> |RPMSG| D

现代SoC通常包含多个异构处理器核心，每个核心可能运行不同的操作系统：

  • 主核(如Cortex-A系列)：运行通用操作系统(如Linux/Android)
  • 从核(如Cortex-M系列)：运行实时操作系统(RTOS)
  • 专用处理器(如DSP)：运行特定任务的系统

AMP系统特点：

  • 核心间存在主-从(Master-Slave)结构
  • 主核负责系统启动和管理
  • 核心间通过IPC机制(如RPMSG)通信
  • 各核心可独立运行不同操作系统

我一般先把主从关系理清：主核跑 Linux 管启动，从核跑 RTOS 干实时活，后面所有配置都围绕这个前提转。

3. 工作原理：共享内存加 VRING 加中断通知¶

3.1 基本架构¶

flowchart TB subgraph A9["A9 Core (Linux)"] A9App[应用程序] A9Driver[RPMSG驱动] end subgraph M4["M4 Core (RTOS)"] M4App[应用程序] M4Driver[RPMSG驱动] end subgraph SharedMemory["共享内存"] VRingTx1[Tx VRING: A9->M4] VRingRx1[Rx VRING: A9<-M4] VRingTx2[Tx VRING: M4->A9] VRingRx2[Rx VRING: M4<-A9] end A9App <--> A9Driver M4App <--> M4Driver A9Driver <--> VRingTx1 A9Driver <--> VRingRx1 M4Driver <--> VRingTx2 M4Driver <--> VRingRx2 VRingTx1 <--> VRingRx2 VRingTx2 <--> VRingRx1

RPMSG通信基于共享内存和中断机制，主要组件包括：

  • 共享内存区域：由主处理器分配和管理
  • **虚拟环缓冲区(VRINGs)**：每个通信方向有两个缓冲区（USED和AVAIL）
  • 中断机制：用于通知对方有新消息

3.2 通信流程：两个方向各走各的环¶

sequenceDiagram participant Master as 主核 participant AVAIL as AVAIL缓冲区 participant USED as USED缓冲区 participant Slave as 从核 Note over Master,Slave: 主核向从核发送消息 Master->>USED: 1. 从USED缓冲区获取内存块 Master->>Master: 2. 填充RPMSG消息 Master->>AVAIL: 3. 链接到AVAIL缓冲区 Master->>Slave: 4. 触发中断通知从核 Slave->>AVAIL: 5. 接收并处理消息 Note over Master,Slave: 从核向主核发送消息 Slave->>AVAIL: 1. 从AVAIL缓冲区获取内存块 Slave->>Slave: 2. 填充RPMSG消息 Slave->>USED: 3. 链接到USED缓冲区 Slave->>Master: 4. 触发中断通知主核 Master->>USED: 5. 接收并处理消息

主核向从核发送消息的流程：

  1. 主核从USED缓冲区获取一块内存
  2. 按照RPMSG协议格式填充消息内容
  3. 将该内存块链接到AVAIL缓冲区
  4. 触发中断通知从核有新消息
  5. 从核处理消息

从核向主核发送消息的流程：

  1. 从核从AVAIL缓冲区获取一块内存
  2. 按照RPMSG协议格式填充消息内容
  3. 将该内存块链接到USED缓冲区
  4. 触发中断通知主核有新消息
  5. 主核处理消息

调试时我习惯盯着 VRING 的 AVAIL/USED 两个环看，消息卡住基本都是这两个环没对上。

4. 协议三层：传输层、MAC 层、物理层¶

flowchart TB subgraph "RPMSG协议栈" Transport["传输层 (virtio_rpmsg_bus.c)"] MAC["MAC层 (imx_rpmsg.c)"] PHY["物理层 (硬件相关实现)"] end subgraph "Linux驱动应用" APP1["rpmsg_tty.c<br>(终端通信)"] APP2["imx_rpmsg_pingpong.c<br>(Ping-Pong测试)"] end APP1 --> Transport APP2 --> Transport Transport --> MAC MAC --> PHY

RPMSG协议分为三层：

  1. 传输层：处理消息的封装与解析
  2. MAC层：负责消息的寻址与传递
  3. 物理层：实现硬件相关的底层通信

我一般读驱动先从传输层入手，virtio_rpmsg_bus.c 就是整个核心实现。

7.2 NXP i.MX8 平台实例¶

i.MX8平台上，A53与M4之间的RPMSG通信也遵循类似的原理，但在具体实现上有所差异：

  2. 资源域分配：确保M4核心拥有其需要访问的资源
  3. 中断路由：配置合适的中断路由以支持RPMSG通信

8. 注意事项：对齐、缓存一致性与资源保护¶

  1. 内存对齐：共享内存需要按照缓存行大小对齐
  2. 缓存一致性：确保主、从核对共享内存的访问保持缓存一致性
  3. 资源保护：避免多核同时访问共享资源导致的竞争条件
  4. 兼容性问题：不同平台的RPMSG实现可能存在差异，需要注意适配
  5. 调试难度：核间通信的异步特性增加了调试复杂性

我一般最先查缓存一致性，异步通信里这类问题最难复现。

9. 演进方向：标准化、高性能与安全增强¶

  1. 标准化：RPMSG协议可能会进一步标准化
  2. 更高性能：更高效的内存管理和中断处理机制
  3. 更广泛应用：在更多异构系统中被采用
  4. 安全性增强：增加安全通信机制，防止恶意攻击
  5. 工具链改进：更完善的开发和调试工具
