并发编程基础

[!info] 本页概览
本文讲解 Python 并发三件套：多线程 threading、多进程 multiprocessing 与 asyncio 的选型，重点解释 GIL 对 CPU/IO 密集任务的影响，以及线程池/进程池用法。

核心概念

  • GIL（全局解释器锁）：同一时刻只有一个线程执行 Python 字节码，导致 CPU 密集任务多线程无加速。
  • 多线程：适合 I/O 密集（网络、文件等待），切换开销小。
  • 多进程：适合 CPU 密集，每进程独立解释器与内存。
  • asyncio：单线程协作式，I/O 密集最省资源。

选型决策表

场景 方案
I/O 密集、网络爬虫 asyncio / 线程池
CPU 密集、数值计算 多进程 / numpy
大量并发连接 asyncio
简单并行任务 ThreadPoolExecutor / ProcessPoolExecutor

常见坑

  1. GIL 认知错误：以为线程能加速 CPU 任务，实际更慢（调度开销）。
  2. 共享变量无锁：counter += 1 在 GIL 下仍可能交错，必须用锁或 threading.Lock。
  3. 进程池传递不可序列化对象：lambda 不能 pickle，用顶层函数。
  4. daemon 线程未 join：程序退出时机不可控，显式 join。
  5. 死锁：多锁顺序不一致，固定加锁顺序或用 RLock。
  6. 进程间数据不共享：multiprocessing 用 Queue/Manager/Pipe 通信，别指望全局变量。

最佳实践

  • 优先 concurrent.futures 高层 API，少直接操作 Thread。
  • 用 queue.Queue 解耦生产者消费者。
  • CPU 密集考虑 C 扩展（numpy）而非盲目多进程。
  • 并发任务用 asyncio + 异步库，资源占用最低。
  • 数据竞争用 threading.Lock + 最小临界区，或改用不可变数据结构。
