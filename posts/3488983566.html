性能优化

ℹ️本篇目标
从硬件规划、组件配置、数据库与 Gitaly 调优、缓存四个维度优化 GitLab 性能，覆盖单机与大用户量场景。

1. 先测后调：性能基线¶

🔥判断瓶颈
页面慢：看 Puma 线程与 PostgreSQL；push/clone 慢：看 Gitaly 与磁盘 IO；Pipeline 排队：看 Runner 并发；整体卡：看内存 swap。

2. 硬件规划¶

用户量 内存 CPU 关键点
≤100 4-8 GB 2-4 核 默认配置即可
100-500 8-16 GB 4-8 核 调 Puma worker、开 UPSERT
500-2000 16-32 GB 8-16 核 Gitaly 独立、SSD 必须
>2000 按官方参考架构 多节点 拆 Gitaly/PostgreSQL/Redis
⚠️内存是第一瓶颈
GitLab 各组件内存占用高，内存不足会触发 swap 导致整体卡顿。单机部署建议 预留 1-2 GB 系统余量，并监控 free -h。

3. Puma 调优¶

📝单 worker 模式
小内存实例可保持 worker=2 或使用 puma['worker_processes'] = 0（单进程多线程），减少内存但并发能力下降。

4. PostgreSQL 调优¶

⚡不要照抄
数据库参数与内存/负载强相关，参考官方 gitlab.rb 注释与 gitlab-rake gitlab:db:check，在维护窗口小步调整并观察。

5. Gitaly 与仓库存储优化¶

  • Gitaly 独立：大用户量将 Gitaly 拆到独立节点，仓库 IO 不再与 Web 争抢。
  • SSD 必须：仓库随机读写密集，机械盘 clone/push 明显变慢。
  • GC 与优化：
  • 禁用仓库静态对象缓存（内存不足时）：gitaly['configuration'] 中评估是否使用 pack_objects_cache。

6. Redis 与缓存¶

  • Redis 默认本机，内存不足时考虑独立节点。
  • 清理失效缓存：sudo gitlab-rake cache:clear（谨慎，先备份）。
  • 前端静态资源由 Nginx 缓存，监控 /var/log/gitlab/nginx/ 的 4xx/5xx 占比。

7. CI/CD 侧性能¶

  • Runner 并发：按需求调 concurrent（见 06-Runner部署），避免 Job 排队。
  • 缓存与产物：合理设置 cache 与 artifacts expire_in，减少重复下载与磁盘占用。
  • 镜像预热：常用构建镜像提前 pull 到 Runner 节点。
  • Pipeline 精简：合并小 Job、用 rules 裁剪不需要跑的分支。

8. 监控与压测¶

🔥压测前须知
压测会真实产生负载，选低峰期并对测试项目做隔离；压测脚本可参考 gitlab-load-test 项目思路（见 90-资料索引指南）。
