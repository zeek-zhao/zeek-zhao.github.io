Linux 设备驱动模型：Kobject 是地基，Bus 和 Class 是两套视角

先说我的判断：设备模型看着概念一大堆，真正要抓住的其实就两件事——Kobject 提供底层数据结构和生命周期管理，Bus/Class 提供上层”按什么角度看设备”。我在读内核源码时，先把 kobject、kset、ktype 三个结构体啃下来，后面 Uevent、Sysfs、Platform 设备就都能顺下来了。

这一篇按内核里的依赖关系铺开：基本概念 → Kobject → Uevent → Sysfs → Device/Driver → Bus → Class → Platform 设备。

一图看懂：设备模型用 kobject、sysfs、uevent 收敛硬件差异。

graph TD K[kobject 引用计数 层次] --> S[sysfs 导出文件目录] K --> U[uevent 热插拔通知] BUS[bus 总线] --> DEV[device 设备] DRV[driver 驱动] --> DEV CLASS[class 类] --> DEV DEV --> K

1. 基本概念：设备模型把硬件差异收敛成四个抽象¶

1.1 为什么需要设备模型：热插拔、电源管理与设备多样性¶

为了降低设备多样性带来的Linux驱动开发复杂度，以及处理设备热拔插、电源管理等问题，Linux内核引入了设备模型(Device Model)的概念。设备模型将硬件设备归纳、分类，抽象为一套标准的数据结构和接口。驱动开发就简化为对内核规定的数据结构的填充和实现。

我一般把这一节当成后面所有章节的地图：先认清四个核心概念，再去看它们各自的结构体。

1.2 四个核心概念及其关系¶

下图展示了Linux设备模型中的核心概念及其关系：

Bus（总线）：Linux认为总线是CPU和一个或多个设备之间信息交互的通道。为简化设备模型设计，所有设备都应连接到总线上(内部总线、虚拟总线或Platform Bus)。

Class（分类）：类似面向对象程序设计中的类概念，集合具有相似功能或属性的设备，抽象出可在多个设备间共用的数据结构和接口函数，避免代码重复。

Device（设备）：抽象系统中所有硬件设备，描述其名称、属性、所属Bus、所属Class等信息。

Device Driver（驱动）：抽象硬件设备的驱动程序，包含设备初始化、电源管理相关的接口实现。

1.3 核心思想：统一描述、即插即用、树状依赖、共性抽象¶

Linux设备模型的核心思想包括：

  1. 用Device和Device Driver两个数据结构从”有什么用”和”怎么用”两个角度描述硬件设备，统一驱动开发格式。

  2. 通过同名的Device和Device Driver实现即插即用(热拔插)功能。当设备插入时，内核创建设备对应的Device结构，触发匹配Driver的执行。

  3. 通过”Bus→Device”的树状结构解决设备间依赖关系，在开关机和电源管理过程中自动处理设备间依赖。

  4. 使用Class结构引入面向对象概念，最大限度抽象共性，减少驱动开发中的重复劳动。

我在这节最想强调的是第 2 点：同名 Device 和 Device Driver 的匹配是热插拔的根基，后面 Bus 的 match 回调就是在做这件事。

2. Kobject：引用计数、层次结构和 sysfs 导出都靠它¶

2.1 Kobject 解决的两个问题¶

Kobject是Linux设备模型的基础，也是设备模型中最难理解的部分。它主要解决两个问题：

  1. 抽象设备模型中大量数据结构的共性，避免代码重复
  2. 为这些数据结构提供基础功能，如引用计数、层次结构组织等

以下是Kobject和相关结构的关系图：

2.2 三个主要功能¶

Kobject提供三个主要功能：

  1. 通过parent指针，将所有Kobject以层次结构组合起来
  2. 使用引用计数(reference count)记录Kobject被引用的次数，在引用次数为0时自动释放
  3. 配合sysfs虚拟文件系统，将每个Kobject及其特性以文件形式开放到用户空间

实测下来，理解 kobject 最快的方式是顺着 parent 指针看它怎么挂进 sysfs 目录树。

2.3 相关结构体：kobject、kset、kobj_type¶

2.3.1 kobject结构体

关键成员说明：

  • name: Kobject的名称，也是sysfs中目录名称
  • parent: 指向父Kobject，形成层次结构
  • kset: 该Kobject所属的Kset
  • ktype: 该Kobject所属的kobj_type
  • kref: 引用计数，用于内存管理

2.4 使用流程：定义 → 初始化 → 注册 → 引用计数管理¶

典型的Kobject使用流程如下：

  1. 定义包含Kobject的数据结构
  2. 定义适合的ktype并实现其回调函数
  3. 初始化并注册Kobject到内核
  4. 使用kobject_get/kobject_put接口管理引用计数
  5. 引用计数为0时，自动释放资源

我一般照这个顺序写，引用计数一旦配错，卸载模块时就会踩到 use-after-free。

3. Uevent：内核状态一变就通知用户空间¶

3.1 Uevent 主要服务热插拔¶

Uevent是Kobject的一部分，用于在Kobject状态发生改变时(如增加、移除等)通知用户空间程序。这一机制主要用于支持热插拔设备，如U盘插入后，动态创建设备节点并挂载文件系统。

当Kobject状态改变时，Uevent机制按以下流程工作：

  1. 检查Kobject是否属于某个kset
  2. 检查是否设置uevent_suppress标志
  3. 调用kset的filter函数过滤事件
  4. 创建环境变量，包括action、路径信息等
  5. 通过netlink或kmod机制通知用户空间

4. Sysfs：把内核对象摊成可读写的文件目录¶

4.1 Sysfs简介¶

Sysfs是基于RAM的文件系统，与Kobject配合将内核数据结构导出到用户空间，以文件目录结构形式提供访问接口。每个注册到内核中的kobject都会在sysfs中对应一个目录。

4.2 Attribute概念¶

在sysfs中，attribute指kobject的”属性”，以文件形式存在于kobject对应的sysfs目录下。这些文件通常可读写，内核中定义属性的模块会处理用户空间的读写操作。

4.3 文件操作：VFS → sysfs_ops → show/store¶

Sysfs中attribute文件的读写由以下流程处理：

  1. 用户程序对sysfs中的文件执行读写操作
  2. VFS调用sysfs_file_operations的read/write方法
  3. Sysfs从kobject获取ktype中的sysfs_ops指针
  4. 调用sysfs_ops中的show/store方法处理读写请求

5. Device 与 Device Driver：从”有什么用”和”怎么用”两侧描述硬件¶

5.1 Device结构体¶

Device结构体抽象硬件设备：

关键字段说明：

  • parent: 父设备指针，通常是所属的bus或controller
  • kobj: 内嵌的kobject结构
  • bus: 设备所属的总线
  • driver: 设备对应的驱动
  • platform_data: 平台相关数据

5.2 Device Driver结构体¶

Device Driver结构体抽象设备驱动：

关键字段说明：

  • name: 驱动名称，用于匹配设备
  • bus: 所驱动设备的总线类型
  • probe/remove: 设备检测与移除回调函数
  • suspend/resume: 电源管理回调函数

5.3 匹配与初始化：device_register 和 driver_register 都会触发 probe¶

设备模型框架下驱动开发的基本步骤：

  1. 分配并注册device结构
  2. 分配并注册device_driver结构
  3. 设备驱动匹配和probe的时机：
    • device注册时（device_register）
    • driver注册时（driver_register）
    • 手动触发（device_attach/driver_attach）

我一般在 probe 里只打日志、不急着配硬件，先确认设备真的匹配上了再填寄存器。

6. Bus：所有设备都得挂到一条总线上¶

6.1 Bus的概念与功能¶

Bus（总线）是连接处理器和其它设备的通道。在Linux设备模型中，每个设备都要连接在一个Bus上，这个Bus可以是物理总线、内部总线、虚拟总线或Platform Bus。

Bus模块的功能：

  • 注册和注销bus
  • 处理设备和驱动注册到bus时的匹配
  • 管理bus下的所有device和device_driver

6.2 bus_type结构体¶

关键字段说明：

  • name: bus名称，在sysfs显示为目录
  • match: 判断device和driver是否匹配
  • probe/remove: 在device_driver的probe前执行的bus级初始化/清理

7. Class：跨总线把功能相似的设备归成一类¶

7.1 Class的概念与功能¶

Class是设备的更高层次视图，抽象出底层实现细节。Class代表具有相似功能的一组设备，如输入设备、网络设备等，允许这些设备共享代码和接口。

Class的主要功能：

  • 在/sys/class/下创建类别目录
  • 将不同bus上具有相同功能的设备归类
  • 为用户空间提供统一的访问接口

8. Platform 设备：SoC 片上外设的统一抽象¶

8.1 Platform设备概念¶

Platform设备是可通过CPU总线直接寻址的设备，包括：

  • 集成在SOC平台上的控制器
  • 连接到物理总线的桥设备
  • 基于端口的传统设备

8.2 软件架构¶

8.3 platform_device结构体¶

关键字段说明：

  • name: 设备名称，用于与驱动匹配
  • id: 设备ID，区分同名设备
  • resource: 设备使用的资源描述(内存、IO、中断等)

8.4 platform_driver结构体¶

8.5 注册流程：device 与 driver 各自注册，同名即触发 probe¶

Platform设备注册过程：

  1. 分配platform_device结构
  2. 设置设备名称和资源
  3. 调用platform_device_register注册到内核
  4. 内核会将设备添加到platform bus

Platform驱动注册过程：

  1. 初始化platform_driver结构，设置probe等回调
  2. 调用platform_driver_register注册到内核
  3. 如果存在同名设备，自动调用probe函数初始化

我写 platform 驱动时习惯先让 device 侧把 resource 填对，再看 driver 的 probe 有没有被调到。

9. 走到实例：设备树、probe 与开发流程怎么接起来¶

9.1 开发流程：先定总线，再写 driver，probe 初始化、remove 释放¶

基于Linux设备模型开发驱动的一般流程：

  1. 确定设备类型和所属总线
  2. 实现platform_driver或其他总线特定的驱动结构
  3. 在probe函数中初始化设备
  4. 在remove函数中释放资源
  5. 注册驱动到内核

我一般把第 3、4 步先写成空壳，等 probe 确认匹配后再往里填内容。

9.2 设备树与设备模型：硬件拓扑由 DT 描述，匹配靠 of_match_table¶

在现代Linux中，设备树(Device Tree)与设备模型紧密配合：

  • 设备树描述硬件拓扑和资源
  • 内核解析设备树，创建对应的device结构
  • 驱动通过of_match_table与设备树节点匹配

9.3 这套抽象带来的五个实际好处¶

  1. 统一的框架：为各类设备提供一致的抽象和接口
  2. 热插拔支持：自动处理设备的插入和移除
  3. 电源管理：系统级的设备休眠和唤醒管理
  4. 用户空间接口：通过sysfs提供统一的设备访问方式
  5. 代码复用：通过Bus和Class抽象减少重复代码

下一步可以直接照着 9.1 的五步去写一个 platform_driver：先让 probe 打上日志确认匹配，再逐步填 resource 和电源管理回调。
