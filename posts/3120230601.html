概述：先统一提交口径，再谈自动化¶

规范化的代码提交信息对于项目的长期维护至关重要，它不仅提高了代码历史的可读性，还能够自动化生成结构清晰的变更日志(Changelog)，帮助团队和用户快速了解项目的演进。本文档定义了代码提交的规范要求，并介绍如何利用工具实现提交规范检查和自动化生成变更日志。

1.1 适用范围¶

本规范适用于所有使用Git版本控制系统的项目，特别是：

  • 开源项目
  • 团队协作项目
  • 需要生成标准化变更日志的项目
  • 有版本发布需求的项目

1.2 主要目标¶

  • 确保提交信息的一致性和可读性
  • 简化版本发布工作流程
  • 自动化生成项目变更日志
  • 提高协作效率和代码维护质量

提交信息规范： Conventional Commits 是可执行的标准¶

2.1 Conventional Commits规范¶

采用Conventional Commits规范，提交信息的基本格式如下：

类型(Type)

必须是以下类型之一：

  • feat: 新功能
  • fix: 错误修复
  • docs: 文档更新
  • style: 代码风格变更(不影响代码运行)
  • refactor: 代码重构
  • perf: 性能优化
  • test: 添加或修改测试
  • build: 构建系统或外部依赖变更
  • ci: CI配置变更
  • chore: 其他不修改源代码或测试的变更
  • revert: 撤销之前的提交

作用域(Scope)

可选的作用域用于提供额外的上下文信息，通常是受影响的模块、组件或功能区域：

描述(Description)

描述应简明扼要地说明本次变更的内容，使用现在时态的动词开头：

  • 使用”添加”而非”添加了”
  • 使用”修复”而非”修复了”
  • 首字不要大写
  • 结尾不加句号

2.2 重大变更标记¶

当提交包含不兼容的变更(Breaking Changes)时，应在类型/作用域后面添加感叹号，并在正文或脚注添加BREAKING CHANGE标记：

feat(api)!: 重新设计用户认证API

BREAKING CHANGE: 用户认证API现在需要提供额外的安全参数，旧的认证方式将不再支持。

2.3 提交规范示例¶

feat(user): 添加密码重置功能

实现了通过邮箱验证的密码重置流程，包括：

  • 发送重置链接到用户邮箱
  • 验证重置令牌有效性
  • 提供密码更新界面

Closes #123

fix(dashboard): 修复数据加载状态错误

修复当数据加载失败时仍显示加载成功的状态问题

2.4 Angular 提交规范详解¶

Angular 项目的提交规范是 Conventional Commits 的前身和基础，为许多项目提供了参考。Angular 规范有更严格的格式要求：

Angular 类型(Type)

Angular 规范明确定义以下类型：

  • feat: 新增功能
  • fix: 修复缺陷
  • docs: 文档变更
  • style: 代码格式调整（空格、格式化、缺少分号等）
  • refactor: 代码重构，既不修复错误也不添加功能
  • perf: 性能优化
  • test: 添加或修改测试代码
  • build: 构建系统或外部依赖项的变更
  • ci: 持续集成的配置文件和脚本变更
  • chore: 其他不修改源代码或测试的变更

最佳实践：规范要短、要硬、要能被工具验证¶

5.1 提交信息准则¶

  • 保持描述简洁明了，通常不超过50个字符
  • 使用命令式语气描述变更内容
  • 在正文中提供必要的上下文和解释
  • 链接相关的issue或其他参考资料
  • 考虑变更对用户的影响，尤其是API变更

5.2 工作流建议¶

  1. 功能开发流程:

    • 创建功能分支
    • 进行开发和提交(使用git cz)
    • 提交Pull Request
    • 审查通过后合并到主分支
    • 自动触发发布流程

  2. 版本发布流程:

    • 使用npm run release预览变更
    • 验证CHANGELOG内容
    • 推送版本提交和标签
    • 或完全依赖CI/CD自动发布

5.3 常见问题解答¶

Q: 如何处理不符合规范的旧提交?
A: 考虑使用git rebase -i调整历史提交，或从某个时间点开始实施规范。

Q: 如何在多人协作项目中推行提交规范?
A: 先通过团队培训和文档，再利用CI检查和预提交钩子强制执行。

Q: 自动版本号如何定义?
A: 根据Conventional Commits规范，feat类型提交增加minor版本，fix类型提交增加patch版本，带有BREAKING CHANGE标记的提交增加major版本。

5.4 Angular 团队工作流¶

Angular团队的工作流可以作为大型开源项目的参考：

  1. 创建新分支，分支名包含工作类型和问题描述
  2. 开发完成后使用Angular提交规范提交变更
  3. 提交到Fork的仓库
  4. 创建Pull Request并等待CI检查
  5. 代码评审和讨论
  6. 根据评审意见修改代码
  7. 合并到主分支

5.5 Gerrit 代码审查最佳实践¶

Gerrit工作流有其独特之处：

  1. 克隆仓库并设置Gerrit远程仓库

  2. 创建主题分支并开发功能

  3. 提交代码(使用规范)

  4. 发送到Gerrit审查

  5. 根据评审意见修改
