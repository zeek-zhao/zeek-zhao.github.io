TTY子系统：终端抽象与驱动框架

我第一次认真读这块代码，是串口控制台死活不出日志的时候。后来才反应过来，”TTY” 在内核里既是一类字符设备，也是一整套框架——名词不先拆开，越看越乱。

一图看懂：TTY Core 居中，上接应用下接驱动，线路规程做转换。

graph LR APP[应用] --> CORE[TTY Core] CORE --> LINE[线路规程 line discipline] LINE --> DRV[TTY Driver] DRV --> HW[硬件] CON[Console 日志出口] --> CORE

1. 基本概念：终端、TTY 与控制台不是一回事¶

1.1 先把最容易被问住的那个词讲清楚¶

TTY 是 Linux 里最普遍的一类设备，几乎每个用 Linux 的人都会跟它打交道，但真要回答”TTY 到底是什么”并不容易。我在实际用的时候，是先把它当成电报时代留下来的一个名字记住，再去看它在内核里怎么落地，这样比一上来就啃数据结构顺得多。

1.2 终端（Terminal）：负责输入和输出的那一端¶

1.2.1 基本概念

在计算机或通信系统中，终端是一个电子设备，用于向系统输入数据（input）或将系统接收到的数据显示出来（output），即我们常说的”人机交互设备”。

最典型的例子是电传打字机（Teletype）——一种基于电报技术的远距离信息传送器械。电传打字机通常由键盘、收发报器和印字机构组成。发报时按下字符键就能将该字符的电码信号自动发送；收报时能自动接收电码信号并打印出相应字符。

1.2.2 Unix终端

在计算机世界中，键盘和显示器是最常用的终端设备，分别用于输入和输出信息。

在大型机和小型机时代，终端设备与计算机主机同属一个整体。但到了PC时代，情况发生了变化。Unix创始人肯•汤普逊和丹尼斯•里奇想让Unix成为多用户系统。多用户系统意味着要给每个用户配置一个终端，但当时计算设备价格昂贵，键盘与主机是集成的。

最后他们采用了价格低廉的ASR33电传打字机作为终端。ASR33打字机的键盘用来输入，打印纸用来输出。多个ASR33连接到同一主机，每个用户可以通过终端登录主机。这样他们创造了计算机历史上第一个真正的多用户系统Unix，而ASR33成为第一个Unix终端。

1.2.3 TTY设备

第一个Unix终端是电传打字机（Teletype或Teletypewritter，缩写为TTY）。这就是TTY名称的来源。在现代Unix/Linux系统中，TTY设备已演变为不同的意义。

ASR33电传打字机本身是硬件设备，在Unix/Linux系统中，这个硬件设备被抽象为”TTY设备”。

1.2.4 串口终端（Serial Terminal）

早期TTY终端（电传打字机）通常通过串口与Unix设备连接。随后，电传打字机被替换为带有键盘、显示器和串口的各种硬件设备。

对Unix/Linux系统来说，通过串口连接的设备都可作为终端设备。逐渐地，终端设备、TTY设备、串口设备等概念混在一起：

  1. TTY设备即是终端设备，无需区分。
  2. 所有串口设备都是TTY设备。
  3. 除串口设备外，也有其它形式的TTY设备，如虚拟终端（VT）、伪终端（Pseudo Terminal）等。

1.3 控制台（Console）：从”自带终端”退化成日志出口¶

了解终端和TTY概念后，再来看控制台（console）。

在Unix多用户系统早期，PC有一个自带的昂贵终端（键盘和显示器），以及通过串口连接的多个TTY终端。自带终端被称为console，以显示其特殊地位。

控制台（console）与普通TTY终端的区别：

  1. 控制台更昂贵。
  2. 控制台拥有更多权限，如用户建立、密码更改、权限分配等。
  3. 系统运行日志、错误信息等通常只输出到控制台，方便管理和控制。

随着计算机技术发展，控制台和普通终端的界限越来越模糊。在当前Linux系统中，console主要保留了日志输出功能。

2. 软件架构：TTY Core 居中，上下各留一层适配¶

2.1 这套框架要解决什么问题¶

Linux内核中的TTY框架用于简化终端的使用和终端驱动程序的编写。它向应用程序提供使用终端的统一接口，也为编写终端驱动程序提供统一的框架。我一般先盯住这句话里的两个”统一”：一个面向应用，一个面向驱动，后面看各层职责就都有落点了。

2.2 分层：应用 → Core → 线路规程/Console → 驱动 → 硬件¶

Linux内核TTY框架位于”drivers/tty”目录，其软件框架包括几个主要部分：

2.2.1 TTY Core

TTY Core是TTY框架的核心逻辑，功能包括：

  1. 以字符设备形式向用户空间提供访问TTY设备的接口，例如：

  3. 抽象出线路规程（Line Disciplines）模块，处理TTY数据传输过程中的特殊字符转换等。

2.2.2 System Console Core

Linux内核的System Console主要功能：

  1. 向系统提供控制台终端（Console Terminal），让用户登录进行交互。

  2. 提供printk功能，让内核代码输出日志。

3. 从应用角度看TTY设备：几种设备节点对应几种用法¶

3.1 从每天在用的场景反推¶

在使用Linux系统时，我们每时每刻都在与TTY打交道：显示输出、键盘输入、用户登录、shell终端等。我排查登录卡住这类问题时，习惯先问自己当前拿到的是 /dev/console、/dev/ttyN 还是 /dev/tty，三者行为差得很多。下面从熟悉的场景出发，把这些概念再过一遍。

3.2 再谈终端设备¶

终端设备是帮助人机交互的设备，包括输入（向计算机发送指令）和输出（计算机显示执行结果）两方面。

3.2.1 终端的类型

根据输入输出设备类型，常见终端包括：

  1. 控制台终端（Console）

    • 输入设备通常是键盘，输出设备通常是显示器
    • 输入输出设备通过各类总线直接与计算机相连
    • “终端”是这些设备的逻辑抽象

  2. 虚拟终端（VT）

    • 基于控制台终端，Linux系统虚拟出多个终端
    • 不同应用程序可在虚拟终端上独立输出
    • 通过键盘组合键（CTRL+ALT+F1~F6）切换不同虚拟终端

  3. 串口终端（TTY）

    • 输入输出设备集成在独立硬件上，通过串口与计算机连接
    • 输入转换为串口RX数据包发送给计算机
    • 计算机输出以TX数据包形式发送给TTY设备并显示

  4. 软件终端

    • 在另一台计算机上用软件模拟终端设备
    • 软件从键盘接收用户输入并通过串口发送给对端
    • 从串口接收对端输出并在软件界面显示
    • 常见软件如PuTTY、SecureCRT、Windows超级终端等

  5. USB、网络等终端

    • 使用USB、以太网等通信接口代替串口
    • 原理与串口终端类似

  6. 图形终端

    • 通过GUI界面交互的终端
    • 超出TTY框架范围（TTY仅涵盖字符界面）

3.2.2 输入和输出

对计算机而言，输入输出都是由运行其中的软件处理的。人机交互实际是人与软件的交互：

  • 内核通过控制台终端输出日志（printk）
  • 启动后init进程打开控制台终端接收指令并应答
  • getty应用打开终端设备让用户登录
  • 登录后getty将终端控制权交给shell
  • 用户与shell交互，可命令shell启动其它应用

3.3 软件视角¶

3.3.1 Console Driver

Linux系统中存在多种终端设备，每种由TTY driver驱动。可基于TTY driver创建console driver并注册给内核：

  1. 可同时注册多个console driver并选择使用
  2. 内核启动时可通过命令行指定使用哪些控制台终端
  3. 内核日志可在所有选中的控制台终端上输出
  4. 用于人机交互的控制台终端只能有一个（最后指定的）

3.3.2 控制台终端（/dev/console）

内核启动后期，kernel_init线程会打开控制台终端。由于控制台终端类型多样，内核通过固定的/dev/console（设备号5,1）访问。应用程序打开此设备时，TTY Core会向System Console Core查询哪个终端适合作为控制台终端。

3.3.3 虚拟终端（/dev/ttyN）

虚拟终端是虚拟出来的终端，不对应具体设备。应用程序无法区分虚拟终端和物理终端。由于物理资源（键盘和屏幕）只有一套，同一时刻只能与一个虚拟终端对接。各虚拟终端轮流使用物理资源进行人机交互。

3.3.4 伪终端(Pseudo Terminal，pty)

伪终端解决了非串口类接口（如网络）与应用程序交互的问题：

  • pty由pts（pseudo-terminal slave）和ptm（pseudo-terminal master）组成
  • pts伪造标准TTY设备供应用程序访问
  • ptm负责与实际通信接口（如网络）交互
  • 应用程序向pts写入的数据传到ptm，从pts读取的数据来自ptm

典型应用如GUI环境中的Terminal软件（xterm等）：

  1. 启动Terminal软件时生成pts和ptm对，并执行shell
  2. Terminal将pts交给shell，shell将其视为标准TTY设备
  3. shell通过pts读写数据实际是与ptm交互
  4. Terminal软件从ptm读取shell输出并显示，将用户输入通过ptm发送给shell

3.3.5 控制终端（Control Terminal，/dev/tty）

控制终端与Unix/Linux的Job Control功能相关：

  1. Job control是shell中用于管理进程组（process group）的机制
  2. Linux启动后，终端控制权交给shell，shell可通过TTY读取输入、输出
  3. 通过shell启动的应用程序也可获得TTY控制权
  4. 同时只能有一个应用占有TTY（前台应用），其他为后台应用
  5. 控制终端（/dev/tty，设备号5,0）允许应用选择实际终端设备
  6. 后台应用若尝试读取控制终端，通常会收到SIGTTIN信号而终止
  7. 写入控制终端时会收到SIGTTOU信号，但shell通常重设此信号行为，允许后台应用输出内容

4. TTY Driver详解：抓住 struct tty_driver 与 ops 就够了¶

4.1 关键数据结构：device、driver、struct、port 各管一层¶

4.1.1 TTY Device

Linux TTY框架管理TTY设备，为应用程序提供接口。内核不将TTY device视为实体设备，而是”虚拟的数据通道”：

  • 串口终端：TTY device是从串口控制器抽象的数据通道
  • 网络终端：TTY device是基于网络socket虚拟的数据通道

TTY框架从两个角度抽象TTY设备：

  1. 设备模型：为每个”数据通道”注册struct device，在sysfs中体现：

4.1.2 TTY Driver

TTY框架淡化device概念，强调driver。struct tty_driver包含了TTY device的所有内容：

编写TTY driver时需要关心的字段：

  • driver_name：TTY driver名称，内部使用
  • name：驱动的TTY devices名称，体现在sysfs和/dev/目录下
  • major、minor_start：字符设备的主次设备号
  • num：该driver驱动的tty device数量
  • type、subtype：TTY driver类型
  • init_termios：初始termios设置
  • flags：控制flags
  • ops：操作函数集
  • driver_state：driver私有数据

我自己踩过的坑是先盯着 ops 看，把 major/minor 拖到最后，结果设备号冲突查了很久；顺序倒过来会快很多。

内部使用的字段：

  • ttys：struct tty_struct类型指针数组
  • ports：struct tty_port类型指针数组
  • termios：struct ktermios类型指针数组

4.1.3 TTY Struct (struct tty_struct)

TTY struct是TTY设备在TTY core中的内部表示：

  • 对TTY driver：类似文件句柄，指代某个TTY设备
  • 对TTY core：保存TTY设备生命周期中的中间变量，包括：
    • dev：该设备的struct device指针
    • driver：该设备的struct tty_driver指针
    • ops：该设备的tty操作函数集指针
    • index：设备编号
    • 同步锁、等待队列、buffer信息等

4.1.4 TTY Port (struct tty_port)

TTY port是另一种TTY device抽象方式：

  • TTY struct是”动态抽象”，保存临时信息，生命周期为设备打开到关闭
  • TTY port是”静态抽象”，保存固定不变的属性值
  • TTY core负责逻辑抽象，不关心具体属性
  • TTY port将不同TTY设备的共同属性抽象出来，供TTY driver使用

TTY struct由TTY core提供和使用；TTY port由TTY core提供，由具体TTY driver使用——这句是我用来区分两者归属的记忆点。

4.1.5 Termios (struct ktermios)

POSIX terminal interface定义了termios数据结构（用户空间为struct termios，内核空间为struct ktermios）：

常用字段：

  • c_cflag：控制TTY设备特性（data bits、parity type、stop bit、flow control等）
  • c_ispeed、c_ospeed：控制输入输出速度（如串口波特率）

4.1.6 TTY Driver Flags

TTY driver可设置的flags：

  • TTY_DRIVER_DYNAMIC_DEV：表示TTY driver会自行调用tty_register_device注册TTY设备；若未设置，TTY core会根据driver->num自行创建TTY设备

4.1.7 TTY操作函数集

TTY core定义了struct tty_operations接口，具体TTY driver实现这些接口：

主要特点：

  • 操作函数的对象是struct tty_struct指针，即TTY设备的操作句柄
  • TTY driver可从struct tty_struct获取设备信息（如TTY port）
  • TTY core通过.write接口发送输出信息给终端显示
  • 输入信息通过TTY buffer APIs从TTY driver传递给TTY core

4.3 TTY Driver的编写步骤¶

编写TTY driver的基本步骤：

  1. 实现TTY设备操作函数集，保存在struct tty_operations变量中
  2. 调用tty_alloc_driver分配TTY driver，设置各字段（包括操作函数集）
  3. 调用tty_register_driver注册driver
  4. 如需动态注册TTY设备，调用tty_register_device或tty_register_device_attr
  5. 数据处理：
    • 接收数据：调用tty_insert_flip_string等API将数据交给TTY core
    • 发送数据：TTY core调用driver提供的回调函数操作硬件发送数据

5. System Console Driver：console 是架在 TTY 之上的日志通道¶

5.1 为什么不直接复用 TTY 字符设备接口¶

System console框架提供”控制台终端”功能，用于内核日志输出和基础人机交互。

为什么不直接使用TTY框架？出于以下考虑：

  1. 内核空间代码不应直接使用用户空间接口访问资源。TTY框架通过字符设备向用户空间提供接口，内核代码（如printk）不应直接使用，因此需要console框架：

  1. Console框架构建在TTY框架之上，大部分实现与TTY框架复用

  2. 只有附加了console驱动的TTY设备才能成为内核日志输出目的地或控制台终端

  3. 驱动开发者在编写TTY driver时，可同时编写console driver使其成为候选控制台设备

我调试 printk 没输出时，第一步就是确认那个 TTY 设备有没有挂 console driver——没挂的话，框架再完整也用不上。

5.2 核心数据结构¶

Console框架核心数据结构是struct console：

主要字段：

  • name：console名称，与命令行”console=xxx”匹配
    • 如name为”ttyS”，index≥0（如2），匹配”console=ttyS2”
    • 如name为”ttyS”，index<0（如-1），匹配任何”console=ttySn”
  • write：输出日志回调函数
  • device：获取TTY driver，绑定console与TTY设备
  • setup：初始化回调，必须返回0才能使console可用
  • flags：属性标志
    • CON_BOOT：临时console，启动后注销
    • CON_CONSDEV：作为控制台终端（对应/dev/console）

5.3 接口说明¶

5.3.1 Console Driver注册接口

对Console Driver开发者来说，只需关心console的注册/注销接口：

  1. 临时console：注册时设置CON_BOOT标志，系统启动后会自动注销
  2. 多个console：命令行可指定多个，内核日志将输出到所有指定的console
  3. 控制台终端：命令行指定的最后一个console作为控制台console(/dev/console)

5.4 Console Driver编写步骤¶

编写Console Driver的基本步骤：

  1. 若希望该console可作为系统控制台(/dev/console)，先实现对应TTY设备的TTY driver
  2. 定义struct console变量并填充：
    • name：匹配命令行参数用
    • index：配合name使用
    • write：输出日志回调函数
    • device：（可选）返回对应的TTY driver
    • setup：（可选）初始化回调
    • flags：设置适当的标志位
  3. 调用register_console注册到内核

8. 收口：先分清三层抽象，再逐个认节点¶
