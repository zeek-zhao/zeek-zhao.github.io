设备树基础：DTS 语法与内核解析

以前改一块板子的硬件配置，得改内核里的板级代码再重新编译，改一次编一次，很折腾。我第一次把 jz2440 的 LED 节点从 DTSI 里挪出来覆盖时，才真正明白“硬件描述与内核解耦”是什么意思——下面按语法、DTB 结构、内核处理、驱动应用的顺序捋。

1. 设备树要解决的是硬件描述与内核解耦¶

设备树(Device Tree)是一种描述硬件资源的数据结构，它以树形结构描述单板上的硬件资源信息，主要用于硬件资源配置和管理。在引入设备树之前，嵌入式系统中的硬件资源配置大多是写死在代码中的，修改配置需要修改源代码并重新编译，这种方式不够灵活。设备树的引入使得硬件资源配置可以从内核代码中分离出来，实现了硬件和软件的解耦。

1.1 板级代码膨胀催生了设备树¶

在ARM Linux早期，一个内核映像只能在一款特定硬件上运行。随着ARM平台数量的增长，这种方式变得不可持续。内核中充斥着大量的板级描述代码，厂商自定义的board代码占据了越来越大的比例。为解决这个问题，社区决定借鉴PowerPC的设备树解决方案。

2.6.39版本的内核中加入了对设备树的支持，自3.x版本开始，ARM架构开始大力支持设备树，4.x版本的内核完全依赖设备树进行硬件描述。

1.2 DTS、DTSI、DTB 三件套¶

设备树的核心思想是将硬件资源的描述与内核代码分离。内核通过解析设备树获取硬件资源信息，进而加载相应的驱动程序。

设备树主要由三部分组成：

  • DTS(Device Tree Source)：设备树源文件，人类可读的文本文件
  • DTSI(Device Tree Source Include)：可被DTS包含的设备树源文件
  • DTB(Device Tree Blob)：设备树二进制文件，由DTS编译而成，供内核解析使用
    我理解这三件套的分工是：DTSI 放公共部分，DTS 写板子差异，dtc 编成 DTB 给内核读，改硬件只动文本文件。

1.3 Bootloader 传地址，内核启动时解析¶

在实际使用中，bootloader(如U-Boot)会将DTB文件加载到内存中，然后将DTB文件的内存地址传递给内核。内核启动时解析DTB文件，获取硬件资源信息，再根据这些信息注册相应的设备和驱动。

3.4 五种 token 标记节点与属性¶

结构块存储节点和属性的信息，由一系列标记(token)组成：

  • FDT_BEGIN_NODE(0x1)：节点开始
  • FDT_END_NODE(0x2)：节点结束
  • FDT_PROP(0x3)：属性
  • FDT_NOP(0x4)：空操作
  • FDT_END(0x9)：结构块结束

3.5 属性名统一放这里按偏移引用¶

字符串块存储所有属性名称的字符串。结构块中的属性通过偏移引用这些字符串。
实测下来 DTB 最容易踩的是大端格式：拿十六进制工具看 magic 是 d00dfeed 就对了，读成 feedd00d 说明字节序理解错了。

4. 内核解析：从 DTB 地址到 platform_device¶

4.1 从 head.S 到 unflatten 的七步¶

  1. Bootloader加载DTB到内存，并将DTB地址传给内核
  2. 内核head.S中保存DTB地址
  3. start_kernel调用setup_arch，其中处理DTB
  4. setup_machine_fdt函数解析设备树，选择最合适的machine_desc
  5. 解析设备树中的runtime配置信息(如bootargs、内存大小等)
  6. unflatten_device_tree函数将扁平的DTB转换为device_node树结构
  7. 设备树中的设备节点转换为platform_device，并与driver匹配

4.2 compatible 按顺序匹配 machine_desc¶

内核根据设备树根节点的compatible属性选择最合适的machine_desc：

4.3 两类节点会转成 platform_device¶

以下节点会被转换为platform_device：

  1. 含有compatible属性的根节点的子节点
  2. 含有特殊compatible属性节点的子节点(如”simple-bus”、”simple-mfd”等)

4.4 四级匹配，命中即绑定驱动¶

平台设备与驱动的匹配按以下优先顺序进行：

  1. 比较platform_dev.driver_override和platform_driver.drv->name
  2. 比较platform_dev.dev.of_node的compatible属性和platform_driver.drv->of_match_table
  3. 比较platform_dev.name和platform_driver.id_table
  4. 比较platform_dev.name和platform_driver.drv->name

只要有一个匹配成功，该设备就会使用对应的驱动。
我调驱动匹配时习惯先看 /proc/device-tree 里节点的 compatible 字符串，再对 of_match_table，比直接看代码猜快得多。

6. 调试手段：sysfs、dtc 与 U-Boot fdt¶

6.1 三个路径查看运行时设备树¶

在Linux系统中，可以通过以下路径查看设备树信息：

  • /sys/firmware/fdt：原始DTB文件的内存映射
  • /sys/firmware/devicetree/base：以目录结构展示的设备树
  • /proc/device-tree：指向/sys/firmware/devicetree/base的符号链接

6.2 dtc 编译与反编译¶

DTC(Device Tree Compiler)是编译和反编译设备树的工具：

  • 编译设备树：dtc -I dts -O dtb -o output.dtb input.dts
  • 反编译设备树：dtc -I dtb -O dts -o output.dts input.dtb

6.3 fdt 命令读改 DTB¶

U-Boot提供fdt命令用于查看和修改DTB：
我现场改节点最喜欢用 fdt set 加 fdt print 这一对组合，改完先打印确认，再擦写回 flash，避免把 DTB 分区写坏。

nand read.jffs2 32000000 device_tree // 从flash读取DTB到内存
fdt addr 32000000 // 指定DTB地址
fdt print /led pin // 查看/led节点的pin属性
fdt set /led pin <0x00050005> // 修改/led节点的pin属性
nand erase device_tree // 擦除flash分区
nand write.jffs2 32000000 device_tree // 将修改后的DTB写回flash

8. 落点与延伸：设备树已经取代板级文件¶

现在 ARM 平台基本不再维护 board 级代码，硬件描述全部放进 DTS 和 DTSI，改引脚、改时序只需要改文本再 dtc 编一次。把 DTS 语法、DTB 四段结构和内核的 compatible 匹配这条链打通之后，再去看具体的驱动代码会发现，大部分板级差异已经被挡在驱动之外了。

下一步值得动手的是 Overlay：在 U-Boot 里用 fdt 命令临时改一个节点，验证通过后再固化进 DTS，比反复编译内核试错快得多。
