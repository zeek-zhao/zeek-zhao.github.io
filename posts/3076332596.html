大规模仓库管理

ℹ️本页概览
本文讲解大规模仓库（monorepo/大仓）管理：多仓 vs 单仓、分仓策略、性能优化、工具与 CI，配真实方案示例。

多仓 vs Monorepo¶

多仓（Multi-repo）：每个服务/组件独立仓库

  • 优点：独立版本、独立权限、独立发布
  • 缺点：跨仓库改动难、版本对齐难、重复基础设施

Monorepo：所有代码放同一仓库

  • 优点：原子提交、统一依赖、统一 CI、代码复用
  • 缺点：仓库大、权限粗、工具链要求高

主流案例：Google、Meta、Uber（monorepo）；K8s、Linux（超大单仓）

常用工具¶

  • 前端：Turborepo、Nx、pnpm workspaces
  • 多语言：Bazel、Pants（依赖图 + 增量构建）
  • Go：go.work + build cache
  • 代码搜索：OpenGrok、Sourcegraph（见工具目录教程）

常见坑¶

  1. 一刀切 monorepo：工具链未就绪反而更慢。
  2. 全量 CI 跑全仓：规模大后必须影响分析。
  3. 权限形同虚设：无 CODEOWNERS，跨域乱改。
  4. 依赖版本不统一：workspace 统一提升（hoist）策略。
  5. 历史过大：用 shallow/partial clone，必要时 filter-repo 瘦身。

最佳实践¶

  • 按团队规模渐进演进（先多仓，再合并为 workspace）。
  • 影响分析 + 缓存 + owner 制。
  • 更多性能手段见 14-Git性能优化。
⚠️踩坑提示
Monorepo 的 git clone 全量拉下来可能几个 GB，日常用稀疏检出（git sparse-checkout）或浅克隆（--depth）只取相关目录，但要清楚浅克隆的 git log 和 blame 不完整。影响分析构建按依赖图只重建受影响模块，前提是依赖关系声明准确——漏声明会导致该建的没建。代码所有权（CODEOWNERS）要配强制 review 才生效，光写文件没人看等于没有。
