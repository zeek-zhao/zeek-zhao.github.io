设备树架构：从 DTS 到内核设备节点的完整链路

设备树这东西，单看 DTS 语法觉得挺简单，真到移植板子时才发现它串起了启动、内核初始化和驱动匹配一整条链。我第一次读源码也是从 DTS 格式入手的，后来才意识到关键在内核怎么把 DTB 展开成 device_node 树。下面按这条链路把架构讲清楚。

一图看懂：Bootloader 传 DTB 地址，内核校验、展开并注册设备。

graph LR UB[U-Boot 加载 DTB] --> R2["R2 寄存器传地址"] R2 --> K[内核校验 DTB] K --> UF[unflatten 还原 device_node] UF --> M[compatible 匹配 machine] M --> P[of_platform_populate 注册平台设备]

1. 设备树为什么出现：把硬件描述从内核里搬出来¶

设备树（Device Tree，简称 DT）用树形结构描述嵌入式系统的硬件拓扑。我理解它的核心动作就一个：把硬件资源配置从内核代码里挪出来，让硬件和软件解耦，一份内核镜像因此能跑多块板子。

1.1 硬编码之痛：一板一内核，改硬件就要重编¶

在引入设备树之前，ARM Linux 面临一个很实际的问题——硬件资源信息被硬编码进内核，带来三个后果：

  1. 每款不同的板子都需要单独的内核镜像
  2. 内核代码中充斥着大量的板级描述代码
  3. 硬件变更需要修改内核代码并重新编译

设备树给出统一的硬件描述方法后，上面三条都绕开了。我实际用下来的感受是，真正省事的不是少写几行代码，而是硬件改版时不用再动内核。

顺带把它带来的好处摆在这里，后面几节都建立在这几点上：

  1. 硬件与软件分离：硬件描述与内核代码分离，改配置不必重编内核
  2. 统一描述方式：标准化的硬件资源描述，易读易维护
  3. 多平台支持：一份内核镜像支持多种硬件平台，减少冗余
  4. 动态配置能力：运行时可修改设备树、支持可插拔设备

1.2 三层看设备树：文件格式、数据结构、系统交互¶

我一般从三个层面理解它的整体架构：

  1. 文件格式层面：

    • DTS（Device Tree Source）：文本格式的设备树源文件
    • DTSI（Device Tree Source Include）：可被引用的设备树源文件
    • DTB（Device Tree Blob）：二进制格式的设备树数据

  2. 数据结构层面：

    • 设备树是一个树形结构
    • 由节点（node）和属性（property）组成
    • 节点可以包含子节点，形成树形层次

  3. 系统交互层面：

    • Bootloader 加载 DTB 到内存
    • 内核通过解析 DTB 获取硬件信息
    • 内核根据设备树信息初始化系统和注册设备

2. 启动链路里的设备树：Bootloader 把 DTB 地址交给内核¶

基于 ARM 的系统里，设备树在启动流程中位置很固定：U-Boot 加载它、内核解析它。我调启动问题时最常做的，就是先确认 DTB 地址有没有正确传下去——地址错了，后面全是无用功。

2.1 三个阶段：U-Boot 加载、内核解析、系统初始化¶

设备树在启动流程中扮演三个角色：

  1. Bootloader 阶段：

    • U-Boot 读取并加载 DTB 文件到内存
    • U-Boot 可以修改 DTB 中的内容（如使用 fdt 命令）
    • U-Boot 将 DTB 文件的地址传递给内核

  2. 内核启动阶段：

    • 内核通过 R2 寄存器接收 DTB 地址
    • 内核校验 DTB 有效性
    • 解析 DTB 并构建内核中的设备树表示

  3. 系统初始化阶段：

    • 根据设备树选择合适的 machine_desc
    • 提取系统配置信息（如内存大小、启动参数等）
    • 注册设备并匹配驱动

2.2 R2 寄存器传地址，fdt 命令就地改 DTB¶

Bootloader（如 U-Boot）把 DTB 传递给内核，遵循三条约定：

  • U-Boot 将 DTB 加载到内存中的特定位置
  • 在执行内核代码前，U-Boot 设置 R2 寄存器为 DTB 的物理地址
  • 内核通过检查 R2 寄存器获取 DTB 地址

3. DTB 的四段结构：头部、保留块、结构块、字符串块¶

DTB 是设备树的二进制表示。我习惯先确认头部魔数，再去翻结构块——直接 hexdump 全文很容易迷路。

3.1 DTB 是扁平二进制：四块拼成一个文件¶

DTB 文件由四个主要部分组成：

  1. FDT 头部（struct fdt_header）：包含魔数、总大小、偏移量等信息
  2. 内存保留块（memory reservation block）：定义系统保留的内存区域
  3. 结构块（structure block）：包含节点和属性的层次结构
  4. 字符串块（strings block）：存储属性名称的字符串池

  1. 预处理：处理宏定义和包含文件
  2. 解析：分析 DTS 语法，构建内存中的树结构
  3. 生成：将内存中的树转换为 DTB 格式
  4. 优化：合并相同的字符串，对齐数据等

4. 内核拿到 DTB 后的五步：校验、选平台、展开、注册¶

内核对设备树的处理大致可分五步。我排查平台没匹配上时，一般先打印根节点的 compatible，再看 machine_desc 的 dt_compat——顺序反过来会浪费很多时间。

4.1 五个关键调用：从校验到 of_platform_populate¶

  1. 基本检查与验证：

    • early_init_dt_verify：验证 DTB 有效性
    • 保存 DTB 地址到 initial_boot_params

  2. 平台识别：

    • of_flat_dt_match_machine：根据 compatible 属性选择 machine_desc

  3. 运行时配置处理：

    • early_init_dt_scan_nodes：处理根节点、chosen 节点和内存节点
    • 提取 bootargs、内存大小等信息

  4. 设备树展开：

    • unflatten_device_tree：将 DTB 转换为 device_node 树

  5. 设备注册：

    • of_platform_populate：注册 platform devices

4.2 compatible 字符串逐个匹配，按 score 选 machine_desc¶

内核根据设备树根节点的 compatible 属性选择合适的 machine_desc：

内核会尝试找到最匹配的 machine_desc：

  1. 尝试匹配第一个 compatible 字符串 “samsung,smdk2440”
  2. 如果找不到，尝试第二个 compatible 字符串 “samsung,smdk24xx”
  3. 选择 score 最低的 machine_desc

4.3 哪些节点会变成 platform_device，以及怎么匹配驱动¶

内核会把某些设备树节点转换为 platform_device：

  1. 哪些节点会被转换：

    • 根节点的直接子节点（具有 compatible 属性）
    • “simple-bus”、”simple-mfd” 等特殊 compatible 节点的子节点

  2. 转换过程：

    • of_platform_populate -> of_platform_bus_create -> of_platform_device_create
    • 解析节点的 reg 属性转换为 device 资源
    • 解析节点的 interrupt 属性转换为 irq 资源

  3. 设备与驱动的匹配：

    • 平台设备与驱动之间的匹配通过 platform_match 函数完成
    • 匹配优先级：driver_override > of_match > id_table > name

9. 落地建议：从绑定到分层的几条硬规矩¶

我自己的规矩是先写绑定文档再写 DTS，不然过两个月连自己都看不懂。下面五条是实际项目里最值得守住的。

9.1 五条实践规矩：绑定、文档、分层、去硬编码、错误处理¶

  1. 遵循标准绑定：

    • 查阅内核文档中的绑定规范
    • 参考类似设备的设备树描述

  2. 文档化设备树需求：

    • 为驱动编写清晰的设备树绑定文档
    • 指明必需属性和可选属性

  3. 模块化设计：

    • 使用 DTSI 文件共享公共配置
    • 将 SoC、板子、变种分层组织

  4. 避免硬编码：

    • 避免在驱动中硬编码硬件信息
    • 尽可能从设备树中获取配置

  5. 良好的错误处理：

    • 处理属性缺失或无效的情况
    • 提供合理的默认值

要动手的话，先翻 Documentation/devicetree/bindings/ 下对应的绑定文档，再按 SoC → 板子 → 变种的层次拆 DTSI，最后用 make dtbs 验证整棵设备树能不能过编译。
