GitHub Actions自动部署

上一篇 11-部署方式总览 把部署路径摊开了，这里挑我最常用的那条往下拆。用专用 Deploy Key 和一份 workflow 文件，就能让 Hexo 博客实现”git push 即上线”，从此告别本地手动构建。

把构建搬到云端，先拆成三块¶

手动部署的痛点在于：本地环境坏了就发不了版、构建过程不可追溯、换电脑需要重配环境。GitHub Actions 把构建搬到了云端，你只负责提交 Markdown 源码，其余交给流水线。整个方案分为三块：SSH 密钥体系（谁有权发布）、仓库配置（密钥放哪里）、工作流文件（流水线做什么）。

第一步：单独生成一把 Ed25519 部署密钥¶

不要复用个人 SSH 密钥，应为部署单独生成一对，推荐更安全、更短的 Ed25519 算法：

生成两个文件：github_actions_deploy 是私钥（放入 Secret），github_actions_deploy.pub 是公钥（填入 Deploy Key）。私钥务必妥善保管，绝不能提交到任何公开仓库。

第二步：公钥进 Deploy Key，私钥进 Secret¶

方案使用”源码仓库 + 部署仓库”分离结构。假设源码仓库为 blog-source，部署仓库为 username.github.io。

部署仓库添加 Deploy Key：进入 Settings > Deploy keys > Add deploy key，粘贴公钥内容，命名为 Hexo Deployment Key，必须勾选 Allow write access，否则 Actions 没有推送权限。

源码仓库添加 Secret：进入 Settings > Secrets and variables > Actions > New repository secret，名称设为 DEPLOY_KEY，值为私钥完整内容。Secret 只进不出，连仓库管理员也无法再查看明文。

两个坑我踩过：Deploy Key 忘勾选 write access 时，部署步骤会报 Permission denied (publickey)；私钥从 Windows 复制到 Linux 时可能带入 \r 回车符，导致 SSH 认证失败，工作流中要用 tr -d '\r' 清洗。

密钥专用、定期轮换、最小权限¶

三项最佳实践值得坚持：密钥专用（只用 Deploy Key，不碰个人密钥）、定期轮换（重新生成密钥对并同步更新 Deploy Key 与 Secret）、最小权限（workflow 里显式声明 permissions，默认只给读取）。此外建议保留部署仓库的 Git 历史，一旦发布异常可以按 commit 快速回滚。

排查从本地密钥验证开始¶

若站点长时间未更新，依次检查：Pages 设置中的发布分支是否正确、部署仓库根目录是否有 .nojekyll（防止 Jekyll 二次处理）、Actions 运行日志中部署步骤是否实际成功。更多疑难场景见 21-常见问题排查。
