53-TensorFlow与Caffe2在自动驾驶中的应用

发表于2026-10-25|apollo
|浏览量:

[!info] 本节目标
系统了解 TensorFlow 生态与 Caffe2 的技术特点，理清 Caffe2 并入 PyTorch 的历史脉络，掌握从”研究框架”到”生产部署”的转换思路。框架选型可与 52-PyTorch与自动驾驶实践 对照阅读。

1. TensorFlow 基础

1.1 发展与版本分水岭

TensorFlow 由 Google Brain 于 2015 年开源。1.x（静态图 + Session）与 2.x（默认即时执行 Eager Execution + Keras 高级 API）是两代完全不同的编程体验：

TF 2.x 的 tf.function 装饰器可把 Python 函数编译为图执行，兼得开发效率与运行性能。

1.2 分层 API 体系

层级 API 用途
高级 Keras（Sequential/Functional） 快速建模，90% 场景够用
中级 tf.Module、自定义 Layer 灵活组件
低级 张量算子、tf.GradientTape 自定义训练循环
扩展 TensorFlow Probability 概率推理

Keras 典型流程：构建模型 → compile(优化器/损失/指标) → fit → evaluate → save。

1.3 数据管道与训练

  • tf.data.Dataset：from_tensor_slices → shuffle → map(预处理) → batch → prefetch(AUTOTUNE)，异步预取可打满 GPU
  • 自定义训练：with tf.GradientTape() as tape: 记录前向，tape.gradient 求梯度
  • 分布式：MirroredStrategy（单机多卡）、MultiWorkerMirroredStrategy（多机）、TPUStrategy
  • 混合精度：tf.keras.mixed_precision.set_global_policy("mixed_float16")

1.4 模型保存与格式

格式 特点 用途
HDF5 (.h5) 单文件，含结构与权重 开发阶段
SavedModel 目录形式，含完整计算图 生产部署标准格式
Checkpoint 仅权重 训练备份
TF Lite (.tflite) 轻量量化模型 移动/边缘设备

2. TensorFlow 在自动驾驶中的应用

2.1 感知模型

  • 目标检测：SSD（基于 MobileNetV2/VGG16 多尺度特征图 + 检测头）、Faster R-CNN
  • 语义分割：DeepLab 系列（TF 官方实现完善）、U-Net
  • 端到端：Keras Functional API 融合图像输入与车辆状态输入，输出油门/刹车/转向

2.2 边缘部署：TF Lite 与 TensorRT

在 NVIDIA 车载平台（Xavier/Orin）上则走 TensorRT：TF 模型 → ONNX/UFF → TensorRT 引擎，配合 FP16/INT8 与算子融合获得确定性低延迟。

2.3 生产化组件

  • TF Serving：模型服务化，支持版本管理、热更新、A/B 测试，适合云端推理服务
  • TFX：端到端 ML 流水线（数据验证 TFDV、特征变换 TFT、模型分析 TFMA），可对接 56-自动驾驶云服务与基础设施 中的数据管线
  • 模型优化工具包：量化感知训练（QAT）、剪枝、聚类

3. Caffe2：从独立框架到并入 PyTorch

3.1 历史脉络

[!important] 关键结论：Caffe2 已”消失”
自 2018 年起，Caffe2 不再作为独立框架维护，其代码与理念已融入 PyTorch 生态。新项目请直接使用 PyTorch；遇到老 Caffe2 模型，通过 ONNX 转换迁移（见 3.3）。学习 Caffe2 的价值在于理解”静态图部署优先”的设计思想——它正是今天 ONNX/TensorRT 部署体系的先声。

3.2 Caffe2 的核心概念（历史回顾）

  • 静态计算图：先定义 Net（由算子 Operator 组成），再在 Workspace 中执行
  • Blob / Workspace：数据以命名 Blob 存于全局 Workspace
  • 声明式编程：brew.conv(model, data, ...) 逐算子搭建网络，与 PyTorch 动态图形成鲜明对比
  • 部署优势：静态图便于算子融合、INT8 量化（DNNLOWP）、OptimizeForMobile 移动端优化、ARM NEON 加速——这些能力后来都体现在 PyTorch Mobile / ExecuTorch 中

3.3 经 ONNX 的互操作桥梁

ONNX（开放神经网络交换格式）曾是 PyTorch 前端与 Caffe2 后端之间的关键桥梁，至今仍是跨框架部署的通用中间格式：

老 Caffe2 模型迁移路径：Caffe2 net → caffe2_frontend.caffe2_net_to_onnx_model → ONNX → PyTorch/TensorRT；或直接用 PyTorch 同构模型 + 权重手动映射，再 np.testing.assert_allclose 校验输出一致。

4. 框架选型对比

维度 TensorFlow 2.x PyTorch Caffe2（已并入）
计算图 动态 + tf.function 图编译 动态（torch.compile 编译） 静态图
调试体验 良好 最佳 差
生产部署 TFLite/Serving/TFX 完善 TorchScript/ONNX/ExecuTorch 静态图优化思想被继承
生态 成熟全面，TFX 数据管线强 学术界主流，新模型最快 无
自动驾驶典型用途 云端服务、TFLite 边缘 感知模型训练首选 历史项目迁移

[!tip] 选型建议

  • 模型训练：PyTorch 优先（新论文实现最快、社区最活跃）
  • 云端模型服务：TF Serving 或 TorchServe 均可，按团队栈决定
  • 边缘/移动部署：目标硬件决定格式——NVIDIA 平台走 ONNX→TensorRT；ARM/手机端 TFLite 或 ExecuTorch
  • 遗留 Caffe2/Caffe 项目：经 ONNX 渐进式迁移，保留验证集做数值一致性回归

5. 2026 年现状

[!note] 2026 年更新
TensorFlow 仍广泛用于 Google 生态与存量工业系统，但在自动驾驶研究前沿（BEV、端到端 UniAD/VLA）中，PyTorch 已占绝对主导。Caffe2 作为独立框架早已退役，仅以”PyTorch 部署血统”的形式存在。对 Apollo 开发者而言，实用结论是：训练用 PyTorch，部署走 ONNX/TensorRT/PaddleInference（见 52-PyTorch与自动驾驶实践 第 4 节），TF 与 Caffe2 的知识主要用于理解存量系统与面试历史题。

6. 小结

  • TF 2.x = 即时执行 + Keras + tf.data + TFLite/Serving/TFX 全家桶，强在生产化
  • Caffe2 的静态图、量化、移动优化思想已全部融入 PyTorch 部署体系，独立框架已死
  • ONNX 是打通”任意训练框架 → 任意推理后端”的通用桥梁
  • 自动驾驶实践：训练侧 PyTorch 为主，部署侧按目标硬件选 TensorRT / TFLite / PaddleInference
