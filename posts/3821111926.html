性能优化与构建加速

接着上一篇 12-GitHub-Actions自动部署 说上线之后的事。性能优化分两条线：让访客更快打开页面（压缩、懒加载、CDN），让构建更快出结果（缓存、增量、并行）。两条线别混着做，我一般先动访客侧。

优化前先量一次基线¶

动手前先用 Lighthouse 或 PageSpeed Insights 跑一次基准分数，记录 FCP（首次内容绘制）、LCP（最大内容绘制）、CLS（布局偏移）三项核心指标。没有基线数据的优化是盲目的：很多时候瓶颈不是 CSS 太大，而是一张没压缩的头图，或者一段同步加载的第三方脚本。优化后复测对比，才能确认投入有回报。

图片是页面体积的大头，优先处理¶

图片通常占据页面字节数的 60% 以上，是投入产出比最高的优化点：

  1. 懒加载：Butterfly 主题内置 lazyload 配置，打开后图片进入视口才加载，首屏体积立减。
  2. WebP 格式：同等画质下比 JPEG 小 25%-35%，可用 cwebp 或图床服务自动转换，<picture> 标签做降级兜底。
  3. 构建期压缩：用 gulp-imagemin 或脚手架脚本在发布前统一压图，顺便清除 EXIF 信息保护隐私。
  4. CDN 分发：图片走独立 CDN 域名，与 HTML 主域分离，充分利用浏览器并发连接。
  5. 画廊与预览：用主题的 {% gallery %} 标签组织多图，配合预览图减少一次性加载。

加载策略比资源本身更影响体感¶

除了资源本身，加载策略同样关键：开启主题的 Pjax（局部刷新 + 页面预取），用户站内跳转几乎瞬时完成；对第三方统计、评论脚本统一异步加载（async/defer），避免阻塞渲染；字体文件用 font-display: swap 防止文字白屏；对确定不变的资源配置长缓存（Cache-Control 一年 + 文件名指纹），命中缓存后二次访问接近秒开。

如果只做三件事：开懒加载、压缩图片、上 CDN。这三项通常能把 LCP 从 4 秒压到 2 秒以内，而配置成本不到半小时——这是我给新站的第一优先级。

构建加速靠缓存和少折腾¶

站点文章多了以后，构建本身也会变慢，优化方向与站点性能不同：

  • 缓存 node_modules：跳过每次全量 npm install，省下 1-2 分钟。
  • 减少 hexo clean：无异常时不清缓存，Hexo 的增量渲染比全量快数倍。
  • 拆分重插件：搜索索引、sitemap 生成放在独立步骤或定时任务，而非每次提交都跑。
  • 控制文章数量：把早期低价值草稿归档到不渲染的目录，构建时间与文章数线性相关。

上线后还得持续盯指标¶

优化不是一次性的。把 Lighthouse 检查接入 CI（如 lhci autorun），每次大改主题后自动跑分；用 Google Search Console 观察核心网页指标的真实用户数据；若集成了访问统计，留意”跳出率突然升高”这类性能劣化信号。性能是一场与内容增长的长期赛跑，见 21-常见问题排查 中的监控手段。
