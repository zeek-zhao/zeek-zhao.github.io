云原生详解：概念、架构与最佳实践

云原生这三个字被讲烂了，但真正落地的团队没那么多。我更关心它到底解决了什么实际问题。

云原生为什么会被推到台前¶

1.1 什么是云原生¶

云原生可分解为”云”（Cloud）和”原生”（Native）两个词。实际上是暗指云原生计算（Cloud Native Computing），一种与传统计算模式截然不同的新型计算方式。

1.1.1 云原生的概念演进

云计算的概念最早由戴尔公司于1996年提出。2006年，亚马逊公司推出了弹性计算云（Elastic Compute Cloud，EC2）服务，随后越来越多的企业开始接受云计算这一概念，并将应用迁移到云端。

在云计算发展早期，大多数应用只是简单地从私有数据中心迁移到云端，而没有根本性地改变应用架构。这种”搬家式”迁云并不能充分发挥云计算的优势，特别是在以下方面:

  • 稳定性：传统应用架构未针对分布式环境优化
  • 服务同步：组件或服务间数据同步问题
  • 高可用容灾：系统整体高可用性设计未随环境变化
  • 自动化程度：CI/CD流程的自动化程度不足
  • 资源利用率：资源调度不够灵活
  • 可观测性：端到端链路跟踪困难

为解决这些问题，诞生了真正的”云原生”概念：

  • 2011年，Heroku提出十二因子应用，被认为是最早的云原生应用技术特征
  • 2015年，Pivotal明确提出了云原生概念
  • CNCF定义：云原生技术有利于各组织在公有云、私有云和混合云等新型动态环境中构建和运行可弹性扩展的应用

1.1.2 云原生是云计算的趋势

从技术发展趋势看，越来越多企业广泛应用云原生技术。在国家政策和企业需求双重驱动下，更多企业选择上云，中国云计算的强势增长成为必然趋势。

从软件开发角度看，云原生技术为企业带来更快业务创新的价值。企业逐渐意识到云服务的专业性和高SLA，将IaaS和PaaS的通用技术复杂性委托给云平台，从而专注于业务逻辑创新。

落地云原生，先从这几处动手¶

2.1 云原生是云计算的再升级¶

从云原生的定位可以看到，云原生包含大量新的PaaS层技术和新的开发理念，是释放云计算价值的最短路径，推动着云计算的再升级。

整个云原生技术栈基于开源、开放的技术标准。CNCF致力于云原生技术的标准化，为用户提供云服务的标准界面，避免厂商锁定。

2.1.7 运维模式的升级

配置变更是运维场景下的高频操作。针对配置变更，云原生提倡采用不可变的基础设施，即任何变化都是基于容器重新生成镜像来部署，而不是在原有环境下直接变更配置。

配置管理方式分为:

  1. 开关配置：使用配置中心管理
  2. 非开关配置：Configuration as Code，归于代码仓库

云原生架构真正值钱的地方¶

3.1 云原生架构的定义¶

云原生架构是基于云原生技术的一组架构原则和设计模式的集合，旨在帮助企业和开发人员充分利用云平台的平台化能力和弹性资源能力。

3.2 云原生架构能为企业带来的价值¶

3.2.1 降低研发成本和项目维护复杂度

云原生架构强调业务研发应充分利用云平台所提供的IaaS和PaaS的通用能力。虽然云计算不能解决所有非功能性问题，但云平台确实能够处理大量的分布式环境下的复杂非功能性问题。以高可用性为例，云平台在多个层面为应用提供了解决方案：

flowchart TD A[云平台高可用机制] --> B[虚拟机层面] A --> C[容器层面] A --> D[云服务层面] B --> B1[硬件异常检测] B --> B2[虚拟机热迁移] B --> B3[无感知切换] C --> C1[健康检查] C --> C2[异常节点下线] C --> C3[新节点自动上线] C --> C4[流量自动切换] D --> D1[多可用区部署] D --> D2[数据多副本存储] D --> D3[自动故障转移] D --> D4[全托管式服务] style A fill:#f9f7ff,stroke:#333,stroke-width:2px style B fill:#e6f7ff,stroke:#333,stroke-width:2px style C fill:#d9f2e6,stroke:#333,stroke-width:2px style D fill:#ffe6e6,stroke:#333,stroke-width:2px

通过为Pod配置云原生标准的健康检查机制，实现：

  • Pod自动重建：当容器健康检查失败时，系统自动重启或重建Pod
  • Pod自动迁移：当母机出现资源瓶颈时，系统自动将Pod迁移到其他低负载的节点
  • 全天候监控告警：7×24小时对服务健康度进行监控和告警

3.2.2 加快软件迭代速度，降低管理和运行成本

面向云服务与云API研发

云原生架构使编程模型发生了巨大变化。传统的单机资源开发模式转变为面向云服务与云API的开发模式：

flowchart LR A[传统编程模式] --> B[云原生编程模式] A --> A1[文件操作] A --> A2[网络编程] A --> A3[线程管理] A --> A4[本地存储] B --> B1[对象存储服务] B --> B2[负载均衡服务] B --> B3[容器编排服务] B --> B4[分布式存储服务] style A fill:#f9f9f9,stroke:#333,stroke-width:2px style B fill:#e6f7ff,stroke:#333,stroke-width:2px
高度自动化的软件交付能力

云原生提供完整的CI/CD流水线，实现从代码提交到产品环境部署的全自动化流程：

云原生接下来的走向¶

4.1 无处不在的计算需求催生新一代容器运行时¶

5G、AIoT 这些技术铺开后，随处可见的计算需求冒了出来。不同的计算场景对容器运行时有不同的需求。Kata Container、Firecracker、gVisor、Unikernel等新的容器运行时技术层出不穷，分别解决了安全隔离性、执行效率和通用性三个不同维度的需求。

flowchart TD A[新一代容器运行时] --> B[安全隔离性] A --> C[执行效率] A --> D[通用性] B --> B1[Kata Container] B --> B2[gVisor] C --> C1[Firecracker] C --> C2[WebAssembly] D --> D1[Docker/containerd] D --> D2[CRI-O] style A fill:#f9f7ff,stroke:#333,stroke-width:2px style B fill:#e6f7ff,stroke:#333,stroke-width:2px style C fill:#d9f2e6,stroke:#333,stroke-width:2px style D fill:#ffe6e6,stroke:#333,stroke-width:2px

OCI（Open Container Initiative）标准的出现，使得不同的技术可以采用一致的方式管理容器生命周期，从而进一步促进容器引擎技术的持续创新。

4.2 云原生操作系统的发展¶

Kubernetes 成了容器领域的事实标准，各种场景持续演进，它已经是云原生时代的操作系统。Kubernetes的发展历程和特性与Linux有着诸多相似之处。

flowchart LR subgraph Linux操作系统 A1[进程] --> B1[系统调用] B1 --> C1[内核] C1 --> D1[硬件资源] end subgraph Kubernetes云原生操作系统 A2[Pod] --> B2[API调用] B2 --> C2[控制平面] C2 --> D2[集群资源] end style A1 fill:#f9f9f9,stroke:#333,stroke-width:1px style B1 fill:#f9f9f9,stroke:#333,stroke-width:1px style C1 fill:#f9f9f9,stroke:#333,stroke-width:1px style D1 fill:#f9f9f9,stroke:#333,stroke-width:1px style A2 fill:#e6f7ff,stroke:#333,stroke-width:1px style B2 fill:#e6f7ff,stroke:#333,stroke-width:1px style C2 fill:#e6f7ff,stroke:#333,stroke-width:1px style D2 fill:#e6f7ff,stroke:#333,stroke-width:1px

Linux与Kubernetes都提供了对底层计算、存储、网络、异构计算设备的资源抽象和安全访问模型，可以根据应用需求调度和编排资源。Linux的计算调度单元是进程，调度范围限制在一台计算节点上；而Kubernetes的调度单位是Pod，调度范围是在分布式集群中，甚至可以跨越不同的云环境。

4.3 Kubernetes的价值展现¶

过往在Kubernetes上运行的主要是无状态的Web应用。技术和社区都在推进，越来越多有状态应用、大数据和 AI 负载往 Kubernetes 上迁。Kubernetes的技术价值将在以下四个方面集中展现：

mindmap root((Kubernetes价值)) 统一技术栈，提升资源利用率 多计算负载统一调度 异构资源高效利用 AI与大数据工作负载支持 统一技能栈，降低人力成本 统一部署和交付 DevOps文化与工具集 跨云与混合云管理 加速数据服务云原生化 计算存储分离 分布式缓存加速 调度优化 容器Serverless化 免运维体验 按需自动弹性 极致性价比

4.3.1 统一技术栈，提升资源利用率

多种计算负载在Kubernetes集群上统一调度，可以有效提升资源的利用率。通过自动化工具来完成资源阈值的计算，以提高资源利用率和增强系统的稳定性：

  • 动态容器生命周期管理：采用脚本动态设置PreStop钩子，优化容器关闭时间
  • 自动资源配额管理：集群剩余配额自动统计，支持后续的自动扩缩容

4.3.2 统一技能栈，降低人力成本

Kubernetes可以在IDC、云端、边缘等不同场景中进行统一部署和交付。云原生提倡的DevOps文化和工具集可以有效提升技术的迭代速度并降低人力成本：

  • 所有服务完全上云，完成云原生化建设
  • 持续部署(CD)采用声明式基础设施(IAC)方式，通过API自动化完成服务部署
  • 采用Kubernetes原生工作负载类型进行统一管理
  • 实现符合云原生标准的灰度发布流程

4.3.3 加速数据服务云原生化

计算存储分离具备巨大的灵活性和成本优势，数据服务的云原生化也逐渐成为发展趋势。容器和Serverless的弹性可以简化对计算任务的容量规划，结合分布式缓存加速和调度优化，可使数据计算类任务和AI任务的计算效率得到很大提升。

4.3.4 容器Serverless化降低运维和资源成本

Serverless和容器技术开始融合并快速发展，主要体现在以下几个方面：

flowchart TD A[容器Serverless化] --> B[从离线到在线业务] A --> C[推动基础设施Serverless化] A --> D[最优性能功耗比] A --> E[小镜像快速分发] A --> F[解决状态传递问题] style A fill:#f9f7ff,stroke:#333,stroke-width:2px style B fill:#e6f7ff,stroke:#333,stroke-width:2px style C fill:#d9f2e6,stroke:#333,stroke-width:2px style D fill:#ffe6e6,stroke:#333,stroke-width:2px style E fill:#e6e6ff,stroke:#333,stroke-width:2px style F fill:#ffffe6,stroke:#333,stroke-width:2px
  • 从离线业务到在线业务：早期Serverless主要应用于对响应时间不敏感的事件驱动型离线业务，现在逐步扩展到在线业务场景
  • 基础设施Serverless化：业务代码托管给Serverless平台后，即可享受自动弹性、按请求计费等功能
  • 性能与资源开销平衡：新一代Serverless技术追求最高的安全性与最小的资源开销的平衡
  • 镜像优化：构建更小的应用镜像，实现快速分发和极短的启动时间
  • 状态管理：解决函数间状态传递的效率问题

实践落地：别为了上云而上云¶

云原生理念和技术铺开后，越来越多企业开始做云原生架构的实践和探索。虽然不同行业的云原生实践方式有所不同，但我们可以总结出一套基本方法论：

5.1 引入云原生的PaaS和BaaS产品¶

利用云原生中间件和数据库产品自带的多种特性，如自动化部署、无缝升级、便捷扩容、高可用部署、多地域多可用区的数据自动化同步等，企业可以将更多的注意力放在业务领域本身。

在数据安全方面，云上数据可以轻松实现异地备份，专业云厂商的归档存储产品具备高可靠、低成本、安全性、无限存储等特点，能更好地保障企业数据安全。

5.2 应用容器化¶

flowchart LR A[应用容器化优势] --> B[环境一致性] A --> C[效率与速度提升] A --> D[微服务适配] A --> E[快速弹性扩容] style A fill:#f9f7ff,stroke:#333,stroke-width:2px style B fill:#e6f7ff,stroke:#333,stroke-width:2px style C fill:#d9f2e6,stroke:#333,stroke-width:2px style D fill:#ffe6e6,stroke:#333,stroke-width:2px style E fill:#e6e6ff,stroke:#333,stroke-width:2px

容器化技术能有效解决环境不一致产生的问题，确保开发、测试、生产环境的一致性。与虚拟机相比，容器让效率与速度都得到了提升，使应用更适合微服务场景，从而有效提升产研效率。

通过容器化部署，企业可以利用容器服务的快速弹性优势，在业务高峰期实现资源的快速扩容。

5.3 微服务改造¶

将整体应用拆分为微服务架构，有以下几点好处：

  • 业务逻辑模块化：将业务逻辑变成更具复用性的微服务
  • 业务域拆分：按业务域进行拆分，使系统更易于维护
  • 计算与存储分离：将有状态服务转变为无状态，便于服务实例的自动横向扩展
  • 服务解耦：形成高内聚、低耦合的服务体系，减少服务间的依赖关系，避免循环依赖

5.4 平台层改造¶

mindmap root((Kubernetes平台优势)) DevOps闭环 统一测试与集成 环境一致性 自动化部署 资源优化 环境隔离 机器资源利用率高 弹性扩缩容 统一管理 流量精细化管理 集成日志系统 链路诊断 指标监控 多云支持 统一API接口 混合云部署 跨云管理

基于Kubernetes打造的云原生PaaS平台优势明显：可打通DevOps闭环，实现环境资源隔离，提高机器资源利用率，支持流量精细化管理，集成了日志、链路诊断、指标监控平台，并统一了API接口及扩展，能很好地支持多云部署和混合云部署。

5.5 应用服务层改造¶

每个应用在Kubernetes上创建单独的命名空间，实现应用间的资源隔离。规范定义应用配置模板，部署时可直接编辑镜像版本快速升级；本地启动历史版本镜像可实现快速回滚。

5.6 CICD的自动化编排¶

flowchart TD A[CICD自动化编排] --> B[CI: Pipeline as Code] A --> C[CD: Infrastructure as Code] A --> D[GitOps版本化] B --> B1[代码提交触发] B --> B2[自动化测试] B --> B3[镜像构建与推送] C --> C1[资源声明式定义] C --> C2[部署步骤代码化] C --> C3[自动化部署] D --> D1[配置版本化] D --> D2[环境隔离] D --> D3[变更追踪] style A fill:#f9f7ff,stroke:#333,stroke-width:2px style B fill:#e6f7ff,stroke:#333,stroke-width:2px style C fill:#d9f2e6,stroke:#333,stroke-width:2px style D fill:#ffe6e6,stroke:#333,stroke-width:2px
  • CI采用Pipeline as Code：将持续集成流程代码化
  • CD采用Infrastructure as Code：实现资源可控化和部署步骤代码化
  • GitOps实践：完成CI和CD的版本化和环境隔离

5.7 可观测性建设¶

建立全链路监控平台，将追踪(Trace)、日志(Log)和指标(Metrics)结合，形成完整的可观测性方案：

  • 提前接入全链路监控平台，跟踪分布式环境下复杂服务调用
  • 快速定位异常服务，帮助在测试和生产中及时修复问题
  • 根据链路和服务的重要性进行等级划分(P0, P1, P2…)，针对不同等级实施差异化的监控和告警策略
  • 持续优化指标，为精细化运维奠定基础

5.8 高稳定性与高可用性建设¶

flowchart TD A[系统稳定性保障] --> B[链路过载保护] A --> C[存储层保护] A --> D[SLA保障] A --> E[多集群部署] B --> B1[限流] B --> B2[熔断] B --> B3[降级] C --> C1[慢日志处理] C --> C2[高频日志处理] D --> D1[链路SLA: 99.9%+] D --> D2[核心链路SLA: 99.99%+] E --> E1[同城双活] E --> E2[两地三中心] E --> E3[多区域部署] style A fill:#f9f7ff,stroke:#333,stroke-width:2px style B fill:#e6f7ff,stroke:#333,stroke-width:2px style C fill:#d9f2e6,stroke:#333,stroke-width:2px style D fill:#ffe6e6,stroke:#333,stroke-width:2px style E fill:#e6e6ff,stroke:#333,stroke-width:2px
  • 过载保护：在链路拥塞时进行限流，对非核心服务熔断，对特殊功能降级，防止雪崩效应
  • 存储层保护：处理慢日志和高频日志，防止存储层雪崩
  • SLA目标：链路至少达到99.9%以上，核心链路达到99.99%以上
  • 多地域部署：实现中间件和数据库的多地域多可用区集群部署，支持读写分离
  • 应用高可用：采用同城双活、两地三中心或多区域部署模式，提升整体可用性

最后给个判断口径¶

云原生正在成为企业数字化转型的重要技术抓手。通过云原生技术，企业不仅能够提升研发效率，降低技术复杂度，还能将精力更多地聚焦于业务逻辑实现，加速创新。云原生技术越来越成熟，它会在更多领域展现出强大的价值，推动整个IT生态系统的演进。

只有提前拥抱云原生，才能在新基础设施的浪潮中占据先机，实现业务的可持续发展和技术的长期领先。
