设备树开发：从环境搭建到驱动调试的完整流程

设备树开发听着像是写 DTS 的事，实际做下来一半时间花在编译和调试上。我刚开始也只盯着语法，后来发现工具链、分层组织和驱动侧的读取方式才是决定效率的地方。这篇按真实开发顺序走一遍。

一图看懂：设备树六步走，从分析硬件到编译测试。

graph LR A[分析硬件] --> B[DTSI 描述 SoC] B --> C[DTS 描述板级] C --> D[DTC 编译] D --> E[DTB 二进制] E --> F[内核解析并测试]

1. 设备树开发解决什么：一份内核适配多块板¶

设备树（Device Tree）把硬件描述与内核代码分离，一个内核映像因此能支持多种硬件平台。我见过太多项目一开始把硬件地址写死在驱动里，换板子时全得返工——设备树就是冲这个痛点来的。

1.1 四个关键点：抽象、单内核、简化驱动、动态配置¶

在嵌入式 Linux 开发中，设备树解决了四个关键问题：

  • 硬件抽象：将硬件描述从内核代码中分离出来
  • 一份内核支持多平台：减少了定制内核的需求
  • 简化驱动开发：标准化的硬件资源描述方式
  • 动态硬件配置：无需重新编译内核即可适应硬件变更

1.2 六步流程：从分析硬件到测试优化¶

一个典型的设备树开发流程包括：

  1. 分析目标硬件，确定需要描述的资源
  2. 创建或修改设备树源文件（DTS/DTSI）
  3. 编译设备树为二进制格式（DTB）
  4. 集成 DTB 文件到系统中
  5. 开发和调试基于设备树的驱动程序
  6. 测试和优化设备树配置

2. 先把工具链备齐：DTC、交叉编译器和内核源码¶

我一般先把 DTC 和交叉编译器装好再动 DTS——不然编译报错时，分不清是语法问题还是环境问题。

2.1 DTC、交叉编译器、编辑器三样必备¶

要进行设备树开发，需要以下工具：

  1. 设备树编译器（DTC）：将 DTS 文件编译为 DTB 格式

  2. 交叉编译工具链：针对目标架构的编译工具

  3. 文本编辑器：用于编辑 DTS 文件

4. 编译链路：预处理到 DTB，六步走完¶

我排查编译问题时第一步就是把 DTB 反编译回 DTS，跟源文件对着看——比猜快得多。

4.1 六步：预处理、语法、语义、建树、优化、生成¶

DTS 文件编译为 DTB 的流程包括以下步骤：

  1. 预处理：处理包含指令、宏定义和条件编译
  2. 语法分析：检查语法正确性
  3. 语义分析：解析节点和属性
  4. 树构建：构建内存中的树结构
  5. 树优化：合并节点、解析引用等
  6. 生成 DTB：将树转换为二进制格式

4.2 dtc 常用选项：-@、-S、-p 各管什么¶

DTC 是设备树编译器，用于将 DTS 文件编译为 DTB 文件：

常用选项说明：

  • -I：输入格式（dts, dtb, fs）
  • -O：输出格式（dts, dtb, asm）
  • -o：输出文件
  • -@：生成符号信息
  • -S：输出文件大小
  • -p：填充大小

4.3 DTB 四块：头部、保留块、结构块、字符串块¶

DTB 文件包含四个主要部分：

  1. FDT 头部：包含魔数、版本和各块偏移量
  2. 内存保留块：定义保留的内存区域
  3. 结构块：包含节点和属性
  4. 字符串块：存储属性名称

6. 调试有章法：反编译、debugfs、U-Boot 三处下手¶

我踩过的坑是节点名拼错——编译只给个警告，运行时设备死活不出来，最后靠 fdtdump 才定位到。

6.1 五种手段：反编译、fdtdump、debugfs、proc、dmesg¶

在开发过程中，设备树调试是必不可少的，常用的调试方法包括：

  1. 设备树反编译：将 DTB 转换回 DTS，检查编译结果

  2. 使用 fdtdump 工具：查看 DTB 文件的内容

  3. 利用内核提供的 debugfs：运行时检查设备树

  4. 检查 /proc/device-tree：在运行的系统中查看设备树

  5. dmesg 日志分析：检查内核启动时的设备树处理日志

6.2 五类常见坑：命名、类型、缺属性、reg、phandle¶

开发中常见的设备树问题及其解决方案：

  1. 节点命名冲突

    • 症状：编译警告或错误
    • 解决方案：确保节点名称唯一或使用地址区分

  2. 属性值类型错误

    • 症状：设备无法正常工作
    • 解决方案：检查属性值类型是否符合规范

  3. 缺少必要属性

    • 症状：驱动加载失败
    • 解决方案：查阅驱动文档，确保所有必要属性都已设置

  4. reg 属性格式错误

    • 症状：地址映射失败
    • 解决方案：确保 reg 属性的大小和地址对应父节点的 cells 设置

  5. phandle 引用错误

    • 症状：无法找到引用的节点
    • 解决方案：检查标签名称，确保引用格式正确

9. 落地清单：组织、命名、匹配表与 CI 都要管¶

我的习惯是新项目先把 CI 里的 dtc 编译加上——语法错当场拦住，别留到板子上才暴露。下面三份清单照着做基本不会跑偏。

9.1 文件组织与命名：分层、注释、标签¶

基于前述内容，总结设备树开发的最佳实践：

  1. 组织结构：

    • 使用分层结构组织设备树文件
    • 将 SoC 级定义放在 DTSI 文件中
    • 将板级特有配置放在 DTS 文件中

  2. 命名规范：

    • 遵循内核文档中的命名规范
    • 为重要节点和属性添加注释
    • 使用标签简化引用

  3. 属性设置：

    • 确保属性值类型正确
    • 提供所有必要属性
    • 避免冗余属性

  4. 版本控制：

    • 将设备树文件纳入版本控制系统
    • 记录重要变更的原因和影响
    • 对重大变更进行审查

  5. 测试验证：

    • 使用设备树编译器检查语法
    • 验证设备树在目标硬件上的功能
    • 测试边界情况和错误处理

9.2 驱动侧清单：匹配表、取属性、查返回值¶

驱动程序应当合理处理设备树信息：

  1. 匹配表设置：

    • 在 of_match_table 中列出所有支持的 compatible 值
    • 考虑使用 data 字段区分不同设备变体

  2. 属性获取：

    • 使用 of_property_read_* 函数族获取属性
    • 提供合理的默认值
    • 对必要属性进行错误检查

  3. 资源获取：

    • 使用 platform_get_resource 获取内存资源
    • 使用 platform_get_irq 获取中断资源
    • 使用 of_clk_get 获取时钟资源

  4. 错误处理：

    • 检查所有 API 返回值
    • 提供有意义的错误信息
    • 在出错时正确清理已分配资源

  5. 文档化：

    • 在驱动文档中说明所需的设备树节点和属性
    • 说明属性的含义和取值范围
    • 提供设备树示例
