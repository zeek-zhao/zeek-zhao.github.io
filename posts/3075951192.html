1. Systemd 是一组协作的组件，不是单个守护进程¶

我一般先画出组件边界，再逐个看它们各自负责什么，比一上来就啃完整手册省事得多。

1.1 设计理念是用统一接口管住启动与服务¶

Systemd是一个系统和服务管理器，专为Linux操作系统设计。它的核心设计理念包括：

  1. 统一系统管理：提供一套统一的工具和接口来管理系统的各个方面
  2. 声明式配置：使用简单的配置文件定义服务行为，而非复杂的脚本
  3. 依赖关系管理：自动处理服务之间的复杂依赖关系
  4. 并行处理：充分利用现代多核处理器的能力，并行启动系统服务
  5. 按需激活：只在需要时才启动服务，提高系统资源利用效率
  6. 状态追踪：持续监控所有进程，确保系统状态的可靠性
  7. 系统组件整合：将系统的多个管理功能整合到一个一致的框架中

Systemd项目由Lennart Poettering和Kay Sievers于2010年发起，目标是改进和替代传统的SysV init系统。如今，它已成为大多数主流Linux发行版的默认初始化系统和服务管理器。

1.2 组件架构与交互¶

Systemd不是单一程序，而是一系列紧密集成的组件集合，形成了一个完整的系统管理平台。其核心架构可以分为以下层次：

  1. 核心层：

    • systemd：PID 1进程，负责系统初始化和服务管理
    • systemctl：主要的命令行界面，用于控制systemd系统
    • systemd-journald：日志管理组件
    • systemd-logind：用户会话管理

  2. 系统管理层：

    • systemd-networkd：网络配置管理
    • systemd-resolved：DNS解析服务
    • systemd-timesyncd：时间同步服务
    • systemd-boot：引导加载程序

  3. 资源控制层：

    • systemd-cgtop：控制组监控工具
    • systemd-oomd：内存压力处理服务
    • 各种资源控制机制（通过cgroups v2）

  4. 容器和虚拟化层：

    • systemd-nspawn：容器管理工具
    • systemd-machined：虚拟机和容器注册服务
    • machinectl：虚拟机和容器控制工具

  5. 安全层：

    • 各种安全隔离机制
    • 资源限制功能
    • 权限控制组件

各组件之间通过D-Bus消息总线进行通信，形成一个紧密集成但又相对解耦的架构。这种设计允许各组件独立发展，同时保持整体系统的一致性。

1.3 组件分类与功能概述¶

按照功能划分，Systemd的组件可以分为以下几类：

组件类别 核心功能 主要组件

这些组件共同构成了Systemd的完整生态系统，提供了从系统启动到关机的全生命周期管理。

2. PID 1、systemctl、journald、logind、udevd 撑起核心¶

踩过的坑是把 systemctl 当成服务本身，它其实只是发号施令的客户端，真正干活的还是 PID 1。

2.1 systemd (PID 1)¶

systemd是整个Systemd系统的核心组件，它是系统启动后运行的第一个用户空间进程（PID 1）。作为初始化系统，它负责将系统引导到可用状态，并在系统运行期间管理服务。

主要功能：

  1. 系统初始化：

    • 挂载文件系统
    • 设置主机名
    • 初始化网络
    • 启动系统服务

  2. 服务管理：

    • 启动、停止、重启服务
    • 监控服务状态
    • 管理服务依赖关系

  3. 并行处理：

    • 分析服务依赖关系图
    • 并行启动没有依赖冲突的服务
    • 优化启动顺序

  4. Socket激活：

    • 在服务启动前预先创建socket
    • 当收到连接请求时启动相应服务
    • 连接缓冲直到服务启动完成

  5. 事务处理：

    • 以事务方式处理服务启动和停止
    • 确保系统状态一致性

    • 通过cgroups跟踪服务和进程
    • 实施资源限制

systemd如何替代传统的init：

4.2 Socket激活（systemd.socket）¶

systemd.socket是Systemd的Socket激活机制，它允许按需启动服务，而不是在系统启动时就启动所有服务。这种机制可以显著减少系统资源使用并加快启动过程。

工作原理：

  1. Systemd创建并监听指定的Socket（可以是TCP/IP套接字、Unix域套接字或FIFO）
  2. 当有连接请求到达Socket时，Systemd自动启动关联的服务
  3. 连接请求会被缓冲，直到服务完全启动
  4. 服务启动后，Systemd将Socket传递给服务进程，连接正常建立

主要优势：

  • 减少系统启动时间（延迟启动服务）
  • 降低内存使用（未使用的服务不会消耗资源）
  • 自动处理服务启动顺序
  • 支持连接请求排队
  • 提供零停机服务更新能力

11. 配置分散在多个目录，覆盖机制决定最终值¶

踩过的坑是改了文件没生效，后来才养成先确认覆盖顺序、再看最终合并值的习惯。

11.1 主要配置目录¶

Systemd使用分层配置结构，按优先级从低到高：

  1. **/usr/lib/systemd/**：

    • 厂商提供的默认配置
    • 软件包安装的单元文件
    • 不应手动修改

  2. **/run/systemd/**：

    • 运行时生成的配置
    • 临时配置和覆盖

  3. **/etc/systemd/**：

    • 系统管理员配置
    • 覆盖默认配置
    • 持久性配置

主要子目录：

  • system/：系统单元
  • user/：用户单元
  • network/：networkd配置
  • resolved.conf.d/：DNS配置
  • journald.conf.d/：日志配置
  • coredump.conf.d/：核心转储配置

  2. 片段覆盖：

    • 创建.d/目录和片段文件
    • 例如：/etc/systemd/system/service.service.d/override.conf

12. D-Bus 是主线，事件与状态转换把组件串起来¶

我一般顺着 D-Bus 的接口调用去看组件协作，比逐个读单元文件更容易看清数据怎么流动。

12.1 D-Bus集成¶

D-Bus是Systemd组件间通信的核心机制：

  1. 服务发现：

    • 组件通过D-Bus接口公开功能
    • 支持动态服务激活

  2. 方法调用：

    • 组件间使用D-Bus方法调用进行交互
    • 例如：systemctl通过D-Bus与systemd通信

  3. 信号通知：

    • 组件通过D-Bus信号广播事件
    • 例如：设备添加/删除事件

常见的Systemd D-Bus接口：

  • org.freedesktop.systemd1：systemd主接口
  • org.freedesktop.login1：登录管理
  • org.freedesktop.hostname1：主机名管理
  • org.freedesktop.timedate1：时间和日期管理
  • org.freedesktop.resolve1：DNS解析

使用busctl检查D-Bus接口：

12.2 事件机制¶

Systemd基于事件驱动架构，组件间通过多种事件机制协作：

  1. Socket激活：

    • systemd-journald通过socket激活接收日志
    • 多个组件可以等待相同的socket就绪

  2. 依赖链触发：

    • 服务状态变化触发依赖链反应
    • 例如：网络可用触发依赖网络的服务

  3. D-Bus信号：

    • 设备事件、电源管理事件等通过D-Bus信号传播
    • 监听特定信号的组件会作出响应

  4. udev规则集成：

    • 硬件事件通过udev规则转换为Systemd事件
    • 例如：插入USB设备可以触发特定服务

12.3 Systemd状态转换机制¶

Systemd组件协作实现了系统状态的有序转换：

  1. 启动流程：

    • systemd（PID 1）→ 初始化journald → udevd → 基本系统 → 网络 → 服务
    • 状态通过目标单元（target）标记

  2. 电源管理状态转换：

    • systemd-logind接收电源事件 → 广播D-Bus信号 → 触发suspend/hibernate/poweroff目标
    • 相关单元有序停止/启动

  3. 故障恢复：

    • 服务失败 → systemd检测 → 触发OnFailure单元 → 可能的自动重启
    • 依赖链传播确保系统状态一致

  4. 服务重新加载：

    • 配置变化 → systemctl reload → systemd发送SIGHUP → 服务重载配置
    • 相关依赖服务可能也会重载（通过PropagatesReloadTo）

  3. 条件激活：

    • 使用Condition*指令避免不必要的服务启动
    • 例如：ConditionPathExists=, ConditionVirtualization=

  4. 缩短超时：

    • 调整非关键服务的超时时间

14.3 从日志与状态入手排查常见问题¶

排查常见的Systemd组件问题：

    • 检查日志存储配置：grep Storage /etc/systemd/journald.conf
    • 验证目录权限：ls -la /var/log/journal/

    • 检查配置文件：networkctl status
    • 验证网络接口：ip a
    • 重载配置：networkctl reload

  3. resolved DNS解析失败：

    • 检查DNS配置：resolvectl status
    • 验证DNS服务器：cat /etc/systemd/resolved.conf
    • 刷新DNS缓存：resolvectl flush-caches

  4. 系统启动慢：

    • 分析启动耗时：systemd-analyze blame
    • 检查关键链路：systemd-analyze critical-chain
    • 优化慢服务：systemctl edit slow-service.service
