54-自动驾驶测试方法

核心挑战有四个：场景爆炸——真实交通没法穷举；稀有事件——关键安全场景极难收集；AI 组件不确定性——深度学习行为难精确预测；还有足够安全本身就缺乏统一定义。
📅 2026-09-27· 更新于 2026-09-27 · 4149 字 · 约 11 分钟 ✍ zeek.zhao #实战#apollo

测试这块最容易犯的错，是拿传统软件那套思路直接套上来。自动驾驶的输入连续且无限，光靠写用例穷举不出来。这篇把分层体系、三类环境和场景库串一遍，仿真平台实操见 50-仿真平台对比与Gazebo-LGSVL实战，测试数据的来源见 55-标注工具与数据闭环。

1. 为什么传统测试那套不够用¶

特性 自动驾驶测试 传统软件测试
安全关键性 失效可能危及生命 通常不直接威胁生命
输入空间 连续、无限，难以穷举 相对有限，可边界划分
判断基准 多指标平衡，无唯一”正确答案” 有明确对错
场景覆盖 需海量场景与长期里程累积 用例可控

核心挑战有四个：场景爆炸——真实交通没法穷举；稀有事件——关键安全场景极难收集；AI 组件不确定性——深度学习行为难精确预测；还有”足够安全”本身就缺乏统一定义。

2. 从单元测试到运营监控，七层¶

层级 目标 工具/环境 方法
单元测试 函数/类正确性 GTest、pytest 白盒、覆盖率分析
模块测试 感知/规划/控制单模块 Cyber RT 单测、数据回放 接口与功能测试
集成测试 模块协同链路 Docker、CI/CD 系统集成测试
系统测试 端到端功能 SIL/HIL 功能与性能测试
场景测试 典型/极端场景 Carla、LGSVL、Apollo 云仿真 场景驱动测试
实车测试 真实环境 试验场、公开道路 功能验证、故障注入
运营监控 持续验证 云平台、车队管理 数据分析、异常监测

测试目标盯五个维度：功能正确性、安全性、鲁棒性、性能（延迟/资源占用）、合规性。

3. 仿真、场地、道路各管一段¶

3.1 仿真测试¶

在环（X-in-the-Loop）类型对比：

类型 说明 真实度 成本 典型应用
MIL 纯算法模型仿真 低 低 早期算法验证
SIL 实际软件代码仿真 中 低 软件功能验证、回归
HIL 真实控制器/传感器 + 仿真环境 中高 高 ECU 与感知验证
VIL 真实车辆 + 仿真环境 高 极高 整车集成验证
DIL 驾驶员在环 高 高 HMI、接管研究

关键工作是传感器仿真：相机用渲染引擎或神经风格迁移；激光雷达用光线追踪（精确）或几何投影（高效）；毫米波雷达用电磁仿真或简化目标模型。仿真测试的固有局限是”仿真-现实差距（Sim-to-Real Gap）”，得靠仿真-实车对比校准和域随机化来缓解。

流程走一遍：需求分析 → 场景设计 → 仿真配置 → 批量执行 → 结果分析 → 问题回溯闭环。

3.2 封闭场地测试¶

介于仿真与公开道路之间的受控验证环节，典型内容：基本控制（车道保持）、感知能力（目标模型测距）、交通规则（红绿灯响应）、异常场景（突然切入、急刹）、极端条件（低光/恶劣天气）、故障注入。

流程四阶段：测试准备（方案/标定/安全措施）→ 执行（checklist + 实时监控 + 数据记录）→ 分析评估 → 改进迭代回归。

3.3 公开道路测试¶

按阶段渐进扩展：

阶段 目标 里程规模
初始验证 基础功能，简单路线 数百公里
能力扩展 ODD 扩展、场景覆盖 数千公里
能力评估 统计量化系统水平 数万公里
长期验证 稳定性与耐久性 数十万公里

安全管理体系：安全员选拔与培训、工时限制（单次路测 ≤2h）、接管数据分析、远程监控与紧急预案。路测的核心产出是接管数据——接管原因、前置条件、系统状态，这几样凑起来才是问题分析的金矿。

4. 场景库是核心资产¶

4.1 场景层次与来源¶

场景类型 例子 来源
基础场景 跟车、变道、红绿灯 专家设计、标准提取
挑战场景 施工区、非标路口、合流 路测挖掘、事故案例
边界场景 紧急避让、传感器边界 对抗测试、参数扫描
失效场景 定位跳变、执行器延迟 故障注入

场景描述语言：OpenSCENARIO（ASAM 开放标准，行业接受度最高）、SCENIC（概率编程）、GeoScenario（Apollo 生态）。

4.2 测试用例设计¶

常用技术：等价类划分、边界值分析、正交试验（多参数组合压缩）、场景驱动、故障注入。一个合格用例包含：前置条件、测试步骤、预期结果、通过标准（如”纵向距离误差 < ±5m，加速度 < 2.5 m/s²”）、测试变量参数化表。

参数化是关键。”前车 60km/h 减速”可以抽象成”前车速度 ∈ [40,80]km/h，减速度 ∈ [0.5,2.0]m/s²”这样的参数模板，少量模板加参数采样，就能覆盖巨大的场景空间。我更愿意在参数模板上多花时间，而不是堆用例数量。

5. 五种挖场景的进阶手段¶

方法 思路 适用
对抗性测试 构造对抗样本、传感器干扰、组合故障注入 发现模型弱点与系统韧性
基于搜索的生成 遗传算法/MCTS/强化学习在参数空间搜索危险场景 自动挖掘边界场景
数据驱动测试 从路测数据聚类提取真实场景，变异生成变体 长尾场景覆盖
形式化验证 数学证明关键安全属性 核心决策逻辑
混合现实测试 数字孪生、实虚结合 感知系统测试

混合测试策略的效率杠杆在这里：约 80% 场景在仿真验证、15% 进封闭场地、5% 上公开道路；路测发现问题 → 场景提取 → 仿真重构 → 参数空间探索 → 实车验证。整体效率相对纯路测能提升数十倍。这个配比我认，它把最贵的那部分路测压到了最小。

6. 数据怎么存、报告怎么写¶

  • 采集：多传感器原始数据（10-100 GB/小时/车）、算法中间输出、控制命令、事件日志；触发式采集（急刹/接管/异常）降低存储成本
  • 组织：日期/测试ID/{metadata, raw/, processed/, events/, metrics/} 目录规范 + 元数据索引
  • 分析：Pandas/Grafana 时序分析、Open3D 点云重现、ELK 日志关联
  • 报告：执行摘要 → 环境与方法 → 结果 → 问题根因分析 → 改进建议

7. 合规三条主线¶

标准 范围 重点
ISO 26262 功能安全 开发全生命周期、ASIL 分级
ISO 21448 (SOTIF) 预期功能安全 非故障性危害、性能边界
UL 4600 自动驾驶安全 安全论证（Safety Case）完整性
区域法规 路测许可 中国智能网联测试规程、加州 DMV 等

安全论证常用 GSN（目标结构化表示法）：从”系统在 ODD 内安全”逐层分解为子目标，用测试证据支撑，形成可审计的证据链。

8. 白盒剖析取代黑盒压测¶

Apollo 10.0 发布了 5+ 款可视化性能分析工具（包括火焰图等），可以直接定位 Cyber RT 各模块的调度延迟、消息吞吐与资源占用，把”性能测试”从黑盒压测推进到白盒剖析阶段。仿真回归和实车数据分析时值得配合着用（框架层原理见 58-自动驾驶运行时框架对比）。

云端那边，Apollo Cloud Sim 让”虚拟车队 + 万级场景并行”成了量产验证的标配路径（见 56-自动驾驶云服务与基础设施）。火焰图这类工具比单纯多跑里程更能说明问题，至少瓶颈落在哪个模块是一眼能看出来的。

操作步骤 使用流程¶

搭一套可落地的测试体系，建议按下面的流程：

  1. 定分层策略：按七层模型（单元→模块→集成→系统→场景→实车→运营）分配资源，明确每层测什么、谁负责。
  2. 写单元测试：对函数/类用 pytest/GTest，核心算法覆盖率目标 ≥ 90%（用 pytest --cov 统计）。
  3. 建场景库：按基础/挑战/边界/失效四类攒场景，用 OpenSCENARIO 描述，保证跨平台可复用。
  4. 参数化场景：用 scenario_matrix 把单点场景扩成参数空间，用 pairwise 压缩组合，避免用例爆炸。
  5. 仿真批量执行：80% 场景在仿真里跑，用 run_scenario_batch 自动判分，失败的入库回溯。
  6. 封闭场地验证：15% 场景进场地，重点测传感器能力、交通规则响应与故障注入（流程见 50-仿真平台对比与Gazebo-LGSVL实战）。
  7. 公开道路测试：5% 上公开道路，按阶段渐进扩里程；严格记录接管数据，用 compute_disengagement_rate 统计。
  8. 白盒性能剖析：用 Apollo 火焰图等工具定位 Cyber RT 各模块延迟与吞吐，把性能测试从黑盒压测推进到白盒剖析。
  9. 合规与安全论证：按 ISO 26262/21448/UL 4600 整理 GSN 证据链，形成可审计的安全论证。

注意事项与常见坑¶

测试体系里最容易踩的坑：

  1. 拿传统测试思路硬套：自动驾驶输入连续无限，写用例穷举不出来。必须用场景驱动 + 参数化，别幻想覆盖率 100%。
  2. 忽视 Sim2Real 差距：仿真里全过、实车就翻。传感器噪声和动力学太理想，必须用封闭场地标定校准（见 50-仿真平台对比与Gazebo-LGSVL实战）。
  3. 场景库不参数化：堆几千个写死的用例，维护成本高、覆盖有限。用参数模板 + pairwise 压缩才是正解。
  4. 通过标准模糊：”感觉开得还行”不算标准。必须写清量化门槛（如横向误差 < 5m、加速度 < 2.5 m/s²），用 evaluate_pass 自动判定。
  5. 只盯平均指标：平均接管率好看不代表安全，要看长尾场景和最坏情况；p99 延迟同理。
  6. 路测里程虚高：只记录总里程、不记接管数据和前置条件，出了问题没法回溯。接管的原因/状态/环境缺一不可。
  7. 安全员超时驾驶：单次路测 ≤2h 的工时限制不是形式主义，疲劳会直接带来安全风险。
  8. 故障注入走过场：只测正常场景，不注入定位跳变、执行器延迟等失效，系统韧性无从验证。
  9. 覆盖率数字游戏：追 90% 行覆盖率但断言写得很水，测了个寂寞。要关注分支覆盖和断言质量。
  10. 合规证据链断点：GSN 论证缺测试证据支撑，审计时补不齐。每次测试的数据要能关联到具体子目标。
  11. 仿真和实车数据割裂：路测发现的问题没回流到场景库，同类问题反复出现。要建立”路测→场景提取→仿真重构→实车验证”的闭环（见 55-标注工具与数据闭环）。
  12. 性能压测只看 FPS：端到端延迟与确定性比平均帧率更重要，火焰图比压测数字更能定位瓶颈（见 58-自动驾驶运行时框架对比）。
