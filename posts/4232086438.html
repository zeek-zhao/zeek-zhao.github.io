I2C开发指南

I2C 是我接触嵌入式时最先摸到的总线，两根线就能挂一堆设备，看着简单，真到调试的时候地址、上拉、时序哪个出问题都够喝一壶。我把协议、Linux 驱动框架、设备树配置到调试命令整理成一条线，方便顺着往下查。

1. I2C 协议：两根线、主从架构、7/10 位寻址¶

I2C (Inter-Integrated Circuit) 是一种串行通信总线，由飞利浦公司在1980年代初开发，用于连接微控制器和各种低速外设设备。它的特点就是只需两根信号线：

  • SCL：串行时钟线，提供通信时钟
  • SDA：串行数据线，传输数据

协议本身有几个固定特征，我列在这里备查：

  • 双向通信
  • 主从架构
  • 7位或10位设备寻址
  • 多主机支持
  • 传输速率可调整（标准模式：100 Kbit/s，快速模式：400 Kbit/s，高速模式：3.4 Mbit/s）
  • 每个设备都有唯一地址，可连接多个设备

速率这块我一般先确认设备支持哪档，调试阶段宁可先用 100 Kbit/s 的标准模式把链路跑通，再往上提。

通信原理：起始信号后跟地址加读写位，从设备给应答¶

sequenceDiagram participant Master as 主设备 participant Slave as 从设备 Note over Master,Slave: 起始条件(S) Master->>Slave: 发送设备地址(7位)+读/写位(1位) Slave->>Master: 应答(ACK) alt 写操作 Master->>Slave: 发送数据 Slave->>Master: 应答(ACK) Note over Master,Slave: 可重复上述数据传输 else 读操作 Slave->>Master: 发送数据 Master->>Slave: 应答(ACK) Note over Master,Slave: 可重复上述数据传输 end Note over Master,Slave: 停止条件(P)

信号时序：SCL 高电平时 SDA 的跳变定义起停¶

2. Linux I2C 驱动框架：核心、适配器、设备、驱动四个对象¶

Linux I2C 子系统由几个主要组件构成，我的读代码习惯是先找 I2C 核心，再看它下面挂的总线驱动和设备驱动。

flowchart TD A[I2C核心] --> B[I2C总线驱动] A --> C[I2C设备驱动] B --> D[I2C适配器] C --> E[I2C设备] D --- E

核心对象¶

1. I2C 总线

I2C总线管理着I2C设备与I2C驱动的匹配、初始化等操作。

2. I2C 适配器

I2C适配器代表硬件上的I2C控制器，负责实际的I2C总线访问。

3. I2C 设备

I2C设备对应总线上的从设备，包含其地址和各种属性。

4. I2C 驱动

I2C驱动用于操作I2C设备，提供设备的具体功能实现。

驱动架构关系图¶

classDiagram class I2C总线 { +match() +probe() +remove() } class I2C适配器 { +algorithm +master_xfer() +functionality() } class I2C设备 { +addr +name +adapter } class I2C驱动 { +probe() +remove() +id_table } I2C总线 --> I2C设备: 管理 I2C总线 --> I2C驱动: 管理 I2C适配器 --> I2C设备: 通信 I2C驱动 --> I2C设备: 操作

这四个对象的关系我一般这么记：总线管匹配，适配器管通信，设备是总线上的节点，驱动实现对节点的操作。

设备树配置要点¶

  1. compatible属性: 用于驱动与设备匹配
  2. reg属性: 表示设备在I2C总线上的地址
  3. status属性: 控制节点是否启用
  4. clock-frequency: 设置I2C总线频率

我踩过的坑是 reg 里的地址忘了按数据手册换算成 7 位形式，结果 i2cdetect 扫出来的地址和设备树对不上，核对了好久才发现。

6. 通信状态机：起始—地址—应答—数据—停止¶

把通信过程画成状态机，排查时对着数状态比凭记忆猜要快。

stateDiagram-v2 [*] --> 空闲 空闲 --> 起始条件: SDA从高到低(SCL高) 起始条件 --> 发送地址: 7位地址+读/写位 发送地址 --> 等待应答 等待应答 --> 数据传输: 收到ACK 等待应答 --> 错误处理: 收到NACK 数据传输 --> 等待数据应答: 发送/接收8位数据 等待数据应答 --> 数据传输: 继续传输 等待数据应答 --> 停止条件: 传输完成 停止条件 --> 空闲: SDA从低到高(SCL高) 错误处理 --> 停止条件

我一般盯着”等待应答”这一步，扫不到设备时大概率就是在这里收到 NACK 走进错误处理的。

7. 常见问题：探测不到看地址电源，数据异常看格式¶

1. 设备无法探测¶

可能原因：

  • 设备地址错误
  • 设备未上电
  • I2C总线时钟频率不匹配
  • 硬件连接问题

解决方案：

  • 确认设备地址（使用i2cdetect扫描）
  • 检查电源和引脚连接
  • 尝试降低I2C时钟频率
  • 使用示波器检查SCL和SDA信号

2. 通信错误¶

可能原因：

  • 时序问题
  • 上拉电阻不合适
  • 地址冲突
  • 传输速率过高

解决方案：

  • 检查设备时序要求
  • 确保使用适当的上拉电阻（典型值2.2kΩ-10kΩ）
  • 解决地址冲突
  • 降低通信速率

3. 数据异常¶

可能原因：

  • 寄存器地址错误
  • 字节序问题
  • 数据格式理解有误
  • 噪声干扰

解决方案：

  • 参考设备数据手册确认寄存器
  • 注意大小端格式
  • 理解数据格式（原始值、缩放、偏移等）
  • 改善电路布局，增加去耦电容

这三类里我遇到最多的是通信错误，尤其是上拉电阻选得不合适，换到 2.2kΩ 到 10kΩ 这个典型区间后往往就稳了。

8. 最佳实践：先规划地址，用现成框架，补调试接口¶

下面这几条是我自己写 I2C 驱动时会照着做的，按从前期规划到收尾调试的顺序排：

  1. 提前规划：

    • 了解设备的通信协议和寄存器映射
    • 确认设备地址和可能的冲突

  2. 驱动编写：

    • 使用合适的框架（如hwmon、input等）
    • 实现设备休眠和唤醒功能
    • 处理错误和异常情况

  3. 调试技巧：

    • 使用printk输出关键信息
    • 添加sysfs接口用于调试
    • 使用i2c-tools验证基本通信

  4. 性能优化：

    • 避免频繁的单字节读写
    • 使用块传输提高效率
    • 按需读取，避免无意义的轮询

把设备地址和寄存器映射在动手前核对清楚，能避开后面大半的返工。
