53-TensorFlow与Caffe2在自动驾驶中的应用

TensorFlow 全家桶和 Caffe2 的来龙去脉，重点说清 Caffe2 早已并入 PyTorch，以及 ONNX 为什么是跨框架部署的通用桥。
📅 2026-09-28· 更新于 2026-09-28 · 4000 字 · 约 10 分钟 ✍ zeek.zhao #实战#apollo

上一篇讲 PyTorch 怎么训模型，这篇补上另两条线。Caffe2 为什么不再单独存在、TF 那套生产化工具还剩什么用，其实是同一个问题：训练框架和部署框架未必是同一个。框架选型可以跟 52-PyTorch与自动驾驶实践 对照着看。

1. 两代 TensorFlow 是两种写法¶

TensorFlow 由 Google Brain 于 2015 年开源。1.x（静态图 + Session）与 2.x（默认即时执行 Eager Execution + Keras 高级 API）是两代完全不同的编程体验：

TF 2.x 的 tf.function 装饰器可把 Python 函数编译为图执行，兼得开发效率与运行性能。

1.1 分层 API 体系¶

层级 API 用途
高级 Keras（Sequential/Functional） 快速建模，90% 场景够用
中级 tf.Module、自定义 Layer 灵活组件
低级 张量算子、tf.GradientTape 自定义训练循环
扩展 TensorFlow Probability 概率推理

Keras 典型流程：构建模型 → compile(优化器/损失/指标) → fit → evaluate → save。

1.2 数据管道与训练¶

  • tf.data.Dataset：from_tensor_slices → shuffle → map(预处理) → batch → prefetch(AUTOTUNE)，异步预取可打满 GPU
  • 自定义训练：with tf.GradientTape() as tape: 记录前向，tape.gradient 求梯度
  • 分布式：MirroredStrategy（单机多卡）、MultiWorkerMirroredStrategy（多机）、TPUStrategy
  • 混合精度：tf.keras.mixed_precision.set_global_policy("mixed_float16")

1.3 模型保存与格式¶

格式 特点 用途
HDF5 (.h5) 单文件，含结构与权重 开发阶段
SavedModel 目录形式，含完整计算图 生产部署标准格式
Checkpoint 仅权重 训练备份
TF Lite (.tflite) 轻量量化模型 移动/边缘设备

2. 云端服务和边缘部署¶

2.1 感知模型¶

  • 目标检测：SSD（基于 MobileNetV2/VGG16 多尺度特征图 + 检测头）、Faster R-CNN
  • 语义分割：DeepLab 系列（TF 官方实现完善）、U-Net
  • 端到端：Keras Functional API 融合图像输入与车辆状态输入，输出油门/刹车/转向

2.2 边缘部署：TF Lite 与 TensorRT¶

在 NVIDIA 车载平台（Xavier/Orin）上则走 TensorRT：TF 模型 → ONNX/UFF → TensorRT 引擎，配合 FP16/INT8 与算子融合获得确定性低延迟。

2.3 生产化组件¶

  • TF Serving：模型服务化，支持版本管理、热更新、A/B 测试，适合云端推理服务
  • TFX：端到端 ML 流水线（数据验证 TFDV、特征变换 TFT、模型分析 TFMA），可对接 56-自动驾驶云服务与基础设施 中的数据管线
  • 模型优化工具包：量化感知训练（QAT）、剪枝、聚类

3. Caffe2 已经并进了 PyTorch¶

3.1 历史脉络¶

2013 Caffe（Berkeley，Yangqing Jia）——首代主流框架，protobuf 定义网络
2015 Facebook 接手 Caffe 维护
2017 Caffe2 发布——重写版，主打轻量、模块化、移动端与大规模分布式训练
2018 Caffe2 与 PyTorch 正式合并
2019 PyTorch 1.0 发布，吸收 Caffe2 的生产部署后端（后演化为 torch.jit /
mobile 体系与 ATen 算子库的一部分）

自 2018 年起，Caffe2 不再作为独立框架维护，代码与理念都已经融进 PyTorch。新项目直接用 PyTorch 就行；手上还有老 Caffe2 模型的，走 ONNX 转换迁移（见 3.3）。今天回头看它，价值主要在设计思想——“静态图部署优先”这套思路，正是 ONNX/TensorRT 部署体系的先声。

3.2 Caffe2 的核心概念（历史回顾）¶

  • 静态计算图：先定义 Net（由算子 Operator 组成），再在 Workspace 中执行
  • Blob / Workspace：数据以命名 Blob 存于全局 Workspace
  • 声明式编程：brew.conv(model, data, ...) 逐算子搭建网络，与 PyTorch 动态图形成鲜明对比
  • 部署优势：静态图便于算子融合、INT8 量化（DNNLOWP）、OptimizeForMobile 移动端优化、ARM NEON 加速——这些能力后来都体现在 PyTorch Mobile / ExecuTorch 中

3.3 经 ONNX 的互操作桥梁¶

ONNX（开放神经网络交换格式）曾是 PyTorch 前端与 Caffe2 后端之间的关键桥梁，至今仍是跨框架部署的通用中间格式：

老 Caffe2 模型迁移路径：Caffe2 net → caffe2_frontend.caffe2_net_to_onnx_model → ONNX → PyTorch/TensorRT；或直接用 PyTorch 同构模型 + 权重手动映射，再 np.testing.assert_allclose 校验输出一致。

4. 按场景选，别按偏好选¶

维度 TensorFlow 2.x PyTorch Caffe2（已并入）
计算图 动态 + tf.function 图编译 动态（torch.compile 编译） 静态图
调试体验 良好 最佳 差

生态 成熟全面，TFX 数据管线强 学术界主流，新模型最快 无

真要落地，我的判断是按场景分：

  • 模型训练：PyTorch 优先（新论文实现最快、社区最活跃）
  • 云端模型服务：TF Serving 或 TorchServe 均可，按团队栈决定
  • 边缘/移动部署：目标硬件决定格式——NVIDIA 平台走 ONNX→TensorRT；ARM/手机端 TFLite 或 ExecuTorch
  • 遗留 Caffe2/Caffe 项目：经 ONNX 渐进式迁移，保留验证集做数值一致性回归

5. 训练 PyTorch，部署看硬件¶

TensorFlow 今天仍广泛用于 Google 生态与存量工业系统，但在自动驾驶研究前沿——BEV、端到端 UniAD/VLA——里，PyTorch 已经占绝对主导。Caffe2 作为独立框架早已退役，只剩”PyTorch 部署血统”这层身份。对 Apollo 开发者来说，实用结论就一句：训练用 PyTorch，部署走 ONNX/TensorRT/PaddleInference（见 52-PyTorch与自动驾驶实践 第 4 节）。

TF 和 Caffe2 的知识，如今主要用来读存量系统，以及应付面试里的历史题。真要我给建议，现在花时间深挖 TF 1.x 的 Session 机制性价比不高，除非手上正接着一套老系统。

操作步骤 使用流程¶

框架选型与迁移落地，建议按下面的流程：

  1. 明确任务与硬件：先定训练还是部署、目标硬件（NVIDIA Orin / ARM / 云端），硬件决定格式。
  2. 框架选型：新项目训练用 PyTorch；云端服务可用 TF Serving；边缘 ARM 端用 TFLite；NVIDIA 平台走 ONNX→TensorRT。
  3. 搭 tf.data 或 torch DataLoader：用 prefetch(AUTOTUNE) / pin_memory 打满 GPU，避免数据等模型。
  4. 训练模型：TF2 用 Keras fit 或 GradientTape 自定义循环；大规模用 MirroredStrategy / MultiWorkerMirroredStrategy。
  5. 导出标准格式：TF 用 SavedModel + 签名；PyTorch 用 ONNX/TorchScript（见 52-PyTorch与自动驾驶实践）。
  6. 量化压缩：边缘端做 INT8 量化（TFLite 或 TensorRT），必须提供代表性校准集，比较精度损失。
  7. ONNX 桥梁校验：跨框架迁移后，用 onnxruntime 跑一遍，与原框架输出做 assert_allclose，确认数值一致。
  8. 部署服务化：云端用 TF Serving 做版本管理与热更新；车端走 TensorRT/PaddleInference，由 Cyber RT 模块加载。
  9. 遗留系统迁移：老 Caffe2/Caffe 项目经 ONNX 渐进迁移，保留验证集做回归，确认无精度倒退再切换。

注意事项与常见坑¶

TF/Caffe2/ONNX 使用里的高频坑：

  1. TF1.x 与 TF2.x 混用：tf.Session 代码在 TF2 默认 Eager 下跑不通；老代码用 tf.compat.v1.disable_eager_execution() 过渡，别硬改。
  2. tf.function 重追踪：把可变 Python 对象（如 list 累积）放进被装饰函数，会导致反复追踪、性能暴跌；用 Tensor 参数代替。
  3. 混合精度输出层类型错：最后一层没 cast 回 float32，softmax 在 FP16 下数值不稳，精度异常。
  4. TFLite 量化没校准集：representative_dataset 缺失或不具代表性，INT8 量化精度暴跌；必须提供覆盖真实分布的校准数据。
  5. SavedModel 签名漏定义：部署时找不到签名，服务加载失败；导出时显式指定 signatures。
  6. ONNX opset 不兼容：低版本 opset 不支持某些算子（如 attention），转换失败先升 opset；目标推理引擎也要支持该版本。
  7. ONNX 转换后没校验：转换成功不等于数值一致，算子实现差异可能导致输出偏差。务必用 assert_allclose 核对。
  8. 动态 shape 丢失：导出时把 batch 写死，推理换 batch 就报错；用 input_signature 或 dynamic_axes 保留动态维度。
  9. Caffe2 已退役还新建项目：2018 年就并入 PyTorch，新项目用 Caffe2 是给自己挖坑；只有存量系统迁移才需要碰。
  10. Caffe2→ONNX 缺 shape 信息：caffe2_net_to_onnx_model 不指定 value_info 会导致输出形状推断失败，迁移时务必提供输入尺寸。
  11. 训练与部署框架混为一谈：训练用 PyTorch、车端用 TensorRT 是常态，别指望在车端跑完整 PyTorch 训练图（见 58-自动驾驶运行时框架对比）。

附录：迁移核对清单¶

老系统往新框架迁移时，按这张清单逐条核对，能避开大部分回归问题：

  1. 算子覆盖率：导出前列出模型算子集，确认目标推理引擎（TensorRT/TFLite/ONNX Runtime）全部支持，缺的算子要手写插件或改模型结构。
  2. 动态维度：导出时保留 batch 与时序维度的动态性，避免换输入尺寸就报错。
  3. 数值一致性：用 assert_allclose 对比原框架与新引擎输出，rtol/atol 按精度要求设阈值（FP32 通常 1e-5，INT8 放宽）。
  4. 预处理对齐：归一化均值/方差、通道顺序（RGB/BGR）、输入缩放必须在训练和部署两端完全一致——这是迁移后精度掉点最常见的原因。
  5. 量化校准集：INT8 校准数据要覆盖真实分布（白天/夜间、晴/雨），别用训练集随手抽的几百张。
  6. 回归验证集：保留一份固定验证集，每次迁移改动作一遍完整指标对比，确认无精度倒退再切换。

这份清单与正文第 3.3 节的迁移路径配套使用：Caffe2/TF 老模型经 ONNX 过渡，每一步都用清单核对，比一次性重写稳妥得多。需要具体校验代码时回看”代码示例”小节的 ONNX 转换与一致性校验片段。
