kmemleak内核内存泄漏检测

排查内核里”内存莫名其妙变少”这类问题时，我第一个想到的工具往往是 kmemleak。它不需要像用户态的 valgrind 那样重新编译程序，而是直接集成在内核里，盯着每一次分配和释放。我在实际用的时候，最省心的一点是它能直接给出分配当时的调用栈——不过它也不是万能的，稍不留神就会撞上误报。

kmemleak（kernel memory leak detector）是 Linux 内核中集成的内存泄漏检测工具，专门用于发现内核中未释放的内存。内核里一旦发生泄漏，资源会慢慢耗尽，最终可能造成系统不稳定或崩溃，所以能定位到”哪块内存没人管了”非常关键。

1. kmemleak是什么：内核自带的可达性泄漏检测¶

1.1 工作原理：跟踪分配、定期扫描可达性¶

kmemleak的基本原理是通过跟踪内核内存分配函数（如kmalloc()、vmalloc()、kmem_cache_alloc()等）的调用，记录内存分配信息，并定期扫描内存，识别出那些已分配但无法访问的内存块。

flowchart TD A[内存分配<br>kmalloc/vmalloc] --> B[kmemleak<br>记录分配信息] C[内存释放<br>kfree/vfree] --> D[kmemleak<br>移除分配记录] B --> E[内存扫描线程<br>kmemleak-scan] E --> F{判断内存是否可达} F -->|可达| G[正常内存] F -->|不可达| H[疑似泄漏<br>生成报告]

1.2 优势与局限：无需硬件支持但会误报¶

优势：

  • 专为内核空间设计，无需特别的硬件支持
  • 对性能的影响相对较小
  • 能提供详细的内存泄漏位置和调用栈信息
  • 集成在内核中，无需额外工具

局限性：

  • 可能存在误报，尤其是对于一些特殊的内存管理模式
  • 不适用于所有类型的内存泄漏（如复杂的指针关系）
  • 需要启用相关的内核配置选项
  • 在资源受限的系统上可能会增加系统负担

我一般把 kmemleak 当第一道筛子：先靠它找出”没人引用”的内存块，再回头对着代码查分配路径。别指望它一锤定音，误报得自己甄别。

3. 工作流程：基于可达性分析的扫描算法¶

kmemleak采用了一种基于可达性分析的内存泄漏检测方法，类似于许多垃圾回收算法。

3.1 对象跟踪机制¶

flowchart LR A[内存分配调用] --> B[kmemleak钩子] B --> C[记录对象信息] C --> D[存储在红黑树中] E[内存释放调用] --> F[kmemleak钩子] F --> G[从红黑树中移除]

当调用内存分配函数时，kmemleak会：

  1. 捕获调用栈信息
  2. 记录分配的内存地址和大小
  3. 将这些信息存储在内部数据结构中

当内存被释放时，相应的记录会被从数据结构中删除。

3.2 扫描算法¶

kmemleak使用的扫描算法可以分为以下几个步骤：

flowchart TD A[扫描开始] --> B[标记所有对象为白色] B --> C[扫描数据段和栈] C --> D[将找到指针指向的白色对象标记为灰色] D --> E[扫描灰色对象] E --> F{还有灰色对象?} F -->|是| G[检查对象内部指针] G --> H[标记新发现的对象为灰色] H --> F F -->|否| I[报告剩余的白色对象] I --> J[扫描结束]
  1. 将所有已知的内存对象标记为”白色”（未访问）
  2. 从内核数据段和所有任务的栈开始扫描
  3. 当找到指向”白色”对象的指针时，将该对象标记为”灰色”（已访问）
  4. 扫描所有”灰色”对象，查找它们内部的指针
  5. 如果找到指向其他”白色”对象的指针，将那些对象也标记为”灰色”
  6. 重复步骤4-5，直到没有新的”灰色”对象产生
  7. 剩余的”白色”对象被认为是不可达的，可能是内存泄漏

3.3 跟踪扫描行为¶

在内核日志中可以看到kmemleak的扫描行为：

默认情况下，kmemleak会每10分钟（600秒）自动进行一次扫描。

实测下来，默认 10 分钟一次对排查缓慢累积的泄漏够用，但我赶时间时都会直接 echo scan 手动触发，不等它。

4. 检测内存泄漏：通过debugfs接口操作¶

4.1 基本操作命令¶

kmemleak的操作主要通过debugfs接口进行，常用操作包括：

操作 命令 说明
触发扫描 echo scan > /sys/kernel/debug/kmemleak 立即进行一次内存泄漏扫描
清除记录 echo clear > /sys/kernel/debug/kmemleak 清除当前所有已检测到的泄漏记录
关闭kmemleak echo off > /sys/kernel/debug/kmemleak 永久关闭kmemleak（不可逆）
禁用栈扫描 echo stack=off > /sys/kernel/debug/kmemleak 关闭任务栈扫描，减少误报
启用栈扫描 echo stack=on > /sys/kernel/debug/kmemleak 启用任务栈扫描
启动/停止自动扫描线程 `echo scan=on off > /sys/kernel/debug/kmemleak`
设置扫描间隔 echo scan=<秒数> > /sys/kernel/debug/kmemleak 设置自动扫描间隔，0表示停止
查看特定内存块 echo dump=<地址> > /sys/kernel/debug/kmemleak 查看指定地址的内存块详细信息

4.3 内存泄漏检测流程¶

一个完整的内存泄漏检测流程包括以下步骤：

  5. 修复问题并重新测试

踩过的坑是：echo clear 这一步别省，否则看到的还是上一次的旧报告，很容易把”已经修好”误判成”还在泄漏”。

5. 解读输出：从backtrace定位泄漏源¶

kmemleak的输出包含丰富的信息，可以帮助开发者准确定位内存泄漏的来源。

5.1 输出格式解析¶

以下是典型的kmemleak输出示例：

这个输出包含以下关键信息：

  1. 对象地址和大小：0xffffffc008efcc00 (size 512)
  2. 进程信息：comm "swapper/0", pid 1
  3. 泄漏时长：jiffies 4294892779 (age 162.728s)
  4. 内存内容：通过hex dump展示内存前32字节内容
  5. 调用栈：backtrace部分展示了内存分配时的完整调用栈

5.2 调用栈分析¶

调用栈是定位内存泄漏最重要的信息，一般从下往上阅读：

  1. 最底部（如usb_probe_device）通常是触发内存分配的高层函数
  2. 中间部分显示了函数调用链
  3. 顶部通常是实际执行内存分配的底层函数

通过分析调用栈，可以确定：

  • 哪个子系统/模块发生了泄漏
  • 泄漏发生的具体函数
  • 内存分配的目的和上下文

我看 backtrace 习惯先从最底部那个高层入口读起，顺着调用链往上，能快速判断泄漏属于哪个子系统，再落到具体函数。

5.3 典型问题模式识别¶

通过分析kmemleak输出，可以识别出一些典型的内存泄漏模式：

  1. 初始化失败未释放：在设备初始化函数中分配内存，但在错误处理路径中忘记释放
  2. 配对函数缺失：使用了kmalloc但缺少对应的kfree
  3. 链表/数组元素泄漏：释放了容器但忘记释放其中的元素
  4. 资源获取函数未释放：获取了资源但没有在对应的释放函数中处理

7. 高级使用技巧：降误报、进流程、控开销¶

在复杂的内核开发环境中，可以采用一些高级技巧使kmemleak更加高效和准确。

7.1 减少误报¶

kmemleak可能会产生误报，特别是对于一些特殊的内存使用模式。以下技术可以减少误报：

  1. 禁用任务栈扫描：如果某些栈上的指针导致误报

  2. 增加扫描间隔：对于正常生命周期较长的对象

  3. 手动标记对象为非泄漏：对于已知的特殊情况

  4. 清除旧记录后再测试：确保只关注新产生的泄漏

我遇到栈上残留指针引起的误报时，第一反应就是 echo stack=off，通常能把噪声压下去。

8. 工具对比：按问题类型选kmemleak还是KASAN¶

Linux内核提供了多种内存问题检测工具，每种工具各有其优缺点和适用场景。

8.1 内核内存调试工具对比¶

工具 功能 性能影响 内存开销 误报率 适用场景
kmemleak 内存泄漏检测 中等 中等 中等 一般内存泄漏问题
KASAN 内存访问错误检测 高 高 低 越界访问、UAF等
KMSAN 未初始化内存使用检测 高 高 低 未初始化内存问题
SLUB调试 内存分配器级别检测 低-中 低 高 对象释放后使用
KFENCE 轻量级KASAN 低 低 中 生产环境采样检测

8.2 何时选择kmemleak¶

kmemleak最适合以下场景：

  • 长期运行测试：系统需要长时间运行以检测缓慢累积的泄漏
  • 资源受限环境：无法承担KASAN等工具带来的高性能开销
  • 一般性内存泄漏检测：不需要专注于特定类型的内存错误
  • 持续监控：需要在系统运行过程中持续检测内存泄漏

如果只关心”有没有忘了释放”、机器资源又紧，我会一直用 kmemleak，不去碰 KASAN 那份开销。

8.3 何时选择其他工具¶

在以下场景中，其他工具可能更适合：

  • 需要检测访问越界：选择KASAN
  • 关注未初始化内存使用：选择KMSAN
  • 生产环境采样检测：选择KFENCE
  • 用户空间应用：选择Valgrind或AddressSanitizer

9. 常见问题：缓冲区溢出、误报与漏报¶

使用kmemleak进行内存泄漏检测时，可能会遇到一些常见问题，以下是解决方案。

9.1 早期日志缓冲区溢出¶

解决方案：
增加CONFIG_DEBUG_KMEMLEAK_EARLY_LOG_SIZE的值，通常设置为4000或更高，然后重新编译内核。

这个报错我碰到过，把 EARLY_LOG_SIZE 调到 4000 以上再重新编译就消停了。

9.2 误报处理¶

问题：kmemleak报告了已知不是泄漏的内存块

解决方案：

  1. 使用kmemleak_not_leak(ptr)在源码中标记
  2. 临时解决：清除当前记录并重新扫描

9.3 漏报问题¶

问题：已知存在泄漏但kmemleak未报告

解决方案：

  1. 检查是否有指针仍在指向泄漏的内存（可能从栈或全局变量）
  2. 尝试禁用栈扫描以减少误判
  3. 手动强制触发gc并立即扫描

9.4 kmemleak文件为空¶

问题：/sys/kernel/debug/kmemleak文件存在但为空

解决方案：

  1. 确认kmemleak已正确启用：检查内核日志中是否有”kmemleak: Automatic memory scanning thread started”
  2. 手动触发扫描并检查内核日志
  3. 如果系统刚启动，等待至少一次自动扫描完成（默认10分钟）

9.5 性能问题¶

问题：启用kmemleak导致系统性能下降

解决方案：

  1. 增加扫描间隔
  2. 在开发/测试完成后禁用kmemleak
  3. 在生产环境中完全禁用kmemleak（在内核配置中）

10. 最佳实践：早启用、管好错误路径、定期基线¶

根据多年的内核开发经验，总结出以下使用kmemleak的最佳实践。

10.1 开发流程集成¶

  1. 在开发初期启用：尽早发现内存泄漏问题
  2. 持续测试：每次重大变更后进行内存泄漏测试
  3. 自动化检测：集成到CI/CD流程，自动分析报告
  4. 定期全面检查：除了针对特定变更的测试外，定期进行全面检查

10.2 编码建议¶

  1. 清晰的内存所有权：明确定义谁负责释放内存
  2. 一致的分配/释放模式：使用统一的模式处理内存
  3. 错误路径处理：特别注意在错误处理路径中释放已分配的资源
  4. 使用容器辅助管理：利用内核提供的列表、数组等容器简化内存管理

我写代码时会特别盯着错误路径——分配成功后的一堆 return 分支，恰恰是最容易漏 kfree 的地方。

10.3 长期维护策略¶

对于需要长期支持的内核项目：

  1. 定期基线测试：建立内存使用的基线，定期比较
  2. 分类记录已知问题：对无法立即修复的问题进行记录和分类
  3. 优先修复频繁触发的泄漏：根据影响范围和泄漏速度制定修复优先级
  4. 特性开关：为复杂功能提供开关，便于隔离问题

11. 落地建议：先跑通一次完整的检测闭环¶

我的建议是别一上来就全量铺开，先在一台开发机上跑通”启用 → 触发操作 → scan → 读 backtrace → clear 复测”这一整套，确认输出能看明白，再考虑接进 CI。定位内核泄漏时把 kmemleak 和 KASAN 搭配着用，前者抓”忘了释放”，后者抓”越界和 UAF”，覆盖才算完整。

ℹ️
在使用kmemleak进行内存泄漏检测时，需要注意它与用户空间内存检测工具的区别。kmemleak专为内核空间设计，有其特有的工作机制和使用方式。合理结合其他内核调试工具，可以更全面地解决内核中的内存问题。
