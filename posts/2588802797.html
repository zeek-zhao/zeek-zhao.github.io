27-Cyber时间系统与定时器

融合解析 Cyber RT 时间体系：Time/Duration/Clock 三类时钟与两级时间轮定时器、累积误差补偿机制。
📅 2026-10-25· 更新于 2026-10-25 ✍ zeek.zhao #系统#apollo
ℹ️本节目标
一篇讲透 Cyber RT 的时间体系：Time/Duration 数据类型、SystemClock/SteadyClock/UserClock 三种时钟的取舍，以及定时器内部的两级时间轮算法与累积误差补偿机制。

本篇是第四阶段 Cyber RT 深度剖析的第三篇，将时间表示与定时执行两大主题融合。时间戳贯穿数据链路（29-Cyber数据系统详解 的消息排序依赖它），定时器任务则运行在 26-Cyber调度系统详解 的协程之上。

1. 时间系统总览¶

自动驾驶对时间的要求是纳秒级表示 + 统一基准 + 不会跳变。Cyber 的架构分四层：

graph TD A[用户 API: Time / Duration] --> B[Clock 抽象层] B --> C1[SystemClock CLOCK_REALTIME] B --> C2[SteadyClock CLOCK_MONOTONIC] B --> C3[UserClock 编程控制] C1 --> D1[NTP / PTP / GPS 时间源] C2 --> D2[内核单调时钟] C3 --> D3[仿真/回放注入]

源码目录：cyber/time/（time.h、duration.h、clock.h）、cyber/rate.h。

2.2 三种时钟¶

classDiagram class Clock { <<interface>> +Now() Time +GetMonotonicTime() Time +SetNow(now)* } class SystemClock { +Now() Time } class SteadyClock { +Now() Time } class UserClock { +SetNow(now) } Clock <|-- SystemClock Clock <|-- SteadyClock Clock <|-- UserClock
特性 SystemClock SteadyClock UserClock
底层调用 clock_gettime(CLOCK_REALTIME) clock_gettime(CLOCK_MONOTONIC) 内部变量
可被外部调整 是（NTP/人工） 否（单调递增） 编程控制
会跳变 可能 不会 可控
典型用途 对外时间戳、日志、同步 间隔测量、超时控制 仿真、回放、单测

选择原则一句话：对外打时间戳用 SystemClock（要与真实世界对齐），测耗时/算超时用 SteadyClock（要稳定），写测试/回放用 UserClock（要可控）。

⚠️常见时间陷阱
  • 用 SystemClock 计算超时：NTP 校时会跳变，超时逻辑瞬间错乱——一律用 SteadyClock。
  • 混用秒/毫秒/纳秒：Cyber 全链路统一纳秒（int64_t），转换时用类方法，不要手写乘除。
  • 时间戳回退：消息处理需容忍单调性破坏（参见数据同步策略）。

3. 定时器：从算法选型到实现¶

3.1 三种实现方式对比¶

方式 插入/删除 取最近任务 特点
有序双向链表 O(1)（已知位置） O(1) 取队头，但插入需 O(n) 排序 简单，任务多时劣化
最小堆 O(log n) O(1) 通用，但周期任务需反复调整堆
时间轮 O(1) O(1) 高并发友好，精度受槽宽限制

Cyber 选择时间轮——因为自动驾驶系统的定时任务是”数量多、周期性强、高并发”的典型画像（控制 50Hz、监控 1Hz、心跳若干……）。

3.2 两级时间轮架构¶

graph TD A[Timer 用户 API] --> B[TimerManager] B --> C[TimingWheel 单例] C --> D[工作时间轮 512 槽 × 2ms = 1024ms 一圈] C --> E[辅助时间轮 64 槽 × 1024ms ≈ 65s 一圈] D --> F[TimerBucket → TimerTask 列表] E --> F

参数速记（cyber/timer/timing_wheel.h）：

  • WORK_WHEEL_SIZE = 512，TIMER_RESOLUTION_MS = 2 → 工作轮一圈 1024ms
  • ASSISTANT_WHEEL_SIZE = 64 → 辅助轮覆盖约 65 秒
  • 类比手表：工作轮是”分针”，辅助轮是”时针”；工作轮转满一圈，辅助轮走一格，并把格内任务级联（Cascade）回工作轮

5. 累积误差补偿：定时器的灵魂¶

5.1 误差从哪来¶

操作系统调度延迟、tick 粒度（2ms）、回调本身执行耗时、系统负载，都会让第 n 次触发晚于理想时刻。若简单地”每次回调后再睡一个周期”，误差会单调累积：一个 100ms 周期的控制任务，每次慢 1ms，10 秒后就慢了 100ms。

5.2 补偿算法¶

Cyber 的做法：维护 accumulated_error_ns，在每次触发时记账并用缩短下次间隔来追账：

效果示意：

graph LR subgraph 无补偿 A1[理想] --> A2[晚 1ms] --> A3[晚 2ms] --> A4[晚 3ms] end subgraph 有补偿 B1[理想] --> B2[晚 1ms] --> B3[早补回] --> B4[贴合理想] end
🔥工程含义
误差补偿让”第 N 次触发的绝对时刻”而非”相邻间隔”保持正确——这正是控制系统（MPC/LQR）需要的语义。注意补偿依赖 Time::MonoTime()（单调时钟），这正是第 2 节时钟选型的活例子。

6.2 定时回调与协程¶

Timer 回调的执行环境：Tick 线程只负责”到点取出任务”，实际回调经由调度器在协程上下文执行，享有优先级与亲和性配置（26-Cyber调度系统详解）。因此回调中调用 cyber::Async、SleepFor 等协程原语是安全的（见 28-Cyber异步调用机制）。

6.3 时间戳与数据链路¶

  • 消息 header.timestamp_sec 应在数据产生点尽早用 Time::Now() 打上
  • 定时发布的传感器模拟/桥接组件，定时精度直接决定下游对时间窗口对齐的容忍度
  • Transform 查询（31-Cyber Transform与坐标变换）按时间戳插值，时间系统质量决定融合精度
📝2026 年更新
时间与调度的确定性是 Apollo 10.0 资源降本（整体资源使用降低 50%、单 Orin 支撑 L4）的地基：更准的定时意味着更小的安全裕量、更少的算力冗余。Cyber RT 自 Apollo 3.5（2019）引入以来，两级时间轮 + 累积误差补偿的实现延续至今，是值得细读的经典工程代码。

7. 最佳实践¶

  1. 周期下限思维：2ms 分辨率下，5ms 定时器实际抖动 ±2ms——高频控制请上移到独立线程或 RT 内核方案。
  2. 回调要短：回调耗时逼近周期时补偿机制会退化为”连发”，务必把重活转 28-Cyber异步调用机制。
  3. 及时销毁定时器：时间轮任务队列容量有限，停止的组件应 Stop() 定时器。
  4. 监控抖动：在回调内记录 Time::MonoTime() 与理想时刻差值，超阈值告警。

8. 小结¶

时间系统 = Time/Duration（纳秒 int64）+ 三时钟抽象（System 对外 / Steady 测量 / User 仿真）；定时器 = 两级时间轮（512×2ms 工作轮 + 64×1024ms 辅助轮）+ 回调自我续约 + 累积误差补偿。这套设计在 O(1) 复杂度上同时做到了”高频可扩展”与”长期不失真”，与协程调度（26-Cyber调度系统详解）一起构成 Cyber 实时性的两大支柱。
