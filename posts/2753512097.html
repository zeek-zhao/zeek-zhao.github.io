升级迁移

[!info] 本篇目标
掌握 GitLab 的升级路径、升级前检查与操作步骤，以及跨服务器/跨实例迁移的两种主流方案，安全平稳地演进版本。

1. 升级路径（Upgrade Path）

GitLab 升级 不能跨主版本跳级，必须沿官方 Upgrade Path 逐级升级：

[!danger] 跳级风险
跳过主版本升级会导致数据库结构不兼容、后台迁移缺失，轻则功能异常，重则数据损坏。升级前到官方 Upgrade Path 页确认当前版本到目标的完整路径。

2. 升级前准备

3. 在线升级（Omnibus）

升级过程中 omnibus 包会自动执行数据库迁移与后台任务。升级完成后观察 15 分钟，确认 Pipeline 能跑、页面正常、无 Sidekiq 报错。

4. 升级后的验证清单

[!tip] 回滚
升级失败时：先尝试 apt install gitlab-ce=<旧版本> 回退，必要时用备份恢复（见 10-备份恢复）。回滚后必须重新备份。

5. 跨服务器迁移方案

方案 A：备份/恢复迁移（推荐，保留全部元数据）

优点：用户、权限、CI 记录完整迁移。缺点：有停机窗口。

方案 B：仓库镜像迁移（长迁移、零停机可选）

优点：可边运行边迁。缺点：不迁移元数据与历史设置，适合代码仓库为主、配置不复杂的场景。

[!warning] 迁移注意
方案 A 要求版本一致；方案 B 需重新配置 CI 变量、Runner、Webhook、SSO；迁移后务必更新所有成员的 remote URL 或统一配置 SSH key。

6. 容器环境升级

Docker 部署（见 03-安装部署-Docker）：

[!note] 镜像 tag 选择
生产环境固定 16.11.8-ce.0 这类完整 tag，避免使用 latest 造成不可控升级。
