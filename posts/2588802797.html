27-Cyber时间系统与定时器

选择原则一句话：对外打时间戳用 SystemClock（要与真实世界对齐），测耗时/算超时用 SteadyClock（要稳定），写测试/回放用 UserClock（要可控）。
📅 2026-10-24· 更新于 2026-10-24 · 6445 字 · 约 17 分钟 ✍ zeek.zhao #实战#apollo

时间戳这东西平时没人提，一旦多传感器对不上，排查起来能让人怀疑人生。这篇把 Cyber 的时间表示和定时器放一起讲——时间戳是数据排序的基础（29-Cyber数据系统详解 的排序就靠它），定时任务则跑在 26-Cyber调度系统详解 的协程上。

1. 时间系统分四层¶

自动驾驶对时间的要求是纳秒级表示 + 统一基准 + 不会跳变。Cyber 的架构分四层：

graph TD A[用户 API: Time / Duration] --> B[Clock 抽象层] B --> C1[SystemClock CLOCK_REALTIME] B --> C2[SteadyClock CLOCK_MONOTONIC] B --> C3[UserClock 编程控制] C1 --> D1[NTP / PTP / GPS 时间源] C2 --> D2[内核单调时钟] C3 --> D3[仿真/回放注入]

源码目录：cyber/time/（time.h、duration.h、clock.h）、cyber/rate.h。

2.2 三种时钟怎么选¶

classDiagram class Clock { <<interface>> +Now() Time +GetMonotonicTime() Time +SetNow(now)* } class SystemClock { +Now() Time } class SteadyClock { +Now() Time } class UserClock { +SetNow(now) } Clock <|-- SystemClock Clock <|-- SteadyClock Clock <|-- UserClock

选择原则一句话：对外打时间戳用 SystemClock（要与真实世界对齐），测耗时/算超时用 SteadyClock（要稳定），写测试/回放用 UserClock（要可控）。

这里有个坑值得单说。超时计算千万别用 SystemClock，NTP 一校时就会跳，超时逻辑当场错乱，一律交给 SteadyClock。另一个坑是单位混用——Cyber 全链路统一纳秒（int64_t），换算走类方法，别自己手写乘除。至于时间戳回退，消息处理得容忍单调性被破坏，数据同步那块会再碰到。

3. 定时器为什么选时间轮¶

3.1 三种实现方式对比¶

方式 插入/删除 取最近任务 特点
有序双向链表 O(1)（已知位置） O(1) 取队头，但插入需 O(n) 排序 简单，任务多时劣化
最小堆 O(log n) O(1) 通用，但周期任务需反复调整堆
时间轮 O(1) O(1) 高并发友好，精度受槽宽限制

Cyber 选时间轮，原因很直接：自动驾驶的定时任务就是”数量多、周期性强、高并发”这条路子——控制 50Hz、监控 1Hz、心跳若干……链表和堆在这个画像下都要吃亏。

3.2 两级时间轮架构¶

graph TD A[Timer 用户 API] --> B[TimerManager] B --> C[TimingWheel 单例] C --> D[工作时间轮 512 槽 × 2ms = 1024ms 一圈] C --> E[辅助时间轮 64 槽 × 1024ms ≈ 65s 一圈] D --> F[TimerBucket → TimerTask 列表] E --> F

参数速记（cyber/timer/timing_wheel.h）：

  • WORK_WHEEL_SIZE = 512，TIMER_RESOLUTION_MS = 2 → 工作轮一圈 1024ms
  • ASSISTANT_WHEEL_SIZE = 64 → 辅助轮覆盖约 65 秒
  • 类比手表：工作轮是”分针”，辅助轮是”时针”；工作轮转满一圈，辅助轮走一格，并把格内任务级联（Cascade）回工作轮

5. 误差补偿让触发时刻不漂¶

5.1 误差从哪来¶

调度延迟、tick 粒度（2ms）、回调自己的执行耗时、系统负载，都会让第 n 次触发晚于理想时刻。要是简单地在每次回调后再睡一个周期，误差会单调累积。一个 100ms 周期的控制任务，每次慢 1ms，10 秒后就慢了 100ms——控制系统受不了这种漂移。

6.1 TimerComponent¶

6.2 定时回调与协程¶

Timer 回调的执行环境有点绕：Tick 线程只负责”到点取出任务”，真正的回调经由调度器在协程上下文里跑，享有优先级和亲和性配置（26-Cyber调度系统详解）。所以在回调里调用 cyber::Async、SleepFor 这些协程原语是安全的（见 28-Cyber异步调用机制）。

6.3 时间戳与数据链路¶

  • 消息 header.timestamp_sec 应在数据产生点尽早用 Time::Now() 打上
  • 定时发布的传感器模拟/桥接组件，定时精度直接决定下游对时间窗口对齐的容忍度
  • Transform 查询（31-Cyber-Transform与坐标变换）按时间戳插值，时间系统质量决定融合精度

顺带说个背景。Apollo 10.0 能把整体资源使用砍掉一半、单块 Orin 撑起 L4，时间和调度的确定性是地基——定时越准，留的安全裕量越小，冗余算力就能省下来。Cyber RT 从 Apollo 3.5（2019）引入到现在，两级时间轮加累积误差补偿这套实现一直没换过。要我选，这是 Cyber 里最值得逐行读的一份代码。

7. 用定时器时要盯的几件事¶

  1. 周期下限思维：2ms 分辨率下，5ms 定时器实际抖动 ±2ms——高频控制请上移到独立线程或 RT 内核方案。
  2. 回调要短：回调耗时逼近周期时补偿机制会退化为”连发”，务必把重活转 28-Cyber异步调用机制。
  3. 及时销毁定时器：时间轮任务队列容量有限，停止的组件应 Stop() 定时器。
  4. 监控抖动：在回调内记录 Time::MonoTime() 与理想时刻差值，超阈值告警。

8. 两根支柱撑起实时性¶

时间表示和定时执行看着是两件事，其实互为前提。Time/Duration 用纳秒 int64 打底，三种时钟分头管对外、测量、仿真；定时器那边，512×2ms 的工作轮加 64×1024ms 的辅助轮，任务在回调里自我续约，靠累积误差补偿把第 N 次触发的绝对时刻钉在理想值上。O(1) 复杂度里同时做到高频可扩展、长期不失真，这套设计我觉得挺漂亮。再配上协程调度（26-Cyber调度系统详解），Cyber 的实时性才算完整。

下面是一套「时间/定时器异常」的标准排查与配置 runbook，从确认时钟源、检查同步、观测抖动到验证补偿。

注意事项与常见坑¶

  1. 超时用 SystemClock：NTP 校时跳变会让超时逻辑当场错乱，一律用 SteadyClock / Time::MonoTime()。
  2. 单位混用手写乘除：Cyber 全链路纳秒 int64，换算必须走 ToXxx 方法，自己算会溢出或丢精度。
  3. 周期低于 2ms：时间轮槽宽 2ms，更小粒度不可达，5ms 定时器实际抖动 ±2ms。
  4. 队列满静默丢任务：默认容量 1000，满后丢弃新任务且难以察觉，需监控 Timer 数量。
  5. 回调太重：耗时逼近周期时补偿退化为连发并拖垮协程，重活转异步或独立进程。
  6. Stop 后重复 Start：旧 weak_ptr 失效且任务队列残留，反复 Start 可能导致泄漏或行为异常，应重建 Timer。
  7. 超过 65 秒的延迟任务：辅助轮覆盖约 65 秒，更长延迟级联多次精度下降，应拆成 oneshot + 回调重排。
  8. 时间戳回退未处理：系统时钟可被向前/向后调整，消息消费端要容忍单调性被破坏并过滤异常时间戳。
  9. 忽略传输延迟补偿：多传感器融合时不做延迟补偿会导致时间窗口错位，融合结果不可用。
  10. 混用系统时间函数与 Time API：时间基准不一致，排序和因果判断全乱，项目内应统一 Time API。
  11. 时区混淆：内部应统一 UTC，只在显示层转换本地时区，日志时间戳要标明时区信息。
  12. 把软实时当硬实时：Cyber 软件定时器不保证微秒级硬实时，安全关键场景需 RT 内核或硬件方案，见 40-安全机制与冗余设计。

定时器验证步骤¶
