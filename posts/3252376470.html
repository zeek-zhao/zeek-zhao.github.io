错误处理

[!info] 本页概览
Go 的错误处理哲学是显式：函数返回 error 值，调用方检查并处理。本文讲解 error 接口、创建错误（errors.New/fmt.Errorf）、错误包装（%w/errors.Is/As）以及 panic/recover 的使用边界。

核心概念

error 是内置接口：

约定：函数若可能失败，最后一个返回值是 error；成功时为 nil。调用方必须检查。

创建与返回错误

错误包装（Go 1.13+）

  • errors.Is(err, target)：判断错误链中是否包含目标错误（可比较的哨兵错误）。
  • errors.As(err, &target)：把错误链中匹配类型的错误提取出来。

panic / recover

[!warning] panic 使用边界
panic 仅用于”程序不可能恢复”的错误（如数组越界、状态不一致），或作为库的内部机制。业务错误一律返回 error。recover 只在最高层（如 HTTP server 中间件）统一兜底，防止单个请求崩溃整个进程。

常见坑

  1. 忽略错误：_ 吞掉错误后继续使用可能为 nil 的返回值，生产事故高发。宁可提前 return。
  2. 错误字符串比较：不要用 err.Error() == "..." 判断错误类型，用 errors.Is/As 或哨兵错误。
  3. 包装错误丢失类型：用 fmt.Errorf("...%v", err)（%v）会丢失 errors.Is 匹配能力，必须用 %w。
  4. defer 中返回错误被吞：函数有命名返回值时，defer 里可修改返回值；无命名返回值时 defer 无法影响返回的 error。
  5. 过度 panic：把普通失败当 panic 用，程序失控且难以测试。
  6. 错误信息无上下文：return err 直接透传原始错误，上层无法定位”哪个函数、哪个参数”出的问题，用 %w 包装加上下文。

最佳实践

  • 错误消息首字母小写、不含标点（Go 风格），含关键上下文。
  • 定义哨兵错误（var ErrXxx = errors.New(...)）并用 errors.Is 判断。
  • 用 errors.Join（Go 1.20+）聚合多个错误。
  • 日志记录错误时同时记录请求 ID 与调用栈。
  • 库函数返回错误时保留原始错误链（%w），方便调用方做类型判断。
