20-规划模块

规划这张"大脑"怎么把地图、定位、预测揉成一条安全又舒服的轨迹。参考线、路径速度解耦、ST 图和轨迹校验，一篇讲透 Apollo 的主线算法。
📅 2026-10-31· 更新于 2026-10-31 · 4603 字 · 约 12 分钟 ✍ zeek.zhao #方案#apollo

感知和预测把”外面有什么、接下来会怎样”交代清楚，规划要回答的就是”那我该怎么走”。它把地图、定位、预测和导航揉成一条带时间戳的轨迹，交给控制去执行。本篇接着 19-预测模块 往下——预测给的轨迹概率，到这就要变成实打实的轨迹了。

1. 规划给车定一条什么轨迹¶

规划（Planning）是自动驾驶的核心组件，扮演”大脑”角色：根据感知和预测结果，结合导航路径，规划出安全、舒适、高效的行驶轨迹，输出带时间戳的轨迹点序列给控制执行。

graph LR A[HD Map 地图] --> C[Planning] B[Localization 定位] --> C D[Prediction 预测] -->|障碍物预测轨迹| C E[Routing 路由] -->|导航路径| C C -->|规划轨迹| F[Control 控制]

核心目标一句话：在确保安全的前提下，生成平滑舒适、高效节能、符合交规的轨迹。

2. 一条组件链，三股输入¶

目录结构是这样：

组件关系串起来：PlanningComponent → OnLanePlanning → ReferenceLineProvider（参考线）加 ScenarioManager（场景）→ Scenario → Stage → Task（决策器/优化器）。

内部数据流再看一眼：

flowchart TD A1[地图/路由] --> B[ReferenceLineProvider 参考线] A2[定位/感知/预测] --> C[Frame 数据整合] B --> C C --> D[ScenarioManager 场景选择] D --> E[Scenario/Stage 执行] E --> F1[Deciders 决策任务] E --> F2[Optimizers 优化任务] F1 & F2 --> G[轨迹生成] G --> H[轨迹校验/分区] H --> I[发布 ADCTrajectory]

3. 场景-阶段-任务三层嵌套¶

Apollo 用的是 Scenario → Stage → Task 三层结构：

graph TD A[ScenarioManager] -->|场景选择| B{当前场景} B -->|默认| C[LaneFollow] B -->|信号灯| D[TrafficLight] B -->|停车标志| E[StopSign] B -->|让行标志| F[YieldSign] B -->|裸交叉口| G[BareIntersection] B -->|泊车| H[Park/ValetParking] B -->|靠边停车| I[PullOver] B -->|窄路掉头| J[NarrowStreetUTurn] B -->|紧急停车| K[EmergencyStop]

每个场景包含多个阶段（Stage），每个阶段跑一串任务（Task）。任务分两类：决策器 Deciders，像 PathBoundsDecider（路径边界）、SpeedBoundsDecider（速度边界）、RuleBasedStopDecider（规则停车）、PathLaneBorrowDecider（借道）；优化器 Optimizers，像 PathOptimizer、PiecewiseJerkPathOptimizer、PiecewiseJerkSpeedOptimizer。

决策器按规则和约束划出搜索空间，优化器在空间里生成满足约束的平滑轨迹。两者分工清楚——这也是 Apollo 规划比较好读的原因之一。

4. 参考线：规划的坐标系基准¶

参考线是规划的基础几何结构，也就是车辆期望行驶的基准路径。来源有两个：Routing 模块基于高精地图的路由车道中心线，或无图场景下 RelativeMap 基于感知生成的车道线。

flowchart TD A[接收路由响应] --> B[提取车道序列] B --> C[平滑处理: QP/样条] C --> D[计算曲率等属性] D --> E[存储并提供参考线]

平滑要顾几头：贴近原始参考点、曲率连续避免急转弯、导数连续保证平滑过渡、满足车辆动力学约束（模型见 23-车辆动力学基础）。参考线管理支持分段与拼接，保证行驶过程连续平滑。

规划在参考线的 Frenet 坐标系（纵向 s、横向 l）下做横纵向解耦优化。把三维问题拆成两个二维问题，求解难度一下子降下来。

5. EM Planner：把时空拆成两步¶

EM Planner 是 Apollo 的主线算法，思路是把复杂的时空联合规划拆成两个子问题迭代求解：

graph LR A[EM Planner] --> B[Path 分支] A --> C[Speed 分支] B --> D[路径边界决策] --> E[路径优化] C --> F[ST 边界决策] --> G[速度优化] E --> H[轨迹组合] G --> H

路径规划先在参考线坐标系生成横向路径，暂时不管时间；速度规划再在固定好的路径上用 ST 图规划速度曲线。两步交替迭代，思想类似期望最大化。我个人觉得这种解耦是工程上的务实选择——联合求解理论上更优雅，但实时性和调试难度在车上都不好过关。

5.1 路径规划¶

flowchart TD A[路径边界决策] -->|车道/静态/动态障碍物| B[生成候选路径] B --> C[评估: 安全/舒适/效率] C --> D[QP/Piecewise-Jerk 优化] D --> E[最终路径]

QP 路径规划的目标函数包含路径平滑项、参考线偏差项和曲率项；约束有路径边界、最大曲率、避障；用 OSQP 求解器高效求解。

5.2 速度规划与 ST 图¶

ST 图是处理动态障碍物的核心工具：横轴时间，纵轴沿路径距离 s。

flowchart TD A[构建 ST 图] -->|障碍物/红绿灯/停车点投影| B[生成速度边界] B --> C[速度决策: 巡航/减速/停车] C --> D[DP 粗解 + QP 精化] D --> E[平滑速度曲线]

静态障碍物在 ST 图上是一条垂直线段，移动障碍物是斜线段。车辆与障碍物的时空关系一眼能读出来，跟车、超车、避让的速度曲线就照着这个画。

5.3 Piecewise-Jerk 优化¶

分段加加速度（Piecewise Jerk）优化直接优化位置 s、速度 v、加速度 a 序列：保证加速度连续、提升舒适性；直接约束 jerk（加加速度），避免急加急减；计算效率高，适合实时规划。路径规划和速度规划都能用。

6. 生成之后还要过三道校验¶

路径和速度曲线组合成带时间戳的完整轨迹后，还得过安全校验：

  1. 碰撞检查：轨迹与障碍物有没有时空冲突；
  2. 边界检查：是否超出道路边界；
  3. 动力学检查：是否满足加速度、曲率约束（车辆参数见 23-车辆动力学基础）。

校验不过的轨迹被拒绝并触发重新规划；实在不满足要求，就用回退策略生成简化轨迹（比如减速保持）。轨迹输出频率直接影响控制平滑度。

7. 安全、舒适、效率怎么摆平¶

规划要在安全前提下平衡三个目标，约束来自碰撞、动力学和交规：

目标 关键指标 手段
安全 安全距离维持、碰撞风险 预测避让、安全间距、故障安全
舒适 加速度/加加速度/曲率 Piecewise-Jerk、提前减速、平滑曲线
效率 行程时间、平均速度 合理巡航速度、智能跟车、信号灯配时利用

舒适的参考数值大致是：纵向加速度 ±1.5 m/s²、加加速度 ±1.0 m/s³；紧急范围能放宽到 ±4 m/s² 和 ±5 m/s³。

8. 规划夹在感知和控制中间¶

规划跟几个模块都有来往：向地图/路由查车道、限速、信号灯位置，生成参考线；从定位拿当前位置姿态，映射到参考线确定起点；从预测接收多轨迹概率，投影到参考线和 ST 图（见 19-预测模块）；向控制输出轨迹点序列（位置、方向、曲率、速度、加速度、时间戳），再接收跟踪误差反馈（见 22-控制模块）。

规划模块的计算必须在 100ms 内完成。做法是设严格时间预算、优先安全关键任务、并行计算、给计算密集任务设早期终止、按场景动态调整精度。

Apollo 10.0 这波升级里，决策与候选轨迹生成全面 Learning 化，从人类驾驶数据学习，行为更拟人；还引入了基于车辆角点的约束，相比传统中心点约束，窄道避障的通过性明显提升；ADFM（自动驾驶大模型）也用在了规划控制模块的重构上。端到端规划（传感器直出轨迹或控制）是长期趋势，参见 38-端到端自动驾驶与大模型。

9. 上手路径¶

  1. 启动规划模块，在 DreamView 里看参考线、路径候选和最终轨迹的渲染；
  2. 改 trajectory_period 这类配置，观察轨迹长度和计算负载怎么变；
  3. 构造静止障碍物场景，看借道决策和绕行轨迹；
  4. 构造红灯场景，看 ST 图上停车点投影和减速曲线；
  5. 读场景代码目录，理清 Scenario→Stage→Task 的扩展方式，为 21-决策模块与场景决策 做准备。

操作步骤¶

调一条规划轨迹，按这个走：

  1. 启动规划模块，在 DreamView 里确认参考线、路径候选、速度曲线、最终轨迹四层渲染；
  2. 改 planning.conf 的 trajectory_period，观察轨迹长度和规划耗时变化；
  3. 构造静止障碍物场景，看 PathBoundsDecider 怎么划边界、借道决策怎么触发；
  4. 构造红灯场景，看停车点怎么投影到 ST 图、减速曲线怎么生成；
  5. 构造动态横穿场景，看预测轨迹（见 19-预测模块）如何变成 ST 斜线；
  6. 检查轨迹三道校验日志，确认碰撞/边界/动力学检查在跑；
  7. 故意把 trajectory_time_resolution 调大，观察控制侧（见 22-控制模块）跟踪误差变化；
  8. 用 ndt 或 cyber_monitor 记录规划耗时，确认在 100ms 预算内。

使用流程¶

规划在整条链路里的位置：

EM Planner 的核心是分层解耦：先定空间路径，再在固定路径上定速度，迭代逼近联合最优。这是工程上的务实选择——联合求解理论更优，但 100ms 预算下实时性和调试难度都过不了关。

规划与预测、控制都是双向的：预测给多轨迹概率，规划回传自车轨迹；规划给控制轨迹点，控制回传跟踪误差。任一边不对，规划都要重新调。

注意事项与常见坑¶

  1. 参考线不平滑：原始车道中心线有折角，QP 平滑权重没调好，轨迹出现急转弯
  2. 参考线切换跳变：分段拼接处不连续，车辆突然横向抖动
  3. Frenet 投影歧义：弯道或自交处同一 (x,y) 对应多个 s，投影跳到错误车道
  4. ST 图边界错误：障碍物尺寸/安全间距没算进去，规划轨迹擦着障碍物过
  5. 动态障碍物漏投影：预测轨迹没覆盖横穿目标，ST 图缺斜线，规划没减速
  6. QP 求解失败：约束互相冲突（边界与曲率不可同时满足），OSQP 返回 infeasible，没触发回退
  7. 回退策略缺失：规划失败时没有减速保持轨迹，控制拿到空轨迹直接失控
  8. jerk 权重过小：速度曲线加速度变化剧烈，乘客感到顿挫；权重过大则响应迟缓
  9. 轨迹时域过长：trajectory_period 盲目调大，计算量爆炸，100ms 预算超支
  10. 时间分辨率过粗：trajectory_time_resolution 太大，控制跟踪点稀疏，横向误差增大
  11. 场景切换抖动：ScenarioManager 在两场景间来回跳，轨迹不连续；加迟滞条件（见 21-决策模块与场景决策）
  12. 动力学约束与实际车不符：用默认轴距/最大曲率，与实际车辆参数（见 23-车辆动力学基础）不匹配，控制跟踪不了
  13. 只做碰撞检查不做边界检查：轨迹不撞车但压线/出界，交规风险没兜住
  14. 分区周期与控制周期不匹配：轨迹分区周期和控制滚动周期对不齐，控制频繁重规划
