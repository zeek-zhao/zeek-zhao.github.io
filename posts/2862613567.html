Code Review 全流程

📑端到端走一遍
从开发者提交评审到最终合入的完整链路：push → Change → 评审 → 修改 → 合入。

1. 开发者推送评审¶

输出中会给出 Change URL：

📝Change-Id
Gerrit 在 commit message 自动补 Change-Id: Ixxx；它让同一逻辑的后续补丁归属同一个 Change。

2. 评审者视角¶

打开 Change 页面：查看 File（diff 视图）、Comments（行内评论）、Scores（标签打分）。

行内评论语法（提交到评论后触发邮件通知）：

3. 更新补丁集（PatchSet）¶

同一 Change-Id → 生成 PatchSet 2；评审人可看 PatchSet 1 → 2 的差异。

🔥多提交评审
一个 Change 对应一个 commit；多文件逻辑请拆成多个小提交/Change（小提交）。

4. 打分与合并¶

REST API 打分：

📝Submit 方式
维护者点 Submit（或 API）后，Change 状态变为 MERGED，提交进入 refs/heads/main。

5. 评论与回复（评论线程）¶

  • Inline comment：针对具体代码行；
  • Patch Set comment：整补丁集的总结；
  • 用 @用户 提及可定向通知。

6. 驳回与关闭¶

⚠️常见坑
  • 忘装 commit-msg hook → 无 Change-Id → 每次 push 都建新 Change（配置 require-change-id 强制）；
  • push 前 git pull --rebase 保持线性，避免提交被三方合并弄乱；
  • 评审未通过不要自行 git push origin main（权限也应禁止）。
