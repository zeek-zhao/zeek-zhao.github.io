21-常见问题排查

汇总 Hexo 从构建、部署到渲染的高频故障与排查套路，配一套系统化的排错方法论。

常见问题排查

📑一句话：绝大多数 Hexo 故障可归为四类——依赖坏了、缓存脏了、路径错了、权限丢了，按套路逐层排查即可。

排错总方法论¶

遇到问题先做三件事，能解决一半以上的故障。第一，看完整报错：终端报错往上翻到第一行 error，而不是只看最后一行；GitHub Actions 出问题进 Actions 页面点开失败步骤的完整日志。第二，最小复现：新建一篇只含标题的空文章，如果空文章也出错，问题在环境不在内容；如果只有某篇文章出错，问题在那一篇的语法。第三，清理重来：

现象：生成卡在某篇文章不动。 常见于公式或标签未闭合（$$ 缺另一半、{% endtabs %} 丢失），也见过 frontmatter 里的占位符被引擎展开导致死循环。--debug 模式会打印正在处理的文件名，直接定位。

现象：Node 版本升级后构建报错。 老项目从 Node 12/14 升到 18/20 时，部分老插件用到了被移除的 API。先 npm outdated 列出过期依赖逐个升级，实在无法升级的插件寻找社区 fork 或替代品。

📝2026 更新
在 Hugo/Astro 快速崛起的当下，Hexo 依旧依赖其庞大的中文主题生态保持活跃，这意味着主题与插件版本同步尤其重要：升级 Node 或 Hexo 大版本时，务必同步检查主题是否发布了适配说明，CI 中保留一个能构建通过的”已知良好”版本号。

现象：部署成功但站点没更新。 按序检查：浏览器强刷（Ctrl+F5，CDN 缓存可能滞后）；GitHub Pages 设置中的发布分支是否还是目标分支；部署仓库根目录是否有 .nojekyll 文件（没有的话 Jekyll 会忽略下划线开头的目录）；Actions 日志里 hexo deploy 是否真的推了新 commit。

现象：部署后样式全丢。 通常是 _config.yml 的 url 和 root 配置与实际部署域名不匹配，静态资源按绝对路径引用到了错误地址。二级路径部署（如 user.github.io/repo）时务必设 root: /repo/。

渲染类问题¶

现象：公式显示为原始 LaTeX 代码或乱码。 链路三段逐一验证：主题 math 配置是否开启、文章 frontmatter 是否有 mathjax: true（开了 per_page 时必需）、Markdown 引擎是否转义了下划线（见 17-数学公式与图表渲染 的三层解法）。

现象：Obsidian 双链 xxx 原样出现在网页上。 同步脚本未覆盖该链接，或链接目标笔记未满足发布条件被过滤掉了。在脚本层为”无法解析的 wikilink”设计降级策略（转纯文本或移除），别让原始语法漏到线上。

现象：图片 404。 对照路径规则逐个排查：资源文件夹方案是否开启 post_asset_folder、marked 的 prependRoot 配置、Obsidian 附件目录是否被同步脚本改写。批量检查可用脚本扫描所有 ![]() 引用并验证文件存在。

现象：代码块高亮异常或整页 JS 报错。 优先怀疑压缩器误伤（hexo-neat 或 Gulp 的 uglify 配置），把对应文件加入压缩排除列表验证；其次检查主题升级后 inject 注入的旧脚本是否失效。

静态资源与性能问题¶

现象：Service Worker 缓存顽固，更新不生效。 进入 DevTools > Application > Service Workers，勾选 Update on reload 或直接 Unregister 后刷新；长期方案是每次发布递增缓存版本号（见 18-PWA与进阶功能 的调试三板斧）。

现象：站点越来越慢。 用 Lighthouse 定位：图片体积大 → 回到 16-图片与资源管理 的压缩链路；JS 阻塞 → 检查新加的第三方脚本是否异步加载；搜索索引膨胀 → 调低 limit 或分片。

内容安全类问题¶

现象：私密笔记被发布到了线上。 这是知识库工作流最危险的事故。排查 status 过滤逻辑的边界情况：字段缺失时脚本的默认行为是什么（应当默认不发布）、目录规则的优先级、callout 内嵌 frontmatter 的解析。修复后立即在部署仓库回滚到上一个 commit，并强制 Google 重新抓取。

现象：误提交了密钥或隐私文件。 立即轮换泄露的密钥（Secret 泄露等同失效），从 Git 历史中用 git filter-repo 清除敏感文件，GitHub 侧联系支持清理缓存。事前预防：.gitignore 覆盖密钥文件、提交前 hook 扫描。

建立自己的应急预案¶

最后的建议：把本篇沉淀为自己的排错手册。每次故障修复后，用三行记录——现象、根因、修法——追加到个人笔记；把高频命令写成 scripts/fix.sh；重要操作（主题升级、Node 升级、平台迁移）前打 tag 留好退路。故障不可避免，但重复踩同一个坑是可以避免的。排查工具的配置细节可在 20-实战：从零到上线完整流程 的运维阶段一并落地。
