用户与团队权限

栈能编排应用了（接着上一篇 08-栈与Compose），但谁能看、谁能改就得靠权限来定。这一页我按权限模型、用户团队、角色、环境授权到 LDAP 集成走一遍。核心思路是：按职能建团队、按环境授角色，尽量别给个人直接授权，人员一变动维护成本会很高。

RBAC 就是用户进团队再挂角色¶

Portainer RBAC 模型：
用户（User） → 团队（Team） → 角色（Role）
↘ 环境授权（Environment）

角色分类：

  • 管理员（Administrator）
  • 环境管理员（Environment Admin）
  • 操作员（Operator）
  • 只读（Read-Only）
  • 自定义角色（BE）

首个管理员在部署时就要建好¶

设置 → 用户：

  • 创建用户：用户名 + 密码
  • 编辑用户：重置密码、启用/禁用
  • 删除用户

认证模式：

  • 本地认证（默认）
  • LDAP / AD（企业）
  • OAuth（BE）

注意：

  • 首个管理员在部署时创建
  • 管理员可创建其他管理员

按团队授权省去逐个配用户¶

设置 → 团队：

  • 创建团队：运维组、开发组
  • 添加成员
  • 团队授权环境

用途：

  • 按职能分组：devops、dev、viewer
  • 环境按团队授权
  • 避免逐个用户授权

四种角色能力差在删除和管理上¶

环境按团队加角色来授权¶

我一般先按职能把团队建好，再做环境到团队的映射，这样人走了也不用一条条改。

设置 → 环境授权：

  • 选择环境/环境组
  • 授权给团队 + 角色
  • 公开访问控制

示例：

环境组 团队 角色
生产 devops 环境管理员
生产 dev 只读
开发 dev 操作员

容器级 ACL 要在创建时就设¶

Portainer 支持容器级访问控制（ACL）：

  • 容器可指定拥有者团队
  • 其他团队仅按角色访问

用途：

  • 生产数据库仅运维组可管理
  • 开发容器对开发组开放

注意：

  • ACL 配置在容器创建时设置
  • 需环境权限配合

LDAP 让账号离职即失效¶

全员管理员和公开环境最危险¶

这两个坑我基本一接手就先查，管理员一多权限就收不回来了。

  1. 全员管理员：权限失控，最小化管理员。
  2. 用户级授权：人员变动维护成本高，用团队。
  3. 只读账号可删除：角色设置错误导致误操作。
  4. LDAP 映射失败：组 DN 配置错误，用户无权限。
  5. 公开环境未关：匿名可管理容器，关闭公开访问。

我的授权原则就这几条¶

  • 角色化：管理员 / 环境管理员 / 操作员 / 只读。
  • 团队授权环境，个人不直接授权。
  • 生产环境只读 + 运维操作员。
  • 企业集成 LDAP/SSO。
  • 配合 14-安全加固 完成安全基线。
