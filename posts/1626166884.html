代码评审与 MR

[!info] 本篇目标
掌握 Merge Request（MR）的完整生命周期：创建、评审、流水线联动、审批规则与合并策略，把代码评审做成团队习惯。

1. MR 是什么

Merge Request 是 把功能分支合并到目标分支前的变更提案，包含 diff、讨论、审批、流水线结果等完整上下文。相比直接 push 到主干，MR 提供了可审查、可追溯、可自动校验的入口。

4. 评审体验提升

  • Inline comments：在 diff 行上直接评论，可发起 Thread。
  • Resolve conversations：讨论解决后标记完成，MR 才可合并（可配置）。
  • Suggestion：评审人直接给出可一键应用的代码建议块。
  • Code owners：.gitlab/codeowners 指定文件的所有者，改动对应文件必须由其审批：

5. 审批规则（Approval rules）

在项目 Settings -> Merge requests -> Approval rules 配置：

规则 配置示例
至少 N 人审批 2 个审批人
指定角色 必须含 Maintainer
Code owners 审批 改动 owner 文件必须 owner 审批
安全扫描阻断 SAST 高危漏洞未解决不可合并

[!warning] 审批是门禁不是摆设
设置 Merge checks -> Pipeline must succeed 与 Discussions must be resolved，让流水线和讨论状态成为硬门禁，避免”形式上审批”。

6. 合并策略

策略 提交历史 适用
Merge commit 保留合并节点 需要完整时间线
Squash commit 压缩为单提交 功能分支历史杂乱
Rebase 线性历史 追求简洁可回滚

[!note] 建议
团队默认 Squash + 删除源分支：主干历史干净、每条提交对应一个功能，配合 git revert 易于回滚。

7. MR 与 CI/CD 联动

  • MR 触发测试流水线（rules: if: $CI_PIPELINE_SOURCE == "merge_request_event"）。
  • Review Apps：MR 自动部署临时环境，评审人可实际点击验证。
  • 流水线失败默认阻止合并，可在 Merge checks 中调整。
