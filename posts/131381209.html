服务通信

[!info] 本节目标
掌握 ROS2 服务通信机制，能编写服务端与客户端，并理解同步请求-响应模型。

1. 服务通信模型

服务是同步双向通信：客户端发送请求，服务端处理并返回响应。服务接口（srv）由请求（request）与响应（response）两部分组成。

特性 说明
方向 同步请求-响应
接口 srv（request + response）
并发 一个服务端可服务多个客户端
适用 查询、配置、低频指令

2. 定义服务接口

[!note] 内置服务
std_srvs/srv/Empty（无参数）、std_srvs/srv/SetBool、std_srvs/srv/Trigger 等内置类型可直接使用。

3. Python 服务端

[!tip] 回调线程
服务回调同样在 Executor 中执行；默认回调组为 MutuallyExclusive，长任务会阻塞其它回调，需要时配置 Reentrant（见 14-执行器与回调组）。

4. Python 客户端

[!danger] 同步 vs 异步
call_async 返回 future，需配合 spin_until_future_complete 或 Executor 处理；不要在回调里直接 call（死锁）。

5. C++ 服务端

6. 客户端与服务端匹配

项 要求
服务名 完全一致（含命名空间）
接口类型 一致
QoS 兼容（默认可靠）

[!tip] 等待服务
客户端启动时服务端可能未就绪，务必 wait_for_service，否则调用会抛异常。

7. 常见问题

现象 排查
找不到服务 ros2 service list、命名空间检查
调用超时 服务端阻塞、回调未响应
类型不匹配 ros2 service type 对比
回调卡死 长任务回调、Executor 单线程

[!note] 延伸
服务接口自定义见 13-自定义消息接口；长时任务改用动作见 08-动作通信。

8. 服务设计注意事项

服务适合请求-应答式交互，但服务调用是阻塞的，服务端一次只能处理一个请求（默认单线程回调），频繁调用会互相等待，因此高频率周期性交互不应使用服务。服务端处理时间较长时，应在回调内尽快返回或将耗时操作移到独立线程，必要时改用动作通信表达长时任务。服务接口应保持职责单一，请求与响应字段尽量精简，命名遵循语义化规范。客户端调用前需确认服务已就绪，可通过 ros2 service list 或 wait_for_service 等待。

[!note] 建议
判断通信模式：周期性数据用话题，请求应答用服务，长时任务用动作；动作详见 08-动作通信。
