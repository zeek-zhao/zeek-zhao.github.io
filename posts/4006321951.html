工程实践与代码规范

[!info] 本页概览
写出”能跑”的代码只是起点，可读、可维护、可测试才是工程标准。本文讲解头文件组织、命名规范、const 正确性、RAII、错误处理策略与单元测试。

核心概念

工程实践的三个目标：可读（别人能看懂）、可维护（改动安全）、可测试（行为可验证）。规范的核心是让团队代码风格一致，降低认知成本。

头文件与项目结构

命名规范（Google Style 示例）

项 规范
类型/类 PascalCase：BankAccount
函数/变量 snake_case：get_balance、total_count
常量 kMaxSize 或全大写 MAX_SIZE
宏 UPPER_SNAKE_CASE
成员变量 尾下划线：balance_

[!tip] 一致性最重要
选择一种风格并全项目遵守，比哪种风格更”正确”更重要。可用 clang-format 统一格式。

const 正确性

const 成员函数保证不修改对象，也让 const 对象可调用；这也是编译器发现逻辑错误的手段。

错误处理策略

场景 策略
可预期业务错误（文件不存在） 返回错误码 / std::optional / 异常
编程错误（越界、非法参数） 断言 assert / 异常
资源获取 RAII 对象，天然异常安全
边界（C 接口、回调） 不抛异常，错误码转换

单元测试

常见坑

  1. 魔法数字：代码里到处是 42、0x3F，加 constexpr 命名常量。
  2. 深嵌套：超过 3 层 if/for 的代码极难维护，提取函数。
  3. 全局可变状态：全局变量让测试互相污染，尽量依赖注入。
  4. 注释撒谎：注释与代码不一致比没注释更糟，改了代码必须改注释。
  5. 忽略警告：-Wall -Wextra -Werror 是底线，警告往往是真 bug。

最佳实践

  • 小步提交、频繁编译测试；CI 跑单元测试 + sanitizer + 静态分析（clang-tidy）。
  • 代码评审关注逻辑正确与可读性，而非逐行风格（交给 formatter）。
  • 接口设计”最小暴露”：头文件只暴露必要类型与函数。
  • 用版本管理（git）与构建脚本（CMake）管理工程，一切可复现。
  • 定期重构：消灭重复代码（DRY）、简化复杂分支。
