目录概念与数据模型

接着上一篇 01-LDAP概述 往下，这篇把 LDAP 的数据模型拆开看：条目、属性、对象类、Schema，再加上 DN 怎么命名，都会配上真实示例。这些概念搞明白，后面建目录才不会返工。

一图看懂：LDAP 数据模型四要素如何拼成一棵目录信息树。

graph TD E[Entry 条目] --> AT[Attribute 属性] E --> OC[ObjectClass 对象类] OC --> SC[Schema 定义与匹配规则] DN["DN 从根到叶子拼出唯一路径"] --> E E --> T[DIT 目录信息树]

数据模型就四个要素¶

LDAP 数据模型四个要素：

  1. 条目（Entry）：树上的一个节点/记录
  2. 属性（Attribute）：条目的字段
  3. 对象类（ObjectClass）：条目类型定义
  4. Schema：类型与规则集合

整个目录 = 一棵树（DIT，Directory Information Tree）

条目靠属性描述，dn 唯一定位¶

条目示例（LDIF）：
dn: cn=zhangsan,ou=people,dc=example,dc=com
objectClass: inetOrgPerson
cn: zhangsan
sn: Zhang
uid: zhangsan
mail: zhangsan@example.com
telephoneNumber: 13800000000

解释：

  • dn：条目唯一标识
  • objectClass：必须的类
  • cn/sn/uid/mail…：属性
  • 属性可多值（如多个 mail）

对象类决定必选和可选属性¶

对象类分类：

  • STRUCTURAL：结构类（必须，如 inetOrgPerson）
  • AUXILIARY：辅助类（补充，如 posixAccount）
  • ABSTRACT：抽象基类（top）

常用类：

  • person / organizationalPerson / inetOrgPerson
  • organizationalUnit（OU）
  • organization（组织）
  • groupOfNames / groupOfUniqueNames（组）
  • posixAccount / posixGroup（Linux 用户）
  • device（设备）

对象类决定：

  • 必选属性（MUST）
  • 可选属性（MAY）

Schema 管定义和匹配规则¶

Schema 组成：

  • 对象类定义（objectClass）
  • 属性定义（attributeType）
  • 匹配规则（matching rules）
  • 语法（syntax）

示例属性定义：
attributeType ( 1.3.6.1.4.1.1466.115.121.1.15 NAME ‘mail’
DESC ‘RFC1274: RFC822 email address’
EQUALITY caseIgnoreIA5Match
SYNTAX 1.3.6.1.4.1.1466.115.121.1.26{256} )

OpenLDAP 默认 Schema：
/usr/share/slapd/schema/

  • core.schema
  • cosine.schema
  • inetorgperson.schema
  • nis.schema
  • dyngroup.schema

DN 从根到叶子拼出来¶

DN 规则：

  • 全局唯一
  • 从根到叶子拼接
  • 由 RDN 序列组成

示例：
cn=zhangsan,ou=people,dc=example,dc=com
|– RDN: cn=zhangsan
|– RDN: ou=people
|– RDN: dc=example
`– RDN: dc=com

根条目（base DN）：
dc=example,dc=com

命名规范建议：

  • ou 用功能/部门（people、groups、servers）
  • 用户用 uid 或 cn
  • 避免中文与特殊字符

DIT 设计要浅要稳¶

设计原则：

  1. 层级清晰、稳定
  2. 访问控制可划分
  3. 便于复制与分布
  4. 避免过深嵌套

常见顶层：
ou=people 用户
ou=groups 组
ou=servers 服务器
ou=departments 部门
ou=applications 应用

不要：

  • 按组织结构硬编码层级（人员调动）
  • 层级过深（性能与维护）

我一般先把 ou 按功能划好（people、groups、servers 这种），不照着组织结构硬编码层级，人员一调动层级就跟着乱。

变更用 LDIF 导入¶

这五个坑很容易踩¶

  1. objectClass 缺失：条目必须有 STRUCTURAL 类。
  2. DN 不一致：dn 与属性值不一致报错。
  3. Schema 未加载：自定义属性不可用。
  4. 大小写敏感：DN 匹配规则（cn 一般忽略大小写，uid 可能敏感）。
  5. 多值冲突：单值属性传多值报错。

守住这几条就不会跑偏¶

  • 先设计 DIT 再建目录。
  • 使用标准 Schema，少用自定义。
  • 统一命名规范（小写英文）。
  • 用 LDIF 管理变更，保留版本。
  • 目录结构稳定优先。
  • 下一步：03-OpenLDAP部署与安装。

结构定稳之后再加属性和 ACL 都省事，急着建目录往往就是返工的起点。
