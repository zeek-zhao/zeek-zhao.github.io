U-Boot：从基础概念到启动流程

在嵌入式 Linux 里，引导加载程序是最先跑起来的那段代码，负责初始化硬件、建立内存映射，把内核的运行环境准备好。U-Boot（Universal Boot Loader）是其中用得最广的开源实现之一。我在嵌入式板上第一次跑它时，最不理解的不是命令，而是为什么要分两阶段启动——后来把 gd、重定位和 SPL 串起来才明白，这套设计基本是被片上 SRAM 的大小逼出来的。

一图看懂：U-Boot 两阶段启动，重定位是分界点。

graph LR RST[复位] --> S1["第一阶段 汇编 底层初始化"] S1 --> REL[重定位到 RAM] REL --> S2["第二阶段 C 代码 完整初始化"] S2 --> CMD[命令行与环境变量] CMD --> K[加载并启动内核]

一、U-Boot概述：跨架构、跨系统的开源引导程序¶

1.1 U-Boot简介¶

U-Boot，全称Universal Boot Loader，是遵循GPL条款的开源项目，由德国DENX软件工程公司开发维护。它起源于FADSROM、8xxROM、PPCBOOT项目，逐步演化发展而来。U-Boot作为嵌入式系统的引导加载程序，支持多种计算机系统架构，其主要作用是引导系统启动。

我一般先看它支持的架构和操作系统清单，判断手头板子有没有现成配置可以抄。

目前，U-Boot不仅支持Linux系统的引导，还支持NetBSD、VxWorks、QNX、RTEMS、ARTOS、LynxOS、Android等多种嵌入式操作系统。

1.2 U-Boot主要特性¶

  • 开放性：完全开源，遵循GPL许可证
  • 多平台支持：支持ARM、PowerPC、MIPS、x86、RISC-V等多种CPU架构
  • 多操作系统支持：可引导多种嵌入式操作系统
  • 丰富的设备驱动：内置以太网、SDRAM、NAND、NOR、MMC、USB、LCD等驱动程序
  • 网络支持：支持TFTP、NFS、BOOTP等网络协议
  • 命令行界面：提供丰富的命令集，方便调试与开发
  • 脚本支持：支持环境变量和引导脚本
  • Flash管理：支持多种Flash设备的读写、分区管理
  • 功能扩展：可通过配置选项定制功能

1.3 U-Boot获取途径¶

U-Boot官方源码仓库：

  • Git仓库：https://source.denx.de/u-boot/u-boot
  • FTP下载：https://ftp.denx.de/pub/u-boot/
  • GitHub镜像：https://github.com/u-boot/u-boot

1.4 U-Boot版本命名规则¶

U-Boot使用三级版本号：主版本号.次版本号.补丁版本号，如”U-Boot-2.34.5”表示主版本号为”2”，次版本号为”34”，补丁版本号为”5”。

官方发布的正式版本补丁版本号通常为”0”，例如U-Boot-2.34.0。补丁版本号大于0表示开发版本。

二、U-Boot存在的意义：没有 BIOS 时谁来初始化硬件¶

2.1 嵌入式系统引导过程¶

嵌入式系统由于缺少像PC那样的BIOS，需要一个Bootloader来完成系统的初始化和操作系统的加载工作。典型的嵌入式系统引导过程包括：

  1. 上电或复位后，CPU从固定地址开始执行（通常是ROM中的代码）
  2. 执行芯片厂商提供的引导ROM代码（如果有）
  3. 加载并执行Bootloader（U-Boot）
  4. Bootloader初始化硬件，加载操作系统内核
  5. 操作系统接管系统控制权并启动用户程序

2.2 U-Boot的作用¶

U-Boot在嵌入式系统中的主要作用包括：

  1. 硬件初始化：初始化CPU、内存控制器、时钟等关键硬件
  2. 内存空间设置：设置内存映射，为系统运行准备环境
  3. 加载操作系统：从存储设备（如Flash、SD卡、网络）加载操作系统内核到RAM
  4. 传递启动参数：向操作系统传递必要的启动参数，如内存大小、根文件系统位置等
  5. 调试环境提供：提供命令行界面，方便系统调试
  6. 固件更新：支持通过各种接口（串口、网络、USB等）更新系统固件
  7. 系统恢复：提供系统恢复功能，避免系统无法启动

2.3 U-Boot的”生命周期”¶

U-Boot的生命周期是指从U-Boot开始运行到它结束运行的过程：

  1. U-Boot是一个裸机程序（非操作系统），上电或复位后直接运行
  2. U-Boot运行期间，系统只执行U-Boot程序，不能同时运行其他程序
  3. U-Boot的唯一出口是启动操作系统内核，一旦内核启动，U-Boot就结束运行
  4. 要再次进入U-Boot，只能通过系统复位重启
  5. 虽然U-Boot可以执行多种任务（如烧写固件），但都是在U-Boot环境内执行，而非多任务并行

我把 U-Boot 当裸机程序记，就不会纠结它为什么不能像 Linux 那样多任务并行。

三、U-Boot目录结构：按功能和架构分层¶

U-Boot的源码组织结构清晰，按功能和架构分类：

  • api API接口实现

  3. CPU相关代码：arch/arm/cpu/arm920t/目录
  4. 链接脚本：board/xxx/u-boot.lds

四、U-Boot启动流程：两阶段分工，重定位是分界点¶

U-Boot的启动过程通常分为两个阶段：

4.1 U-Boot启动第一阶段¶

第一阶段主要在汇编中完成初步的硬件设置，为C环境运行做准备：

  1. CPU初始化：设置CPU运行模式，关闭中断，初始化寄存器
  2. 硬件初始化：初始化关键硬件，如时钟、存储控制器
  3. 存储初始化：初始化SDRAM，为加载第二阶段代码准备
  4. 初始化堆栈：设置堆栈指针，为C代码执行做准备
  5. 代码重定位：将第二阶段代码从Flash拷贝到RAM
  6. 跳转执行：跳转到RAM中执行第二阶段代码

主要涉及文件：

  • arch/arm/cpu/armxx/start.S：处理器相关初始化
  • board/xxx/lowlevel_init.S：板级低级初始化

4.2 U-Boot启动第二阶段¶

第二阶段在C环境中执行，完成更复杂的初始化：

  1. board_init_f：前期板级初始化

    • 初始化全局数据结构（gd）
    • 初始化串口
    • 初始化各类硬件设备
    • 配置内存布局

  2. 重定位操作：将U-Boot代码拷贝到RAM高地址处

    • 计算重定位目标地址
    • 复制代码到新地址
    • 设置新的堆栈和全局数据

  3. board_init_r：后期板级初始化

    • 初始化更多设备（网络、存储等）
    • 设置环境变量
    • 初始化命令行接口
    • 进入主循环

  4. main_loop：进入命令行循环

    • 显示命令提示符
    • 处理用户输入命令
    • 执行自动启动命令

主要涉及文件：

  • common/board_f.c：前期初始化
  • common/board_r.c：后期初始化
  • lib_arm/board.c：arm架构板级初始化
  • common/main.c：主循环

我调启动流程时，是拿 board_init_f / board_init_r 这两个函数当分界线的，前后半段各自负责什么一眼就清楚。

4.3 启动流程详细分析¶

Global Data结构

U-Boot使用全局数据结构(gd)在不同阶段和函数之间传递信息。该结构在RAM中分配，地址通常保存在特定寄存器中（ARM64中为X18）。

重定位过程

U-Boot初始运行在ROM/Flash中，但速度较慢，因此会将自身代码复制到RAM中执行：

  1. 计算重定位地址（通常在RAM高端）
  2. 复制代码到目标地址
  3. 更新全局数据和堆栈指针
  4. 跳转到新地址继续执行

五、U-Boot启动方式：NAND、NOR、SD 与 SPL 各有套路¶

我习惯先确认板子从哪种介质启动，再去看对应的片上 ROM 读取流程，顺序反过来容易把 SPL 和完整 U-Boot 混成一层。

5.1 NAND Flash启动¶

当系统配置为从NAND Flash启动时：

  1. CPU复位后，片上ROM从NAND Flash读取前4KB数据到内部SRAM（stepping stone）
  2. CPU从内部SRAM开始执行，初始化关键硬件
  3. 从NAND Flash加载完整U-Boot到SDRAM
  4. 跳转到SDRAM继续执行

NAND Flash启动的特点：

  • 需要特殊的启动头部，适配片上ROM的读取机制
  • 通常需要处理坏块和ECC校验
  • 无法直接执行（非XIP），必须先拷贝到RAM

5.2 NOR Flash启动¶

当系统配置为从NOR Flash启动时：

  1. CPU复位后直接从NOR Flash起始地址执行代码
  2. 初始化关键硬件后，仍可继续在NOR Flash执行或拷贝至RAM执行

NOR Flash启动的特点：

  • 支持芯片内执行(XIP)，CPU可直接从NOR Flash取指令
  • 读取速度较快，但容量通常较小
  • 适合存储小型Bootloader

5.3 SD/MMC卡启动¶

当系统配置为从SD/MMC卡启动时：

  1. CPU复位后，片上ROM读取SD/MMC卡引导扇区到内部SRAM
  2. 执行引导代码，从SD/MMC卡加载完整U-Boot到SDRAM
  3. 跳转到SDRAM继续执行

SD/MMC启动的特点：

  • 需要特定引导区布局，通常在前几个扇区
  • 容易更新，插拔方便
  • 适合开发阶段使用

5.4 SPL（Secondary Program Loader）¶

对于RAM较小的系统，U-Boot采用两级加载策略：

  1. 首先加载体积小的SPL（数KB大小）
  2. SPL初始化最小系统（时钟、SDRAM等）
  3. SPL从存储设备加载完整U-Boot到SDRAM
  4. 跳转到完整U-Boot继续执行

SPL的优点：

  • 体积小，适合有限的片上SRAM
  • 可以支持更复杂的启动设备
  • 提供更灵活的启动选项

六、U-Boot工作模式：倒计时决定进自动还是命令行¶

6.1 自动启动模式（正常模式）¶

在自动启动模式下，U-Boot会：

  1. 完成初始化后，显示倒计时（通过环境变量bootdelay控制）
  2. 倒计时结束后，自动执行bootcmd环境变量中的命令
  3. 加载并启动操作系统内核

这是产品发布时的默认工作模式，无需用户干预。

6.2 交互模式（命令行模式）¶

在交互模式下，U-Boot提供命令行界面，允许用户：

  1. 在倒计时期间按任意键进入命令行
  2. 执行各种命令进行调试、配置和系统维护
  3. 手动引导系统或执行其他操作

这种模式主要用于开发调试阶段。我实际用的时候，倒计时那一两秒就是进命令行的唯一窗口，错过只能复位重来。

6.3 下载模式¶

下载模式是交互模式的特殊应用，用于：

  1. 通过各种接口（串口、网络、USB等）下载文件到目标板
  2. 将下载的文件（内核、文件系统等）写入存储设备
  3. 更新系统固件

十一、常见问题与解决方案：先看输出，再看加载¶

我排查启动问题时严格按”有没有输出 → 能不能加载 → 参数对不对”的顺序走，跳步只会反复烧写。

11.1 U-Boot无法启动¶

可能原因与解决方案：

  • 硬件连接问题：检查电源和关键信号连接
  • 启动设备损坏：尝试使用JTAG或ISP重新烧写
  • 时钟配置错误：检查时钟设置是否匹配硬件
  • 内存参数错误：检查SDRAM参数配置
  • 启动设备格式错误：确认启动设备分区格式正确

11.2 串口无显示/乱码¶

可能原因与解决方案：

  • 波特率不匹配：确认串口工具波特率设置
  • 时钟频率错误：检查CPU和外设时钟配置
  • 串口引脚配置错误：检查GPIO复用功能
  • 串口驱动初始化失败：检查初始化代码
  • 控制台配置问题：检查是否正确设置默认控制台

11.3 无法加载内核¶

可能原因与解决方案：

  • 内核镜像损坏：重新下载或生成内核镜像
  • 加载地址错误：确认加载地址与编译地址匹配
  • 内存不足：检查内存是否足够加载内核
  • 文件系统问题：检查存储设备文件系统是否损坏
  • 启动参数错误：检查bootargs环境变量

十二、落点：把启动链路按阶段、介质、参数三段记牢¶

回头看，U-Boot 的复杂度主要堆在三处：两阶段启动与重定位决定了代码在哪执行，启动介质决定了片上 ROM 怎么把你搬进 RAM，bootargs 与 bootcmd 决定了内核最终拿到什么参数。这三条线各盯一遍，移植和调试时基本不会跑偏。下一步如果要在具体板子上验证，先用 printenv 把环境变量抄下来，再用 md 看一眼内核加载地址，比反复烧写省时间。
