Git 变基与冲突解决

ℹ️本页概览
本文深入讲解变基（rebase）与冲突解决：rebase 原理、冲突场景、解决技巧、reflog 救援，配真实示例。

Rebase 原理¶

rebase = 把当前分支的提交”重放”到目标分支顶端，产生新提交。

main: A—B—C
feat: A—B—D—E
git rebase main（在 feat 上）
→ feat: A—B—C—D’—E’

特点：线性历史、提交被改写（新 SHA）

何时用 Rebase¶

用 rebase：

  • 合入前同步 main，保持线性历史（Trunk 风格）
  • 交互式整理自己的提交（rebase -i）
  • 个人分支/未共享分支

用 merge：

  • 共享分支（他人已基于此开发）
  • 保留真实合并记录（GitFlow）
  • 简单同步，不想改写历史

常见冲突场景¶

  1. 同一文件同行修改：手动合并
  2. 一个删一个改：决定保留删除或修改
  3. 新增文件同名：改名或保留一个
  4. 二进制文件：选一边（–ours/–theirs）
  5. 结构化文件（JSON/锁文件）：用工具合并后校验

技巧：

  • 小步变基：先 rebase 到中间点，避免一次大量冲突
  • 频繁同步：功能分支经常 rebase main，冲突小
  • 结构化文件冲突用 git mergetool 或专用工具

Reflog 救援¶

⚠️危险命令
  • git push --force 会覆盖远程，用 --force-with-lease
  • git reset --hard 丢弃工作区，先确认或 stash
  • rebase 共享分支会改写共享历史，禁止

常见坑¶

  1. rebase 共享分支：他人 pull 时历史混乱。
  2. 冲突解决只取一边：丢失逻辑，需理解合并。
  3. rebase 中断后新提交：混乱，先 abort 或完成当前。
  4. 强制推送覆盖他人：用 –force-with-lease 防呆。
  5. 丢失提交不会找：reflog 保留 90 天，快速救援。

最佳实践¶

  • 个人分支尽情 rebase，共享分支只用 merge。
  • 冲突解决保持”最小惊讶”：理解双方意图。
  • 参见 02-Git分支与合并 与 14-Git性能优化。
