25-Cyber启动系统详解

一个模块为什么起不来，往上追往往是启动链路这几步。mainboard、Init、launch/DAG、ClassLoader 到组件装配，顺着走一遍就清楚了。
📅 2026-10-26· 更新于 2026-10-26 · 5971 字 · 约 15 分钟 ✍ zeek.zhao #概念#apollo

一个模块为什么起不来，往上追往往就是启动链路这几步。本篇把 Cyber RT 从 mainboard 进程拉起到组件就绪这条线走一遍，目标很实际：下次遇到”模块起不来”，你能直接定位到是哪个环节。这是第四阶段 Cyber RT 深度剖析的开篇，接着 24-仿真平台与场景数据 往下。后面讲调度（26-Cyber调度系统详解）、时间（27-Cyber时间系统与定时器）、数据（29-Cyber数据系统详解）都压在它上面。组件的使用层 API 已在第二阶段 12-Cyber消息通信与组件开发 讲过，这里只看内部机制。

1. 启动分四层¶

Cyber RT 启动系统采用四层设计：

graph TD A[系统入口 mainboard] --> B[框架初始化层 cyber::Init] B --> C[模块加载层 ModuleController + ClassLoader] C --> D[组件创建层 Component::Initialize] D --> E[任务调度层 Scheduler] B --> B1[日志系统] B --> B2[GlobalData 全局状态] B --> B3[调度器初始化] C --> C1[launch/DAG 解析] C --> C2[dlopen 动态库] D --> D1[Node/Reader/Writer 创建] E --> E1[协程任务创建]

核心组件职责：

组件 源码位置 职责
mainboard cyber/mainboard/mainboard.cc 进程入口，解析命令行参数
ModuleController cyber/mainboard/module_controller.cc 驱动模块加载循环
ClassLoader cyber/class_loader/ dlopen/创建类实例
DagManager cyber/mainboard/dag_manager.cc 解析 DAG 配置
GlobalData cyber/common/global_data.cc 进程名、任务名、通道 ID 全局注册表

Cyber RT 是 Apollo 3.5（2019 年）引入的，专为自动驾驶设计的首个开源高性能运行时框架：组件依赖用 DAG 图组织，运行时生成轻量用户级任务，按优先级和资源可用性调度。GitHub 主分支已经走到 10.0/11.0 代际（公开 tag 止于 v9.0.0），启动链路的整体结构倒是一直没怎么变。

要点：

  1. GlobalData 是单例注册中心。进程名、任务名、通道名在这里注册成”字符串 → 64 位哈希 ID”，之后通信子系统只传 ID。
  2. InitScheduler 决定协程环境。本进程所有组件任务都跑在协程之上（见 26-Cyber调度系统详解）。
  3. 信号处理保证优雅关闭。SIGINT 触发后，框架按依赖逆序停组件。

4. launch 管进程，DAG 管组件¶

启动配置分两层：launch 文件（XML，进程级）→ DAG 文件（proto，组件级）。

4.1 launch 是 XML¶

  • <module>：一个待加载模块
  • <dag_conf>：DAG 配置路径
  • <process_name>：进程名，用于系统监控（cyber_monitor/Dreamview 显示）

4.2 DAG 描述数据拓扑¶

DAG 描述”这个进程里有哪些组件、各自订阅哪些通道”：

字段含义：

  • module_library：组件所在动态库（.so）路径
  • components：组件列表，一个进程可加载多个组件
  • readers：声明组件输入通道，框架据此自动创建 Reader 并装配数据链路

DAG 里的 readers 决定 DataVisitor 的配置，而 DataVisitor 的唤醒回调，正是调度器创建协程任务时的通知源。换句话说，DAG 是数据拓扑，调度配置（/apollo/cyber/conf/profilexxx.pb.txt）是执行拓扑，两者在任务名上对齐。

sequenceDiagram participant MC as ModuleController participant CL as ClassLoader participant C as Component participant N as Node participant S as Scheduler MC->>CL: CreateClassObj(class_name) CL-->>MC: 组件实例 MC->>C: Initialize(config) C->>N: new Node(name) C->>C: 用户 Init() C->>N: CreateReader × N C->>C: 构建 DataVisitor C->>S: CreateTask(factory, name) S-->>C: 协程就绪，等待数据唤醒

注意第 6 步：组件初始化完成后，Proc 并不会立即执行。它注册为协程，等第一条消息到达、经 DataVisitor 唤醒（详见 29-Cyber数据系统详解）。

7. 起不来时怎么查¶

7.1 四类错误¶

类别 典型原因 表现
配置错误 DAG 路径不存在、channel 缺失 ModuleController::Init 返回 false
库加载错误 .so 缺失、符号未定义、依赖库缺失 dlopen 失败日志
组件初始化错误 用户 Init() 返回 false Component Init() failed.
资源错误 内存不足、端口/共享内存冲突 各子系统创建失败

7.2 四条命令够用¶

几个常踩的坑也记一下。CLASS_LOADER_REGISTER_CLASS 忘写，或者写在匿名命名空间外被裁剪，会报 CreateClassObj failed。DAG 里 readers 的通道名跟上游 Writer 对不上，组件能起来但 Proc 永远不触发，用 cyber_channel hz 看数据到没到。一个进程加载多个组件时，组件名（Node 名）重复会引发 DataVisitor 注册冲突。

8. 启动慢就压这五处¶

启动时间的关键路径是：动态库加载 → 组件 Init → Reader/任务创建。可选优化：

  1. 并行加载：launch 中无依赖关系的模块并行启动（cyber_launch start 天然多进程并行）。
  2. 懒加载：重资源（模型、地图）延迟到首次使用时加载，缩短 Init 时间。
  3. 减少 .so 依赖链：依赖越深 dlopen 越慢，可用预链接/LTO 减小体积。
  4. 内存预分配：高频消息通道的对象池在 Init 期建好，避免运行期抖动。
  5. 依赖排序：DAG 之间有数据依赖的模块按拓扑序启动，避免上游未就绪导致下游空转重试。

要我先动一处，会选懒加载——模型、地图这类重资源搬出 Init，收益通常最直接。

9. 排障时顺着链路走¶

启动系统拆开就是五段：mainboard 进程壳、cyber::Init 基础设施、launch/DAG 配置、ClassLoader 插件机制、组件自动装配。Component::Initialize 是粘合剂，Node、Reader、DataVisitor、协程任务在这里一次建好。下次遇到启动失败，按这五段逐段排除，比到处猜快得多。协程任务被创建之后的世界，就是下一篇 26-Cyber调度系统详解 的主题。

代码示例与实现细节¶

下面这组代码片段进一步展开启动链路的细节：从框架初始化的完整流程、模块加载循环、配置层次，到错误处理与标准启动顺序。它们回答的是「每一层内部究竟怎么跑」。

1. cyber::Init 的进程组与信号处理¶

这段解决「初始化时除了调度器还装配了什么」的问题：设置进程名、计算进程组 ID、初始化调度器、注册优雅退出信号。

参数怎么调：process_group 来自工作根目录，同一车辆上不同模块应共享同一进程组以便统一调度；常见坑是 WorkRoot() 返回空导致 CHECK_NOTNULL 直接 abort，启动前必须确认工作目录环境变量已正确设置。

2. 模块加载循环¶

这段解决「launch/DAG 如何驱动模块逐个加载」的问题：解析命令行 → 加载 launch → 遍历 Module → 加载 DAG → ClassLoader 加载动态库 → 创建实例。

参数怎么调：模块加载顺序应按数据依赖拓扑排序；常见坑是上游模块未就绪就启动下游，导致下游 Reader 空转重试浪费 CPU。

3. 多模块 launch 配置¶

这段解决「一个 launch 如何同时拉起多个模块」的问题：列出 planning、perception、control 三个模块各自的 DAG 路径。

参数怎么调：process_name 会显示在 cyber_monitor 和 DreamView 中，取名要能一眼识别模块；常见坑是 DAG 路径写错（相对路径在不同工作目录下解析失败），建议统一用绝对路径或相对工作根目录的一致写法。

这段解决「launch、DAG、组件配置之间是什么关系」的问题：四层配置逐层细化，从模块列表一路到参数文件路径。

参数怎么调：调试时从顶层 launch 逐层向下核对；常见坑是只检查了 DAG 却忽略了组件引用的参数文件不存在，Init 阶段才会报加载失败。

5. 配置加载时序¶

这段解决「配置文件是如何被解析并校验的」的问题：MainBoard → ModuleController → DagManager → ProtobufLoader 的调用顺序。

6. 动态库加载流程¶

这段解决「ClassLoader 如何判断库是否已加载并创建实例」的问题：查找 → 加载 → 符号解析 → 类注册 → 实例创建。

参数怎么调：同一个 .so 只应加载一次，重复 dlopen 会造成静态变量重复注册；常见坑是不同模块引用同一库的不同版本，版本冲突检测缺失会导致符号解析到错误实现。

这段解决「启动失败时如何按类排查」的问题：把错误分为配置、库加载、组件初始化、资源四大类，每类再细分。

8. 错误诊断代码¶

这段解决「Init 失败时如何输出足够的诊断信息」的问题：打印组件名、类名，并 dump 详细信息。

参数怎么调：日志级别要设为 ERROR 以上确保这类信息落盘；常见坑是只打一句「init failed」而不带组件名，多个组件同时启动时根本定位不到是哪一个。

9. 启动重试与容错时序¶

这段解决「组件初始化失败后框架如何处理」的问题：记录错误、有限次重试、达到上限后标记失败并尝试启动其他组件。

参数怎么调：重试次数默认有限，别无限重试掩盖真实故障；常见坑是「降级模式」下关键组件被跳过却无人察觉，必须在监控里显式标记降级状态。

10. 标准启动顺序¶

这段解决「生产环境里模块按什么顺序启动」的问题：Dreamview → 车辆配置 → 定位 → 感知 → 预测 → 规划 → 控制。

注意事项与常见坑¶

  1. 注册宏忘写或位置错误：CLASS_LOADER_REGISTER_CLASS 忘写、写在匿名命名空间外被链接器裁剪，会报 CreateClassObj failed，组件根本无法实例化。
  2. DAG readers 通道名与上游不匹配：组件能起来但 Proc 永远不触发，必须用 cyber_channel hz 确认数据实际到达。
  3. Node 名重复：一个进程加载多个组件时组件名重复会引发 DataVisitor 注册冲突，导致后加载的组件工作异常。
  4. 工作根目录未设置：common::WorkRoot() 返回空会让 CHECK_NOTNULL 直接 abort，进程还没进 Init 就退出。
  5. DAG 路径用相对路径：不同工作目录下解析结果不同，导致「本地能起、车上起不来」，建议统一路径基准。
  6. 参数文件存在但语义错误：proto 格式正确却引用了不存在的参数文件路径，Init 阶段才失败，容易被误判为配置格式问题。
  7. 重复 dlopen 同一库：静态变量重复注册会导致类工厂里出现重复条目，行为不可预测，应保持「一库一 ClassLoader」。
  8. 不同版本同名库冲突：依赖库版本不一致会让符号解析到错误实现，启动看似成功但运行时崩溃。
  9. Reader 创建失败误判：往往是通道名冲突或共享内存不足，不是配置字段缺失，排查时要看资源层。
  10. 无限重试掩盖故障：启动重试次数应有限，无限重试会让真实配置错误长期潜伏。
  11. 降级状态无人察觉：关键组件在降级模式下被跳过必须在监控中显式标记，否则系统「半瘫」运行。
  12. 上游未就绪就启动下游：模块应按数据依赖拓扑排序启动，否则下游空转重试浪费 CPU 并拉长启动时间。
