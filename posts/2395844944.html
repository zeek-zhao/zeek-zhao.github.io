Linux网络子系统架构与数据包流程

网络子系统是内核里最复杂的部分之一，但它的入口其实很朴素——应用调用 socket，最后数据从网卡出去。我看这部分时习惯从一次 send() 一路往下追到驱动，追完一遍，socket、协议栈、net_device 这些名字就不再是孤立的名词。这篇按”是什么—怎么流动—怎么调优—怎么排查”的顺序，把这条链讲清楚。

网络子系统概述：套接字、协议、设备接口三层结构¶

Linux 网络子系统负责处理系统中所有网络通信相关的任务，包括网络协议实现、数据包的收发、网络设备的管理等。它是一个层次化的架构，大致可分为以下几层：

  1. 套接字接口层：为应用程序提供标准网络API
  2. 协议层：实现各种网络协议(TCP、UDP、IP等)
  3. 网络设备接口层：与物理网络设备交互

我一般先把这三层的边界记牢，排查问题时才不会在层间来回跳。

数据包处理：发送走封装，接收走软中断队列¶

发送和接收是两条完全不同的路径：一个逐层加头，一个中断入队后再由软中断分发。我踩过的坑是，接收路径上的软中断很容易被忽略，光盯着硬中断看不出丢包原因。

发送流程：逐层封装直到网卡¶

当应用程序通过socket发送数据时，数据包在内核中的处理流程如下：

核心组件：socket、协议栈与 net_device 三件套¶

三个组件各管一层：socket 面对应用，协议栈实现规则，net_device 抽象硬件。我觉得 socket/sock 这组结构是理解整个子系统的钥匙，先看它再看别的会省很多力。

1. 套接字层：应用与内核的接口¶

Socket是应用程序与网络子系统交互的主要接口，提供了一组标准API：

📝套接字API
  • socket() - 创建新的通信端点
  • bind() - 将套接字与地址关联
  • listen() - 开始监听连接
  • connect() - 建立连接
  • accept() - 接受连接请求
  • send()/recv() - 发送/接收数据
  • setsockopt() - 设置套接字选项

2. 协议层：完整的 TCP/IP 实现¶

TCP/IP 协议栈的分层

Linux实现了完整的TCP/IP协议栈，主要包括：

3. 网络设备接口层：用 net_device 统一设备¶

sk_buff：靠移动指针避免数据拷贝¶

Linux内核使用sk_buff (socket buffer)结构体来表示和管理网络数据包。我印象最深的是它靠挪 data/tail 指针加解协议头，几乎不搬动实际数据。

classDiagram class sk_buff { +struct sk_buff *next +struct sk_buff *prev +struct sock *sk +struct net_device *dev +unsigned int len +unsigned char *data +unsigned char *head +unsigned char *tail +unsigned char *end }

sk_buff 结构详解¶

sk_buff是一个非常复杂的结构，它通过指针的灵活移动，避免了数据的频繁拷贝：

  • head: 指向分配的内存块的开始
  • data: 指向实际数据的开始
  • tail: 指向实际数据的结束
  • end: 指向分配的内存块的结束

当数据包在不同协议层之间传递时，通过调整data和tail指针来添加或删除协议头部，而不需要移动实际的数据。

高级功能：命名空间、Netfilter 与流量控制¶

这三项功能都作用在协议栈的不同位置。我判断命名空间是容器网络隔离的起点，Netfilter 管的是包要不要过，TC 管的是包怎么排队发出去。

1. 网络命名空间：veth 对连接隔离协议栈¶

网络命名空间是Linux网络虚拟化的基础，允许创建相互隔离的网络栈实例：

2. Netfilter：五个挂钩点串起包过滤¶

Netfilter是Linux内核中的包过滤框架，为防火墙、NAT和包修改提供了挂钩点：

flowchart TD A[进入网络] --> B[PREROUTING] B --> C{路由决策} C -->|本地投递| D[INPUT] D --> E[本地进程] E --> F[OUTPUT] C -->|转发| G[FORWARD] G --> H[POSTROUTING] F --> H H --> I[发出网络] style B fill:#f9f,stroke:#333,stroke-width:2px style D fill:#f9f,stroke:#333,stroke-width:2px style F fill:#f9f,stroke:#333,stroke-width:2px style G fill:#f9f,stroke:#333,stroke-width:2px style H fill:#f9f,stroke:#333,stroke-width:2px

每个挂钩点都可以注册处理函数，执行如下操作：

  • NF_ACCEPT: 继续正常处理
  • NF_DROP: 丢弃数据包
  • NF_QUEUE: 将包发送到用户空间
  • NF_REPEAT: 再次调用hook函数
  • NF_STOLEN: 数据包被”偷走”，处理停止

性能优化：NAPI、零拷贝与多队列¶

这三项优化分别打在中断、拷贝和 CPU 扩展三个点上。我一般调网络性能时先看有没有中断风暴，再决定要不要动拷贝路径和队列绑定。

1. NAPI：中断加轮询抑制中断风暴¶

NAPI是一种混合中断驱动和轮询的数据包接收机制，有效减少高负载下的中断风暴：

🔥NAPI工作原理
  1. 当首个数据包到达时，触发中断
  2. 驱动禁用进一步的接收中断，并将自己添加到轮询列表
  3. 系统在适当时机对列表中的设备进行轮询，批量处理多个数据包
  4. 当没有更多数据包时，重新启用中断

2. 零拷贝：用引用传递替掉两次拷贝¶

零拷贝通过减少内核与用户空间之间的数据拷贝来提高性能：

3. 多队列网卡：RSS/XPS 配合多核扩展¶

现代网卡支持多个发送和接收队列，配合RSS(接收端扩展)和XPS(发送包分流)，可以在多核系统上实现更好的扩展性：

诊断工具：从 ping/tcpdump 到 eBPF 与 ftrace¶

基础工具¶

  • ping: 测试基本连通性

高级工具¶

  • conntrack: 连接跟踪工具
  • dropwatch: 监控内核丢包情况

内核调试¶

  • /proc/net/: 网络相关的proc文件
  • ftrace: 内核函数跟踪
  • kprobes: 动态插入探针点
