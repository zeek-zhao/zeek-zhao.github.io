OB-AI 工程管理总方案（树状版）

日常生效版本已模块化：入口 AI.md → 规则 90-OB工程管理/rules/ → skill 90-OB工程管理/skills/ → 模板 90-OB工程管理/模板/ → 主页 主页.md。本文件仅作总览背景（历史设计快照，路径以规则文档为准）。

版本：v1.0 | 日期：2026-10-24
定位：本工程是 给 AI 使用的生产线——AI 读入口、查规则、用模板、调 skill、走流水线。人是监督者与最终确认者。
核心思想：一个入口、三类资产、一条流水线。

0. 总方案（Master Plan）

三类资产：

资产类型 载体 归属仓库
内容资产 00~60 内容目录 ob-content（私有）
规则资产 AI.md、_ai/rules、90-模板、_ai/skills ob-content（私有，随内容同库）
代码资产 Hexo 站点工程 hexo-engine（可私有）

一条流水线：hexo-engine 定时/手动触发 → git 拉取 ob-content → 扫描每篇 md 的 frontmatter → published: true 且 status: published 者转换进入构建 → hexo generate → 产物推送到 username.github.io 主页仓库。

1. AI 总入口方案

方案：单一入口文件 + 指令路由表 + 执行留痕。

  • 位置：Vault 根目录 AI.md，配套 _ai/ 目录（规则、skill 的家）。
  • AI.md 结构固定为三段：
    1. 身份声明：你是本知识库的管理与写作助手，遵循 _ai/rules/ 下全部规范。
    2. 指令路由表：用户指令 → 处理流程 → 需读取的规则/skill/模板，一查即得。
    3. 执行记录：每次任务在 _ai/log/2026-10.md 追加一行（时间、指令、影响文件），保证可追溯。

路由表（AI.md 内核）：

用户指令 流程 依赖
“收一条信息” 按素材模板建文件 → 填 frontmatter → 存 50 区 tpl-material、metadata.md
“记一个灵感” 按灵感模板建文件 → 存 10 区 tpl-idea
“写文章” 从 ready 灵感或 used 素材建稿 → 30-永久笔记 tpl-article、md-format.md
“质检/准备发布” 走 quality-gate skill → 输出检查报告 skill: quality-gate
“发布” 质检通过后置 published:true → 推 git skill: publish-flow
“清 Inbox / 周回顾” 按流转规则逐条处理并汇报 rules/lifecycle.md

规则：任何 AI 任务必须先读 AI.md；AI 不得绕过路由表直接改内容；未覆盖的指令先补路由表再执行。

2. 目录管理方案

方案：生命周期前缀目录 + _ai 工作区 + 私密隔离区。

命名规则（_ai/rules/naming.md）：

类型 格式 示例
文章 YYYY-MM-DD-短横线英文slug.md 2026-10-24-ai-vault-setup.md
素材 YYYY-MM-DD-来源-标题.md 2026-10-24-rss-agent框架.md
灵感/笔记 主题-要点.md 发布流水线-双仓库方案.md
附件 assets/YYYY-MM-描述.扩展名 assets/2026-10-pipeline.png
  • 目录名含中文可，文件名 slug 用英文小写+连字符（URL 友好，Hexo permalink 干净）。
  • 禁止：空格、新建笔记、未命名、重名仅差序号。

3. 模板管理方案

方案：一份模板 = frontmatter 骨架 + 章节骨架 + AI 填写提示。 全部放 90-模板/，由 AI 入口按文档类型取用。

模板 适用文档 frontmatter 差异字段 章节骨架
tpl-article 要发布的文章 categories, description, cover, published, status 导入→观点→论证→总结→参考
tpl-news 新闻/资讯类 source, source_date, region(可选) 事实摘要→背景→影响→来源链接
tpl-idea 灵感 status: spark, topic 一句话想法→上下文→下一步
tpl-material 信息收集条目 source, note, status: collected 原文/要点→AI 提炼→关联选题
tpl-daily 日记 mood(可选) 今日完成→收获→明日计划
  • 模板内用 <!--AI: 提示语--> 注释告知 AI 每节怎么填、字段怎么取值。
  • 模板版本化管理：改动模板 = 改动生产标准，须在 _ai/log/ 留痕。

4. Skill 管理方案

方案：_ai/skills/ 目录，一个 skill 一个 md 文件，统一格式，带版本号。

skill 文件格式（固定五段）：

skill 清单（首批 6 个）：

skill 职责 触发指令
capture-classify Inbox 清洗、分类打标、提升/删除建议 “清 Inbox”
metadata-fill 补全/校验 frontmatter 必填字段 “补元数据”
quality-gate 发布门禁质检，PASS 才允许发布 “质检”
hexo-convert 发布格式转换（§8 预检用） “准备发布”
digest 周报：产出统计、管线状态、待办 “本周回顾”
publish-flow 发布操作：改状态 → git 推送 → 核对 Actions “发布”

管理规则：skill 只能被 AI.md 路由调用；改 skill 必须升 version 并留痕；skill 之间不互相调用，保持扁平。

5. 元数据字段管理规范

方案：三层字段模型 + 字段字典统一收口在 _ai/rules/02-metadata.md。

层 字段 说明
核心层（全类型必填） title, date, tags 最小元数据集
类型层（按文档类型） 素材: source/topic/status；文章: categories/description/cover；灵感: topic 见 §3 模板
发布层（仅 40 区成稿） status(draft/review/published), published(true/false), updated, permalink(可选) Hexo 消费依据

发布层字段字典（Hexo 判定核心）：

字段 取值 消费方
status draft → review → published Dataview 视图 + Hexo 过滤
published true/false Hexo 唯一发布开关
date / updated YYYY-MM-DD Hexo 排序与 sitemap
tags / categories 数组 Hexo 归档分类
description ≤120 字 Hexo SEO 摘要
cover assets 路径 Hexo 封面图

管理规则：新增字段必须先入字典并写明消费方，否则视为非法字段；字段值只能取枚举内的值；AI 每次写 frontmatter 后自校验。

6. MD 格式规范（OB + Hexo 双兼容）

方案：以 Hexo 能正确渲染为底线，以 OB 编辑体验为优先，冲突时用”约定写法”绕开。 收口在 _ai/rules/03-md-format.md。

事项 规范写法 原因
Frontmatter 必须是文件第一行起的合法 YAML，UTF-8 无 BOM Hexo gray-matter 解析的硬前提
站内链接 发布区（40）禁用 wikilink，一律 [文字](/perfmalink/) 标准链接；30 区内部笔记随意 Hexo 不识别 wikilink
图片 文章配图统一放 40-发布/assets/，正文用 /assets/xxx.png 绝对路径；Hexo 侧配置 root 对齐 双端路径一致，免转换
摘要截断 首段后加 <!-- more --> Hexo 首页摘要标准分隔符
嵌入 40 区禁用 Obsidian 嵌入语法 > [!warning] 未转换的 Obsidian 嵌入: xxx，引用其他笔记用链接 Hexo 不支持
数学/代码 代码块用标准 ``` 围栏；LaTeX 用 $...$（Hexo 装 mathjax/katex 插件） 双端兼容
HTML 允许少量内联 HTML（如 <figure>），禁止整页 HTML 保持 md 可读

一票否决项（发布预检 hexo-convert skill 检查）：frontmatter 不合法、含 wikilink、图片路径悬空、含 ![[ 嵌入。

7. 发布流水线方案（三仓库架构）

方案：内容与工程彻底分库，Hexo 工程库作为”装配车间”拉取内容库，主页库只放产物。

仓库 性质 内容 谁写入
ob-content 私有 Vault 全部内容 + 规则资产 AI/人（Obsidian Git 自动推）
hexo-engine 私有 Hexo 工程 + 转换脚本 + Actions 维护时手动改
username.github.io 公开 Hexo 构建产物（静态文件） 仅流水线写入

流水线（hexo-engine 仓库 .github/workflows/deploy.yml 要点）：

关键点：

  • 主页仓库 Pages 源设为其 main 分支；hexo-engine 需配 PAT（CONTENT_TOKEN 读内容库、PAGES_TOKEN 推主页库）。
  • Actions 失败开邮件通知；流水线幂等（每次全量重建），回滚 = revert ob-content 的发布 commit 或重跑旧 commit。

8. Hexo 消费端设计（转换脚本方案）

方案：一个 collect.js 脚本完成”识别 → 过滤 → 转换 → 落位”四步。

  • 脚本运行报告同时存为 artifact，供 AI（publish-flow skill）核对。
  • Hexo 侧配置对齐：permalink: :year/:month/:day/:slug/、post_asset_folder: false（统一用 assets 目录）、root 与 /assets/ 对齐。
  • 首页仓库只接收 public/ 产物，不带任何源码与私有内容；98-私人/ 因不在 40 区天然不会进入构建，且 .gitignore 双保险。
