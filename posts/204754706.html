Linux Kernel 调试详解

1. 内核调试概述：为什么它和用户态调试不是一回事¶

内核调试要解决的是「系统自己出了问题、而普通调试器插不上手」这类场景：驱动加载失败、系统无故重启、性能突然掉下来，或者进程在内核态卡死。我实际排查时一般先分清这是逻辑 Bug、性能问题还是崩溃现场，再决定用哪类工具——这一节的分法就是按这个来的。

调试 Linux 内核是内核开发和问题排查中的一项关键技能。由于内核的特殊运行环境（高权限、直接操作硬件、对稳定性要求极高），其调试方法与用户空间程序有显著不同。

1.1 五个典型场景¶

  • 内核 Bug 定位: 内核 Bug 可能导致系统不稳定、性能下降、数据损坏甚至系统崩溃 (Kernel Panic)。调试是找出这些 Bug 根源的必要手段。
  • 驱动开发与测试: 开发新的硬件驱动或修改现有驱动时，需要在内核环境中进行测试和调试，确保其正确性和稳定性。
  • 性能分析与优化: 定位内核中的性能瓶颈，例如调度延迟、内存分配效率低、I/O 性能差等，需要借助调试和跟踪工具。
  • 理解内核行为: 通过调试和跟踪，可以深入了解特定子系统（如内存管理、进程调度）的工作流程和内部机制。
  • 安全漏洞分析: 分析内核安全漏洞的成因和影响范围。

1.2 难点：Ring 0、不能停、并发与硬件耦合¶

  • 运行环境特殊: 内核运行在最高权限级别 (Ring 0)，一个小错误就可能导致整个系统崩溃。
  • 无法轻易停止: 不能像用户程序那样随意设置断点暂停整个内核，否则系统将完全失去响应。
  • 并发性高: 内核中存在大量并发执行的代码路径（中断处理、多核并行、内核线程），使得问题难以复现和定位。
  • 硬件交互复杂: 内核直接与硬件交互，问题可能源于硬件故障、固件 Bug 或驱动与硬件的交互时序问题。
  • 调试信息有限: 发生崩溃时，可获取的信息可能有限，需要专门的机制（如 kdump）来保存现场。
  • 工具链差异: 内核调试工具的使用方式和配置通常比用户空间工具更复杂。

1.3 六类方法：从日志打印到高级探测¶

根据介入方式和获取信息的不同，内核调试方法大致可分为：

  1. 日志打印 (Logging): 最简单直接的方法，通过在代码中插入打印语句输出信息。
    • 工具: printk, dump_stack, dev_dbg 等。
  2. 状态查看 (Status Inspection): 通过内核提供的接口查看内部状态和统计信息。
    • 工具: /proc 文件系统, /sys 文件系统。
  3. 动态追踪 (Dynamic Tracing): 在运行时动态地探测和记录内核事件、函数调用等，通常开销较低。
    • 工具: ftrace, perf, tracepoints, kprobes.
  4. 源码级调试 (Source-Level Debugging): 类似用户空间调试，可以设置断点、单步执行、查看变量等。
    • 工具: gdb + kgdb (串口/网络), gdb + QEMU (虚拟机)。
  5. 崩溃转储分析 (Crash Dump Analysis): 在系统崩溃后分析保存的内存转储文件，进行事后调试。
    • 工具: kdump, crash.
  6. 高级探测与分析 (Advanced Probing & Analysis): 使用更灵活、强大的脚本化或编程方式探测内核。
    • 工具: SystemTap, eBPF (BCC, bpftrace)。

2. 基础调试技术：printk 打点、调用栈与动态开关¶

最基础也最常用的是在代码里插打印语句，输出关键变量和执行路径。我一般用 dmesg -w 跟着日志看，比反复敲 dmesg 省事；%pS 这种带符号的打印在定位调用点时尤其顺手。

2.1 printk：日志级别、缓冲区与指针修饰符¶

printk 是内核中最基本、最常用的调试手段。它类似于用户空间的 printf，但有一些关键区别：

  • 日志级别 (Log Levels): printk 输出的信息带有日志级别，内核根据配置的控制台日志级别决定哪些信息会显示在控制台上。
  • 日志缓冲区 (Log Buffer): printk 的输出首先进入内核的环形日志缓冲区。
  • dmesg 命令: 用户空间可以使用 dmesg 命令查看和控制这个缓冲区的内容。
  • 使用场景:
    • 快速打印变量值、函数进入/退出点。
    • 在早期启动阶段或中断上下文中使用（但要注意锁和上下文限制）。
    • 作为其他复杂调试手段的基础。
  • 注意事项:
    • 性能影响: 大量或频繁的 printk 会显著影响系统性能，尤其是在中断上下文或持有锁时。
    • 缓冲区覆盖: 日志缓冲区大小有限，旧信息可能被新信息覆盖。
    • 死锁风险: 在某些持有锁的上下文中调用 printk 可能导致死锁（printk 内部可能尝试获取控制台锁）。printk_deferred 可以在某些情况下缓解。
    • 格式化字符串: 确保格式化字符串与参数类型匹配，否则可能导致崩溃或奇怪的输出。特别注意 %p 用于打印指针地址，内核有特殊的修饰符以提供更多信息：
      • %p: 普通指针地址 (通常会哈希处理，除非内核参数 printk.devkmsg=on)
      • %pS: 打印符号名称 + 偏移量 (例如 SyS_read+0x10/0x20)
      • %pF: 打印函数名 + 偏移量 (类似 %pS，但更侧重函数)
      • %pB: 打印 BPF 函数的符号名称 + 偏移量
      • %ps: 打印符号名称 (不带偏移量)
      • %pf: 打印函数名 (不带偏移量)
      • %p[fl]: 打印 struct file 的路径 (需要 CONFIG_CHECKPOINT_RESTORE)
      • %p[uv]: 打印 struct uvec
      • %p[ud]: 打印 struct user_namespace
      • %pI[46]: 打印 IPv4/IPv6 地址
      • %pM: 打印 MAC 地址
      • %p[ah]: 打印 struct address_space
      • %p[dn]: 打印 struct dentry 名称
      • 使用 %px 打印原始指针值 (不进行哈希处理)。
    • 日志速率限制 (Rate Limiting): 为避免日志风暴淹没缓冲区或影响性能，可以使用 printk_ratelimited() 或检查 printk_ratelimit() 的返回值。

2.2 dump_stack：把调用路径打出来¶

当需要知道代码是如何被调用到当前位置时，dump_stack() 非常有用。它会打印当前的内核调用栈信息到日志缓冲区。

🔥WARN_ON 和 BUG_ON
内核还提供了 WARN_ON(condition) 和 BUG_ON(condition) 宏。当 condition 为真时，它们会打印警告信息（包括调用栈），BUG_ON 还会导致内核 Panic（除非配置为仅警告）。它们是比 dump_stack() 更结构化的断言方式。

2.4 /proc 与 /sys：不用改代码的状态入口¶

这两个虚拟文件系统提供了大量关于内核状态、硬件信息、系统参数的接口。

  • /proc: 主要关注进程信息和一些遗留的系统信息。
    • /proc/<PID>/: 特定进程的信息 (状态 status, 内存映射 maps, 文件描述符 fd/, 命令行 cmdline 等)。
    • /proc/cpuinfo: CPU 信息。
    • /proc/meminfo: 内存使用情况。
    • /proc/interrupts: 中断统计。
    • /proc/slabinfo: Slab 分配器信息 (需要 CONFIG_SLAB 或 CONFIG_SLUB_DEBUG)。
    • /proc/modules: 已加载模块列表。
    • /proc/cmdline: 内核启动命令行参数。
    • /proc/kallsyms: 内核符号表 (地址和名称)。对于地址转换非常有用。
    • /proc/sched_debug: 调度器状态和运行队列信息。
    • /proc/vmstat: 虚拟内存统计信息。
  • /sys: 提供更结构化的设备和内核对象视图，与内核数据结构关系更紧密。
    • /sys/devices/: 系统中所有设备的层次结构。
    • /sys/class/: 按设备类别组织的符号链接 (如 net, block, gpio)。
    • /sys/bus/: 按总线类型组织的设备和驱动 (如 pci, usb, i2c)。
    • /sys/module/: 每个已加载模块的目录，包含参数、状态等。
    • /sys/kernel/debug/: debugfs 的挂载点，许多调试工具（如 ftrace, dynamic_debug）的接口都在这里。
    • /sys/kernel/tracing/: ftrace 的主要控制目录 (通常是 /sys/kernel/debug/tracing 的符号链接)。
  • 用途: 查看系统状态、硬件配置、内存/CPU使用情况、模块参数等，有时也可以通过写入这些文件来调整内核参数或触发某些操作。

3. 动态追踪：ftrace 看流程，perf 看热点¶

动态追踪允许在不修改内核代码、不重新编译的情况下观察内核行为，开销相对较低。我读函数图时一般先看 duration 那一列，哪一层耗时突然拉长，就先盯哪一层。

3.1 ftrace：function_graph 与事件追踪¶

ftrace 是内核内置的强大追踪框架，最初设计用于追踪函数调用，现已扩展到支持事件追踪、延迟分析等多种功能。

  • 主要功能:
    • 函数追踪 (function tracer): 记录内核函数的调用。
    • 函数图追踪 (function_graph tracer): 记录函数调用关系和执行时间，生成类似 C 代码的调用图。对于理解函数执行流程和定位耗时函数非常有用。
    • 延迟追踪 (latency tracers): 如 irqsoff (中断禁用时间), preemptoff (抢占禁用时间), wakeup (唤醒延迟), preemptirqsoff (抢占和中断都禁用)。用于分析实时性和调度延迟问题。
    • 事件追踪 (event tracing): 基于内核中静态定义的 tracepoints，追踪特定事件（如系统调用、调度、块 I/O、网络包收发等）。比函数追踪更精确、开销更低。
    • 动态探针 (kprobes/uprobes): 在任意内核/用户函数入口/返回点设置动态探针。ftrace 可以将 kprobes 作为事件源。
    • 快照 (snapshot): 保存当前追踪缓冲区内容，继续追踪。
  • 使用接口: 主要通过 debugfs 下的 tracing 目录进行配置和查看。
  • 优点: 内核内置，功能强大，接口相对统一，支持多种追踪场景。trace-cmd 提供了易用的命令行接口，kernelshark 提供了图形化分析界面。
  • 缺点: debugfs 接口手动操作繁琐。输出信息量可能很大，需要有效过滤。对于非常高频的事件，仍有性能开销。

3.2 perf：stat 看计数，record/report 找热点¶

perf 是一个强大的性能分析工具集，基于内核的 perf_events 子系统。它不仅可以用于性能分析，也可以用于事件追踪和调试。

  • 主要功能:
    • 性能计数器统计 (perf stat): 统计硬件/软件性能计数器（如 CPU 周期、指令数、缓存命中/缺失、分支预测失败、上下文切换、缺页中断等）。是快速评估程序或系统性能特征的首选工具。
    • 事件采样 (perf record / perf report): 对特定事件（如 CPU 周期、函数调用）进行采样，分析热点函数和代码路径。核心功能，用于定位性能瓶颈。
    • 事件追踪 (perf trace): 类似 strace，但基于 perf_events，可以追踪系统调用、调度事件等，开销更低。适合观察系统交互。
    • 动态探针 (perf probe): 定义 kprobes/uprobes。
    • 火焰图 (Flame Graphs): 结合 perf script 和 FlameGraph 工具生成可视化性能瓶颈图。
  • 使用示例:
  • 优点: 功能全面，覆盖统计、采样、追踪，适合性能分析和热点定位，社区活跃。与 ftrace 相比，更侧重性能分析和采样。
  • 缺点: 需要内核编译时开启 perf_events 相关选项。调用图生成 (-g) 可能需要调试信息 (vmlinux 或带 -g 编译的模块)，并且栈回溯方式（fp, dwarf, lbr）的选择和可靠性可能受内核配置和硬件影响。

3.3 底层机制：kprobes 灵活，tracepoints 稳定¶

ftrace, perf, SystemTap, eBPF 等许多高级工具都依赖于内核提供的底层探测机制：

  • kprobes (Kernel Probes):

    • 允许在几乎任何内核指令地址动态插入探测点。
    • 包括 kprobe (在函数入口或任意指令处)、kretprobe (在函数返回处) 和 jprobe (在函数入口处，可以无缝访问函数参数，但已被废弃，推荐使用 kprobe + regs)。
    • 优点: 极其灵活，可以探测未导出函数或函数内部。
    • 缺点: 依赖指令地址可能因内核版本或配置变化而失效；插入探针有一定开销；使用不当可能导致系统不稳定。
    • perf probe, SystemTap (部分), eBPF (kprobe 类型) 使用 kprobes。

  • tracepoints:

    • 内核代码中静态定义的探测点，位于关键逻辑路径上（如系统调用、调度器、网络栈、文件系统等）。
    • 提供稳定、低开销的 API。
    • 优点: API 稳定，开销低，语义清晰（知道在哪个逻辑点触发）。
    • 缺点: 探测点位置受限于内核开发者的预置，不能探测任意位置。
    • ftrace (事件追踪), perf (tracepoint 事件), SystemTap (部分), eBPF (tracepoint 类型) 使用 tracepoints。

选择: 如果有合适的 tracepoint，优先使用，因为它更稳定、开销更低。如果需要探测没有 tracepoint 的地方，或者需要函数内部信息，则使用 kprobes。

4. 源码级调试：gdb 借 kgdb 或 QEMU 打进内核¶

当需要深入代码逻辑、检查变量值、单步执行时，源码级调试是必要的。内核调试通常需要两台机器（或一台机器加虚拟机）配合。我搭 kgdb 时踩过的坑是 vmlinux 与目标机内核版本对不上——符号错位会直接让断点落不到预期位置。

4.1 kgdb：串口或网络把目标机交给 gdb¶

kgdb 是内核内置的调试代理，它允许通过串口或网络连接将目标机器（被调试内核）置于 gdb 的控制之下。

  • 工作原理:

    1. 目标机 (Target): 运行待调试的内核，开启 kgdb 支持。通过特定方式（如 SysRq、串口中断、专门的 kgdbwait 参数）进入调试模式，等待 gdb 连接。
    2. 开发机 (Host): 运行 gdb，加载带调试信息的内核镜像 (vmlinux)。通过串口线或网络连接到目标机的 kgdb 代理。
    3. 连接: gdb 通过调试协议 (GDB Remote Serial Protocol) 与 kgdb 通信，发送命令（设置断点、继续执行、查看内存等），kgdb 在目标机上执行这些命令并返回结果。

  • 配置内核: 需要开启以下内核选项：

    • CONFIG_KGDB=y
    • CONFIG_KGDB_SERIAL_CONSOLE=y (串口方式) 或 CONFIG_KGDB_KDB=y (网络方式需要 kdb)
    • CONFIG_DEBUG_INFO=y (生成调试信息)
    • CONFIG_FRAME_POINTER=y (可选，有助于生成更可靠的栈回溯)
    • CONFIG_MAGIC_SYSRQ=y (允许通过 SysRq 进入 kgdb)

  • 设置调试环境 (串口方式):

    1. 硬件: 需要一根 Null Modem 串口线连接开发机和目标机的串口。
    2. 目标机配置:
      • 在内核启动参数中指定 kgdboc=<串口设备>,<波特率>，例如 kgdboc=ttyS0,115200。
      • (可选) 添加 kgdbwait 参数，使内核在启动早期就进入 kgdb 等待连接。
    3. 开发机配置:
      • 确保串口设备权限正确。
      • 启动 gdb 并加载内核镜像：gdb /path/to/vmlinux
      • 在 gdb 中连接目标机：

  • 设置调试环境 (网络方式, kgdboe):

    • 需要内核开启 CONFIG_KGDB_ETH=y (较新内核) 或依赖 netconsole。
    • 目标机启动参数: kgdboe=<netdev>,<server-ip>:<port>[,<client-ip>]
    • 开发机 gdb 连接: target remote udp:<target-ip>:<port>
    • 网络方式配置相对复杂，串口更常用。

  • 进入调试模式:

    • kgdbwait: 内核启动时自动进入。
    • SysRq: 在目标机控制台按 Alt + SysRq + g (如果 Magic SysRq key 启用)。
    • 串口中断: 从开发机向目标机串口发送 BREAK 信号 (如 gdb 中 Ctrl+C，或 minicom 中 Ctrl+A F)。
    • 代码触发: 在内核代码中调用 kgdb_breakpoint()。

  • gdb 常用命令 (内核调试补充):

    • lx-symbols: 加载模块的符号信息 (在 gdb 中执行 add-symbol-file /path/to/module.ko <text_address>)。lx-symbols 命令（需要内核源码树中的 vmlinux-gdb.py 脚本支持）可以自动完成这个过程。
    • info threads: 查看所有 CPU 线程。
    • thread <N>: 切换到 CPU N 的上下文。
    • 访问 Per-CPU 变量: 需要知道变量地址和当前 CPU。p per_cpu(<variable>, <cpu_id>) (需要 vmlinux-gdb.py 脚本)。
    • break <module_name>:<function_name>: 在模块函数中设置断点 (需先加载符号)。
    • hbreak: 设置硬件断点 (数量有限，但通常更快)。
    • watch <expression>: 设置观察点 (watchpoint)，在表达式值改变时暂停 (硬件支持时效率较高)。
    • directory /path/to/source/code: 添加源代码搜索路径。
    • set logging on: 将 gdb 输出记录到文件 gdb.txt。

  • 调试内核模块:

    1. 确保模块编译时带有调试信息 (-g 选项，通常 Kbuild 会自动处理)。
    2. 加载模块到目标内核 (insmod)。
    3. 在 gdb 中，找到模块加载的基地址。可以通过查看 /sys/module/<module_name>/sections/.text 或在 dmesg 中查找模块加载信息。
    4. 使用 add-symbol-file /path/to/module.ko <text_section_address> 命令加载模块符号。<text_section_address> 是模块 .text 段在内核中的加载地址。
    5. 现在可以在模块代码中设置断点、查看变量等。
    6. (推荐) 使用内核源码树中的 vmlinux-gdb.py 脚本，它可以简化模块符号加载 (lx-symbols) 和 Per-CPU 变量访问。

  • 常见问题与提示:

    • 无法连接: 检查串口线 (Null Modem)、串口设备权限、波特率设置是否一致。检查目标机内核参数 (kgdboc) 是否正确。网络方式检查 IP 和端口。
    • 连接后无响应或卡死: 可能是 gdb 与目标内核版本不完全兼容。尝试更新 gdb 或使用目标系统发行版推荐的 gdb 版本。确保加载的 vmlinux 与目标运行的内核完全匹配。
    • 无法设置断点: 确认 vmlinux 包含调试信息 (CONFIG_DEBUG_INFO=y)。确认函数名拼写正确。对于模块函数，确保已使用 add-symbol-file 或 lx-symbols 加载符号。
    • 栈回溯 (bt) 不完整或错误: 确保内核编译时开启 CONFIG_FRAME_POINTER=y。尝试 bt full。

  • 优点: 功能强大，提供完整的源码级调试能力。

  • 缺点: 配置复杂，需要两台机器或特殊设置，目标机在调试期间完全停止响应。QEMU 方式相对简单但可能与真实硬件行为有差异。调试 I/O 密集型或对时序敏感的问题可能效果不佳。对于需要精确硬件交互的驱动调试可能不适用。

4.2 gdb + QEMU：一台机器上的源码级调试¶

使用 QEMU 虚拟机可以更方便地在单台机器上进行内核调试。QEMU 内置了 GDB Stub，可以将虚拟机的状态暴露给 gdb。

  • 工作原理:

    1. 目标机 (QEMU 虚拟机): 运行待调试的内核。启动 QEMU 时添加 -s (等同于 -gdb tcp::1234) 或 -gdb <device> 参数，使 QEMU 监听来自 gdb 的连接。添加 -S 参数使 QEMU 在启动时暂停，等待 gdb 连接后再开始执行。

4.3 JTAG：不依赖内核运行状态的最底层手段¶

对于非常底层的调试（如 Bootloader、早期启动代码、硬件相关问题），或者当 kgdb 无法使用时，可以使用 JTAG (Joint Test Action Group) 接口配合硬件调试器（如 OpenOCD, Lauterbach TRACE32）和 gdb 进行调试。这允许直接控制 CPU，访问内存和寄存器，独立于操作系统运行状态。

  • 优点: 最底层的调试能力，不依赖于内核运行状态。
  • 缺点: 需要专门的 JTAG 硬件调试器和目标硬件支持，配置复杂，价格昂贵。

5. 崩溃转储：kdump 留现场，crash 做事后复盘¶

当内核发生严重错误导致系统崩溃 (Panic) 时，如果配置了 kdump，系统可以在主内核崩溃后启动一个独立的、小型的“捕获内核”(Capture Kernel)，将主内核崩溃时的内存镜像保存到磁盘或网络。之后，可以使用 crash 工具对这个内存转储文件 (vmcore) 进行事后分析。我进 crash 后第一件事是敲 log，先把 Panic 消息和前面的警告读完，再看 bt。

5.1 kdump：预留内存启动捕获内核¶

  • 工作原理:

    1. 预留内存: 系统启动时，主内核会预留一小部分物理内存供捕获内核使用。
    2. 加载捕获内核: kdump 服务会将捕获内核镜像和 initramfs 加载到预留内存中。
    3. 崩溃触发: 当主内核发生 Panic 时，它会跳转到预加载的捕获内核入口点。
    4. 捕获内核启动: 捕获内核启动，它拥有自己独立的环境，不会使用主内核崩溃时的内存（除了读取）。
    5. 转储内存: 捕获内核通过 /proc/vmcore 接口访问主内核崩溃时的物理内存内容，并将其写入配置的目标位置（如本地文件系统 /var/crash 或通过 NFS/SSH 传输到远程服务器）。
    6. 重启: 转储完成后，系统通常会重启。

5.2 crash：从 vmcore 里还原崩溃现场¶

crash 是一个强大的交互式工具，用于分析 kdump 生成的 vmcore 文件或实时运行的内核。

  • 启动 crash:

    需要提供带调试信息的内核镜像 (vmlinux) 和 vmcore 文件。

  • 常用命令:

    • log 或 dmesg: 查看崩溃时的内核日志缓冲区。通常是分析的第一步！
    • bt: 查看崩溃时所有 CPU 上活动进程的调用栈 (backtrace)。bt -a 查看所有进程。bt <PID> 查看特定进程。
    • ps: 查看崩溃时的进程列表。
    • files <PID>: 查看特定进程打开的文件。
    • vm <PID>: 查看特定进程的内存映射信息 (VMA)。
    • struct <struct_name> <address>: 按结构体格式解析内存地址。例如 struct task_struct ffff88810abcde00。
    • rd <address> <count>: 读取内存 (read memory)。
    • wr <address> <value>: 写入内存 (write memory, 仅限实时内核，危险)。
    • sym <symbol_name>: 查看符号地址或名称。
    • kmem -i: 查看内存使用统计。
    • kmem -s <address>: 查看 Slab 缓存信息。
    • net: 查看网络相关信息 (socket, sk_buff)。
    • mod: 查看加载的模块信息。
    • help: 获取帮助。help <command> 查看特定命令帮助。
    • q: 退出。

  • 常用命令 (补充):

    • p <symbol_name>: 打印符号的值 (通常是地址)。
    • *<address>: 解引用地址，显示该地址处的值 (类似 C 的 *)。
    • struct <struct_name>.<member> <address>: 直接访问结构体成员。例如 struct task_struct.pid ffff88810abcde00。
    • list <address>: 反汇编指定地址周围的代码。list <function_name> 反汇编函数。
    • foreach bt: 显示所有进程的调用栈。
    • foreach ps: 显示所有进程信息。
    • timer: 查看定时器队列。
    • irq: 查看中断相关信息。
    • dev: 查看设备相关信息。
    • mount: 查看挂载的文件系统信息。
    • search <value>: 在内存中搜索特定值。
    • whatis <address_or_symbol>: 显示地址或符号所属的内存区域或数据结构类型。
    • extend /path/to/crash_extension.so: 加载 crash 扩展模块，提供额外命令（例如，特定驱动或子系统的分析命令）。许多内核子系统（如 drbd, lustre）提供自己的 crash 扩展。

  • 分析流程示例 (更详细):

    1. 启动 crash: crash vmlinux vmcore。
    2. 查看 Panic 信息和日志: log 或 dmesg。仔细阅读 Panic 消息、OOPS 信息以及之前的警告或错误。记录关键函数名、地址、错误码。
    3. 查看崩溃时的调用栈: bt。关注导致崩溃的 CPU 上的栈。如果栈不清晰或损坏，尝试 bt -f (强制回溯) 或 bt -F (使用 Frame Pointer)。
    4. 识别关键函数和地址: 从调用栈和日志中找出可疑的函数调用。使用 sym <address> 或 whatis <address> 确认地址对应的符号。
    5. 检查函数参数和局部变量: 切换到可疑的栈帧 (set <frame_number>)，使用 info args 和 info locals 查看参数和局部变量值 (需要调试信息)。如果不可用，尝试根据汇编代码和寄存器值 (bt -r) 手动推断。
    6. 检查相关数据结构: 使用 struct <name> <addr> 或 p <variable> 检查调用栈中涉及的关键数据结构（如 task_struct, sk_buff, inode 等）的内容。特别关注指针是否为 NULL 或无效地址 (如 0xdeadbeef)。
    7. 反汇编代码: 使用 list <function> 或 list <address> 查看崩溃点附近的汇编代码，结合源代码理解执行逻辑。
    8. 查看系统状态: 使用 ps, kmem -i, files, net, mount 等命令了解崩溃时的整体系统状态，判断是否与资源耗尽、特定进程行为等有关。
    9. 关联源代码: 打开内核源代码，对照 crash 中看到的信息，逐步跟踪代码逻辑，找出导致错误的条件。
    10. 迭代分析: 根据发现的信息，提出假设，然后使用 crash 命令进一步验证或排除假设。

  • 优点: 事后分析，不影响线上系统运行；可以全面检查崩溃时的内核状态。

  • 缺点: 需要预先配置 kdump；vmcore 文件可能很大；分析需要对内核有较深理解和经验。

6. 内存调试：开发用 KASAN，生产用 KFENCE¶

内存错误（如 use-after-free, buffer overflow）是内核中最常见和最危险的 Bug 之一。内核提供了多种工具来帮助检测这些问题。我一般开发和测试阶段直接上 KASAN，只有要看生产环境的低概率问题才换成 KFENCE。

6.1 KASAN：影子内存加插桩，检测最强¶

  • 原理: 基于编译时插桩技术，在内存访问指令（读、写）之前插入检查代码。它将内核内存映射区域划分为正常内存和影子内存 (shadow memory)。影子内存中的字节对应正常内存的状态（是否可用、是否已释放等）。访问内存时，检查影子内存以判断访问是否合法。
  • 检测能力: 可以检测 use-after-free, heap buffer overflow/underflow, stack buffer overflow, global buffer overflow, use-after-return, use-after-scope 等多种内存错误。
  • 类型:
    • Generic KASAN: 通用模式，支持 SLUB 和 SLAB 分配器。
    • Software Tag-Based KASAN: 利用 ARMv8.5 MTE (Memory Tagging Extension) 或 SPARC ADI (Application Data Integrity) 硬件特性，性能开销更低。
    • Hardware Tag-Based KASAN: 依赖硬件 MTE，开销最低。
  • 启用: 内核配置选项 CONFIG_KASAN=y，并选择 KASAN 类型。通常还需要关闭 CONFIG_SLAB 并使用 CONFIG_SLUB=y (对于 Generic KASAN)。
  • 优点: 检测能力强，报告详细（包含分配和释放时的调用栈）。
  • 缺点: 性能开销和内存开销较大（尤其是 Generic KASAN），通常只在调试版本中启用。

6.2 KFENCE：采样加保护页，开销极低¶

  • 原理: 一种低开销的内存安全错误检测器。它在 SLUB/SLAB 分配器的基础上，采样性地将部分内存分配请求重定向到一个特殊的内存区域。在这个区域中，每个分配的对象前后都放置了保护页 (guard pages)。访问这些保护页会触发 Page Fault。
  • 检测能力: 可以检测 use-after-free 和 buffer overflow/underflow。
  • 启用: 内核配置选项 CONFIG_KFENCE=y。
  • 优点: 性能开销和内存开销极低，可以用于生产环境，旨在捕获那些在常规测试中难以发现的低概率内存错误。
  • 缺点: 采样性质意味着它不能保证检测到所有错误，只检测被采样到的分配。报告信息可能不如 KASAN 详细。

6.3 SLUB/SLAB Debug：红区与 Poisoning¶

SLUB 和 SLAB 分配器自身也提供了一些调试选项，用于检测内存损坏和泄漏。

  • 启用: 通过内核配置选项 (CONFIG_SLUB_DEBUG=y, CONFIG_SLAB_DEBUG_OPTIONS=y) 或内核启动参数 (slub_debug, slab_flags)。
  • 功能:
    • Red zoning: 在对象前后添加红色区域，检测溢出。
    • Poisoning: 在分配和释放时用特定模式填充内存，检测 use-after-free 或未初始化使用。
    • Tracking: 跟踪对象的分配和释放调用栈，帮助定位内存泄漏。
  • 优点: 集成在内存分配器中，相对 KASAN 开销较低。
  • 缺点: 检测能力不如 KASAN 全面，可能需要手动检查日志或 /proc/slabinfo。

选择:

  • 对于开发和测试阶段，优先使用 KASAN 以获得最强的检测能力。
  • 对于生产环境或需要低开销检测，使用 KFENCE。
  • SLUB/SLAB Debug 可作为补充，或在无法使用 KASAN/KFENCE 时使用。

7. 高级探测：SystemTap 脚本化，eBPF 靠验证器兜底¶

这两个工具提供了更灵活、更强大的内核探测能力，允许用户编写脚本或程序来动态地分析和修改内核行为。我选型时通常先问一句：有没有现成的 tracepoint？有的话就不必上 kprobe。

7.1 SystemTap：.stp 脚本编译成模块¶

  • 工作原理: 用户编写 .stp 脚本，stap 工具将脚本编译成内核模块，加载到内核中执行探测和数据收集，然后卸载模块。它使用 kprobes 等机制来放置探针。

  • 优点: 脚本语言相对易学，可以方便地访问内核变量和数据结构，适合快速原型开发和特定问题分析。

  • 缺点: 需要内核编译时开启 CONFIG_DEBUG_INFO 和 CONFIG_KPROBES 等选项，并且通常需要安装对应的 kernel-debuginfo 包。编译脚本和加载模块有一定开销。安全性模型不如 eBPF 严格。

7.2 eBPF：验证器保安全，CO-RE 保可移植¶

  • 工作原理: eBPF 允许在内核中运行用户编写的、经过验证器 (Verifier) 检查以确保安全的字节码程序。这些程序可以在各种**钩子点 (Hook Points)**（如 tracepoints, kprobes, network events, perf events）触发执行，用于收集信息、修改行为等。
  • 生态系统:
    • BCC (BPF Compiler Collection): 提供 Python/Lua 等前端，简化 eBPF 程序的编写、加载和交互。包含大量实用的预制工具。
    • bpftrace: 提供类似 awk 或 dtrace 的高级追踪语言，用于快速编写 eBPF 追踪脚本。
    • libbpf + CO-RE: C 库 (libbpf) 结合 BTF (BPF Type Format) 调试信息，实现 **CO-RE (Compile Once - Run Everywhere)**。这是现代 eBPF 开发的主流方式，允许预编译的 eBPF 程序在不同内核版本上运行，大大提高了可移植性。
  • 优点:
    • 安全: 内核验证器确保 eBPF 程序不会导致内核崩溃或死循环。
    • 高效: JIT 编译器将 eBPF 字节码编译成本地机器码执行。
    • 灵活强大: 支持多种钩子点，可以通过 Maps 在内核和用户空间共享数据，甚至修改内核行为（如 XDP）。
    • 可移植性 (CO-RE): 使用 libbpf 和 BTF 可以编写一次，到处运行。
    • 社区活跃: 发展迅速，工具链和应用场景不断丰富。
  • 缺点: 学习曲线较陡峭（尤其是直接编写 C 程序或理解验证器规则），需要较新版本的内核支持。

  4. 验证修复: 修复问题后，使用之前的调试工具验证问题是否解决，性能是否恢复。

9. 环境搭建：虚拟机加串口和符号是标配¶

我自己的习惯是先在 QEMU 里把 console=ttyS0 配通，再谈别的调试手段——系统起不来的时候，串口往往是唯一能看到现场的地方。

  • 虚拟机是首选: 使用 VirtualBox, VMware 或 QEMU+KVM。可以方便地创建快照、克隆环境、进行破坏性实验，并且易于设置 gdb 调试。
  • 串口控制台: 即使不使用 kgdb，配置串口控制台（物理串口或虚拟机的模拟串口）也非常有用。当系统因图形驱动或网络问题无法访问时，串口通常是最后的救命稻草，可以看到内核启动日志和 Panic 信息。
    • QEMU: -nographic -serial mon:stdio
    • 内核参数: console=ttyS0,115200 (或相应的串口设备和波特率)
  • 调试符号: 始终保留与内核版本匹配的 vmlinux 文件（未压缩、带调试信息）。这是 gdb 和 crash 进行符号解析的基础。如果使用发行版内核，安装对应的 kernel-debuginfo 或 linux-image-*-dbg 包。
  • 源码访问: 方便地访问内核源代码，用于 gdb 调试时查看代码，或结合追踪工具理解执行流程。使用 ctags 或 cscope 为源码建立索引，可以快速跳转和查找。

10. 落地建议：从 dmesg 起步，按场景往上加工具¶

工具没有高低之分，只有合不合适：

  • 从简单的 printk 和 /proc, /sys 开始，了解基本信息。
  • 使用 ftrace 和 perf 进行动态追踪和性能分析，定位问题区域和瓶颈。
  • 当需要深入代码逻辑时，配置 gdb + kgdb/QEMU 进行源码级调试。
  • 配置 kdump 并在发生崩溃时使用 crash 进行事后分析。
  • 利用 KASAN, KFENCE 等工具检测内存错误。
  • 对于复杂或需要高度定制化的探测，学习使用 SystemTap 或 eBPF (BCC/bpftrace/libbpf)。
  • 参考 工具选择指南 选择最适合当前问题的工具。

下一步建议：挑一个能在 QEMU 里稳定复现的问题，按第 8 节的表从 printk 走到 ftrace，把这条链先跑通一遍；能复现、能观测，后面的工具才有意义。
