29-Cyber数据系统详解

剖析 Cyber RT 数据内幕：DataDispatcher 分发、CacheBuffer 环形缓存、DataNotifier 唤醒与 AllLatest 数据融合。
📅 2026-10-25· 更新于 2026-10-25 ✍ zeek.zhao #系统#apollo
ℹ️本节目标
深入消息从”到达本进程”到”触发组件回调”之间的内部机制：DataDispatcher、CacheBuffer、DataNotifier、DataVisitor 与数据融合策略，理解零拷贝与无锁设计如何支撑高吞吐。

本篇是第四阶段 Cyber RT 深度剖析的第五篇。第二阶段 12-消息通信与组件开发 讲的是使用层 API（怎么建 Writer/Reader、怎么发消息）；本篇聚焦框架内部——消息进来之后发生了什么。它与 26-Cyber调度系统详解 的唤醒链路是同一条故事的两侧。

1. 数据系统全景¶

一条消息的生命周期（本进程视角）可归纳为六步：

sequenceDiagram participant W as Writer participant TR as Transmitter participant RE as Receiver participant DD as DataDispatcher participant CB as CacheBuffer participant DN as DataNotifier participant DV as DataVisitor participant CR as 协程 W->>TR: 写入通道 TR->>RE: 传输（进程内引用/共享内存/网络） RE->>DD: 触发回调分发 DD->>CB: Fill 进每个订阅者的环形缓存 DD->>DN: Notify(channel_id) DN->>DV: 调用注册的唤醒回调 DV->>CB: TryFetch 取数据/融合 DV->>CR: 唤醒协程执行 Proc

设计目标：高吞吐、低延迟、灵活融合、无锁热路径、故障隔离。

2. DataVisitor：数据访问器¶

2.1 职责¶

DataVisitor 是”组件与数据系统”的接线员，构造时完成三件事（回看 25-Cyber启动系统详解 中组件 Initialize 第 5 步）：

  1. 向 DataDispatcher<M> 注册自己的 ChannelBuffer
  2. 向 DataNotifier 注册唤醒回调
  3. 多输入场景创建数据融合器

每种消息类型 M 对应一个 DataDispatcher<M> 单例，内部维护”通道 ID → 订阅者缓存列表”的原子哈希表：

关键设计：

  • std::shared_ptr<M> 贯穿全链：从 Receiver 到 CacheBuffer 到回调，传递的是同一个对象引用——这就是 Cyber 进程内”零拷贝”的真正实现层（真正的内存级零拷贝传输见 30-Cyber网络IO详解）
  • weak_ptr 存储订阅者：组件销毁后残留 buffer 自动失效，不阻塞分发
  • AtomicHashMap 使热路径免锁

4. CacheBuffer：环形缓存¶

每个”订阅者 × 通道”持有独立的 CacheBuffer，容量由 DAG 中的 queue_size/history_depth 决定：

环形缓存决定了组件”追不上时”丢的是旧数据——这是刻意为之的自动驾驶语义（处理最新观测比补历史更重要）。queue_size 过小会加剧多输入组件的数据对不齐，过大则放大内存与延迟。

5. DataNotifier：通知机制¶

DataNotifier 单例维护”通道 ID → Notifier 列表”，把分发器与具体的 DataVisitor 解耦：

6. 数据融合：AllLatest¶

多输入组件（如 Planning 同时吃预测/定位/底盘）依赖融合策略保证”取到一组互相匹配的数据”。

6.1 AllLatest 语义¶

以第一个通道的新消息为基准，搭配其余通道各自的最新消息：

graph LR A[通道A: 1, 2, 3, 4] --> C{AllLatest} B[通道B: a, b] --> C C --> D["输出: (1,null), (2,a), (3,a), (4,b)"]

6.2 实现¶

Fusion(index, m0, m1) 随后从融合缓存按游标取出成对数据。

📝精度边界
AllLatest 只保证”都尽量新”，不保证时间戳严格对齐。要求时间对齐的融合（如感知多传感器）需在业务层做时间窗口校验——结合 27-Cyber时间系统与定时器 的时间戳体系，以及 31-Cyber Transform与坐标变换 的时空插值。更复杂的策略（按时间戳配对）可仿照此模式自定义融合器。

7. 数据链路与调度器闭环¶

把本篇与调度篇串起来，一次完整的”消息→回调”闭环：

graph TB A[消息到达 Receiver] --> B[DataDispatcher.Dispatch] B --> C[CacheBuffer.Fill 共享指针入环形缓存] B --> D[DataNotifier.Notify] D --> E[Scheduler.NotifyProcessor task_id] E --> F[CRoutine SetUpdateFlag → READY] F --> G[Processor 取协程执行] G --> H[DataVisitor.TryFetch] H -- 无数据 --> I[协程进入 DATA_WAIT] H -- 有数据 --> J[组件 Proc 执行] J --> K[处理完成，协程再次等待]

8. 关键工程特性¶

  1. 无锁/低锁热路径：AtomicHashMap、AtomicRWLock、原子状态机将锁压缩到临界区极小的位置
  2. shared_ptr 全链传递：杜绝大消息拷贝；引用计数的原子性保证跨线程安全
  3. 每订阅者独立缓存：慢消费者只覆盖自己的旧数据，不拖累其他订阅者
  4. 通道 ID 体系：通道名经 GlobalData::RegisterChannel 哈希为 uint64，哈希表查找 O(1)

9. 常见问题诊断¶

现象 可能原因 排查
Proc 永不触发 通道名不匹配 / 上游未发布 / DataNotifier 未注册 cyber_channel hz 验证上游；cyber_node info 验证订阅
多输入组件频繁跳拍 下游消费慢，环形缓存覆盖旧数据 增大 queue_size；检查 Proc 耗时（SysMo）
多输入数据”对不齐” AllLatest 天然不对齐 业务层时间窗口校验
内存持续增长 shared_ptr 循环引用（回调捕获自身） 回调改捕获 weak_ptr
同名任务/通道冲突 哈希碰撞或重复注册 检查 DAG 中组件名唯一性
📝2026 年更新
Cyber RT 自 Apollo 3.5（2019）引入时即以 DAG 图组织组件依赖、运行时生成轻量任务、支持零拷贝消息通信；官方称 10.0 代际传输性能提升约 10 倍，其中进程内 shared_ptr 引用传递、进程间共享内存与无锁数据系统是主要贡献点。数据系统的六步链路与本文所述结构在 10.0/11.0 代际保持稳定。

10. 小结¶

数据系统 = 分发（DataDispatcher）+ 缓存（CacheBuffer 环形覆盖）+ 通知（DataNotifier）+ 访问/融合（DataVisitor + AllLatest） 四件套，以 shared_ptr 全链零拷贝为底色，以”满则覆盖旧数据”为默认 QoS。它向下通过 Notify 钩住调度器（26-Cyber调度系统详解），向上承接组件的 Reader/Proc（25-Cyber启动系统详解）；跨进程的那一程（Transmitter/Receiver 之下）则交给 30-Cyber网络IO详解。
