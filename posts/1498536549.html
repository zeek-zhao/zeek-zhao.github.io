接口

[!info] 本页概览
接口是 Go 实现多态与解耦的核心机制：鸭子类型——类型只要实现了接口的方法集，就自动满足该接口，无需显式声明。本文讲解接口定义、实现、类型断言、空接口与接口最佳实践。

核心概念

接口定义一组方法签名。隐式实现：任何类型只要拥有这些方法就自动满足接口，编译器负责检查。这让代码可以面向接口编程，与具体实现解耦。

接口定义与实现

类型断言

空接口 interface{} / any

空接口没有任何方法，所有类型都满足它，类似其他语言的 Object：

[!warning] 尽量少用空接口
any 丧失类型信息，需要断言才能使用，运行时开销与错误风险增加。明确类型优先，any 仅用于泛型边界、JSON 解析、日志参数等场景。

接口嵌套与组合

常见坑

  1. 接口的 nil 陷阱：var s *MyType = nil; var i Shape = s 后 i != nil 成立（接口包含类型信息）。判断前应明确是否可能传入 nil 指针。
  2. 值类型 vs 指针类型实现方法集：方法定义在 *T 上的类型，只有 *T 满足接口；T 不满足（值拷贝无法调用指针接收者方法）。var s Shape = Circle{} 若 Area 定义为 (c *Circle) 则编译失败。
  3. 接口太大（fat interface）：接口方法越多越难被实现，遵循”接口尽量小”（I 原则）。
  4. 对 any 类型值直接运算：x + 1 编译失败，必须先断言。
  5. 接口值比较：接口可比较（动态类型与值都相等），但包含 slice/map 等不可比较类型的接口会 panic。

最佳实践

  • 面向接口编程：函数参数用接口（如 io.Reader）而非具体类型，提高复用与可测试性。
  • 接口定义放在使用方：type Database interface { Save(x any) error } 由调用方声明需求。
  • 小接口组合成大接口；返回具体类型，接收接口参数。
  • 标准库是最好的范例：io.Reader、error、fmt.Stringer。
  • 用 errors.As 处理接口包装的错误链（见 08-错误处理）。
