评论系统与互动

[!abstract] 一句话：静态站点没有后端，评论系统的选型本质上是在回答一个问题——你愿意把读者的数据交给谁。

静态站为什么需要评论系统

Hexo 构建出的页面没有数据库，无法存储评论，所以评论能力必须由外部系统提供：要么是第三方托管服务（评论数据存在别人服务器上），要么是自己部署的轻后端（数据归自己）。选型前先想清楚三个约束：数据归属（读者留言算不算你的资产）、隐私合规（收集了哪些信息、要不要 Cookie）、维护成本（愿不愿意养一个后端服务）。

五大主流方案对比

方案 架构 数据存储 特点
Waline 服务端 + 数据库 自托管或 Vercel + 云数据库 功能全面，支持匿名评论与管理后台
Twikoo 轻量云函数 腾讯云 / Vercel / 私有部署 国内友好，部署简单，管理界面完善
Giscus 纯前端 GitHub Discussions 零后端，评论即 GitHub 讨论，需 GitHub 账号
Valine 纯前端 + LeanCloud LeanCloud 老牌方案，匿名评论，近年维护放缓
Artalk 自托管服务 自有服务器 支持多站点统一管理，适合多站作者

方案一：Giscus——极简派首选

Giscus 把评论存储在 GitHub Discussions 里，读者用 GitHub 账号登录评论，所有数据留在你的仓库中。配置步骤：仓库开启 Discussions → 安装 giscus App → 在 giscus.io 生成配置 → 主题里填入仓库信息：

优点是零成本零维护、数据绝对自有；缺点是要求评论者有 GitHub 账号，对非技术读者门槛偏高。技术博客受众恰好匹配，因此是当前技术圈最热门的选择。

方案二：Waline / Twikoo——通用受众

如果希望游客无需注册即可留言，Waline 与 Twikoo 是主力。两者都需要一个轻量后端：Waline 可一键部署到 Vercel 并配合免费云数据库（如 PlanetScale 的替代品、Supabase），Twikoo 则支持部署为云函数或 Docker 容器。以 Twikoo 的 Vercel 部署为例，主题配置只需填后端地址：

匿名评论是把双刃剑：降低门槛的同时带来垃圾评论风险，务必在后端开启管理员审核（先审后显）与频率限制。两者都提供管理面板，可回复、置顶、拉黑，体验接近传统论坛。

方案三：Artalk——多站点统一管理

拥有多个站点（博客、文档站、项目主页）的作者，Artalk 的多站点模式很实用：一个后端服务管所有站的评论，统一审核与通知。它以 Docker 单容器部署，配合 Nginx 反代即可上线：

方案四：Valine——了解即可

Valine 曾是最流行的无后端方案，基于 LeanCloud 存储，匿名即评。但近年来其数据接口被曝可被第三方读取、维护活跃度下降，新站不建议再选。如果老站仍在用，建议计划迁移至 Waline（兼容数据导入）。

[!warning] 隐私与数据归属
评论区收集的 IP、邮箱属于个人信息。托给第三方服务时，读者数据实际存在对方账户体系里；用 LeanCloud 这类平台时注意免费额度与接口公开性问题；自托管则要自己负责备份。原则：要么数据完全自有（自托管/Giscus），要么明确告知读者数据去向。GDPR 场景下还需在评论区声明 Cookie 使用情况。

互动增强：不止于评论

评论之外还有更多轻互动可以叠加：页面底部访客计数（不蒜子一行脚本接入 PV/UV）；文章点赞/表情反馈（部分主题内置，如 Butterfly 的 reactions）；分享按钮生成带文章卡片的社会化分享链接；邮件订阅或 RSS 承接不愿登录评论的读者。互动功能宜精不宜多，每加一个都是一次 HTTP 请求和一段 JS 开销——参考 13-性能优化与构建加速 的原则做取舍。

选型决策树

一句话总结：技术读者为主、追求零维护 → Giscus；希望游客可评、接受轻运维 → Twikoo 或 Waline；多站统一管理 → Artalk；数据敏感、合规要求高 → 自托管 Waline/Artalk + 审核机制。无论选哪个，都记得在上线后于自己的文章下留第一条评论，测试移动端与深色模式的表现。
