30-Cyber网络IO详解

解析 Cyber RT 传输层：进程内/共享内存/网络三路传输、epoll 异步 IO、服务发现与零拷贝优化。
📅 2026-10-25· 更新于 2026-10-25 ✍ zeek.zhao #系统#apollo
ℹ️本节目标
理解消息”跨出进程”之后的传输世界：Cyber RT 的三路传输选路逻辑、Receiver/Transmitter 抽象、基于 epoll 的异步 IO、服务发现机制与零拷贝优化手段。

本篇是第四阶段 Cyber RT 深度剖析的第六篇。29-Cyber数据系统详解 讲到消息抵达本进程 Receiver 后的旅程；本篇补全前半程——消息如何在进程间乃至跨机传输。它与调度优化共同支撑了 Cyber 的性能底盘。

1. 网络 IO 的定位¶

Cyber 的通信设计哲学是”按距离选传输“：

通信范围 传输方式 开销
同进程 shared_ptr 引用传递 零拷贝零系统调用
同主机跨进程 共享内存 + 通知 零数据拷贝，一次系统调用级通知
跨主机 UDP（RTPS/DDS 风格） 网络协议栈
graph LR subgraph 进程A W[Writer] --> T[Transmitter] end T -->|进程内| R1[Receiver] T -->|共享内存| R2[Receiver] T -->|UDP/网络| R3[Receiver 进程B]
📝2026 年更新
支持零拷贝消息通信是 Cyber RT（Apollo 3.5，2019 年引入）的核心卖点之一；官方称 10.0 代际传输性能提升约 10 倍。Apollo 10.0 起还打通了 ROS 软件生态，便于复用外部工具链。GitHub 主分支已演进至 10.0/11.0（公开 tag 止于 v9.0.0）。10.0 整体资源使用降低 50%、单 NVIDIA Orin 支撑 L4，传输层优化是重要贡献者。

2. 传输层架构¶

2.1 Transport 三件套¶

classDiagram class Transport { <<singleton>> +CreateTransmitter(desc) TransmitterPtr +CreateReceiver(desc) ReceiverPtr +Listen(ctx) int } class Transmitter~M~ { <<interface>> +Transmit(msg) bool #seq_num_ #qos_profile_ } class Receiver~M~ { <<interface>> -msg_callback_ +OnNewMessage(msg) } class HybridTransmitter~M~ class HybridReceiver~M~ Transport o-- Transmitter Transport o-- Receiver Transmitter <|-- HybridTransmitter Receiver <|-- HybridReceiver

源码目录：cyber/transport/。

  • Transmitter：发送端抽象，负责按通道序列化/分发
  • Receiver：接收端抽象，持有用户回调 msg_callback_，收到消息后触发——回调的下一站就是 29-Cyber数据系统详解 的 DataDispatcher
  • Hybrid 收发器：同时管理进程内/共享内存/RTPS 三条子通道，按对端注册情况动态选路

2.2 HybridTransmitter 的选路逻辑¶

发送时判断每个订阅者的通信方式：

flowchart TD A[Transmit msg] --> B{同进程订阅者?} B -- 是 --> C[直接调 Receiver 回调<br/>shared_ptr 引用传递] B --> D{同主机订阅者?} D -- 是 --> E[写共享内存段 + 发送通知] D --> F[有远端订阅者?] F -- 是 --> G[UDP 发送序列化数据] C --> H[统计与 QoS 处理] E --> H G --> H

选路依据来自服务发现（第 4 节）：框架启动时即监听全网的”谁订阅了什么”，Transmitter据此维护订阅者表。

3. Socket 与异步 IO¶

3.1 Socket 选型¶

类型 特点 用途
UDP Socket 无连接、低开销 传感器数据等高频消息跨机传输
TCP Socket 可靠、面向连接 服务发现、控制类关键消息
Unix Domain Socket 本机高效 本地辅助通信

传感器数据选择 UDP 的理由：频率高、容忍单帧丢失（有更重要的下一帧）、避免 TCP 队头阻塞——典型的自动驾驶 QoS 权衡。

3.2 epoll 事件驱动¶

Cyber 的监听线程基于 epoll 管理所有接收 socket：

特性：

  • 单线程管理大量连接：无需 per-connection 线程
  • 事件驱动零轮询：内核通知，空闲不耗 CPU
  • 读到的消息解码后交 Receiver::OnNewMessage → 进程内数据链路接管

3.3 通知机制：shmtx 与 notifier¶

共享内存传输需要”有新数据”的跨进程通知。Cyber 使用 Unix Domain Socket 通知对端（而非忙轮询）：

sequenceDiagram participant TA as 发送进程 Transmitter participant SHM as 共享内存段 participant NA as 通知 socket participant NB as 接收进程 notifier 监听 participant RB as 接收进程 Receiver TA->>SHM: 写入消息块（索引+数据） TA->>NA: notify(channel_id) 经 UDS NB->>NB: epoll 收到通知事件 NB->>RB: 触发 OnNewMessage RB->>SHM: 读共享内存，构造 shared_ptr

4. 服务发现¶

4.1 TopologyManager¶

跨进程通信的前提是互相知道对方存在。Cyber 用拓扑管理器实现无中心服务发现：

graph TD subgraph 进程A TA[TopologyManager A<br/>TopManager] end subgraph 进程B TB[TopologyManager B] end TA <-->|UDP 组播 + UDS| TB TA -.->|ChangeMsg: 订阅/退出| TB

组件：

  • Participant/Role：每个进程是一个 Participant，携带自身全部 Writer/Reader/Server 信息
  • Topology Change 通报：新 Writer/Reader 创建时广播消息，全网维护一致的拓扑视图
  • 定时心跳：处理进程崩溃，超时即从拓扑中摘除

每个 Transmitter/Receiver 收到拓扑变更后刷新自己的”对端表”——这就是第 2.2 节选路判断的数据来源。

4.2 服务（RPC）的注册与发现¶

Service/Client 模式在此基础上增加服务寻址：

sequenceDiagram participant S as 服务节点 participant TM as Topology participant C as 客户端节点 S->>TM: 注册 Server(service_name) C->>TM: 查询 service_name TM-->>C: 返回服务地址 C->>S: 经传输层发送请求 S-->>C: 返回响应

5. RPC 与 Service/Client¶

发布订阅之外，Cyber 提供请求-响应模式（使用层 API 见 12-消息通信与组件开发）。内部链路：

sequenceDiagram participant C as Client participant T as Transport participant S as Service C->>T: 序列化请求（异步发送） T->>S: 传输 S->>S: 解析 → 执行回调 S->>T: 序列化响应（携带 request_id） T->>C: 传输 C->>C: 按 request_id 匹配 pending future C-->>C: future 就绪，AsyncSendRequest 回调执行

特点：

  • 客户端异步为主：SendRequest 返回 future，不阻塞调用线程；同步封装只是 future.get()
  • 响应通过 request_id 关联，支持并发多请求

6. 零拷贝与传输优化¶

6.1 进程内：引用即零拷贝¶

同进程通信根本不过序列化——Writer::Write 的 shared_ptr 直接进入 29-Cyber数据系统详解 的数据链路。这是把高频组件（感知管线）放进同一进程的架构动机。

6.2 进程间：共享内存¶

大消息（点云、图像）跨进程走共享内存：

  1. 发送方将序列化数据写入共享内存块
  2. 通过 UDS 通知接收方（仅传”有新数据”信号，几十字节）
  3. 接收方 mmap 直接读取，构造对象

对比传统 socket 方案：省去两次内核态拷贝，大消息吞吐提升显著。代价是需要共享内存清理机制（进程崩溃残留段的回收）。

6.3 传输优化清单¶

手段 场景 收益
共享内存 同主机大消息 免内核拷贝
消息合并/批处理 高频小消息 摊薄每包开销
合理 history_depth/QoS 乱序容忍场景 丢旧保新降延迟
序列化复用 buffer 序列化热点 减少 malloc
核隔离 + 中断亲和 网卡软中断 降低抖动

7. 可靠性与错误处理¶

graph TD A[传输异常] --> B[对端崩溃<br/>心跳超时摘除拓扑] A --> C[消息丢失 UDP<br/>依赖下一帧 + 上层重试] A --> D[共享内存残留<br/>启动时清理 + 引用计数回收] A --> E[序列化错误<br/>丢弃该消息并计数告警]

实践要点：

  • 跨机链路默认 UDP + best-effort；需要可靠性的消息（如控制指令）应在业务层做确认或走 TCP/服务
  • 监控丢包计数（cyber_monitor 可见），异常增长说明带宽或订阅端处理能力不足
  • 共享内存目录（/dev/shm/apollo 或 CYBER 环境变量指定）异常时删除残留段再启动

8. 调试与观测¶

🔥跨进程不通的排查顺序
  1. 两端是否都完成了 cyber::Init（拓扑注册依赖它）
  2. cyber_node info 看对端 Writer/Reader 是否出现在拓扑里——不在则是发现层问题（组播/防火墙）
  3. 在拓扑里但无数据 → 检查共享内存权限与残留段
  4. 跨机不通 → 检查 UDP 组播配置与网卡多播路由

9. 小结¶

Cyber 网络层 = 按距离选传输（进程内引用 / 同机共享内存 / 跨机 UDP）+ epoll 事件驱动 + 拓扑式服务发现 + 异步 RPC。它把”在哪传、怎么传”完全下沉到框架，用户只见通道名；而零拷贝的三层实现（进程内引用传递、共享内存、序列化复用）配合 29-Cyber数据系统详解 的无锁数据链路与 26-Cyber调度系统详解 的编排调度，共同构成 Cyber 性能叙事的完整闭环。坐标变换类数据如何被消费，见下一篇 31-Cyber Transform与坐标变换。
