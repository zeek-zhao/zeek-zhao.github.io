Change 生命周期与 refs 规范

Change 有明确的状态机，评审中的提交则存放在特殊 refs 下——这两件事不清楚，CI 和自动化就无从谈起。接着上一篇 06-Code-Review-全流程 走完一遍评审，下面把内部机制捋一遍。

Change 只有 NEW、MERGED、ABANDONED 三种状态¶

一图看懂：Change 只有 NEW、MERGED、ABANDONED 三种状态。

stateDiagram-v2 [*] --> NEW NEW --> MERGED: 评审通过 submit NEW --> ABANDONED: 放弃 ABANDONED --> NEW: 重新激活 MERGED --> [*] ABANDONED --> [*]

REST API 查状态：

评审中的代码藏在 refs/changes 下¶

refs 含义
refs/heads/* 真实分支（合入后）
refs/for/* 评审入口（push 目标）
refs/changes/NN/xxxx/P 评审中的补丁集：NN=编号后两位，xxxx=Change 号，P=补丁序号
refs/meta/* 元数据（reviewnotes、drafts）
refs/tags/* 标签

比如 Change 12345 的 PatchSet 3 对应 refs/changes/45/12345/3，Jenkins/CI 靠这个 ref 精确检出（见 09-与Jenkins集成-Trigger与验证任务）。我一般把「后两位 + Change 号 + 补丁序号」这套记牢，检出脚本写错一位就会 fetch 失败。

用 refs/changes 精确检出某个补丁¶

提交信息按前缀写，changelog 才能自动生成¶

前缀 场景
feat 新功能
fix 修复
docs 文档
style 格式
refactor 重构
test 测试
chore 杂项

信息一致才能自动生成 changelog，CI 也能按前缀分流（比如 docs: 跳过测试）。我基本按 feat/fix/docs 这套前缀写，团队不必再为「这算新功能还是修复」扯皮。

hook 自动补 Change-Id，继续改就用 amend¶

Gerrit 首页 Download 提供 commit-msg hook：

hook 会在提交时自动补 Change-Id。同一逻辑继续修改用 --amend 保持 Change-Id，新逻辑新提交则自动生成新 Change-Id。

依赖链能拆就拆，别堆太长¶

相关 Change 可以关联依赖：

依赖链过长会让合入变难（要按序提交），能拆就拆；大规模重构我习惯用 topic（git push origin HEAD:refs/for/main%topic=refactor-auth）把多个 Change 归组评审。用 Hook 与事件自动响应的做法接着看 08-Hook与事件。
