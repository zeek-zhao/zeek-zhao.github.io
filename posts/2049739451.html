60-Audio模块与扩展开发

发表于2026-10-25|apollo
|浏览量:

[!info] 本节目标
剖析 Apollo 中较小众但极具教学价值的 Audio 模块（Apollo 6.0 新增）：整体结构、数据流、三大核心算法，并以它为范本讲清”在 Apollo 中开发一个自己的模块”的通用模式。运行时框架背景见 58-自动驾驶运行时框架对比，学习资源见 59-自动驾驶学习资源与链接。

1. 模块概述

Audio 模块通过麦克风阵列”听”道路环境，检测紧急车辆（警车、救护车、消防车的警笛声），并判断其移动方向与大致方位。它为自动驾驶增加了一个视觉/雷达之外的感知维度：

  • 360° 全方位：声音可绕过障碍物，感知视线之外的目标
  • 不受光照限制：夜间、雨雾照常工作
  • 成本极低：麦克风阵列远便宜于激光雷达
  • 早期预警：可在视觉系统发现目标之前先”听见”它

当前实现的约束：仅支持单个紧急车辆、要求环境风速 < 20mph（约 32 km/h）、距离估计基于固定假设距离（10m）。

3. 硬件与数据采集

使用 ReSpeaker 四麦环形麦克风阵列（USB 接入，支持 360° 声源定位与波束成形）。采集参数：

参数 值
采样率 16000 Hz
位深 16 bit
通道数 4
帧长 0.075 s（1200 点/帧）
帧间隔 0.02 s

驱动位于 modules/drivers/microphone/，输出标准 AudioData 消息（header + sample_rate + num_channels + data）。注意加载 ReSpeaker→IMU 的外参文件，用于把声学方位转换到自车坐标系。

4. 三大核心子模块

4.1 SirenDetection：警笛识别（深度学习）

基于 CNN 的音频二分类器（PyTorch 训练、LibTorch C++ 推理，呼应 51-深度学习基础与CNN 与 52-PyTorch与自动驾驶实践）：

  • 输入：4 通道 × 4.5 秒音频（4×1×72000）
  • 结构：卷积-池化 ×3 → 全连接 ×2 → Softmax 输出 2 类
  • 结果融合：4 个通道各自推理后投票表决，正样本总得分高于负样本即判定为警笛

4.2 MovingDetection：接近/远离判断（信号处理）

利用两个物理现象：多普勒效应（接近→主频率升高）与强度衰减（接近→能量增大）。流程：FFT → 提取总能量与主频率 → 保留最近 10 帧滑动窗口 → 优先按强度判断、强度不明显时按频率判断 → 4 通道投票（≥2 票一致才输出，否则 UNKNOWN）。

4.3 DirectionDetection：声源定位（GCC-PHAT）

基于 TDOA（到达时间差）：对每对麦克风做广义互相关-相位变换（GCC-PHAT），求得时延 τ，再由 θ = asin(τ·c / d)（c 为声速，d 为麦间距 0.065m）得到方向角，两对麦克风结果取平均；最后乘外参矩阵转换到 IMU 坐标系，并假设 10m 距离生成 3D 位置。

GCC-PHAT 的相位归一化使其对噪声与混响更鲁棒，是声源定位的经典算法。

5. 调试工具

工具 用途
AudioSaver 订阅 AudioData，把麦克风数据存为 WAV 文件
AudioOfflineProcessing 读取 WAV，离线跑三大子模块，用于算法调试与回归

“在线录包 + 离线重放”是 Apollo 模块开发的通用调试范式——先让算法在离线数据上正确，再接入实时链路。

6. 照此模式开发你自己的模块

Audio 模块虽小，却完整展示了 Apollo 模块开发的五步范式：

  1. 定义 proto：在 modules/<你的模块>/proto/ 定义输入/输出消息（如 AudioDetection），并注册到 modules/common_proto 或相应 proto 集合
  2. 写 Component：继承 cyber::Component<InputMsg>，Init() 中创建 Reader/Writer、加载配置与模型；Proc() 中调用处理逻辑。DAG 文件（dag/*.dag）声明订阅的 channel 与配置路径，launch 文件负责启动
  3. 分层解耦算法：把”模型推理”（可复用训练侧 PyTorch 权重导出的 LibTorch/ONNX 模型）与”信号处理规则”拆成独立类，Component 只做编排——便于单测与离线回归
  4. 配置外置：路径、阈值、topic 名全部放 conf/，不硬编码
  5. 配套工具：提供录制与离线处理工具，先离线验证再上车

检查清单：proto 编译通过 → DAG 装配正确 → cyber_monitor 能看到输出 topic → DreamView 可视化（如适用）→ 单元测试 + 数据回放回归。

[!tip] 扩展方向
给 Audio 模块做二次开发的自然方向：多紧急车辆同时检测、风噪自适应抑制、基于声强衰减的真实距离估计、与视觉感知的结果融合（声音预警 → 视觉确认）。工程上也可以把 LibTorch 推理替换为 ONNX Runtime/TensorRT，与其他感知模块统一推理栈（部署链路见 52-PyTorch与自动驾驶实践）。

7. 局限与展望

当前局限：单目标、高噪音环境性能下降、距离估计为固定假设、方位精度低于视觉/激光雷达。

改进方向：多目标检测与分类（区分警笛类型）、多麦克风阵列精化定位、音-视-雷达多模态融合、与 Planning 联动自动避让、利用环境声纹辅助自定位。

8. 小结

  • Audio = “听见”紧急车辆：CNN 警笛识别 + 多普勒/能量移动判断 + GCC-PHAT 声源定位
  • 四麦 ReSpeaker、16kHz/4 通道，LibTorch C++ 推理，多通道投票提升鲁棒性
  • 它是 Apollo 模块开发的完美教学范本：proto → Component → DAG → conf → 工具五件套
  • 照此模式即可开发自己的感知/决策模块，这也是本教程 Cyber RT 系列的收官方法论
