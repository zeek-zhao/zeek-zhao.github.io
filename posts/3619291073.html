网络编程这块我最早是把 socket、bind、listen 这些函数背下来，结果一遇到粘包、TIME_WAIT 就懵。后来改成盯住「字节流怎么变成一条消息、一个连接怎么被高效管理」这两条线，代码就顺了。下面从地址结构讲到 TCP/UDP、I/O 多路复用、并发架构和排障，示例都是能直接编译的 C 代码。

1. 网络编程：C/S 模型与套接字是核心抽象¶

我先把客户端-服务器模型和套接字这两个抽象搞清楚，后面所有 API 都只是围绕它们做文章。网络编程说到底就是让两台机器上的进程按约定格式交换数据。

1.1 网络编程的意义与应用¶

网络编程是指编写在计算机网络上运行的程序的过程，它使不同计算机之间能够通信和交换数据。在当今互联网时代，网络编程的重要性不言而喻：

  • 分布式系统：支持跨地域、跨设备的协同工作
  • 客户端-服务器应用：从Web服务到数据库访问
  • 实时通信：聊天、视频会议、在线游戏
  • 物联网应用：设备间的数据交换和控制
  • 云计算基础设施：资源调度、数据传输、服务发现

Linux作为服务器领域的主导操作系统，其网络编程接口直接影响了现代互联网基础设施的构建方式。

1.2 Linux网络编程的特点¶

Linux网络编程具有以下显著特点：

  1. POSIX兼容性：遵循POSIX标准，与其他UNIX系统具有良好的兼容性
  2. 开放源代码：可以深入理解底层实现机制
  3. 丰富的工具链：提供全面的开发、调试和性能分析工具
  4. 高效的I/O模型：支持多种I/O模型，包括阻塞I/O、非阻塞I/O、I/O多路复用和异步I/O
  5. 强大的扩展性：从嵌入式系统到超级计算机，适应各种规模需求
  6. 活跃的社区支持：丰富的文档、示例和第三方库

1.3 网络编程中的核心概念¶

1.3.1 客户端-服务器模型

大多数网络应用遵循客户端-服务器(C/S)架构：

  • **服务器(Server)**：提供服务，被动等待客户端连接
  • **客户端(Client)**：主动发起连接，请求服务
  • 通信过程：请求-响应模式，遵循特定应用层协议

1.3.2 套接字(Socket)

套接字是网络通信的端点，是应用程序与传输层协议的接口：

  • 本质：文件描述符，可使用标准I/O操作
  • 地址：由IP地址和端口号组成
  • 类型：
    • 流套接字(SOCK_STREAM)：基于TCP，提供可靠连接
    • 数据报套接字(SOCK_DGRAM)：基于UDP，无连接
    • 原始套接字(SOCK_RAW)：直接访问IP层

1.3.3 协议栈与封装

网络通信通过协议栈处理数据：

  • 应用层：定义应用程序间通信格式和规则
  • 传输层：端到端连接控制和数据流管理
  • 网络层：负责寻址和路由
  • 链路层：处理物理传输细节

网络编程主要关注应用层和传输层的交互，通过套接字API间接操作整个协议栈。

3. TCP 编程：可靠字节流与连接生命周期¶

TCP 的可靠是靠握手、确认、重传换来的，我调试连接问题时几乎都会先确认三次握手和四次挥手走到了哪一步。

3.1 TCP协议特性¶

TCP(传输控制协议)是一种面向连接的、可靠的、基于字节流的传输层通信协议。它的主要特性包括：

  1. 面向连接：通信前建立连接，通信后释放连接
  2. 可靠传输：使用确认、重传、序列号等机制保证数据可靠到达
  3. 流量控制：通过滑动窗口机制防止发送方速度过快导致接收方缓冲区溢出
  4. 拥塞控制：动态调整传输速率，避免网络拥塞
  5. 全双工通信：双向同时传输数据
  6. 字节流服务：数据无边界，应用程序负责定义消息边界

这些特性使TCP适合用于需要可靠数据传输的应用，如网页访问、邮件传输、文件传输等。

3.2 TCP连接的生命周期¶

3.2.1 建立连接(三次握手)

TCP连接建立过程：

  1. 客户端发送SYN：设置SYN标志，发送初始序列号x
  2. 服务器回复SYN+ACK：设置SYN和ACK标志，发送初始序列号y和确认号x+1
  3. 客户端发送ACK：设置ACK标志，发送确认号y+1

这个过程确保双方都能发送和接收数据。

3.2.2 数据传输

建立连接后，双方可以自由交换数据：

  • 数据被分割成多个TCP段
  • 每个TCP段有序列号和确认号
  • 接收方发送确认
  • 超时后重传未确认的段

3.2.3 连接终止(四次挥手)

TCP连接终止过程：

  1. 主动方发送FIN：表示不再发送数据
  2. 被动方回复ACK：确认收到FIN
  3. 被动方发送FIN：表示自己也不再发送数据
  4. 主动方回复ACK：确认收到FIN

主动关闭方在发送最后的ACK后，通常会等待2MSL(最大报文段生存期)时间，然后才真正关闭连接，这种状态称为TIME_WAIT。

4. UDP 编程：无连接数据报与可靠性的取舍¶

UDP 省掉了连接和重传，代价是顺序和到达都不保证，我用它跑实时流量时，会自己在应用层补序列号和分片。

4.1 UDP协议特性¶

UDP(用户数据报协议)是一种无连接的传输层协议，其主要特性包括：

  1. 无连接：不需要建立连接，直接发送数据
  2. 不可靠传输：不保证数据包可靠到达，无重传机制
  3. 无序：数据包到达顺序可能和发送顺序不同
  4. 无流量控制和拥塞控制：不限制发送速率
  5. 数据报服务：保留消息边界，每个发送操作对应一个接收操作
  6. 低开销：头部简单，只有8个字节

这些特性使UDP适合用于对实时性要求高、能容忍一定丢包的应用，如视频流、在线游戏、DNS查询等。

4.2 UDP服务器模型¶

UDP服务器的基本步骤：

  1. 创建UDP套接字：socket(AF_INET, SOCK_DGRAM, 0)
  2. 绑定地址：bind()
  3. 接收和发送数据报：recvfrom()/sendto()
  4. 关闭套接字：close()

UDP服务器无需listen()和accept()调用，因为UDP是无连接的。

5. I/O 多路复用：select、poll 到 epoll 的演进¶

高并发服务器上我基本只用 epoll，select 的描述符上限和每次全量拷贝的开销，在连接上千之后就很明显了。

5.1 I/O模型概述¶

Linux支持五种I/O模型：

  1. 阻塞I/O：默认模式，操作被阻塞直到完成
  2. 非阻塞I/O：操作立即返回，无论是否完成
  3. I/O多路复用：单线程监视多个文件描述符
  4. 信号驱动I/O：通过信号通知I/O事件
  5. 异步I/O：操作完全在后台进行，完成时通知

各模型比较：

模型 优点 缺点 适用场景
阻塞I/O 简单直观 效率低下 简单应用
非阻塞I/O 不会阻塞线程 需要轮询，消耗CPU 特定场景下的低延迟要求
I/O多路复用 单线程处理多连接 系统调用开销 高并发服务器
信号驱动I/O 无需轮询 信号处理复杂 特定场景
异步I/O 完全非阻塞，效率高 编程复杂 高性能应用

select是最传统的I/O多路复用函数，可以监视多个文件描述符的读、写和异常事件：

5.5.1 水平触发vs边缘触发

epoll提供两种事件通知模式：

  • **水平触发(Level-Triggered, LT)**：只要文件描述符准备就绪，每次epoll_wait都会通知

    • 默认模式，类似select/poll行为
    • 更容易编程，容错性高
    • 可能导致重复通知

  • **边缘触发(Edge-Triggered, ET)**：只有状态变化时才通知

    • 更高效，减少重复通知
    • 必须一次性处理所有数据（通常使用非阻塞I/O）
    • 编程复杂度高，但性能更好

6. 并发架构：Reactor、线程池与零拷贝¶

模式选对了，性能问题往往少一半，事件驱动管连接、线程池算业务、零拷贝搬数据，这三件事我一般分开设计。

6.1 Reactor模式¶

Reactor模式是一种事件驱动的设计模式，用于处理并发服务请求：

  1. 主要组件：

    • **事件反应器(Reactor)**：管理事件源，分发事件给适当的处理器
    • **事件处理器(Event Handler)**：处理特定类型事件的接口
    • 具体事件处理器：处理特定服务请求
    • **事件源(Event Source)**：产生事件的对象(如I/O通道)

  2. 工作流程：

    • 应用程序注册事件处理器
    • 事件反应器等待事件
    • 事件发生时，反应器调用相应的处理器

  3. 实现方式：使用select, poll或epoll监听多个文件描述符

简化的Reactor模式实现：

6.2 Proactor模式¶

Proactor模式是一种异步I/O模式，针对读取、写入等I/O操作：

  1. 主要组件：

    • Proactor：异步I/O的调度者
    • Completion Handler：处理异步操作完成事件
    • Asynchronous Operation：异步I/O操作
    • Completion Event Queue：完成事件队列

  2. 和Reactor的区别：

    • Reactor是同步I/O模型（等待就绪）
    • Proactor是异步I/O模型（等待完成）

  3. 在Linux上实现：使用原生AIO库或通过线程池模拟

  5. 传输协议特性：TCP(可靠, 有序, 面向连接), UDP(无连接, 不可靠, 高效)
  6. 网络应用架构：客户端-服务器, P2P, 发布-订阅等模型
  7. 性能优化技术：零拷贝, 内存池, 批处理, 缓冲区优化
  8. 安全性考虑：身份验证, 加密通信, 防止常见攻击

11.4 网络编程最佳实践¶

  1. 错误处理：始终检查系统调用返回值，并适当处理错误
  2. 资源管理：确保正确关闭套接字，释放内存等资源
  3. 安全性：输入验证，防止缓冲区溢出，使用TLS/SSL等加密通信
  4. 可扩展性：设计能够处理大量连接的系统架构
  5. 边界情况：考虑网络延迟、断线、超时等异常情况
  6. 调试与监控：实现完善的日志系统，使用合适的调试工具

要落地的话，建议先按第 2 节的 API 写一个能回显的 TCP 服务，再逐步换成 epoll、加线程池和 TLS，每步都用第 10 节的工具验证一次。
