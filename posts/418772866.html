属性元数据与标签

[!abstract] 一句话
标签是贴在笔记上的便利贴，属性（Properties）是写进笔记档案卡的字段——两者共同构成知识库的”数据层”。

标签基础

标签是跨目录的横向组织维度，在正文或 Frontmatter 中以 # 开头：

它与文件夹的本质区别：一篇笔记只能在一个文件夹里，却可以同时拥有多个标签。因此标签适合表达可叠加的维度——状态（#待办 #进行中 #完成）、类型（#笔记 #教程 #会议）、主题（#编程 #读书）。

嵌套标签支持父级聚合：#项目/设计 会归入 #项目 之下，右侧标签面板中可以逐层展开。搜索时用 tag:#编程 精确匹配标签，tag:#项目/阶段 匹配嵌套路径，多个条件可用 AND/OR 组合，例如 tag:#待办 AND tag:#重要。

标签体系设计

标签最容易失控的地方是”越长越多”。几百个无体系的标签等于没有标签。推荐先定一份小型标签字典再开始使用：

三个禁忌：标签爆炸（临时想法随手建标签）；语义重叠（#Python 与 #python 并存——标签大小写不敏感但体系要唯一）；与文件夹完全重复（同一条信息记两遍必然不同步）。标签体系膨胀后，可用社区插件 Tag Wrangler 做批量重命名与合并。

Properties：笔记的结构化字段

Frontmatter 是写在文件开头的 YAML 块，Obsidian 1.4 起将它正式产品化为 Properties（属性），并在编辑器顶部提供可视化面板——无需手写 YAML 也能增删字段、选择字段类型。

支持的属性类型包括：文本、列表、数字、日期与日期时间、复选框。给字段选定类型后，属性面板会提供对应的输入控件（日期选择器、复选框等），数据质量从录入端就有了保障。

[!note] 2026 更新
自 1.9 版本起，部分内置属性名已统一改为复数形式：tag → tags、alias → aliases、cssclass → cssclasses。旧笔记会被自动迁移，但自己写的模板和查询脚本要同步更新，否则属性会失效。

两个高频字段值得单独说明：aliases（别名）让 别名 也能正确跳转到笔记，解决”一词多名”的链接问题；cssclasses 则用于给单篇笔记挂载 CSS 样式类，配合主题实现个性化排版。

属性的意义：让笔记可查询

标签和文件夹回答”这篇笔记是什么”，属性回答”这篇笔记有哪些可计算的事实”。一旦笔记带上了 status、date、rating 这样的字段，它就变成了数据库里的一行记录，可以被：

  • 搜索与筛选：全局搜索支持 ["status":done] 这类属性语法；
  • Dataview 查询：用类 SQL 语法聚合生成动态列表与表格，详见 09-Dataview数据查询；
  • Bases 数据库视图：官方零代码方式，把一批笔记渲染成可排序、可分组、可筛选的表格或卡片，详见 06-Bases数据库视图；
  • 模板自动填充：新建笔记时由模板写入统一字段，保证全库属性命名一致，见 07-模板与快捷键。

[!tip] 先约定，后使用
属性最大的坑是命名不一致：status / 状态、date / created 混用会让所有查询失效。建议把常用字段写在模板里强制统一，全库统一小写英文命名。

标签 vs 属性怎么选

经验法则：出现频率高、粒度粗、需要手动点击浏览的用标签；结构化、可计算、需要批量查询的用属性。例如”这篇笔记是否完成”适合属性（要筛选统计），”这是读书笔记”既可用类型属性也可用标签，二选一即可，不必两者都记。

常见坑

[!warning] 避坑清单

  1. YAML 语法错误：冒号后必须有空格，列表缩进要对齐，错了整个 Frontmatter 失效；
  2. 属性类型漂移：同一字段有的笔记是文本有的是数字，查询时会出错，用类型面板统一；
  3. 标签当文件夹用：试图用标签复刻目录层级，最终两套体系互相打架；
  4. 忘记 tag: 前缀：直接搜索”待办”是全库全文搜索，tag:#待办 才是标签检索。
