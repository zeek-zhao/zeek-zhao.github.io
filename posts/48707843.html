52-PyTorch与自动驾驶实践

PyTorch 的张量、自动微分和动态图怎么用，标准训练流程走一遍，最后说清它在 Apollo 训练侧的位置和车端推理的区别。
📅 2026-09-29· 更新于 2026-09-29 · 4386 字 · 约 11 分钟 ✍ zeek.zhao #指南#apollo

做感知模型，绕不开 PyTorch。这篇把它的核心机制和标准训练流程走一遍，重点说清它在 Apollo 研发链路里到底站在哪一端。基础概念放在 51-深度学习基础与CNN。

1. 靠动态图坐稳训练侧¶

PyTorch 由 Facebook AI 研究院（FAIR）于 2016 年发布，2018 年与专注部署的 Caffe2 合并（这段历史见 53-TensorFlow与Caffe2在自动驾驶中的应用）。它能成为研究主流，靠的是三点：

  • 动态计算图：图在运行时即时构建，可随时用 print/断点调试，与 Python 生态无缝集成
  • 研究社区主流：新论文模型（UniAD、BEVFormer 等）几乎都以 PyTorch 实现
  • 部署工具日益完善：TorchScript、ONNX 导出、ExecuTorch

版本里程碑：1.0（2018，引入 JIT）；2.0（2023，引入 torch.compile 编译加速）；2.x 持续增强 FSDP 分布式训练与编译优化。

3. 大规模训练怎么提速¶

3.1 分布式训练（DDP）¶

超大规模模型可进一步使用 FSDP（全分片数据并行）。

3.2 混合精度训练（AMP）¶

显存省一半、速度提升 2 倍左右，是大规模感知模型训练的标配。

3.3 其他实用技巧¶

  • 梯度累积：loss = loss / accum_steps，多步后再 step()，模拟大 batch
  • 梯度裁剪：torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)，防梯度爆炸
  • 激活检查点：torch.utils.checkpoint 用计算换显存
  • 性能分析：torch.profiler.profile 定位瓶颈，可导出 Chrome trace

4. 训练归 PyTorch，推理由别家¶

分工其实很清楚。PyTorch 负责训练侧：Apollo 生态及多数自动驾驶团队的感知模型——2D/3D 检测、BEV 骨干、红绿灯、车道线网络——都在这里设计和训练。车端推理不走 PyTorch：Apollo 内置推理框架基于 PaddlePaddle（PaddleInference）、ONNX Runtime 与 TensorRT 等，要的是确定性低延迟和硬件加速。训练完成后，得先把模型转成这些引擎认的格式：

端到端范式（UniAD、VLA 模型）起来之后，训练侧模型规模明显增大，PyTorch + FSDP/DeepSpeed 的多机训练成了常态；车端则把蒸馏、量化后的小模型经 ONNX → TensorRT（NVIDIA Orin）等路线部署。训练用大框架、推理用专门引擎，这个”训练-部署分离”的格局我觉得会长期稳住。Apollo 10.0/11.0 的部分感知模型训练也依赖云端平台（见 56-自动驾驶云服务与基础设施）。

整条部署链路是：PyTorch 训练 → 量化/剪枝/蒸馏 → ONNX 导出 → TensorRT/PaddleInference 优化 → 车载 Cyber RT 模块加载推理（运行时框架见 58-自动驾驶运行时框架对比）。

5. 一个端到端小模型¶

可以在 CARLA 这类模拟器里闭环采集数据训练（仿真平台见 50-仿真平台对比与Gazebo-LGSVL实战），再结合真实路测数据微调。端到端模型的安全验证方法见 54-自动驾驶测试方法。

6. 上车前的检查清单¶

  1. 用 num_workers + pin_memory 优化数据加载；避免频繁在 CPU/GPU 间搬运数据
  2. 评估/推理时始终 model.eval() + torch.no_grad()
  3. 保存 state_dict() 而非整个模型对象；训练脚本保存完整 checkpoint（模型+优化器+调度器状态）以便断点续训
  4. 大 batch 训练用 AMP + 梯度累积；显存不足用激活检查点
  5. 上车部署前先做量化验证（PTQ 校准或 QAT），对比精度损失

最后这条最容易被跳过，可它常常才是上车出问题的真正原因。我会把量化验证排在第一位，精度掉多少必须提前量出来。

操作步骤 使用流程¶

从训练到上车部署，建议按这条主线走：

  1. 确定任务与模型：先定检测/分割/端到端，选 ResNet 骨干或现成论文实现（能用 torchvision 预训练就用）。
  2. 搭数据管道：自定义 Dataset + transforms（仅水平翻转）+ DataLoader（num_workers/pin_memory 提速）。
  3. 走通训练循环：定义模型、损失、优化器、调度器，先在小子集上 overfit 一个 batch 验证流程正确。
  4. 大规模训练：多卡用 DDP（nccl），超大用 FSDP；开 AMP + 梯度累积提吞吐，梯度裁剪防爆炸。
  5. 监控与调试：TensorBoard 看损失曲线；torch.profiler 定位瓶颈；效果异常回看数据增强与标注。
  6. 保存完整 checkpoint：带模型/优化器/调度器状态，支持断点续训；只存 state_dict 不存整个对象。
  7. 导出中间格式：model.eval() 后用 torch.onnx.export 导出，dynamic_axes 留 batch 维度，用 onnxruntime 校验输出一致。
  8. 量化验证：PTQ 校准或 QAT，对比 INT8 与 FP32 精度损失，掉点超阈值就调整校准集或改 QAT。
  9. 上车推理：ONNX → TensorRT/PaddleInference 优化，由 Cyber RT 模块加载（见 58-自动驾驶运行时框架对比），整车验证见 54-自动驾驶测试方法。

注意事项与常见坑¶

PyTorch 训练与部署里的高频坑：

  1. 验证忘切 eval/no_grad：BN/Dropout 还在工作且构建计算图，结果不稳定、显存暴涨。推理阶段务必 model.eval() + torch.no_grad()。
  2. optimizer.zero_grad 漏写：梯度累加不清零，loss 越训越大。注意梯度累积时是在 step 之后才清零。
  3. AMP 梯度下溢：FP16 梯度太小会变 0，必须用 GradScaler 缩放；迭代中 scale/step/update 顺序不能乱。
  4. DDP 卡死：init_process_group 的 MASTER_ADDR/PORT 不一致，或各卡拿到的数据不同步；用 DistributedSampler 并保证每卡样本数一致。
  5. torch.compile 与动态 shape：编译对动态控制流和数据依赖 shape 支持有限，遇到图中断先 fallback 回 eager 排查。
  6. ONNX 导出 opset 过低：opset_version 太低不支持新算子（如某些 attention 结构），导出报不支持算子时先升版本。
  7. 导出后没校验数值：导出 ONNX/TorchScript 后不复跑对比，上车才发现输出和训练差很远。用 assert_allclose 把关。
  8. 只存整个模型对象：torch.save(model) 绑定类定义，代码重构后加载失败。只存 state_dict。
  9. 量化跳过验证：PTQ 校准集不具代表性，INT8 精度暴跌，上车漏检。必须对比精度损失再上车。
  10. 垂直翻转做增强：自动驾驶场景上下翻转破坏物理含义，只能用水平翻转。
  11. 数据增强与标注不同步：翻转/裁剪图像时同步改框坐标，否则模型学到错位标签。
  12. 端到端模型输出未约束：转向/油门/刹车要分别用 tanh/sigmoid 约束到物理范围，否则控制量越界（见 38-端到端自动驾驶与大模型）。
