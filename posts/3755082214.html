Linux 内核同步机制：从原子操作到 RCU

在内核里写并发代码，选错同步机制比写错逻辑更难查——我用下来的感受是，先分清临界区会不会休眠，基本就能砍掉一半选项。

1. 概述：并发的三大挑战与四类同步手段¶

1.1 为什么需要同步机制¶

在多处理器系统和支持抢占的内核中，多个执行流可能同时访问共享资源，如果不加以控制，将导致数据不一致或系统崩溃。

📝并发的挑战
并发编程面临三大挑战：原子性、可见性和有序性。Linux内核的同步机制正是为解决这些问题而设计的。

我一般先按”会不会睡眠”给同步原语分类——自旋等待类在原子上下文用，睡眠等待类只能在进程上下文用，这条线划清了，选型就不乱了。

1.2 同步机制的分类：四大类¶

flowchart TD A[Linux内核同步机制] --> B[自旋等待类] A --> C[睡眠等待类] A --> D[无锁同步] A --> E[内存序控制] B --> B1[原子操作] B --> B2[自旋锁及变种] B --> B3[序列锁] C --> C1[信号量] C --> C2[互斥量] C --> C3[读写信号量] C --> C4[完成量] C --> C5[等待队列] D --> D1[RCU] D --> D2[Per-CPU变量] E --> E1[内存屏障] E --> E2[volatile关键字]

2. 原子操作：开销最小的计数与位操作¶

原子操作是最基本的同步操作，确保操作不会被中断。

我理解原子操作的价值就在于”不可中断”——整数加减和位设置都由 CPU 保证一次性完成，适合做引用计数这类简单统计。

3. 自旋锁：短临界区且绝不能休眠¶

3.1 基本自旋锁¶

sequenceDiagram participant CPU1 participant SpinLock participant CPU2 CPU1->>SpinLock: spin_lock() Note right of SpinLock: 锁已获取 CPU2->>SpinLock: spin_lock() Note right of SpinLock: CPU2忙等 CPU1->>SpinLock: spin_unlock() Note right of SpinLock: 锁已释放 SpinLock->>CPU2: 锁获取成功 CPU2->>SpinLock: spin_unlock()
⚠️注意事项
自旋锁持有期间不能休眠，否则可能导致死锁。自旋锁适用于短期持有的场景。

我踩过的坑就是自旋锁里调用可能休眠的函数——一旦持锁线程被切走，其他 CPU 会一直空转，最后整个系统挂住。

3.2 自旋锁的三种变种¶

锁类型 描述 典型使用场景
普通自旋锁 基本的自旋锁实现 短时间的临界区保护
读写自旋锁 允许多个读者或一个写者 读多写少的数据结构
大自旋锁 系统级别的自旋锁 保护全局资源

4. 信号量：允许等待者睡眠的计数锁¶

信号量允许任务在等待资源时进入睡眠状态。

我一般只在需要睡眠的长临界区才用信号量，down_interruptible() 能让等待被信号打断，这一点比自旋锁灵活。

graph TD A[进程尝试获取信号量] --> B{信号量可用?} B -->|是| C[获取信号量] B -->|否| D[进程进入睡眠] D --> E[信号量被释放] E --> F[唤醒等待进程] F --> B

5. 互斥量：比信号量更严格的二值锁¶

互斥量是信号量的特殊形式，更轻量级、更高效。

🔥Mutex vs Semaphore
互斥量相比信号量有更严格的使用规则，比如必须由获取者释放，不能在中断上下文使用，但性能更好。

我理解 mutex 的约束比 semaphore 严——必须由获取者释放、不能用在中断上下文，换来的是更好的性能。

6. 读写锁：读可并发、写须独占¶

允许多个并发读操作，但写操作需要独占访问。

我一般只在读远多于写的数据结构上用读写锁，否则维护读者计数的开销反而抵消收益。

6.1 读写锁的状态转换¶

stateDiagram-v2 [*] --> 无锁状态 无锁状态 --> 读锁状态: 获取读锁 无锁状态 --> 写锁状态: 获取写锁 读锁状态 --> 读锁状态: 其他读者获取读锁 读锁状态 --> 无锁状态: 所有读者释放读锁 写锁状态 --> 无锁状态: 写者释放写锁

7. RCU：读无锁、写靠副本与宽限期¶

RCU是一种专为读多写少场景优化的同步机制，允许读者无锁访问。

我理解 RCU 的关键在”宽限期”——写者替换指针后要等所有旧读者退出，才能安全 kfree 旧数据，这也是它写端复杂的原因。

8. 序列锁：靠重试让写者不阻塞读者¶

序列锁提供了一种读写锁的变体，特别适用于读多写少且读者不修改数据的场景。

我一般把 seqlock 用在时间戳这类小型只读数据上，读者通过 read_seqretry 检查版本号，冲突了就重读一次。

9. 内存屏障：用 mb/rmb/wmb 约束重排¶

内存屏障确保内存访问按期望顺序执行，解决CPU乱序执行和缓存一致性问题。

我理解屏障解决的是乱序执行和缓存可见性问题——源码里把 mb/rmb/wmb 和 smp_mb/smp_rmb/smp_wmb 分开列，就是为区分 SMP 场景。

9.1 屏障类型与作用¶

graph TB A[内存屏障类型] --> B[完全内存屏障] A --> C[写屏障] A --> D[读屏障] A --> E[编译屏障] B --> B1[确保屏障前后的所有内存操作不会重排] C --> C1[确保屏障前的所有写操作完成后<br>再执行屏障后的写操作] D --> D1[确保屏障前的所有读操作完成后<br>再执行屏障后的读操作] E --> E1[防止编译器重排代码]

10. 完成量：一个任务等另一个任务的事件¶

完成量用于一个任务等待另一个任务完成某事件。

我一般用 completion 替代简单的信号量做”等一个事件”的场景，complete_all() 能一次唤醒所有等待者。

11. 等待队列：阻塞与唤醒的基础设施¶

等待队列是内核中用于实现进程阻塞和唤醒的基础设施。

我一般把 wait_event_interruptible() 用在需要响应信号的等待场景，比不可中断的 wait_event() 更安全。

12. 选型指南：按临界区、上下文、读写比例决定¶

我一般按这张表选型：简单计数用原子操作，短临界区用自旋锁，可能睡眠用互斥量，读多写少才上 RCU 或读写锁。

同步机制 适用场景 优点 缺点
原子操作 简单计数器 开销最小 功能有限
自旋锁 短时间持有的锁 无睡眠开销 占用CPU
互斥量 可能长时间持有的锁 不消耗CPU 上下文切换开销
读写锁 读多写少场景 并发读取 实现复杂
RCU 读非常频繁、写罕见 读无锁、无阻塞 写端复杂
序列锁 读多写少且支持重试的场景 写者不阻塞 需要读者重试

13. 常见错误与调试：死锁、锁序和 lockdep¶

我查锁问题第一个工具是 lockdep，它能在启动阶段就报出锁顺序不一致的潜在死锁。

13.1 常见错误¶

  1. 死锁：多个锁交叉获取
  2. 锁顺序不一致：不同代码路径获取多把锁的顺序不同
  3. 自旋锁中休眠：导致系统挂起
  4. 过度加锁：性能下降
  5. 锁粒度过粗：并发性受限

13.2 调试工具清单¶

  • lockdep：内核锁依赖验证器
  • sparse：静态分析工具
  • ftrace：追踪锁操作
  • /proc/locks：查看持有的文件锁
  • perf：性能分析
