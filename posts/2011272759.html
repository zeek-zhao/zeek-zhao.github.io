50-仿真平台对比与Gazebo-LGSVL实战

真车不可能跑遍所有场景，仿真是绕不过去的一环。这篇先讲清仿真到底在测什么、平台怎么挑，再动手把 Gazebo 和 LGSVL 两个开源平台搭起来，接到 ROS/Apollo 上。

真车不可能跑遍所有场景，仿真是绕不过去的一环。这篇先讲清仿真到底在测什么、平台怎么挑，再动手把 Gazebo 和 LGSVL 两个开源平台搭起来，接到 ROS/Apollo 上。上一篇的数据集实战见 49-KITTI与Waymo数据集实战。

1. 仿真到底在测什么¶

1.1 为什么必须仿真¶

graph LR A[仿真价值] --> B[降低路测成本] A --> C[扩展测试场景] A --> D[提高测试安全性] A --> E[支持边缘场景] A --> F[生成训练数据]

自动驾驶的安全验证需要数十亿公里级里程，靠实车测试根本跑不完。接管场景复现、危险场景测试、大规模数据生成，都得靠仿真。

1.2 仿真系统架构¶

闭环是这样转的：物理世界模型 ← 环境条件/交互对象/场景管理器 → 传感器模型 → 数据处理 → 控制算法 → 执行系统 → 回到物理世界。

关键传感器的模拟原理各有讲究：

  • 摄像头：图形渲染 + 视角转换 + 光学效果（畸变/景深）+ 噪声。
  • 激光雷达：光线追踪——发射虚拟线束 → 取碰撞点 → 加噪声/材质反射/大气衰减 → 生成点云。
  • 毫米波雷达：电磁波传播 + RCS + 多普勒效应。
  • IMU/GPS：动力学状态 + 偏差噪声 + 信号遮挡模拟。

1.3 类型划分¶

分类维度 类型
保真度 低（概念验证）/ 中（算法开发）/ 高（系统验证与安全评估）
数据来源 物理模型仿真（游戏引擎）/ 真实数据仿真（回放、增强、重建）/ 混合仿真

混合仿真是当前主流：真实数据构建环境，物理引擎添加动态对象，传感器模型生成数据。数据生成方法包括 GAN 增强真实数据、模拟器生成、结构化数据增强三类。

2. 五个平台怎么挑¶

2.1 主流平台速览¶

平台 开发方 引擎 集成 特点
CARLA CV 中心 Unreal 4 ROS/Apollo/Autoware 开源、社区最活跃、天气丰富
LGSVL LG 电子 Unity Apollo/Autoware（最优） 高精地图支持、Python API
Gazebo Open Robotics 自研 ROS 原生 物理最强、机器人标准
AirSim 微软 Unreal 4 ROS 无人机+车辆、渲染好
DRIVE Sim NVIDIA 自研 DRIVE 平台 光线追踪、商业闭源、保真度最高

提醒一句，LGSVL（SVL Simulator）自 2022 年起已停止官方维护，仓库归档，继续用得自己维护 fork。新项目的替代方案是 CARLA（开源首选，社区持续活跃）、NVIDIA DRIVE Sim（商业高保真）、51Sim 等国产平台；与 Apollo 10.0 的仿真对接也转向以 CARLA 桥接为主。

2.2 选型决策树¶

flowchart TD A[开始选择] --> B{首要因素?} B -->|开源成本| C{对接框架?} B -->|真实度| D{预算?} B -->|开发便捷| E{团队背景?} C -->|Apollo/Autoware| C1[LGSVL] C -->|ROS/ROS2| C2[Gazebo/CARLA] D -->|充足| D1[DRIVE Sim] D -->|有限| D2[CARLA/AirSim] E -->|ROS经验| E1[Gazebo] E -->|游戏引擎经验| E2[CARLA/LGSVL]

按场景推荐：感知研发选 CARLA/AirSim/DRIVE Sim；规划决策选 CARLA/LGSVL；控制算法选 Gazebo/AirSim；全系统集成测试选 LGSVL/CARLA；数据生成选 CARLA/DRIVE Sim。

多平台可以协同着用：低保真快速迭代 → 中保真筛选 → 高保真最终验证；场景用 OpenSCENARIO 标准格式跨平台复用；再用统一的中间件接口层屏蔽各家 API 差异。

3. Gazebo：物理最强那个¶

3.1 安装与配置¶

要求：Ubuntu 18.04/20.04、8GB+ 内存、OpenGL 3.3+ 显卡。渲染出问题就试一下 export SVGA_VGPU10=0。

3.2 模型与传感器¶

模型目录包含 model.config（元数据）和 model.sdf（物理+视觉定义，XML 格式）；ROS 用户可以用 URDF 加 <gazebo> 扩展标签，再手动转：gz sdf -p my_robot.urdf > my_robot.sdf。

URDF 里加 RGB 相机和激光雷达的示例（节选）：

它支持多物理引擎（ODE/Bullet/Simbody/DART），插件系统用 C++ 扩展自定义传感器与行为。

3.3 世界与仿真操作¶

  • .world 文件（XML）保存完整环境配置：gazebo my_world.world 或 roslaunch gazebo_ros empty_world.launch world_name:=...。
  • 交互：左键拖动旋转、中键平移、滚轮缩放；Space 暂停、Ctrl+R 重置。
  • 复杂模型用 Blender 建模导出 .dae；批量模型用脚本生成 SDF。

3.4 与 ROS 集成¶

Gazebo 和 ROS 原生互通：传感器数据直接发成 ROS 话题，控制指令通过话题/服务下发，TF 提供坐标变换。典型闭环是 Gazebo 发布 /camera/image_raw、/scan、/odom → SLAM/导航节点处理 → /cmd_vel 回到 Gazebo 驱动机器人。

它的边界也很清楚：物理引擎强、适合控制和底层算法开发，但渲染质量一般、道路场景构建繁琐——做自动驾驶交通流仿真，不如 CARLA/LGSVL 便捷。

4. LGSVL：和 Apollo 打通闭环¶

4.1 安装与初始化¶

要求：GTX 1080+（6GB 显存）、16GB+ 内存、30GB 磁盘。首次启动访问 Web UI（http://127.0.0.1:8080）创建账户、下载地图与车辆资源、配置集群。

预置地图有 BorregasAve（城市）、SanFrancisco（复杂城市）、Shalun（混合道路）、CubeTown（基础测试）等；支持 HD Map（Apollo 格式）与 OpenDRIVE 导入。

4.2 传感器配置¶

在 Web UI 车辆配置里用 JSON 定义传感器，位置由 transform 的 x/y/z 与 pitch/yaw/roll 控制：

支持 RGB/深度/语义分割相机、激光雷达、毫米波雷达、GPS/IMU、超声波、碰撞检测器；Compensated: true 表示内置运动补偿。环境参数可调雨/雾/湿度/云量（0-1）与一天时间（0-24h）。

4.3 与 Apollo 集成闭环¶

流程三步：

  1. Web UI 创建仿真：选地图（如 SanFrancisco）、车辆、运行时（Interactive/API Only）；
  2. 车辆传感器配置中设置桥接为 Apollo bridge，topic 按上面 JSON 中的 /apollo/sensor/... 通道命名；
  3. 启动 Apollo（如 5.0+）与 dreamview，启动 LGSVL 仿真，二者经桥接建立数据循环。

手动驾驶可用 WASD 控制，Tab 切换手动/自动模式——自动模式即 Apollo 接管。

5. 新项目怎么起步¶

新项目我会从 CARLA 起步——LGSVL 归档之后，生态和文档都差了一截，需要 Apollo 闭环就去找社区 CARLA-Apollo 桥接；对保真度有要求且有预算，再上 DRIVE Sim 或国产 51Sim。手上还有存量 LGSVL 工程的，把归档仓库自行 fork 维护，冻结版本避免依赖漂移。

场景这边统一用 OpenSCENARIO 描述，方便跨平台复用；把仿真测试纳入 CI，每次提交自动回归核心场景。还有个绕不开的话题是 Sim2Real——仿真结果得在封闭场地标定验证，尤其是传感器噪声模型和车辆动力学参数。

操作步骤 使用流程¶

从零搭起一套可跑的仿真闭环，建议按下面的流程：

  1. 平台选型：按场景选——控制/底层算法用 Gazebo，自动驾驶系统集成用 CARLA/LGSVL，商业高保真用 DRIVE Sim。LGSVL 已归档，新项目优先 CARLA。
  2. 装依赖：Gazebo 走 apt 装 gazebo11 与 ros-noetic-gazebo-ros-pkgs；LGSVL 下 2021.3 二进制并确认 GTX 1080+/16GB/30GB 资源。
  3. 配模型与传感器：Gazebo 写 model.sdf/URDF + 传感器插件；LGSVL 在 Web UI 用 JSON 配相机、雷达与 transform，topic 对齐 Apollo 通道。
  4. 建世界/地图：Gazebo 写 .world 配物理引擎；LGSVL 选预置地图或导入 HD Map/OpenDRIVE，下载资源后配集群。
  5. 跑单仿真验证：先手动模式（WASD/Tab）确认车能跑、传感器有数据；再切自动模式让 Apollo 接管。
  6. 接桥闭环：LGSVL 配 Apollo bridge（9090），启动 Apollo + Dreamview，选对应车辆和地图，确认传感器数据进 Apollo、控制指令回仿真。
  7. 脚本化批量测试：用 Python API 生成边缘场景（行人横穿、加塞、鬼探头），按天气/交通参数组合批量跑，自动判分并落 CSV。
  8. Sim2Real 标定：把仿真结果拿到封闭场地对比，校准传感器噪声模型与车辆动力学参数，避免”仿真里全过、实车就翻”。
  9. 纳入 CI 回归：场景用 OpenSCENARIO 描述，每次提交自动回归核心场景（测试方法见 54-自动驾驶测试方法）。

注意事项与常见坑¶

仿真搭建与运行里的高频坑：

  1. LGSVL 归档无维护：官方 2022 年停更，仓库归档、资源下载链接可能失效。新项目别选它做主力，存量工程要自行 fork 并冻结版本，避免依赖漂移。
  2. Gazebo 渲染黑屏：虚拟机/无独显环境常见，先设 export SVGA_VGPU10=0；仍不行再查 OpenGL 3.3+ 支持。
  3. 模型找不到：自定义模型要放进 GAZEBO_MODEL_PATH 包含的路径，否则 Gazebo 里一片空白。用 gazebo --verbose 看加载日志。
  4. TF 坐标树断链：传感器 frame 名和 URDF link 名对不上，RViz 里点云乱飞。确认 frameName 与 TF 树一致。
  5. 物理时间步设太大：ODE max_step_size 过大导致仿真不稳、车辆抖动；一般设 0.001 并配 real_time_update_rate=1000。
  6. LGSVL Web UI 端口占用：8080 被占用会打不开管理界面，启动前确认端口空闲；集群配置里 IP/端口填错则桥接连不上。
  7. Apollo 版本与桥接不匹配：LGSVL 的 Apollo bridge 是 5.0 时代的产物，Apollo 10.0+ 对接要走 CARLA 桥接或社区适配，别硬套旧桥。
  8. 传感器 topic 通道写错：LGSVL JSON 里的 Topic 必须和 Apollo 订阅的 /apollo/sensor/... 完全一致，差一个斜杠就收不到数据。
  9. Compensated 标志误用：Compensated: true 表示内置运动补偿，若自己再做补偿会双重修正，点云位置失真。
  10. Sim2Real 差距被忽略：仿真传感器噪声太干净、动力学太理想，直接拿仿真指标当实车结论。必须用封闭场地标定校准（场地测试见 54-自动驾驶测试方法）。
  11. 场景平台不通用：各家场景格式不同，换平台要重做。统一用 OpenSCENARIO 描述，能省大量重复工作。
