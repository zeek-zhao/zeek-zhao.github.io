44-Apollo与ROS对比及生态互通

Apollo 为什么从 ROS 换成 Cyber RT，三者差在哪，两套生态现在怎么互通、怎么迁。附一张概念对照表和选型建议。
📅 2026-10-07· 更新于 2026-10-07 · 4822 字 · 约 13 分钟 ✍ zeek.zhao #apollo#对比

Apollo 早年是跑在 ROS 上的，后来自己造了 Cyber RT，最近又回过头把 ROS 生态接了回来。这段来回值得捋清楚，不然读模块代码时容易迷糊。接着 43-常见问题排查 往下。

1. 从 ROS 到 Cyber RT，为什么换¶

ROS（Robot Operating System）是机器人领域事实上的标准框架。Apollo 1.0 和早期版本直接构建在 ROS 上，但很快撞上三堵墙：

  1. 通信性能瓶颈：ROS1 基于 TCPROS/UDPROS，主从架构下节点间通信要经过序列化拷贝，扛不住自动驾驶的高频大流量——64 线激光雷达 10Hz 约 1.3M 点/秒。
  2. 调度粒度不足：ROS1 是进程级调度，一个模块一个进程，CPU 资源分配粗放，实时性没保障。
  3. 去中心化需求：自动驾驶要求 Master 宕机后系统还能跑，ROS1 的 Master 单点架构满足不了。

所以从 Apollo 3.5 起，自研的 Cyber RT 顶替了 ROS，成为运行时框架。

不过换框架不等于和 ROS 一刀两断。Apollo 10.0 起正式打通 ROS 软件生态，开发者可以直接在 Apollo 里复用 ROS 的工具、驱动和算法包，软件复用成本明显下降。Cyber RT 提供了 ROS 兼容层，不少 ROS 节点能低成本迁过来跑。

2.1 通信性能差在哪¶

  • Cyber RT 的消息吞吐和延迟都优于 ROS1，靠的是零拷贝共享内存和协程调度，高频大流量的点云、图像尤其受益。
  • ROS2 上了 DDS 之后性能大幅追近，还带 QoS 策略（可靠性、历史深度、生命周期），控制粒度更细。
  • 同一台车上混跑时，Cyber RT 与 ROS2 节点可以通过桥接器交换消息。

选型上，我的判断是：科研原型、快速验证就选 ROS/ROS2；量产车规、高性能感知链路选 Cyber RT 或类似框架。两者概念相通，迁移成本可控。

3. 两套生态怎么互通¶

3.1 Apollo 里复用 ROS 生态¶

从 Apollo 10.0 打通 ROS 软件生态后，常见的复用场景有这几类：

  • 传感器驱动复用：大量 ROS 驱动包（相机、激光雷达、IMU）经兼容层接入，省掉重复开发。
  • 工具链复用：rosbag 录制回放、RViz 可视化这些习惯能延续下来（Cyber 侧对应 cyber_recorder、Dreamview）。
  • 算法包复用：SLAM、标定等开源 ROS 包可以移植进 Apollo 模块。

3.2 三种桥接方式¶

需要 Cyber RT 与 ROS 双向通信时，常用三种办法：

  1. 官方 ros-bridge：Apollo 仓库里提供的桥接组件，做消息格式转换（proto ↔ ROS msg）。
  2. 共享文件/共享内存：适合点云、图像这类大数据，绕开网络序列化开销。
  3. 自研转发节点：两侧各建一个订阅-发布转发节点，灵活，但消息映射得自己维护。

3.3 消息接口怎么迁¶

从 ROS 迁到 Cyber RT，建议按这个顺序走：

  1. 梳理现有话题与节点依赖图，划清迁移边界。
  2. 把 .msg 定义转写成 .proto，保持字段语义稳定。
  3. 逐模块迁移，先做数据通路验证，再验证实时性和吞吐。
  4. 生态依赖重的功能，先保留 ROS 通道经桥接通信，后面逐步替换。

4. 开发者怎么切换¶

  • 熟悉 ROS 的人学 Cyber RT：重点看 Component 模型、协程调度和 channel 概念，可以类比 ROS 的话题和节点，参考 11-Apollo-Cyber-RT框架 与 12-Cyber消息通信与组件开发。
  • 熟悉 Apollo 的人学 ROS：关注它的生态工具（rosbag、RViz、Gazebo）和社区资源，学 SLAM 时尤其有用（见 45-SLAM概述与开发指南）。
  • 两者在消息通信、节点组织上概念相近，最好用一个真实项目带着学，映射关系很快建立起来。

4.1 概念对照表¶

ROS 概念 Cyber RT 对应 差异要点
Node Node / Component Component 以协程运行在调度器上，可配置优先级
Topic Channel Channel 是全局广播，多个 Reader 可订阅
ros::NodeHandle cyber::Node API 风格相似
Subscriber Reader / CreateReader<T> 模板类型为 proto 消息
Publisher Writer / node->CreateWriter<T> 共享内存路径下零拷贝
Service Service（RPC） Cyber 支持同步/异步调用
launch 文件 DAG + launch（cyber_launch） DAG 描述组件与 channel 绑定
rosbag cyber_recorder record/play 子命令用法相近
RViz Dreamview 网页端可视化，绑定 channel
catkin_make bazel build 构建体系完全不同，迁移主要成本之一

4.2 一个最小桥接组件¶

要点是回调里只做”格式转换 + 时间戳透传”，别塞业务逻辑。高频大消息建议改走共享内存或文件交换，不然桥接自己会变成吞吐瓶颈。

5. 选型看这四点¶

框架选型要综合考虑：

  1. 性能需求：是否需要毫秒级端到端延迟、高频点云零拷贝。
  2. 生态成熟度：是否依赖大量现成 ROS 包。
  3. 团队技能：现有的 C++/bazel/DDS 经验。
  4. 长期维护：产品化路线、车规认证要求。

有个误区得避开：别觉得性能好就该全上 Cyber RT。SLAM 建图、标定工具、离线数据处理这些对实时性不敏感的环节，ROS 生态里的成熟工具往往效率更高。混合使用、按需桥接，才是更务实的工程选择。

6. 几个高频问题¶

Q1：Cyber RT 能直接订阅 ROS 话题吗？

不能直接订阅，得经桥接组件做消息转换（proto ↔ ROS msg）。大数据（点云/图像）建议走共享内存方案，减少序列化开销。

Q2：消息定义从 .msg 迁到 .proto 要注意什么？

字段名和语义要稳定，留意默认值差异和数值类型精度（ROS 的 float64 对应 proto 的 double）；字段编号提前预留，避免后续变更破坏兼容。

Q3：两套系统的时间戳怎么对齐？

统一以车载 GPS/授时源为基准，Cyber RT 的 cyber::Time 和 ROS 的 ros::Time 都映射到同一个时钟域。桥接转发时保留原始时间戳，别在桥接层重新打时间戳。

7. 务实的做法是混合用¶

兜了一圈，结论其实朴素：框架服务于场景。感知链路吃 Cyber RT 的性能，工具链和离线环节继续用 ROS 的成熟包，中间靠桥接连起来。真要迁移，先把接口稳住，再一个模块一个模块换——这比一次性重构靠谱得多。

注意事项与常见坑¶

  1. 桥接回调只做格式转换：别塞业务逻辑，否则桥接自己变吞吐瓶颈。
  2. 时间戳必须透传：在桥接层用 ros::Time::now() 重新打时戳会让端到端延迟分析全乱。
  3. 两边要同一授时源：Cyber 用宿主时钟、ROS 用 GPS 时间，offset 每帧漂移，必须统一到 PTP/GPS。
  4. proto 字段编号要预留：用 reserved 占位，避免后续复用破坏数据兼容。
  5. 双向桥接用不同 topic 名：防止消息回环无限转发。
  6. 桥接进程独立命名：Cyber 和 ROS 节点名冲突会让发现机制混乱。
  7. 大消息走共享内存：点云/图像经 proto 序列化拷贝开销大，/dev/shm 默认 64MB 要调大。
  8. **别用 sleep_for 代替 cyber::Rate**：虚拟时钟下回放频率会错乱。
  9. Reader 回调要短小：重计算放独立线程，否则拖慢整个调度队列。
  10. Bazel 引入 ROS 依赖要补全路径：头文件找不到时检查 BUILD 的 includes 与 linkopts。
