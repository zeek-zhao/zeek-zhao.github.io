Nginx URL 重写与跳转

接着上一篇 07-动静分离 往下，请求已经能按路径分发到不同后端了，这一步来解决”地址不对、想换个说法”的问题。重写说白了就是先把请求 URI 改掉，再拿改过的结果重新匹配处理，HTTP 跳 HTTPS、域名跳转、路径规范化都靠它。我一般先分清是要”直接回一个状态码”还是”正则替换路径”，再决定用哪个指令，别一上来就写 rewrite。

先认清重写改的是请求 URI¶

URL 重写：

  • 改变请求 URI 后再匹配处理
  • 301/302 重定向
  • 常用于：HTTPS 跳转、域名跳转、路径规范化

工具：

  • return：直接返回状态码/URL
  • rewrite：正则替换 URI
  • try_files：文件查找回退

简单跳转直接用 return¶

状态码我基本只记这几个，调试时对着看就行：

常用状态码：

  • 301：永久跳转（SEO）
  • 302：临时跳转
  • 307：临时保留方法
  • 308：永久保留方法
  • 444：关闭连接

复杂路径替换才用 rewrite¶

rewrite 的 flag 决定后面还走不走匹配，这块最容易混：

语法：
rewrite [flag];

flag：

  • last：重写后重新匹配 location
  • break：停止重写，当前 location 处理
  • redirect：302
  • permanent：301

跳转场景统一套模板¶

找不到文件就用 try_files 兜底¶

说明：

  • try_files 依次检查文件/目录
  • 最后一项可为 URI/命名 location
  • 适合 SPA 与后端回退

去掉前缀转发，靠 break 收尾¶

注意：

  • rewrite break 与 proxy_pass 搭配路径处理
  • last 会重新走 location 匹配
  • 循环重写会报 500，注意终止条件

重写不能冲开安全边界¶

注意：

  • 重写后路径可能被错误匹配，谨慎
  • 防止开放重定向（拼接外部 URL）
  • 对 $request_uri 做严格校验
  • 避免重写导致 SSRF

这几个坑我踩过¶

  1. rewrite 循环：last 后仍匹配重写，500。
  2. flag 用错：last 与 break 行为混淆。
  3. 301 缓存：调试期误配 301，浏览器缓存跳转。
  4. 丢失参数：跳转时未携带 query。
  5. 正则贪婪：捕获组取错内容。

简单用 return，复杂用 rewrite¶

我的习惯是改完跳转先 curl -I 看一眼状态码，确认没被浏览器缓存再上线。

  • 简单跳转用 return，复杂替换用 rewrite。
  • HTTPS/域名跳转统一配置模板。
  • 改跳转先测试（curl -I 看状态码）。
  • 重写逻辑保持简单可读。
