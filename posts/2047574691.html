生产实践与进阶技巧

上生产我一般先问规模，再决定搭多大摊子，小团队硬上高可用往往得不偿失。接着上一篇 14-常见问题排查 往下，会排错之后才好谈上线。这篇汇总部署模型、上线清单、自动化管理、规模化经验和协作范式，进阶功能按需取用。

1. 部署模型按规模来选¶

规模 部署模型 说明
小（<100 用户） 单机 Omnibus/Docker 成本低，备份即可
中（100-500） 单机 + 独立 Runner Web 与构建隔离
大（>500） 官方参考架构多节点 Gitaly/DB/Redis 分离 + 负载均衡
跨地域容灾 GitLab Geo（EE） 主备站点，灾备切换
⚠️高可用不是搭完即用
HA 增加复杂度与成本：需要共享存储、负载均衡、故障切换演练。小团队先做好备份，再考虑 HA，避免过度工程。

我的习惯是先把备份和恢复演练做扎实，确认能兜底了再评估 HA，不然复杂度上去了反而更难维护。

2. 上线前逐项过一遍清单¶

  1. HTTPS 证书 + 强制跳转
  2. 备份定时任务 + 异地副本 + 恢复演练
  3. 全员 2FA（管理员必开）
  4. 关闭开放注册，收敛 Public 项目
  5. 保护 main + MR 审批门禁
  6. Runner 就绪，白名单镜像
  7. 通知渠道（Webhook 对接企业 IM）
  8. 监控接入（Prometheus + 告警）
  9. 升级路径确认，固定版本基线

3. 规模化靠 API 和 CLI 做自动化¶

用 API 批量管理¶

🔥terraform-provider-gitlab
用 Terraform 管理组、项目、成员、Runner、CI 变量，实现基础设施即代码（IaC），团队规模大时显著降低重复操作。

用 glab CLI¶

4. 规模化先立规范再谈工具¶

  • 命名空间规范：组/子组/项目 三级规划，避免”无处安放”的散项目。
  • CI 模板沉淀：公共 .gitlab/ 模板 + include 复用，全团队统一构建规范：
  • Runner 池化：共享 Runner 多实例 + 标签细分（linux、gpu、arm）。
  • 仓库治理：启用 LFS 管理大文件，设置单仓库大小告警，定期清理死仓库。
  • 容器镜像仓库：启用内置 Registry，CI 产物进镜像仓库，配合部署流水线。

5. 协作范式靠分支和 MR 约定¶

  • 分支模型：main + feature/ 分支，短生命周期
  • 提交规范：Conventional Commits（feat/fix/docs/…）
  • MR 规范：模板 + 1-2 个审批 + 流水线通过 + 删除源分支
  • 发布节奏：tag 打版 + Release 说明 + 环境递进（test -> staging -> prod）
🔥Review Apps
每个 MR 自动部署独立环境，产品/测试可直接点开验证，大幅减少”本地可以，环境不行”。

6. 进阶功能按需启用即可¶

  • GitLab Pages：内建静态站点发布，文档/Wiki 之外做团队知识门户。
  • Dependency Proxy：代理外部镜像与依赖，内网加速 + 供应链可控（EE）。
  • Merge trains：MR 按序排队合并，主干始终绿（EE）。
  • Value stream analytics：分析从提交到交付的周期效率（EE）。
  • ChatOps：/slash 命令在 Issue/MR 中执行操作，机器人自动化。

7. 按月按季做例行检查¶

每月：备份演练 + Runner 利用率检查
每季度：权限审计 + 仓库治理 + 升级评估
每年：容量规划 + 高可用演练（如适用）

📝学习方向
进阶资料：官方 Administrator/Reference architectures 文档、GitLab Learn、社区博客，入口见 90-资料索引指南。

先按上线清单把基础项逐条做实，再按月按季跑例行检查，进阶功能等真有需求了再上。
