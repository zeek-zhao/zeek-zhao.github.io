权限管理

[!info] 本篇目标
理解 GitLab 的 RBAC 角色模型、组与项目权限继承、可见性控制与合规审计，构建最小权限原则下的权限体系。

1. 角色模型（RBAC）

GitLab 在实例级、组级、项目级分别定义角色，成员按角色获得对应权限：

角色 项目级能力摘要
Guest 只读 Issue/Wiki，无法访问代码
Reporter 可查看代码、Issue、流水线
Developer 可推送分支、创建 MR、运行 CI
Maintainer 项目全量管理：设置、保护分支、Runner
Owner 项目所有权、转移/删除

[!warning] 角色最小化
绝大多数研发用 Developer 即可；Maintainer/Owner 拥有删除与设置权限，应严格控制人数，避免”人人都是管理员”。

2. 组与项目权限继承

  • 成员加入组后自动获得组下全部项目权限（除非项目单独覆盖）。
  • 可在 项目 Settings -> Members 单独添加/降级成员，覆盖继承。
  • 组内使用 子组 + 项目结构 而非平铺命名空间，权限管理更清晰。

[!tip] 组级统一管理
将常用权限在组级设置（如默认角色 Developer），项目级只做例外调整；新增成员时加到组，避免逐个项目授权。

3. 可见性与访问限制

  • 项目可见性：Private / Internal / Public，见 04-项目与组管理。
  • 实例级限制（Admin -> Settings -> General -> Visibility and access controls）：
  • 启用 Email confirmation 与 Sign-in restrictions（如要求二次确认）。

4. 保护分支与保护标签

[!tip] 保护分支 + MR 门禁组合
main 设保护分支（Developer 不可直接推送）+ 项目 MR 检查（1 个审批 + Pipeline 成功）即形成基本交付门禁，详见 07-代码评审与MR。

5. 审计日志

  • Admin -> Audit Events：记录登录、权限变更、删除等管理行为。
  • 企业版支持更细粒度审计（项目级、组级事件、合规框架）。
  • 启用审计可追溯”谁在何时改了什么权限”，是合规必需。

[!note] 合规框架（EE）
企业版可创建 Compliance frameworks，为项目打标签并强制对应策略（如必须 Code owner 审批、必须保密管理）。

6. 权限变更最佳实践

[!danger] 慎用管理员
实例管理员（Admin）权限极大：可改配置、看所有项目、执行后台任务。生产环境只保留 1-2 名管理员，并为其开启 2FA（见 12-安全加固）。

7. 与 SSO/LDAP 的协同

权限在 GitLab 内定义，身份来源可交给 LDAP/SSO（见 09-SSO-LDAP集成）：LDAP 负责”这个人是公司的谁”，GitLab 角色负责”他能做什么”。两者配合实现 身份统一 + 权限隔离。
