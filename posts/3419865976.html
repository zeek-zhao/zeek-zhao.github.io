云计算概述：从IaaS到云原生

云计算概述

我一般把云计算当成一种「按需租资源」的思路：网络、服务器、存储、应用都能从网上快速拿到，用完就释放，几乎不用自己维护物理机。NIST 的定义也是这个意思——按需、方便、通过网络访问可配置的计算资源共享池。

下面按定义、服务模型、部署模式一路捋到云原生和安全成本。

先把云计算的定义和发展历史讲清楚¶

云计算是一种按需获取计算资源的模型，这些资源（如网络、服务器、存储、应用和服务）可以通过网络快速获取和释放，且管理成本低。美国国家标准与技术研究院（NIST）将云计算定义为一种模型，通过这种模型，人们可以方便、按需地通过网络访问可配置的计算资源共享池。

云计算的历史发展¶

timeline title 云计算发展历程 1960 : 计算机时代共享 1990s : 互联网兴起 1999 : Salesforce引入SaaS概念 2006 : Amazon推出AWS 2008 : Google App Engine推出 2010 : Microsoft推出Azure 2011 : 云计算标准开始形成 2015 : 容器技术兴起 2018 : 无服务器计算普及 2020+ : 多云和混合云战略成主流

云计算的核心特性¶

云计算有五个基本特性，这几条把它和传统 IT 服务模式区分开：

  1. 按需自助服务：用户可以在需要时自行配置计算能力，无需人工干预
  2. 广泛的网络访问：能力可通过标准机制和各种设备使用
  3. 资源池化：提供商的计算资源被池化以服务多个客户
  4. 快速弹性：资源可以迅速扩展和释放
  5. 服务可计量：自动控制和优化资源使用

三种服务模型要分层看：IaaS、PaaS、SaaS¶

云计算通常分为三种核心服务模型：IaaS、PaaS和SaaS，它们构成了现代云计算的基本框架。

graph TD A[云计算服务模型] --> B[IaaS - 基础设施即服务] A --> C[PaaS - 平台即服务] A --> D[SaaS - 软件即服务] B --> B1[计算资源] B --> B2[存储资源] B --> B3[网络资源] C --> C1[开发环境] C --> C2[中间件] C --> C3[数据库服务] C --> C4[监控和日志] D --> D1[最终用户应用] D --> D2[CRM/ERP系统] D --> D3[协作工具]

IaaS（基础设施即服务）¶

IaaS提供了基本的计算、存储和网络资源等基础设施服务。用户不需要管理或控制底层云基础设施，但可以控制操作系统、存储和部署的应用程序。

主要组件包括：

  • 计算资源：云虚拟机和裸金属服务器
  • 存储资源：云硬盘、对象存储、文件存储NAS
  • 网络资源：虚拟私有网络(VPC)、公网弹性IP、NAT网关

PaaS（平台即服务）¶

PaaS在IaaS的基础上提供了更高层次的抽象，允许开发者在预配置的环境中构建、测试和部署应用程序，无需关心底层基础设施。主要组件包括：

  • 应用托管：Web应用服务、容器服务
  • 开发工具：CI/CD平台、开发环境
  • 数据库服务：关系型数据库、NoSQL数据库
  • 中间件：消息队列、API网关
  • 监控和日志：ELK堆栈、APM工具

SaaS（软件即服务）¶

SaaS直接向最终用户提供现成的应用程序服务，用户只需通过互联网接入，无需安装或维护。主要包括：

  • 协作工具：Office 365、Google Workspace
  • CRM/ERP系统：Salesforce、SAP
  • 通信和协作：Slack、Zoom
  • 文件存储与共享：Dropbox、OneDrive

部署模式怎么选：公有、私有、混合、多云¶

pie title 云计算部署模式市场份额 "公有云" : 60 "私有云" : 20 "混合云" : 15 "多云" : 5

公有云¶

公有云的基础设施由第三方云服务提供商拥有和运营，通过公共互联网提供服务。主要提供商包括：

  • 国际云服务提供商：AWS、Microsoft Azure、Google Cloud Platform
  • 国内云服务提供商：阿里云、腾讯云、华为云

私有云¶

私有云是为单个组织专用的云基础设施，可以由组织自己或第三方管理，可以位于本地或其他位置。

混合云¶

混合云结合了公有云和私有云的特点，允许数据和应用程序在两者之间共享。

多云策略¶

多云是指企业使用来自多个公有云提供商的服务的策略，以避免供应商锁定并优化成本和性能。

云原生绕不开 Kubernetes¶

云原生是一种构建和运行应用程序的方法，它充分利用云计算模型的优势。Kubernetes已成为容器编排的事实标准。

🔥Kubernetes 的组件分工
控制平面负责决策（调度、API、控制器），工作节点负责执行（kubelet、运行时、代理），两者通过 apiserver 联动。

Kubernetes架构¶

flowchart TB subgraph "控制平面组件" A[kube-apiserver] --- B[etcd] A --- C[kube-scheduler] A --- D[kube-controller-manager] end subgraph "工作节点组件" E[kubelet] --- F[容器运行时] E --- G[kube-proxy] end A -.-> E

Kubernetes核心组件¶

  • 控制平面组件：

    • kube-apiserver：提供Kubernetes API服务
    • etcd：持久化存储集群数据
    • kube-scheduler：为新创建的Pod分配节点
    • kube-controller-manager：运行控制器进程

  • 工作节点组件：

    • kubelet：确保容器运行在Pod中
    • kube-proxy：维护节点上的网络规则
    • 容器运行时：运行容器，如containerd

存储资源管理¶

Kubernetes通过持久卷（PV）和持久卷声明（PVC）管理存储资源：

graph LR A[PersistentVolume] -- 提供存储 --> B[PersistentVolumeClaim] B -- 挂载到 --> C[Pod] D[StorageClass] -- 动态创建 --> A

PV是集群范围的资源，与namespace无关，而PVC绑定到特定namespace，这种设计支持资源共享并简化管理。

服务网格用 Istio 把流量、安全、观察统一起来¶

Istio是一个服务网格，提供了连接、安全、控制和观察服务的统一方式。

Istio架构¶

graph TB subgraph "控制平面" A[Pilot] --- B[Mixer] B --- C[Citadel] end subgraph "数据平面" D[Envoy Proxy] --- E[Envoy Proxy] E --- F[Envoy Proxy] end A -.-> D A -.-> E A -.-> F

Istio功能特性¶

Istio提供了多项关键功能：

  • 流量管理：智能路由、负载均衡、故障恢复
  • 安全：服务间和终端用户通信的自动TLS加密
  • 可观察性：跟踪、监控和日志记录
  • 策略执行：资源访问控制和限制

云安全的责任要分清：谁负责哪一块¶

云计算面临多种安全挑战，包括数据保护、合规性、访问管理和供应商锁定。

graph TD A[云安全挑战] --> B[数据安全] A --> C[身份和访问管理] A --> D[合规性] A --> E[供应商锁定] A --> F[共享责任模型] B --> B1[数据加密] B --> B2[数据隔离] C --> C1[多因素认证] C --> C2[最小权限原则] D --> D1[行业标准] D --> D2[区域法规] F --> F1[客户责任] F --> F2[提供商责任]

共享责任模型¶

在云计算环境中，安全责任由云提供商和客户共同承担：

  • 云提供商负责：基础设施、物理安全、网络基础设施
  • 客户负责：数据、应用、身份、访问管理

安全最佳实践¶

  • 实施身份和访问管理(IAM)
  • 加密传输中和静态数据
  • 定期安全审计和合规检查
  • 实施网络安全组策略
  • 保持软件和系统更新

成本优化从规格、计费和闲置资源下手¶

有效管理云计算成本是企业面临的主要挑战之一。

flowchart TD A[云成本优化策略] --> B[资源适当规模] A --> C[预留实例] A --> D[自动伸缩] A --> E[资源标记] A --> F[闲置资源管理] B --> B1[右侧调整] B --> B2[下侧调整] C --> C1[承诺使用折扣] D --> D1[基于需求自动扩展] E --> E1[成本分配] F --> F1[识别和删除未使用资源]

成本优化策略¶

  • 按需与预付费选择：结合按需计费与包年包月以平衡灵活性和成本
  • 监控和分析：持续监控资源使用情况，识别优化机会
  • 自动化：使用自动伸缩来适应负载变化
  • 闲置资源管理：识别和回收未使用的资源

多云和混合云用来避免被一家绑死¶

多云和混合云策略允许组织利用不同云提供商的优势，同时避免供应商锁定。

graph LR A[企业数据中心] -- 专用连接 --> B[公有云A] A -- VPN --> C[公有云B] B -- 云互联 --> C D[分支机构] -- SD-WAN --> A

混合云实施注意事项¶

  • 网络连接：VPC对等连接、VPN或专线
  • 身份管理：跨云身份联合
  • 安全性：一致的安全策略
  • 数据管理：数据一致性和复制策略

云原生应用的架构原则¶

云原生应用设计包括多个关键原则和技术：

graph TD A[云原生应用] --> B[微服务架构] A --> C[容器化] A --> D[DevOps实践] A --> E[声明式API] A --> F[自动化] B --> B1[服务解耦] B --> B2[独立部署] C --> C1[Docker] C --> C2[标准化环境] D --> D1[CI/CD管道] D --> D2[自动测试] E --> E1[基础设施即代码] F --> F1[自我修复系统]

十二要素应用¶

云原生应用通常遵循十二要素应用方法学，包括：

  1. 基准代码
  2. 依赖项隔离
  3. 配置外部化
  4. 后端服务作为附加资源
  5. 严格分离构建和运行阶段
  6. 以无状态进程运行
  7. 通过端口绑定导出服务
  8. 通过进程模型实现扩展
  9. 快速启动和优雅关闭
  10. 开发、预发布和生产环境保持最大相似性
  11. 将日志视为事件流
  12. 将管理任务作为一次性进程运行

未来趋势：边缘、无服务器、AI 和绿色计算¶

mindmap root((云计算未来)) 边缘计算 低延迟应用 IoT设备整合 多云/混合云 云互操作性 无缝集成 无服务器计算 更精细的资源控制 事件驱动架构 AI/ML即服务 预测分析 智能自动化 可持续计算 能源效率 绿色数据中心

未来趋势分析¶

  • 边缘计算：计算资源向数据生成点靠近，减少延迟
  • 无服务器计算：自动扩展和按使用量计费的计算模型
  • 人工智能和机器学习集成：云提供AI/ML能力作为服务
  • 可持续计算：更高效和环保的数据中心

落地结论¶

云计算已经是现代 IT 基础设施的支柱。选公有云、私有云还是混合方案，都要回到业务需求、安全要求和预算约束这三条上——先定好这些，再谈具体技术栈。
