02-版本发展与架构演进

知道 Apollo 是什么之后，再看它怎么一点点长成现在这样。版本不理顺，后面聊 ADFM、Cyber RT、包化开发很容易对不上号。
📅 2026-11-18· 更新于 2026-11-18 · 3466 字 · 约 9 分钟 ✍ zeek.zhao #方案#apollo

知道 Apollo 是什么之后，再看它怎么一点点长成现在这样。版本不理顺，后面聊 ADFM、Cyber RT、包化开发很容易对不上号。本篇接着 01-百度Apollo概述与生态 往下。

1. 版本里程碑：1.0 到 11.0¶

版本 时间 核心能力
1.0 2017.07 封闭场地自动驾驶，高精地图 + 定位
1.5 2017.09 固定车道巡航，简单城市道路能力
2.0 2018.01 简单城市道路自动驾驶，感知/规划/控制闭环
2.5 2018.04 特定区域、特定场景自动驾驶
3.0 2018.07 量产架构，复杂城市道路与高速场景
3.5 2019.01 引入 Cyber RT 框架，替代 ROS
5.0 2019.09 L4 级多场景，车路协同
5.5 2020.01 自动泊车与智能小车场景增强
6.0 2020.09 点云感知升级，深度学习模型加强
7.0 2021 模块解耦，强化学习规划探索，云服务起步
8.0 2022 场景化工具链，量产化推进
9.0 2023 支持包化模块开发，推出 DreamView Plus

11.0 2026.01 面向功能车低速场景的专用版本

几个关键节点值得单独说。10.0（2024 年 12 月）搭载全球首个支持 L4 的自动驾驶大模型 ADFM，感知用 BEV+Transformer+占据栅格网络，系统整体资源使用降低 50%，首次实现单块 NVIDIA Orin 支撑 L4，并打通 ROS 生态、支持物理机直接安装与批量部署。11.0 在 2026 年 1 月 30 日发布，面向”功能车”低速场景——无人配送、环卫清扫、安防巡逻、园区接驳，包含坡道启停、贴边行驶、闸机识别、异常自动恢复等能力；定位重建为 RTK + SLAM + 视觉 + 轮速计融合的厘米级方案。

2. 三条演进主线¶

2.1 通信框架：ROS → Cyber RT → ROS 互操作¶

  • 1.0–3.0：基于 ROS。ROS 在自动驾驶场景下暴露出单点故障（Master 中心化）、大消息吞吐不足、实时性受限等问题。
  • 3.5 起：引入自研 Cyber RT。核心改进包括协程调度、无锁队列、共享内存通信、去中心化服务发现，显著提升吞吐与确定性延迟。
  • 10.0 起：反向打通 ROS 生态，支持 ROS 消息互转，降低生态迁移成本。

2.2 感知：单传感器 → 多传感器融合 → BEV 大模型¶

  • 早期以单激光雷达 + 相机为主的模块化感知。
  • 6.0 前后强化多传感器融合与深度学习模型。
  • 10.0 起采用 BEV+Transformer+占据栅格网络，从”先检测后融合”演进为统一鸟瞰空间表征，并引入大模型 ADFM 统一感知-决策能力。

2.4 Cyber RT 带来的四个质变¶

Cyber RT 替代 ROS 后，架构上发生了几个质变：

维度 ROS 时代 Cyber RT 时代
通信拓扑 Master 中心化，单点故障 去中心化服务发现
调度 进程级回调 协程级调度，支持优先级
传输 TCP/UDP 为主 共享内存 + 无锁队列
实时性 无法保证确定性延迟 高吞吐、低确定性延迟
资源 各节点独立进程 组件可同进程按 DAG 编排

这些改进让感知到控制的端到端延迟显著降低，是 Apollo 能支撑 L4 实时性要求的基础。

2.3 规划控制：规则型 → 学习型 → 端到端探索¶

  • 早期以规则、优化（QP/MPC）为主的规划器。
  • 7.0 引入基于强化学习的规划控制模型。
  • 10.0 的 ADFM 大模型推动感知-决策走向数据驱动的端到端方向。

3. 10.0 与 11.0 差在哪¶

3.1 Apollo 10.0（2024.12）——大模型上车¶

  • ADFM 大模型：全球首个支持 L4 的自动驾驶大模型，统一感知-决策能力
  • 感知重构：BEV + Transformer + 占据栅格网络
  • 算力突破：系统整体资源使用降低 50%，首次实现单 NVIDIA Orin 支撑 L4
  • 生态开放：打通 ROS 生态，支持物理机直接安装与批量部署

3.2 Apollo 11.0（2026.01）——功能车场景¶

  • 目标场景：无人配送、环卫清扫、安防巡逻、园区接驳等低速”功能车”场景
  • 新增能力：坡道启停、贴边行驶、闸机识别、异常自动恢复
  • 定位重建：RTK + SLAM + 视觉 + 轮速计融合，厘米级精度，适应 GPS 遮挡环境

3.3 两代定位差在哪¶

维度 10.0 11.0
目标场景 城市 L4（Robotaxi） 低速功能车
核心技术 ADFM 大模型、BEV 感知 场景化功能集
算力 单 Orin 支撑 L4 低成本平台
定位 沿用 MSF 多传感器融合 RTK+SLAM+视觉+轮速计重建
部署 物理机直装、批量部署 面向功能车批量投放

两代的分工其实很清楚：10.0 解决 L4 的算力经济性，11.0 解决低速场景的商业闭环。Apollo 也借此从”研究平台”走向量产平台。

4. 模块解耦降低了二开门槛¶

7.0 起感知、预测、规划等模块进一步解耦；9.0 引入包化模块开发：模块能作为独立包构建、分发、加载，不必编译整个平台，配合 DreamView Plus 提供更现代的可视化界面。二次开发门槛因此降了不少，相关实践见 04-开发环境搭建-Docker 与 05-源码编译与部署。

5. tag 只到 9.0，之后看 master¶

GitHub 上的 tag 止于 apollo-v9.0.0（2023 年）。10.0 与 11.0 走 Apollo 开放平台发布，代码落在仓库 master 分支。要固定版本做开发，建议 pin commit 而不是依赖 tag。

获取渠道 覆盖版本 建议
GitHub tag ≤ 9.0 教学、源码研究
master 分支 10.0 / 11.0 pin commit 使用
Apollo 开放平台 10.0 / 11.0 官方工具链与文档配套

6. 不同诉求怎么选版本¶

不同版本适合不同诉求：

  • 快速体验完整功能：选择当前主线版本（10.0/11.0），支持物理机直装，部署最便捷。
  • 稳定研究与教学：选择 9.0 等有明确 tag 的版本，环境资料丰富。
  • 源码入门学习：可从 7.0/8.0 等结构相对清晰的版本入手，再对照新版理解演进差异。
  • 版本匹配约束：高版本对 Ubuntu、Docker 镜像与硬件驱动要求更高，搭建环境前务必查阅对应版本官方安装文档，详见 04-开发环境搭建-Docker。

要我选，研究和教学就用 9.0，tag 稳、资料多；真做算法研发才上 10.0。

6.1 演进对开发的实际影响¶

理解版本演进对实际开发的直接影响：

  • 学习源码：建议选择有稳定 tag 的版本（≤9.0），结构清晰、资料丰富
  • 二次开发：需关注模块接口在各版本间的变化，包化开发（9.0+）可只构建目标模块
  • 生产部署：跟随主线版本（10.0/11.0），享受算力优化与物理机直装红利，但需自行 pin commit 管理版本
  • 环境依赖：升级版本前先核对 Ubuntu/CUDA/驱动矩阵，避免环境不匹配

6.2 三步定版本¶

7. 往下走的三个方向¶

  • 模块解耦与标准化：包化开发持续深化，降低二次开发成本
  • 数据驱动比重提升：大模型、仿真与云端工具链愈发重要
  • 量产化与车规化：2025 年 1 月软件框架获 ASIL D 功能安全认证，与国产芯片、域控制器生态深度融合

想抠演进细节，读 Release Notes 最靠谱，这是掌握版本细节最快的途径。理解之后可以进 03-自动驾驶技术基础 补齐领域知识，也可以直接跳到环境搭建动手。

操作步骤 / 使用流程¶

  1. 明确目的：是复现论文、做产品原型，还是学习架构？不同目的选不同版本。
  2. 查 Release Notes：在 GitHub Releases 阅读对应版本的变更说明。
  3. 切 tag：用 git checkout vX.Y.Z，记录当前 commit 便于复现。
  4. 对架构：对照前文版本表，确认该版本的通信框架与模块划分。
  5. 编译验证：按 05-源码编译与部署 编译，跑通基础模块。
  6. 差异核对：用 git diff 对比相邻版本模块变化，形成自己的演进笔记。

注意事项与常见坑¶

  1. tag 不全：很多镜像只保留到 9.0 的 tag，更老版本需从源码自行 checkout。
  2. master 不稳定：主分支持续变动，不适合复现实验，务必用 tag。
  3. 跨版本 API 变化：Cyber RT 的 Component/Writer 接口在版本间有调整，代码不能盲目复制。
  4. ROS 与 Cyber RT 混用：3.5 是分水岭，阅读老文档时先确认版本。
  5. 配置文件格式差异：不同版本 conf/dag 字段不同，直接套用会启动失败。
  6. 依赖镜像版本：Docker 镜像 tag 与源码 tag 需匹配，否则编译环境不一致。
  7. 模块边界变动：某些模块在新版本被拆分或合并，目录结构不能凭记忆。
  8. Release Notes 不全：部分变更只在 commit message 里，需结合 git log 查。
  9. 端到端标签滥用：「端到端」在不同版本含义不同，参见 38-端到端自动驾驶与大模型。
  10. 升级路径坑：跨大版本升级建议逐版本验证，不要一次跳多个版本。
