32-历史版本模块演进（2.0-5.0）

聊版本史容易写成流水账，这篇换个角度：盯着感知、框架、场景三条线，看 2.0 到 5.0 到底变了什么。本篇接着 31-Cyber-Transform与坐标变换 往下。
📅 2026-10-19· 更新于 2026-10-19 · 4254 字 · 约 11 分钟 ✍ zeek.zhao #实战#apollo

聊版本史容易写成流水账，这篇换个角度：盯着感知、框架、场景三条线，看 2.0 到 5.0 到底变了什么。本篇接着 31-Cyber-Transform与坐标变换 往下。

1. 三条主线看懂演进¶

2.0 到 5.0 是 Apollo 从封闭场地走向开放道路、从单场景走向多场景的一段。我把这一阶段拆成三条线来看：

  1. 感知路线：相机+雷达简单组合 → 多传感器融合 → 深度学习强化的点云感知
  2. 框架路线：ROS → 场景化决策 → Cyber RT 高性能实时框架
  3. 场景路线：封闭场地 → 简单城市道路 → 复杂城市+高速多场景

这三条线是后面场景实战（33-车道级导航与决策、36-高速场景）的底子，也解释了后续技术从哪来：6.0/7.0 的端到端探索见 38-端到端自动驾驶与大模型，10.0 的大模型混合架构同样踩在这里。

演进到 5.0 还没停。Apollo 10.0（2024.12）发布全球首个支持 L4 的自动驾驶大模型 ADFM，用单 NVIDIA Orin 平台撑起 L4，整体资源使用降低 50%；Apollo 11.0（2026.1）又进一步面向功能车低速场景。历史里确立的”场景化+规则兜底”，到现在还是 Apollo 混合架构的骨架。

timeline title Apollo 关键版本演进 2018.1 : Apollo 2.0 : 支持简单城市道路自动驾驶 2018.7 : Apollo 3.0 : 支持复杂城市道路和高速，量产规划启动 2019.1 : Apollo 3.5 : 引入 Cyber RT，替代 ROS 2019.9 : Apollo 5.0 : 全面升级感知、规划和控制，支持 3.5 万公里城市场景

2. 四个版本差在哪¶

版本 感知 规划 平台框架 场景能力
2.0 相机+雷达 规则规划 ROS 简单城市道路
3.0 多传感器 场景决策 ROS 复杂城市+高速
3.5 融合感知 城市道路 Cyber RT 城市道路主航道
5.0 点云升级 多场景 Cyber RT 3.5 万公里城市场景

2.1 Apollo 2.0：简单城市道路的起点¶

感知是相机加毫米波雷达，障碍物检测靠传统 CV 方法，能认出红绿灯、车道线和常规车辆。规划用基于规则的状态机，场景概念刚冒头（Lane Follow、Stop Sign 等）。平台沿用 ROS，当时够用，但延迟和调度能力已经开始露瓶颈。

2.2 Apollo 3.0：量产化与多传感器¶

多传感器融合架构在这里落地，激光雷达、相机、毫米波雷达各管一摊。规划提出 Scenario（场景）决策体系，不同工况切不同策略——这套设计一直延续到今天。同期还发布了硬件平台和车辆参考设计，商业化明显提速。

2.3 Apollo 3.5：Cyber RT 的确立¶

3.5 是框架层面的分水岭，Cyber RT 在这里替掉 ROS。三处改动值得记住：共享内存传输减少数据拷贝，点云这类大数据延迟明显下降；调度单位换成协程，支持任务优先级和 CPU 亲和性绑定；模块依赖用 DAG（有向无环图）描述，启动编排更灵活。

Cyber RT 的动机说白了就是补 ROS 的短板——topic 通信延迟不可控、多核利用效率低、缺数据缓存和确定性调度。抓住这一点，Cyber 的源码就好读了。

2.4 Apollo 5.0：感知与规划的全面强化¶

点云检测网络升级，加了语义分割辅助，障碍物检测的精度和召回率都往上走了一截。规划侧支持 3.5 万公里城市场景，场景库大幅扩充，红绿灯倒计时、借道绕行这些能力落地。预测模块也引入学习型模型，行人横穿、变道意图预测更准。

3. 两个分水岭与两条暗线¶

真正改变系统上限的是 3.5 引入的 Cyber RT，通信和调度能力从这里定下来；决定系统下限的是 5.0 的点云感知与融合，感知数据质量从这里抬上去。

另外两条线埋得更深。一条是车路协同，3.0 期就布局 V2X，把路侧信息接进整车决策（见 39-车路协同与V2X）。另一条是规划从规则走向场景化——Scenario 体系让决策可维护、可扩展，后来端到端混合架构里的”规则兜底”就靠它打底。

4. 按版本读源码的顺序¶

我的建议是从旧往新读，别反过来。旧版实现简单，容易看清问题本身；新版功能全，但复杂度也高。具体顺序：

  1. 先读 2.0 的 Planning 规则实现，把问题本质摸清
  2. 对比 3.5 前后的通信框架差异，理解 Cyber RT 为什么这么设计
  3. 再看 5.0 的场景库组织方式，理解 Scenario 注册机制

新版本往哪走，接着看 38-端到端自动驾驶与大模型 和 39-车路协同与V2X。

5. 三个版本怎么读¶

落到代码上，三个版本各有各的读法。2.0 结构简单、规划逻辑清晰，适合入门。3.5 引入 Cyber RT 后可以对比通信框架差异，重点看 cyber/ 目录。5.0 的感知与规划体系趋于完整，适合精读。

我习惯按模块纵向对比，比如把 2.0 和 5.0 的 planning 目录摆在一起看接口和算法怎么变，重点问一句”为什么改”，而不只是”改了什么”。

注意事项与常见坑¶

  • 别把不同版本的实现混着看：这是读版本史最大的坑，2.0 的 ROS 节点和 3.5 的 Cyber 组件接口完全不同，混读会得出错误结论。
  • tag 与文档要对上：官方 Release Notes 描述的功能可能跨多个小版本，看源码前先确认 tag 精确对应。
  • checkout 前清理工作区：直接切 tag 会带着未提交改动，轻则冲突重则丢代码，务必用干净工作区或 worktree。
  • 配置字段不通用：3.5 的 proto 配置拿到 5.0 常常字段不认识，启动报 unknown field，按版本读对应的 conf/ 示例。
  • 地图版本与拓扑图版本要一致：RoutingRequest.map_version() 与拓扑图不匹配会出现 lane NotFoundError，先核对版本再查算法。
  • 场景优先级冲突：多个 Scenario 的 IsTransferable 同时为 true 会导致行为震荡，设计时必须做互斥或显式排序。
  • **别只盯”改了什么”**：版本对比的价值在”为什么改”，比如 Cyber RT 替 ROS 是为了延迟和确定性调度，理解动机才能迁移经验。
  • 社区文章可能滞后：第三方解读常把 5.0 和 6.0 的能力混写，涉及具体版本号时以官方 Release Notes 和源码为准。
  • 代码里的示例参数不是标定值：仓库 conf/ 里的阈值是参考起点，实车要按传感器和场地重新标定。
  • 别用 master 分支代表某个历史版本：master 一直在变，看 5.0 必须切 v5.0.0 这类固定 tag。
