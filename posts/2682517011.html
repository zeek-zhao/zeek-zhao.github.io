11-Apollo Cyber RT框架

为什么 Apollo 弃用 ROS 自研 Cyber RT，它靠什么撑住实时性和大流量数据，以及 Node、Channel、Component、Scheduler 这几个概念怎么用。
📅 2026-11-09· 更新于 2026-11-09 · 4301 字 · 约 11 分钟 ✍ zeek.zhao #实战#apollo

前面几篇讲的模块都跑在同一套运行时上，这篇就来看这块底座：Apollo 为什么从 ROS 换到自研的 Cyber RT，它的分层和几个核心概念是什么。本篇接着 10-CAN总线与车辆控制接口 往下。

1. 为什么弃用 ROS¶

Apollo 早期版本（1.0-3.0）基于 ROS。系统规模一扩大，ROS 在自动驾驶场景下的局限就暴露出来：

局限 具体表现
实时性不足 调度依赖操作系统，消息延迟波动大，缺乏优先级调度
性能瓶颈 进程间通信开销大，高带宽传感器数据（点云/图像）传输效率低
可靠性问题 错误隔离不完善，单点故障易扩散；缺乏故障检测恢复机制
资源管理局限 缺乏精细的资源分配与隔离，难以适应车载受限环境

Apollo 3.5 起引入自研的 Cyber RT（Runtime）框架，全面替换 ROS。

1.1 设计目标¶

  • 高性能：低延迟、高吞吐通信，支持点云/图像级大流量数据；共享内存零拷贝
  • 确定性实时：基于协程的调度，可预测的任务执行时序，优先级保障关键任务
  • 可靠性：模块间故障隔离，组件级错误检测与恢复
  • 灵活性：组件化架构、插件式扩展、分布式部署能力
  • 资源隔离：CPU 亲和性、优先级配额、过载保护

一句话概括 Cyber RT：用协程调度 + 共享内存通信 + 组件化编程模型，为自动驾驶定制的高性能运行时。后面讲的消息通信、组件开发都架在这三个支点上。

2. 五个核心概念¶

概念 说明
Node 节点，通信基本单位；创建并管理 Writer/Reader/Service/Client
Channel 通道，消息传递的逻辑媒介（类似话题 Topic）
Writer / Reader 向通道发布 / 从通道订阅消息
Component 数据驱动的可复用计算组件（见 12-Cyber消息通信与组件开发）
TimerComponent 定时器驱动的组件，按固定周期执行
Scheduler 调度器，基于协程管理任务执行
CRoutine 协程，Cyber 任务的最小执行单位
Shared Memory 共享内存传输，大流量数据零拷贝
Service / Client 请求-响应式服务通信
Parameter 全局参数服务

3. 四层架构怎么分工¶

  • 应用层只面向框架层标准接口编程，不触碰底层实现——这正是各模块可独立开发测试的原因
  • 运行时层是性能核心：协程调度降低上下文切换开销；进程内直接传指针、进程间共享内存、跨机走网络，传输路径自动选择
  • 硬件抽象层保证框架可从工控机移植到 Orin 等 ARM 平台

我判断运行时层才是 Cyber RT 真正的护城河：应用层接口换起来不算难，底下的调度和传输路径才是别处抄不走的东西。

3.1 调度器与协程（概览）¶

Cyber RT 的调度器基于协程实现：组件回调以协程方式执行，协作式切换在用户态完成，避免线程频繁切换的内核开销。支持两种调度策略：

  • 经典调度（Classic）：全局优先级队列统一调度
  • 编排调度（Choreography）：特定任务绑定特定 CPU 核心，提高缓存亲和性与确定性

调度策略通过配置文件指定，可设置核绑定与任务优先级。协程模型让开发者以同步方式写异步逻辑，是 Cyber RT 高性能的关键。调度系统、时间系统、异步机制的源码级解析见第四阶段专题（25-31 篇）。

3.2 通信机制概览¶

层级 传输方式 适用
进程内 共享指针直接传递，零拷贝 同进程高频数据
进程间 共享内存 同主机模块间（点云/图像）
跨机 优化的网络协议 多机部署

消息通信模型与代码级用法见 12-Cyber消息通信与组件开发。

4. 和 ROS 差在哪¶

维度 Cyber RT ROS
通信性能 共享内存优先，高效零拷贝 TCP/UDP 中间件，开销较大
调度机制 协程调度，低开销切换 依赖 OS 线程调度
实时性 优先级调度，确定性保障 实时性弱，不确定性高
资源管理 细粒度控制与隔离 依赖 OS，粒度较粗
生态 聚焦自动驾驶，生态内聚 通用机器人生态丰富

选型参考：产品化自动驾驶优先实时性选 Cyber RT；科研教学与快速原型可利用 ROS 生态。从 ROS 迁移的要点：节点 → Node/Component、话题消息 → Cyber proto 定义、launch → Cyber launch 配置，迁移后验证消息频率、延迟与数据一致性。

有两处更新值得补一句：Apollo 10.0 打通了 ROS 软件生态，ROS 工具和已有 ROS 代码能更低成本地接进来，软件复用成本降了不少；9.0 起又支持包化模块开发（package-based module development），模块以独立包形式开发部署，不再强制依赖完整源码仓库，Cyber 组件的打包发布也更工程化。

代码示例与实现细节¶

示例 1：组件类层次（ComponentBase / Component / TimerComponent） —— 解决「组件有哪些基类、生命周期如何定义」。

常见坑：Component<T> 的 Proc 带数据参数，TimerComponent 的 Proc 不带参数，别混用模板签名。

示例 2：数据发布-订阅（pub-sub） —— 解决「如何在一个组件里写数据、另一个组件里收数据」。

调参：通道名用 /apollo/... 层级命名，便于 cyber_channel 工具过滤；消息里一定要带时间戳，回放同步全靠它。

示例 3：服务-客户端（同步 + 异步调用） —— 解决「请求-响应式交互怎么写」。

常见坑：同步调用必须设超时，服务进程挂掉时无超时的调用会把客户端协程永久卡住。

示例 4：协程创建与让出（yield / resume） —— 解决「协程任务如何创建与协作式切换」。

常见坑：协程是协作式的，单个协程里做长循环不 yield 会饿死同处理器的其他任务；计算密集任务要主动分片让出。

示例 5：调度器配置（classic / choreography） —— 解决「怎么选调度策略、怎么绑核」。

调参：控制这类延迟敏感任务用 choreography 绑独立核；普通任务用 classic 共享队列即可。

示例 6：资源隔离配置（CPU 绑核 + 内存限额） —— 解决「关键任务如何不被其他模块挤占资源」。

常见坑：绑核配置要留几个核心给系统进程，全绑满会让内核线程没地方跑，反而增加抖动。

示例 7：DataVisitor 多源数据融合 —— 解决「多传感器数据如何按时间窗口对齐」。

常见坑：同步窗口设太小（如 10ms）会频繁拿不到对齐数据，设太大引入陈旧数据；相机 10-30Hz、激光 10-20Hz 时 100ms 是常用起点。

示例 8：定时器（时间轮周期任务） —— 解决「周期任务如何按固定频率触发」。

调参：时间轮工作轮 512 bucket × 2ms、辅助轮 64 bucket，累计误差由框架补偿；周期 <2ms 的任务不要用 Timer，精度不够。

示例 9：参数服务读写与变更回调 —— 解决「全局配置如何在组件间共享、运行时热更新」。

常见坑：参数变更回调在参数服务线程里执行，回调里做重活会阻塞其他参数的通知；耗时操作要另起任务。

示例 10：Record 录制与回放 —— 解决「如何录数据、按时间段回放调试」。

常见坑：录 all 通道时点云数据几十 MB/s，磁盘很快写满；调试通常只录问题相关通道。

注意事项与常见坑¶

  1. 协程不主动 yield：协作式调度下长循环不 yield 会饿死同处理器任务，计算密集逻辑要分片让出。
  2. 优先级数值方向：Cyber 里优先级数值越小越高，设反了关键任务反而被低优先级挤占。
  3. 同步服务调用无超时：服务端异常时客户端永久阻塞；必须设超时（如 1000ms）。
  4. DataVisitor 窗口过小：多传感器同步窗口太紧会频繁凑不齐数据，返回空导致处理流程停摆。
  5. 通道命名不规范：随意命名会让 cyber_channel 过滤和回放选择变困难，统一用 /apollo/... 层级。
  6. 消息缺时间戳：没有时间戳无法做回放同步与数据对齐，proto 里务必带 timestamp 字段。
  7. 绑核过满：把所有核心都绑给业务进程，系统线程无核可用，调度抖动反而变大。
  8. 录制全通道撑爆磁盘：点云通道几十 MB/s，调试只录相关通道。
  9. 进程内共享指针的生命周期：零拷贝传的是对象引用，订阅者若在回调外异步持有指针，发布者更新后数据会被覆盖；需要深拷贝时自行拷贝。
  10. 参数回调里做重活：参数变更回调阻塞通知线程，影响其他参数热更新。
  11. 组件 Proc 签名混淆：Component<T> 的 Proc 带数据参数，TimerComponent 不带，模板用错直接编译失败。
  12. 忽略 ROS 兼容更新：Apollo 10.0 已打通 ROS 生态，迁移时别再从零重写已有 ROS 代码。
