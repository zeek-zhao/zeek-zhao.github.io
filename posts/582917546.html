Repo 多仓库管理工具

Repo 是 Google 开发的、建立在 Git 之上的多仓库管理工具，专门用来解决大型项目里”一个项目拆成几百个 Git 仓库”之后怎么统一下载、同步、分支和提审的问题。我的判断是：只要项目规模到了需要多人多模块协作、且各模块独立发版，Repo 比手写 git 循环或 submodule 更省事；它最早服务于 Android，现在也广泛用于各类大型工程。

引入 Repo 是为了把几十上百个仓库当成一个项目来管¶

在大型项目开发中，模块化和组件化是常见的软件架构方式。这种架构下，各模块通常作为独立的 Git 仓库存在，每个仓库独立管理自己的版本。Repo 的主要优势包括：

  • 统一管理：能够同时处理数十甚至上百个 Git 仓库
  • 批量操作：使用一条命令在多个仓库上执行相同操作
  • 版本一致性：通过manifest文件确保项目各组件版本的一致性
  • 工作流简化：简化了分支创建、代码同步和提交流程
  • 代码审核集成：与 Gerrit 等代码审核系统无缝集成

对于 Android 这样的大型项目，包含数百个子项目和开源组件，如果没有统一的管理工具，版本控制将变得极其复杂。

Repo 诞生于 Android 的多仓库拆分实践¶

使用 Repo 前最好先熟悉 Git 基础知识。Repo 最初是为 Android 开源项目开发的，旨在解决管理数百个独立 Git 仓库的挑战。Android 源代码分散在多个仓库中，这种结构有以下优势：

  1. 允许团队只检出他们需要的组件
  2. 减少单一仓库过大导致的性能问题
  3. 更好地控制各组件的访问权限

Repo 作为这些 Git 仓库之上的协调层，简化了开发流程和版本管理。

Manifest文件¶

Manifest（清单）文件是Repo的核心，它使用XML格式定义项目结构，包含各个Git仓库的位置、分支和检出路径等信息。典型的manifest文件结构如下：

主要元素说明：

元素 说明
<remote> 定义远程服务器，包含fetch（Git URL前缀）和name（远程名称）属性
<default> 定义默认属性，如默认remote、revision和并行任务数
<project> 定义一个项目仓库，包含name（仓库名）和path（本地路径）等属性
<linkfile> 创建从项目中的文件到工作目录的符号链接
<copyfile> 复制项目中的文件到工作目录

命令速查按使用频率排列，forall 是最值得掌握的批量入口¶

Repo提供了一系列命令来管理多仓库环境，下面详细介绍这些命令。

repo help¶

显示repo帮助信息。不带参数时显示所有可用命令，带参数时显示指定命令的详细帮助。

repo version¶

显示repo的版本号。

repo selfupdate¶

更新repo工具自身到最新版本。通常在repo sync时会自动执行，无需手动调用。

repo init¶

初始化repo工作环境。这是使用repo的第一步，该命令会:

  1. 创建.repo目录
  2. 下载repo主体代码
  3. 克隆manifest仓库

重要选项：

  • -u <url>: 指定manifest仓库的URL（必需）
  • -m <name>: 指定使用的manifest文件，默认为default.xml
  • -b <branch>: 指定manifest仓库的分支
  • --repo-url=<url>: 指定repo工具源码的URL
  • --no-repo-verify: 不验证repo源码
  • --mirror: 创建镜像仓库而非工作目录

repo sync¶

同步工作目录，下载新的更改并更新本地文件。这是获取或更新代码的主要命令。

重要选项：

  • -c, --current-branch: 只同步当前分支
  • -d, --detach: 将项目切换到manifest指定的修订版本
  • -j <num>, --jobs=<num>: 并行下载的任务数
  • -f, --force-sync: 如需要，强制覆盖本地更改
  • --no-clone-bundle: 不使用Git bundle文件进行初始克隆

重要参数：

  • <branch-name>: 新分支的名称
  • <projects>...: 要在哪些项目上创建分支，使用.表示当前目录的项目

  • 第一列（大写）表示暂存区与HEAD的差异
  • 第二列（小写）表示工作区与暂存区的差异

repo checkout¶

切换到已存在的分支。这是git checkout命令的多仓库版本。

repo branch¶

显示当前可用的主题分支。等同于repo branches命令。

repo diff¶

显示工作区与HEAD之间的差异。这是git diff的多仓库版本。

repo stage¶

交互式地将更改添加到暂存区。相当于git add --interactive。

repo forall¶

在每个项目上执行指定的shell命令。这是一个非常强大的批处理命令。

环境变量：
在命令执行环境中可以使用以下特殊环境变量：

  • $REPO_PROJECT: 当前项目名称
  • $REPO_PATH: 项目在工作区中的相对路径
  • $REPO_REMOTE: 项目远程仓库名称
  • $REPO_LREV: 本地分支名
  • $REPO_RREV: 远程分支名

示例：

repo prune¶

删除已经合并的分支。相当于git branch -d。

repo abandon¶

删除指定的主题分支。相当于git branch -D，会强制删除分支。

repo upload¶

将本地分支上传到代码审核服务器(如Gerrit)。这个命令需要manifest中配置了review属性。

重要选项：

  • --re=<reviewers>: 指定代码审核者
  • --cc=<cc>: 添加抄送人员
  • -t: 包含本地分支名信息

repo download¶

从代码审核服务器下载特定的变更集。用于审核别人提交的代码。

repo grep¶

在项目文件中搜索指定模式。这是git grep的多仓库版本。

repo manifest¶

管理manifest文件的工具。

重要选项：

  • -r, --revision-as-HEAD: 将当前修订版本存为HEAD
  • -o <file>: 输出manifest到指定文件

2. 如何在现有项目中引入Repo管理？¶

  1. 创建manifest仓库并定义项目结构
  2. 在新的工作目录执行repo init和repo sync
  3. 将现有代码复制到对应目录并提交
  4. 推送到各自的Git仓库

3. repo sync和git pull有什么区别？¶

  • git pull只更新单个仓库的单个分支
  • repo sync可以：
    • 同步manifest中的所有项目
    • 处理新增项目的克隆
    • 按照manifest中指定的修订版本更新
    • 并行处理多个项目
    • 处理项目间的依赖关系

4. 如何处理repo sync中的冲突？¶

处理步骤：

  1. 查看冲突文件：git status
  2. 解决冲突
  3. 将解决的文件添加到暂存区：git add <files>
  4. 继续变基：git rebase --continue
  5. 完成后继续同步：repo sync

和 Submodules、Subtree、Bazel 比，Repo 管的是源码不是构建¶

Repo vs Git Submodules¶

功能 Repo Git Submodules
多仓库管理 ✅ ✅
代码审核集成 ✅ ❌
并行同步 ✅ ❌
分支管理 集中式 分散式
学习曲线 中等 较陡
自定义工作流 灵活 有限
适用场景 大型项目 小型依赖

Repo vs Git Subtree¶

功能 Repo Git Subtree
多仓库管理 ✅ ✅
历史保留 完全保留 可选保留
单独更新子项目 简单 复杂
对贡献者友好 ✅ ❌
复杂度 中等 高

Repo vs 构建工具 (Bazel/Buck)¶

功能 Repo Bazel/Buck
主要目的 源代码管理 构建系统
版本控制集成 原生 需配置
依赖管理 项目级 精细级
构建优化 ❌ ✅
