29-can总线协议与编程基础

做嵌入式或者车载通信，迟早会撞上 CAN——两根线、没有主机、靠 ID 抢优先级，这些特性让它在强干扰环境里特别稳。我在实际用的时候，最先确认的永远是三件事：波特率和终端电阻对不对、ID 分配有没有冲突、错误计数器是不是在涨。这篇按我排查问题的顺序，把协议原理、硬件实现、编程方法和 Linux 下的 SocketCAN 串起来。

1. 协议定位：无主机的多主串行总线，为实时通信而生¶

CAN（Controller Area Network，控制器局域网）是一种用于实时应用的串行通信总线标准，最初由Robert Bosch GmbH公司于1986年开发，旨在解决汽车内部电子控制单元（ECU）之间的通信需求。CAN总线以其高可靠性、实时性和抗干扰能力，成为汽车电子系统和工业控制领域广泛应用的通信标准。

我在实际用的时候，最先确认的永远是波特率和两端终端电阻——这两项对不上，后面所有协议分析都白搭。

1.1 发展史：从 1983 年 Bosch 立项到 CAN FD 商用¶

  • 1983年 - Bosch公司开始开发CAN协议
  • 1986年 - CAN协议首次公开发布
  • 1991年 - 首款完全符合CAN规范的芯片出现（Intel 82526和Philips 82C200）
  • 1993年 - ISO 11898标准发布，规范了CAN的物理层和数据链路层
  • 1995年 - 高速CAN标准ISO 11898-2发布，定义了高速CAN的物理层
  • 2000年 - 低速容错CAN标准ISO 11898-3发布
  • 2003年 - Bosch发布CAN FD（CAN with Flexible Data-rate）规范，扩展CAN数据速率
  • 2012年 - ISO发布ISO 11898-1:2015，包含CAN FD标准
  • 2015年 - CAN FD进入商业化阶段
  • 现在 - CAN和CAN FD广泛应用于汽车、工业自动化、医疗设备等领域

1.2 特性：多主、按消息寻址、非破坏仲裁与强纠错¶

CAN总线具有以下主要特性：

  • 多主控制：所有节点均可在总线空闲时发起通信，无中央控制器
  • 消息传输：基于消息发送而非节点寻址，每条消息具有唯一标识符
  • 优先级仲裁：基于标识符的非破坏性总线仲裁，数值较低的标识符优先级更高
  • 错误检测能力：包含CRC校验、位填充、帧检查等多重错误检测机制
  • 错误限制：设备会自动跟踪错误统计，在发生多次错误时自动退出总线
  • 差分信号传输：使用双线差分信号传输，具有较强的抗干扰能力
  • 灵活的网络拓扑：支持总线拓扑，无需主控设备
  • 多节点能力：理论上支持无限个节点，实际取决于总线电气特性，通常为30-110个
  • 通信距离：高速CAN可达1000米（低速），40米（1Mbps）
  • 传输速率：标准CAN最高1Mbps，CAN FD最高8Mbps

CAN协议在汽车、工业自动化、医疗设备和航空航天等领域的广泛应用，证明了其作为一种可靠通信协议的卓越价值，尤其在要求安全关键和实时通信的场景中。

2. 通信原理：差分电平、帧结构与逐位仲裁¶

2.1 电平：显性约 2V 差分，隐性约 0V 差分¶

CAN总线采用差分信号传输方式，使用两条线：CAN_H（CAN高）和CAN_L（CAN低）。通过这两条线上的电压差实现数据传输：

踩过的坑是拿普通单端探头量 CAN_H 对地，波形看着像有干扰；换成差分探头看两线压差，一切就清楚了。

  1. **显性状态(Dominant, 逻辑0)**：

    • CAN_H：约3.5V
    • CAN_L：约1.5V
    • 差分电压：约2V

  2. **隐性状态(Recessive, 逻辑1)**：

    • CAN_H：约2.5V
    • CAN_L：约2.5V
    • 差分电压：约0V

2.1.1 物理层规范

CAN协议规定的物理层主要有以下几种：

  1. 高速CAN (ISO 11898-2):

    • 波特率：最高1Mbps
    • 总线长度：最长40米(1Mbps)，最长1000米(50kbps)
    • 需要两端终端电阻（通常为120Ω）

  2. 低速容错CAN (ISO 11898-3):

    • 波特率：最高125kbps
    • 总线长度：最长500米
    • 允许节点掉线而系统仍能运行

  3. 单线CAN (SAE J2411):

    • 使用单导线和地
    • 主要用于非关键应用
    • 波特率：33.3kbps
    • 成本更低

2.2 帧类型：数据帧、远程帧、错误帧与过载帧¶

CAN协议定义了四种不同类型的帧：

  1. 数据帧：用于传输数据
  2. 远程帧：请求特定标识符的数据
  3. 错误帧：当检测到错误时发送
  4. 过载帧：表示节点尚未准备好接收更多数据

CAN协议有两种不同的帧格式版本：

2.2.1 标准CAN帧格式（CAN 2.0A）

标准CAN帧（也称为基本CAN帧）包含11位标识符，其结构如下：

  • SOF位：起始位，总是显性(0)
  • 标识符（11位）：消息优先级/ID
  • RTR位：远程传输请求位，数据帧为0，远程帧为1
  • IDE位：标识符扩展位，标准帧为0
  • r0位：保留位
  • DLC（4位）：数据长度码，表示数据字节数(0-8)
  • 数据（0-8字节）：实际数据内容
  • CRC（15位）：循环冗余校验
  • CRC界定符：总是隐性(1)
  • ACK槽：发送方发送隐性(1)，任何接收方可发送显性(0)表示确认
  • ACK界定符：总是隐性(1)
  • EOF（7位）：帧结束标志，全部为隐性(1)
  • IFS（3位）：帧间隔，全部为隐性(1)

2.2.2 扩展CAN帧格式（CAN 2.0B）

扩展CAN帧包含29位标识符（11位基本ID + 18位扩展ID），其结构如下：

  • SOF位：起始位，总是显性(0)
  • 标识符A（11位）：基本标识符
  • SRR位：替代远程请求位，总是隐性(1)
  • IDE位：标识符扩展位，扩展帧为1
  • 标识符B（18位）：扩展标识符
  • RTR位：远程传输请求位
  • r1, r0位：保留位
  • DLC（4位）：数据长度码
  • 数据（0-8字节）：实际数据内容
  • CRC（15位）：循环冗余校验
  • CRC界定符，ACK槽，ACK界定符，EOF，IFS：与标准帧相同

2.2.3 CAN FD帧格式

CAN FD（CAN with Flexible Data-rate）在2012年引入，扩展了传统CAN的功能：

  • 支持更大的数据负载（最多64字节，相比传统CAN的8字节）
  • 可在数据阶段使用更高的比特率（最高8Mbps）
  • 使用改进的CRC计算

CAN FD帧格式类似于标准CAN帧，但有以下不同：

  • 增加了FDF位（Flexible Data Format）
  • 增加了BRS位（Bit Rate Switch），指示是否切换到更高速率
  • 增加了ESI位（Error State Indicator）
  • DLC可表示0-64字节数据（0-8字节与传统CAN相同，9-15表示12,16,20,24,32,48,64字节）
  • 使用更长的CRC字段（17位或21位，取决于数据长度）

2.3 接收链路：同步、过滤、校验、应答四步¶

CAN节点在接收消息时经历以下过程：

  1. 位同步：所有接收方同步到总线速率
  2. 帧检测：检测帧起始位
  3. 标识符过滤：根据标识符决定是否接收消息
  4. 帧验证：检查帧格式和CRC
  5. 应答：在ACK槽发送显性位表示成功接收
  6. 消息传递：将有效消息传递给上层应用

CAN控制器通常提供硬件过滤机制，允许节点只接收感兴趣的消息：

  • 掩码过滤：使用标识符掩码指定关注的位
  • 接收列表：维护关注的标识符列表
  • 组过滤：基于标识符范围的过滤

2.4 仲裁：ID 数值越小优先级越高且不丢数据¶

CAN总线的非破坏性仲裁是其关键特性之一，工作原理如下：

  1. 总线空闲时，任何节点可以开始发送
  2. 多个节点同时发送时，会逐位比较标识符
  3. 当节点发送隐性位(1)但监测到总线为显性(0)时，它会意识到存在优先级更高的消息
  4. 发现冲突的节点会立即停止发送，转为接收模式
  5. 具有最低数值标识符（最高优先级）的消息将赢得仲裁

这种仲裁机制确保了：

  • 不会丢失任何数据
  • 优先级最高的消息总是优先传输
  • 总线利用率最大化

节点A标识符: 00101011000 (优先级较高)
节点B标识符: 00110100000 (优先级较低)

节点A发送: 0 0 1 0 1 0 1 1 0 0 0
节点B发送: 0 0 1 1 0 1 0 0 0 0 0
总线状态: 0 0 1 0 1 0 1 0 0 0 0

3. 错误处理：五种检测加三个错误状态¶

CAN协议的可靠性很大程度上来自其强大的错误检测和处理机制。

我一般先看 TEC/REC 这两个计数器，节点是在报偶发错还是正在往 Bus Off 走，比抓一堆错误帧更能说明问题。

3.1 五种错误：位、填充、CRC、格式与应答¶

CAN协议定义了5种错误检测机制：

  1. 位错误：发送方监控总线，如果检测到的位值与发送的不符（仲裁和应答字段除外），则产生位错误

  2. 填充错误：当检测到6个连续相同的位（违反位填充规则）时产生

  3. CRC错误：接收方计算的CRC与接收到的CRC不匹配

  4. 帧格式错误：固定格式的位域（如CRC界定符、ACK界定符）值不符合规范

  5. 应答错误：发送方未在ACK槽检测到显性位（表示没有接收方确认接收到消息）

3.2 三态迁移：主动、被动到总线关闭¶

每个CAN节点维护两个错误计数器：

  • 发送错误计数器（TEC - Transmit Error Counter）
  • 接收错误计数器（REC - Receive Error Counter）

根据这些计数器的值，节点可处于三种状态之一：

  1. **错误主动(Error Active)**：

    • 正常操作状态
    • 当检测到错误时，发送错误标志（6个连续显性位）
    • TEC < 128 且 REC < 128

  2. **错误被动(Error Passive)**：

    • 仍参与总线通信，但发送被动错误标志（6个连续隐性位）
    • 发送后需等待额外的8位时间才能再次发送
    • TEC ≥ 128 或 REC ≥ 128

  3. **总线关闭(Bus Off)**：

    • 完全停止总线活动
    • 只有在软件请求并且监测到128次11个连续的隐性位后才重新连接
    • TEC > 255

错误计数规则（简化版）：

  • 发送帧错误：TEC + 8
  • 接收帧错误：REC + 1
  • 成功发送帧：TEC - 1（如果TEC > 0）
  • 成功接收帧：REC - 1（如果1 ≤ REC ≤ 127）

这种机制确保了：

  • 偶发性错误不会导致节点关闭
  • 持续产生错误的节点会被自动隔离
  • 暂时性干扰对网络影响最小

3.3 错误帧：主动发显性位，被动发隐性位¶

当节点检测到错误时，它会立即发送错误帧：

  • 主动错误帧：由错误主动节点发送，包含6个连续显性位（违反位填充规则）
  • 被动错误帧：由错误被动节点发送，包含6个连续隐性位

错误帧的发送会破坏当前正在传输的消息，导致所有其他节点也检测到错误（通常是帧格式错误），并丢弃该消息。原消息的发送方将在稍后自动重试。

4.1 分工：控制器跑协议，收发器管电平¶

CAN系统的硬件实现通常分为两部分：

选型时我习惯先定收发器再挑控制器：收发器决定电气鲁棒性，控制器决定过滤和缓冲能力，后者不够只能靠软件补。

4.1.1 CAN控制器

CAN控制器负责协议的实现，包括：

  • 帧的生成和解码
  • 位定时和同步
  • 错误检测和处理
  • 消息过滤
  • 缓冲区管理
  • 与主机处理器的接口

典型的CAN控制器包含以下组件：

  1. 消息缓冲区：存储待发送和接收到的消息
  2. 位定时逻辑：生成和同步总线时序
  3. 仲裁逻辑：处理消息优先级
  4. 错误管理逻辑：维护错误计数器
  5. 过滤逻辑：筛选接收的消息
  6. 控制寄存器：配置控制器行为
  7. 状态寄存器：指示控制器状态
  8. 中断逻辑：生成主机中断

CAN控制器可以是独立芯片（如MCP2515），也可以集成在微控制器内部（如STM32、NXP等）。

4.1.2 CAN收发器

CAN收发器（也称为CAN转换器）是连接CAN控制器和物理总线的接口，负责：

  • 将控制器的逻辑电平转换为总线差分信号
  • 提供总线驱动能力
  • 保护控制器免受总线电气干扰
  • 提供电气隔离（某些型号）

典型的CAN收发器（如TJA1050或MCP2551）包含：

  1. 发送器：将TXD转换为差分信号（CAN_H和CAN_L）
  2. 接收器：将差分信号转换为RXD
  3. 静默模式控制：允许禁用发送器但保持接收
  4. 待机/低功耗模式：降低功耗
  5. 保护电路：防止过压、过流和短路

6. 高级协议：CAN FD、CANopen、DeviceNet 与 J1939¶

在CAN的基础上，已发展出多种高级协议，用于特定领域应用。

实测下来，选高层协议别看功能多，得看对手设备支持什么——现场大多数分歧都是 CANopen 和 J1939 混用造成的。

6.1 CAN FD：64 字节载荷加 8Mbps 数据段¶

CAN FD是传统CAN的扩展，提供两个主要增强：

  1. 更大的数据负载：从8字节扩展到最多64字节
  2. 更高的数据传输速率：数据阶段可以使用更高的比特率（最高8Mbps）

CAN FD帧格式与传统CAN有以下主要区别：

  • 引入FDF（Flexible Data Format）位指示CAN FD格式
  • 引入BRS（Bit Rate Switch）位指示是否切换到更高数据速率
  • 引入ESI（Error State Indicator）位指示发送节点的错误状态
  • 扩展DLC编码允许更长数据负载
  • 更强的CRC校验（17位或21位，取决于数据长度）

CAN FD保持与传统CAN的兼容性——传统CAN节点可以接收CAN FD帧的第一部分（但会发送错误帧），而CAN FD节点可以完全处理传统CAN帧。

使用CAN FD的优势：

  • 减少大数据传输所需的帧数，提高带宽利用率
  • 减少长消息传输延迟
  • 提高总线利用率
  • 通过改进的CRC提高可靠性

6.2 CANopen：对象字典加 PDO/SDO 一套标准服务¶

CANopen是一个基于CAN的高层协议，主要用于工业自动化和嵌入式系统：

6.2.1 CANopen主要特征

  • 标准化通信配置文件：定义了设备间通信的标准方法
  • 对象字典：每个设备包含一个标准化的对象字典，存储所有配置参数和过程数据
  • 标准化设备配置文件：针对常见设备类型（伺服驱动器、I/O模块等）定义标准接口
  • 网络管理（NMT）：定义节点状态控制
  • 服务数据对象（SDO）：用于访问设备对象字典
  • 过程数据对象（PDO）：用于高效的实时数据传输

6.2.2 CANopen协议服务

  1. NMT（网络管理）：控制节点的运行状态

    • 使用标识符0x000（最高优先级）
    • 命令包括：启动节点、停止节点、进入预操作状态、复位节点

  2. PDO（过程数据对象）：用于周期性数据交换

    • 无需请求/响应机制
    • 最多8字节数据（CAN FD下更多）
    • 传输可由事件触发或周期性

  3. SDO（服务数据对象）：用于参数访问和配置

    • 请求/响应机制
    • 可访问设备对象字典中的任何条目
    • 支持分段传输（用于大数据）

  4. SYNC（同步）：提供系统同步

    • 触发同步PDO传输
    • 确保系统范围内的同步动作

  5. TIME（时间戳）：提供网络时间同步

    • 主站发送绝对时间给所有节点

  6. EMCY（紧急消息）：报告错误状态

    • 通知网络有关重要错误事件
    • 使用高优先级标识符

6.3 DeviceNet：生产者/消费者模型，集成 24V 供电¶

DeviceNet是一个基于CAN的工业自动化协议，由Allen-Bradley（现在的Rockwell Automation）开发，后由ODVA（Open DeviceNet Vendor Association）维护：

6.3.1 DeviceNet特征

  • 物理层：使用经过修改的CAN物理层，集成电源

  • 通信模型：基于生产者/消费者模型

  • 连接类型：

    • 主/从（明确消息）：I/O轮询
    • 点对点（明确消息）：点对点通信
    • 多点（隐式消息）：多广播

  • 消息类型：

    • I/O消息：周期性过程数据交换
    • 明确消息：参数访问（类似CANopen的SDO）
    • 寻址：
      • MAC ID（物理地址，0-63）
      • 消息ID（功能代码 + MAC ID）

6.3.2 DeviceNet网络特性

  • 支持最多64个节点
  • 集成24V DC电源配送
  • 标准电缆和连接器（圆形和扁平电缆）
  • 网络长度和速率：
    • 500 kbps: 最大100米
    • 250 kbps: 最大250米
    • 125 kbps: 最大500米

6.4 J1939：29 位 ID 拆成优先级、PGN 和源地址¶

J1939是由SAE（Society of Automotive Engineers）开发的高层协议，用于商用车辆网络：

6.4.1 J1939特征

  • 扩展标识符：使用29位CAN标识符

  • 标识符结构：

    • 优先级字段（3位）
    • 参数组号（PGN，18位）
    • 源地址（8位）

  • 高级寻址：

    • 全球寻址（所有节点）
    • 目标特定寻址
    • 功能寻址（特定功能的所有节点）

  • 自动节点地址声明：动态地址分配

  • 传输协议：支持多达1785字节的消息传输

  • 诊断支持：标准故障代码和诊断消息

  • 标准参数组：定义标准消息内容

6.4.2 J1939应用

J1939主要用于：

  • 商用卡车和公共汽车
  • 农业和林业机械
  • 建筑和采矿设备
  • 发电机组和工业设备

7.3 设计清单：布线、ID 分配、带宽和信号映射¶

设计稳健的CAN网络应考虑以下最佳实践：

我一般先做带宽预算再定 ID：把周期消息的负载加起来，超过 70% 就该拆网或降频，别等跑起来丢帧再回头改。

7.3.1 物理层设计

  1. 布线实践：

    • 使用高质量的双绞线（阻抗120Ω）
    • 减少分支和降低分支长度
    • 保持足够的信号完整性
    • 避免与高压或射频信号平行布线

  2. 终端电阻：

    • 正确安装120Ω终端电阻，仅在总线两端
    • 考虑使用分离终端减少EMI
    • 确保系统范围内总阻抗约为60Ω

  3. 接地和屏蔽：

    • 妥善接地电缆屏蔽层，通常仅在一端
    • 避免接地环路
    • 在高噪声环境中使用光电隔离

7.3.2 协议层设计

  1. 标识符分配：

    • 基于消息优先级分配标识符，最重要的消息获得最低ID
    • 为相关功能组预留ID范围
    • 记录标识符分配方案

  2. 带宽管理：

    • 计算和控制网络负载，保持在最大容量的70%以下
    • 考虑最坏情况的总线负载
    • 平衡周期性消息和事件驱动消息
    • 适当选择消息传输频率

  3. 错误处理：

    • 实现超时监控机制
    • 定义明确的错误处理策略
    • 考虑功能安全要求

7.3.3 数据设计

  1. 消息内容：

    • 相关数据应分组在同一消息中
    • 优化数据格式，如信号类型转换
    • 明确定义未使用位的默认值

  2. 信号打包：

    • 有效利用可用带宽
    • 考虑字节对齐和位顺序
    • 记录信号缩放和偏移量

  3. 信号映射表：

    • 创建并维护详细的消息和信号映射
    • 包括标识符、信号名称、位置、缩放、单位等信息

7.3.4 测试与验证

  1. 循序渐进的测试：

    • 从单节点测试开始
    • 逐步添加节点并进行集成测试

  2. 故障注入：

    • 测试各种故障条件（断线、短路、节点故障）

8. 调试排障：先量电平和终端，再看计数器¶

8.1 常见问题：按物理层、链路层、应用层分层定位¶

8.1.1 物理层问题

  1. 总线终端问题：

    • 症状：间歇性通信失败，反射噪声
    • 解决方案：确认终端电阻正确安装且阻值准确，检查总线两端是否各有一个终端电阻

  2. 线缆和连接问题：

    • 症状：通信断断续续，噪声干扰
    • 解决方案：检查线缆完整性，确保接头牢固，使用优质双绞线

  3. 接地问题：

    • 症状：通信不稳定，电平漂移
    • 解决方案：检查接地连接，避免接地环路，确保适当接地屏蔽层

  4. 总线负载过高：

    • 症状：上升沿变慢，通信可靠性降低
    • 解决方案：减少节点数量，分段网络，检查总线电容

8.1.2 数据链路层问题

  1. 位定时错误：

    • 症状：特定速率下通信失败，错误帧频繁
    • 解决方案：检查并调整位定时参数，确保所有节点使用兼容的位定时

  2. 消息丢失：

    • 症状：部分消息未被接收
    • 解决方案：检查过滤器设置，验证总线负载，提高关键消息优先级

  3. 标识符冲突：

    • 症状：某些消息似乎被覆盖或丢失
    • 解决方案：确保网络中没有相同ID的消息，审查标识符分配

  4. 错误被动/总线关闭：

    • 症状：节点突然停止通信
    • 解决方案：检查错误计数器，解决持续错误原因，重置错误计数器

8.1.3 应用层问题

  1. 数据解释错误：

    • 症状：接收到的数据解析不正确
    • 解决方案：检查字节序和位顺序，确认信号定义一致

  2. 定时问题：

    • 症状：周期性消息间隔不一致
    • 解决方案：检查定时器配置，考虑总线负载的影响

  3. 协议不兼容：

    • 症状：高级协议功能无法正常工作
    • 解决方案：确保所有节点支持使用的协议版本和功能集

  • 向后兼容性：支持与传统CAN混合部署

  • LIN：低成本子网络，用于简单控制功能
  • 混合网络架构：多协议网关和区域控制器

11.3 OTA 与硬件安全模块进入 CAN 节点¶

未来CAN系统将更多地与无线技术和安全机制集成：

  • OTA更新：通过无线渠道更新CAN控制器固件
  • 远程诊断：从远程位置监控和分析CAN网络
  • 安全通信层：标准化的CAN安全通信协议栈
  • 集成入侵检测：CAN控制器集成安全监控功能
  • 硬件安全模块：专用硬件加速加密和认证

11.4 软件定义：从信号走向服务，CAN 接口被虚拟化¶

随着软件定义车辆和机器的趋势，CAN的角色正在演变：

  • **服务导向架构(SOA)**：高层通信基于服务而非信号
  • 虚拟化CAN接口：允许同一硬件上多个软件使用CAN
  • 中央网关：智能网关管理CAN与其他协议的转换
  • 人工智能应用：AI辅助CAN数据分析和预测性维护
  • 开发工具创新：CAN开发的协作和自动化工具

12. 落地要点：按优先级分 ID，把总线负载压到 70% 以下¶

真要落地一套 CAN 网络，我建议先定三件事再写代码：基于消息优先级分配标识符（最要紧的消息拿最低 ID）、把总线负载算清楚并控制在 70% 以下、在总线两端各装一个 120Ω 终端电阻。

  • 物理层：用优质差分双绞线，避免与高压线平行布线，屏蔽层只在一端接地。
  • 协议层：定义清晰的消息结构，实施明确的错误处理和超时监控。
  • 软件开发：用成熟驱动库，做可靠的硬件过滤，采用事件驱动架构并测透边缘情况。
  • 安全：对关键数据做认证，上监控和入侵检测，规划好安全更新机制。

先按这套清单把物理层调通，再用 can-utils 抓一段实际流量核对 ID 和周期，比一上来就啃协议手册省事得多。
