Linux驱动程序详解之mmap内存映射

做驱动久了，mmap 是我判断要不要上很干脆的一项技术。普通的 read/write 在用户态和内核态之间来回拷数据，小数据量看不出问题，可一旦碰上视频采集、LCD 显示这种一帧好几兆的场景，CPU 基本就被拷贝占满了——原文算过，1024×600×32bpp 刷一帧大约 2.3MB，频繁传输就是瓶颈。我的判断标准很简单：数据块一大、拷贝开始吃 CPU，就该换成映射。

1. mmap的作用：用一次映射省掉反复拷贝¶

1.1 read/write的拷贝瓶颈¶

在传统的应用程序和驱动程序之间传递数据时，通常使用read、write系统调用。这种方式需要在用户态buffer和内核态buffer之间复制数据，如下图所示：

graph TD A[应用程序] --> |write系统调用| B[用户空间缓冲区] B --> |数据复制| C[内核空间缓冲区] C --> |驱动处理| D[设备硬件] D --> |驱动处理| E[内核空间缓冲区] E --> |数据复制| F[用户空间缓冲区] F --> |read系统调用| G[应用程序]

这种方式在数据量较小时问题不大，但当数据量大时（如视频处理、图像显示等场景），数据复制会消耗大量CPU资源且效率低下。例如，更新1024×600×32bpp格式的LCD显示时，一帧数据约2.3MB，频繁传输会导致性能瓶颈。

我一般在这个环节就开始算拷贝开销：一次 write 加一次 read 至少两次跨态复制，数据量翻倍开销也跟着翻倍，这正是 mmap 要解决的地方。

1.2 mmap省掉拷贝的四个好处¶

mmap（内存映射）提供了一种解决方案，它可以将内核空间的缓冲区直接映射到用户空间，使应用程序能够直接读写这块内存，避免了数据复制的开销：

graph TD A[应用程序] --> |直接访问| B[用户空间映射区域] B --> |内存映射| C[内核空间缓冲区] C --> D[设备硬件]

mmap主要优势：

  • 减少数据复制，提高I/O效率
  • 降低系统调用开销
  • 支持共享内存，便于进程间通信
  • 适合处理大块数据

2. 映射的本质：相同虚拟地址落到不同物理页¶

2.1 内存映射现象¶

考虑以下程序示例：

如果在两个不同终端中运行此程序的两个实例，会发现一个有趣的现象：两个程序中变量a的地址是相同的，但它们的值各自独立。这就是虚拟内存映射的结果。

2.2 虚拟地址经MMU落到物理地址¶

这种现象的解释在于现代操作系统采用的虚拟内存管理机制：

graph TD A[CPU] --> |发出虚拟地址| B[MMU] B --> |查询页表| C[页表] B --> |转换为物理地址| D[物理内存] subgraph 进程1 E[虚拟地址0x6d73c0] --> F[值=12] end subgraph 进程2 G[虚拟地址0x6d73c0] --> H[值=123] end E --> |MMU映射| I[物理地址0x89a73c0] G --> |MMU映射| J[物理地址0x92b73c0]
  • CPU发出的是虚拟地址
  • MMU（内存管理单元）将虚拟地址转换为物理地址
  • 不同进程的相同虚拟地址会被映射到不同的物理地址
  • 这种机制使得每个进程都认为自己独占整个内存空间

我理解这块的关键是先记住一条：CPU 发出的永远是虚拟地址，真正决定落到哪块物理页的是 MMU。两个进程打印出同样的地址却互不影响，就是因为 MMU 把它们映射到了不同物理页。

2.3 四个关键数据结构¶

Linux内核中的内存映射涉及多个关键数据结构：

graph TD A[task_struct] --> |进程的内存管理| B[mm_struct] B --> |虚拟内存区域| C[vm_area_struct链表] B --> |页表目录| D[pgd] C --> E[代码段VMA] C --> F[数据段VMA] C --> G[堆VMA] C --> H[栈VMA] C --> I[共享库VMA] C --> J[mmap映射区VMA]

关键数据结构解析：

  • task_struct：进程描述符，描述一个进程的所有信息
  • mm_struct：内存描述符，管理进程的地址空间
  • vm_area_struct：虚拟内存区域，描述连续的虚拟地址范围及其属性
  • pgd：页全局目录，存储虚拟地址到物理地址的映射关系

3. ARM页表：一级段映射与二级细页映射¶

3.1 一级与二级页表结构¶

ARM架构支持一级和二级页表映射：

graph TD A[一级页表] --> B[1MB Section] A --> C[二级页表指针] C --> D[第二级页表] D --> E[4KB Small Page]
  • 一级页表：地址映射的最小单位是1MB
  • 二级页表：地址映射的最小单位是4KB（Linux中）

我一般把一级页表当成粗粒度入口、二级页表当成细粒度补充。32 位下 4GB 空间被切成 4096 个 1MB 的段，理解了这个拆分，后面的映射过程就顺了。

3.2 一级页表映射过程¶

一级页表映射的过程如下：

graph LR A[CPU虚拟地址 0x12345678] --> B[提取页表索引 0x123] B --> C[查找一级页表第0x123项] C --> D[获取段基地址 0x81000000] D --> E[加上偏移量 0x45678] E --> F[物理地址 0x81045678]

对于32位系统，虚拟地址空间为4GB，分为4096个1MB的段，每个段由一个页表项管理：

  1. MMU根据虚拟地址高12位(31:20)找到对应页表项
  2. 从页表项中获取段基地址
  3. 将段基地址与虚拟地址低20位组合得到物理地址

3.3 二级页表映射过程¶

二级页表映射的过程更复杂：

graph TD A[CPU虚拟地址 0x12345678] --> B[提取一级页表索引 0x123] B --> C[查找一级页表第0x123项] C --> D[获取二级页表基地址] A --> E[提取二级页表索引 0x45] E --> F[查找二级页表第0x45项] F --> G[获取页基地址 0x81889000] A --> H[提取页内偏移 0x678] G --> |组合| I[物理地址 0x81889678] H --> |组合| I

映射过程：

  1. 虚拟地址高12位(31:20)确定一级页表项
  2. 一级页表项指向二级页表
  3. 虚拟地址次8位(19:12)确定二级页表项
  4. 二级页表项包含页基址
  5. 页基址与虚拟地址低12位(11:0)组合得到物理地址

5. Cache与Buffer：四种内存访问策略怎么选¶

5.1 Cache与Buffer各管什么¶

在CPU和内存之间，有Cache和Buffer等中间层：

graph TD A[CPU] <--> B[L1 Cache] B <--> C[L2 Cache] C <--> D[写缓冲器] D <--> E[主存]

Cache：高速缓存，缓存最近使用的数据

  • 时间局部性：最近访问过的数据很可能再次被访问
  • 空间局部性：访问某个位置的数据，很可能接着访问附近位置的数据

**Buffer(写缓冲器)**：FIFO缓冲区，可将多个小写操作合并为一次大写操作

5.2 写通与写回两种策略¶

写通(Write Through)

数据同时写入Cache和内存，保持一致性但效率低。可以配合写缓冲器使用：

  • CPU写入Cache
  • Cache立即将数据传给写缓冲器
  • 写缓冲器异步写入内存

写回(Write Back)

数据只写入Cache，不立即写入内存：

  • 写入数据时，标记Cache行为”脏”(dirty)
  • 当Cache需要替换时，才将脏数据写回内存
  • 效率高但需要特别处理DMA等直接内存访问情况

5.3 四种组合策略怎么选¶

ARM架构提供四种Cache与Buffer组合策略：

graph TD A[内存访问策略] --> B["非缓存非缓冲(UC)"] A --> C["非缓存缓冲(WC)"] A --> D["缓存非缓冲(WT)"] A --> E["缓存缓冲(WB)"] B --> F["适用于寄存器访问"] C --> G["适用于显存操作"] D --> H["适用于只读设备"] E --> I["适用于普通内存"]

映射内存时的选择：

  • **UC (Uncached, Unbuffered)**：读写直达硬件，适合寄存器访问
  • **WC (Uncached, Buffered)**：写操作可能合并，适合显存等连续写操作
  • **WT (Cached, Unbuffered)**：使用读cache，写直达，适合只读设备
  • **WB (Cached, Buffered)**：完全使用cache和buffer，适合普通内存

6. 驱动实现：kmalloc连续内存加remap_pfn_range¶

6.1 三种内存分配方式对比¶

为了实现有效的mmap，驱动程序需要合适的内存分配方式：

方法 物理地址连续性 适用场景
kmalloc 连续 小块内存，需要DMA或mmap
vmalloc 不连续 大块内存，不适合mmap
dma_alloc_coherent 连续且DMA一致 需要DMA且无需手动刷新cache

对于mmap，通常选择kmalloc或kzalloc，因为它们提供物理连续的内存，便于映射。

实测下来，想让 mmap 稳定工作，缓冲区必须用 kmalloc/kzalloc 这类物理连续的内存；vmalloc 分出来的块虚拟连续但物理离散，不适合直接拿来做映射。

7. 用mmap的四个坑：一致性对齐安全与性能¶

7.1 缓存一致性问题¶

当使用cached映射时，需要注意CPU缓存和内存的一致性问题：

  • CPU修改后，DMA读取：需要清空CPU缓存（flush cache）

  • DMA修改后，CPU读取：需要使缓存失效（invalidate cache）

我一般的做法是把方向分清楚：CPU 写完给 DMA 读，就 msync 刷缓存；DMA 写完给 CPU 读，就重新映射让缓存失效。省掉这一步，数据不一致极难查。

7.2 对齐要求¶

  • mmap通常需要页对齐，Linux默认页大小为4KB
  • 映射的起始地址和大小通常需要是页大小的整数倍
  • 驱动程序应考虑对请求的偏移量和大小进行适当对齐

7.3 安全性考虑¶

  • 验证用户提供的参数，避免越界访问
  • 考虑权限控制，防止未授权访问设备内存
  • 处理用户空间访问错误，避免内核崩溃

7.4 性能优化¶

  • 合理选择缓存策略，根据访问模式优化
  • 考虑使用大页(Huge Pages)提高TLB命中率
  • 合理管理映射的生命周期，避免频繁映射/解映射

8. 落地检查清单¶

mmap 的价值归根到底就一条：把内核缓冲区直接铺到用户空间，省掉跨态拷贝。真要落地，我建议按这个顺序逐项检查——先确认缓冲区物理连续（kmalloc/kzalloc），再定好缓存属性（寄存器 UC、显存 WC、普通内存 WB），最后按页对齐映射并处理一致性（msync 或重新映射）。这三步都对了，性能瓶颈基本就不在 mmap 这一层了。
