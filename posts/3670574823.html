28-Cyber异步调用机制

cyber::Async 一行背后到底发生了什么。Async/Yield/SleepFor、TaskManager 的有界队列与协程池，还有 SysMo 怎么盯异步任务。
📅 2026-10-23· 更新于 2026-10-23 · 5352 字 · 约 14 分钟 ✍ zeek.zhao #概念#apollo

Cyber 的异步调用看着简单，cyber::Async 一行就完事，背后其实挂着队列、协程池和调度器一整套东西。这篇顺着这条调用链往下拆。消息驱动那条路走的是 29-Cyber数据系统详解，这里讲的是代码主动发起并发；底座仍是 26-Cyber调度系统详解 的协程。

1. 异步要解决什么问题¶

自动驾驶软件里这类需求反复出现。点云预处理耗时，但不该挡住主流程；MPC 求解可能超时；路径还要并行生成多套方案。Cyber 的异步机制就是围绕这几种情况设计的，目标有五个：

  1. 高性能：实模式下走协程，上下文切换开销近于零
  2. 易用：API 形态对齐 std::async，返回 std::future
  3. 灵活：协程/线程双模型，按运行模式自动切换
  4. 资源可控：有界队列 + 池化协程，防任务风暴
  5. 可观测：SysMo 持续输出协程执行快照

源码目录：cyber/task/（task.h、task_manager.h/cc）。

2. 四个异步原语¶

cyber/task/task.h 暴露四个原语：

接口 行为
Async(f, args...) 提交异步任务，返回 std::future
Yield() 让出执行权（协程让出 / 线程 yield）
SleepFor(dur) 异步休眠指定 Duration
USleep(us) 微秒级异步休眠

这里有个工程上的逃生门值得点出来：IsRealityMode() 为 false 时（仿真或单测，cyber::Init 前设 CYBER_AGENT 或 flag 控制），Async 会退化成 std::async 起线程。单测不用拉起整套调度器也能验业务逻辑，这一手挺实用。

3. TaskManager 怎么跑起来¶

3.1 结构与初始化¶

TaskManager 是进程级单例：一个有界队列 + 一组消费协程。

4. 异步池挂在调度器上¶

异步任务池不是独立的执行体系，而是调度器上的一组”命名协程”：

  • 优先级可控：在调度配置文件中给 task_xxx 前缀任务配置 prio，可让异步任务整体让位于控制任务
  • 亲和性可控：Choreography 策略下可绑定处理器
  • 与消息驱动任务竞争同一批 Processor：因此 TaskPoolSize 配置要量入为出，过大反而加剧队列锁与上下文切换竞争

5.3 五个常见的坑¶

  1. 协程里阻塞：回调中调用阻塞系统调用（read/cudaMemcpy 同步版）会钉死整个 Processor 线程，所有共驻协程遭殃
  2. future.get 死锁：在消费协程内 get 另一个永不完成的任务
  3. 队列积压：生产速率持续高于 TaskPoolSize 消化能力，1000 深的队列会掩盖问题直到爆发
  4. 数据竞争：future 返回前共享状态的写操作需同步，lambda 捕获引用要小心生命周期
  5. 小任务风暴：每个任务有队列 + future 开销，微任务应合并批处理

这五条里，我最想提醒的是第一条——协程看着轻量，一旦在里头做同步阻塞，遭殃的是整个 Processor 上的邻居。

  • task_N 名字表示异步任务池的协程——执行时间异常长说明有慢任务
  • 某处理器长时间不 idle 且同一协程名不变 → 疑似协程内阻塞
  • 配合 cyber_monitor 观察对应组件消息频率是否掉队

7. 与其他异步机制对比¶

特性 cyber::Async std::async ROS 回调队列
底层模型 协程（实）/线程（仿真） 线程 回调 + 线程池
返回值 std::future std::future 回调函数
资源限制 有界队列 + TaskPoolSize 无（系统资源） 队列长度
优先级/亲和 可经调度配置控制 仅 launch 策略 有限
运行时监控 SysMo 无 rqt 等外部工具

8. 一行 API 背后的四件套¶

cyber::Async 把四件事藏在了一行调用后面：packaged_task/future 桥接 + 有界队列背压 + 池化消费协程 + 调度器统一编排。Yield 和 SleepFor 是协程感知的通用原语，落到线程环境会自动退化。我更愿意把这套机制理解成一种约定：组件主流程保持短平快，重活一律异步化——Cyber 的应用差不多都按这个套路写。任务从哪来（消息驱动）见 29-Cyber数据系统详解，任务跑在什么环境（协程与优先级）见 26-Cyber调度系统详解。

2. 任务状态模型¶

这段解决「一个异步任务从提交到结束要经历哪些状态」的问题：Pending / Running / Waiting / Completed / Failed 五态流转。

3. Async 实现决策流程¶

这段解决「Async 在真实模式与仿真模式分别走哪条路」的问题：真实模式进 TaskManager 协程，仿真模式退化 std::async 线程。

参数怎么调：IsRealityMode 为 false 时（仿真/单测）走线程，业务不变；常见坑是单测里验证协程特性（如 SleepFor 不占线程）得到错误结论，须在真实模式测。

6. 链式异步调用¶

这段解决「多个异步任务有先后依赖怎么串」的问题：第二个任务 get 第一个的 future 结果。

10. 性能问题诊断矩阵¶

问题 可能原因 解决方案
任务执行延迟高 任务队列积压 增加协程数量、优化任务粒度

注意事项与常见坑¶

  1. 协程里做同步阻塞：read、cudaMemcpy 同步版等会钉死整个 Processor 线程，所有共驻协程遭殃；重 IO 必须异步化或移出协程。
  2. 链式任务同池互等：TaskPoolSize=1 时第二个任务 get 第一个的 future 会死锁；保证池大小≥2 或避免同池依赖。
  3. future 异常无人接：任务抛异常进 Failed 态且 future 析构时 rethrow，调用方要 try-catch 或 future.get 包在 try 内。
  4. 队列积压掩盖问题：1000 深队列让生产快于消费的问题延迟爆发，需监控队列长度与提交速率。
  5. lambda 捕获引用悬空：异步任务延迟执行，捕获局部变量的引用在任务运行时可能已析构，优先按值捕获或用 shared_ptr。
  6. 仿真模式验证协程特性：非真实模式 Async 退化为 std::async 线程，SleepFor 不占线程等特性须在真实模式验证。
  7. 小任务风暴：每个任务有队列与 future 开销，微任务应合并批处理，否则开销吞掉收益。
  8. 盲目加大 TaskPoolSize：过度增加协程会加剧队列锁与上下文切换竞争，应结合 SysMo 快照与队列指标调整。
  9. 超时后不处理残留任务：wait_for 超时后后台任务仍在跑，迟到结果可能覆盖新状态，降级逻辑要能容忍，见 40-安全机制与冗余设计。
  10. 共享数据无同步：异步任务并发访问共享状态必须加锁或用线程安全容器，数据竞争极难复现。
  11. 硬实时主逻辑用 Async：控制回路主流程应走组件 Proc + 高优先级调度，而非 future 异步，见 26-Cyber调度系统详解。
  12. 忽略任务优先级配置：异步池与消息任务共享 Processor，未配优先级时可能抢占关键控制任务，需在调度配置中为 task_ 前缀设 prio。
