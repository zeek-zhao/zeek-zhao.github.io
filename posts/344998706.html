话题通信

[!info] 本节目标
掌握 ROS2 话题通信机制，能用 rclcpp 与 rclpy 编写发布者/订阅者，并理解 QoS 的作用。

1. 话题通信模型

话题是异步单向通道：发布者（Publisher）向话题名写入消息，订阅者（Subscriber）从话题名读取消息。一对多、多对多皆可，两端完全解耦。

特性 说明
方向 单向异步
匹配 话题名 + 消息类型 + QoS
可靠性 由 QoS 决定（可靠/尽力）
适用 传感器流、状态流、命令流

2. Python 发布者

[!note] 运行
ros2 run my_py_pkg talker_node；队列深度 10 对应 QoS KEEP_LAST(10)。

[!tip] 订阅回调
回调在 Executor 线程中执行，避免在回调中做耗时操作（见 14-执行器与回调组）。

5. QoS 详解

QoS 项 取值 说明
Reliability RELIABLE / BEST_EFFORT 可靠重传或尽力送达
History KEEP_LAST / KEEP_ALL 保留最近 N 条或全部
Depth N KEEP_LAST 的队列深度
Durability VOLATILE / TRANSIENT_LOCAL 是否给迟到订阅者重发
Deadline 时长 最长消息间隔
Liveliness AUTOMATIC / MANUAL 节点存活判定

[!danger] QoS 匹配
发布端 RELIABLE、订阅端 BEST_EFFORT 可通信（订阅降级）；反向不可。传感器数据发布端常用 BEST_EFFORT，订阅端必须一致或更强。

6. 常见消息类型

消息 用途
std_msgs/msg/String 文本
sensor_msgs/msg/LaserScan 2D 激光
sensor_msgs/msg/Image 图像
nav_msgs/msg/Odometry 里程计
geometry_msgs/msg/Twist 速度指令

7. 命令行验证

现象 排查
无数据 话题名/类型不一致、QoS 不匹配
频率低 发布端节流、网络拥塞
延迟大 检查 QoS deadline、网络

[!note] 延伸
自定义消息类型见 13-自定义消息接口；QoS 深入见 33-实时性与QoS策略；多机通信见 29-多机器人协同。

8. 话题设计建议

话题设计应遵循单向数据流原则：发布方只负责产生数据，订阅方只负责消费数据，双方通过消息类型与话题名解耦。话题命名使用层级结构（如 /robot/laser/scan）便于命名空间隔离与权限管理。高频传感器数据使用 BEST_EFFORT 策略降低延迟，指令类数据使用 RELIABLE 保证可靠到达。调试阶段可用 ros2 topic echo 与 ros2 topic hz 确认数据频率与内容，排查发布端或订阅端问题。

[!note] 建议
话题是最常用的通信模式，掌握后应继续学习服务与动作，三者各有适用场景；QoS 细节见 33-实时性与QoS策略。
