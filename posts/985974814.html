2. 环节一：MCP 市场搜索无果¶

⚠️缺项确认
在 MCP 插件 / 市场层面直接搜索可用的「Jenkins MCP」条目时，未能直接命中满足「开箱即用连接内部实例」的官方入口——市场上缺少针对本实例可直接使用的 MCP 服务登记项，无法一步到位完成配置。

结论¶

  • 不能依赖「搜索即得」的现成接入项
  • 需要先确认 Jenkins 侧插件状态，再确定接入路线
  • 决定进入 web_search 调研可行的接入方案

3. 环节二：web_search 调研方案¶

通过联网搜索调研 Jenkins × MCP 的主流接入方案，检索到两条路线：

3.1 方案 A：官方 MCP Server 插件（服务端直连）¶

  • Jenkins 安装官方 MCP Server 插件
  • 插件暴露 HTTP 端点：/mcp-server/mcp
  • 客户端通过 SSE 直连端点
  • 优点：多客户端共享、服务端统一管理
  • 前提：需要插件安装权限，且 Jenkins 必须已安装该插件

3.2 方案 B：npx 桥接（本地 MCP Server 进程）¶

  • 本机通过 npx 启动 Jenkins MCP Server 进程
  • 客户端与该进程以 stdio 通信
  • 进程内部调用 Jenkins REST API，使用 API Token 认证
  • 优点：Jenkins 侧零改动、零插件、零重启

3.3 调研结论¶

维度 方案 A 方案 B
前提 插件已安装 / 可安装 有 API Token 即可
侵入性 需改 Jenkins 无
本次可行性 待探查插件状态 可行，作为兜底
🔥决策逻辑
优先验证方案 A 是否可用；若插件未安装且无安装权限，则采用方案 B。

10. 经验教训与后续建议¶

10.1 经验教训¶

🔥关键经验
  1. 先探查再选型：接入前先确认服务端插件状态，避免在 404 端点上浪费时间
  2. 桥接方案是低侵入首选：无插件权限时，npx 桥接 + API Token 即可完整接入
  3. Token 安全从生成时抓起：仅生成时可见，必须立即本地保存，文档中一律占位符
  4. 版本差异要识别：2.541.3 的 Token 入口在 Security 页而非 /me/configure，Token 为 32 位格式
  5. 查询即验证：getStatus / getJobs 返回真实数据，天然验证连接与权限

10.2 后续建议¶

  • 插件升级路线：若希望多客户端共享接入，可申请安装官方 MCP Server 插件后改用 SSE 直连
  • 报告增强：为「生成 NightlyBuild 任务状态报告」接入邮件 / IM 通知，异常构建主动告警
  • 离线节点治理：跟进 5 个离线节点的恢复（67.207 / 67.212 / 67.63 / 67.67 / 90.226）
  • Token 轮换：按季度轮换 marvis-mcp Token，纳入密码管理器
  • 知识沉淀：将常用查询固化为一组可复用提示词，提升每日巡检效率
