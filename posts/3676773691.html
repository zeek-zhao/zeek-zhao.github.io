KVM架构与CPU内存中断虚拟化

KVM 是把 Linux 变成一个 hypervisor 的内核模块。我一开始以为装个 KVM 模块就能跑虚拟机，后来发现真正做 I/O 模拟的是用户态的 QEMU，两边配合才是一套完整的虚拟化方案。

1. KVM是什么：内核里的hypervisor，配QEMU才完整¶

KVM (Kernel-based Virtual Machine) 是Linux内核的一个模块，可以将Linux转变为一个hypervisor。KVM于2007年被整合到Linux内核中，是目前主流的开源虚拟化解决方案之一。结合QEMU使用时，KVM提供了完整的虚拟机功能，包括CPU虚拟化、内存虚拟化和设备虚拟化。

KVM的主要优势在于：

  • 直接集成在Linux内核中，可利用Linux内核的全部功能
  • 利用硬件虚拟化技术(如Intel VT-x和AMD-V)，实现高性能虚拟化
  • 开源且成熟稳定
  • 与OpenStack等云平台良好集成

2. 架构：内核KVM模块管资源，用户态QEMU做I/O¶

2.1 基本架构：内核态模块与用户态QEMU的分工¶

KVM架构分为两个关键部分：

  1. 位于内核空间的KVM模块，负责虚拟机创建、虚拟内存分配、VCPU寄存器读写及VCPU运行
  2. 用户空间的QEMU，负责模拟虚拟机的I/O设备
flowchart TD subgraph "用户空间" QEMU["QEMU进程"] QEMU --> |ioctl| DevKVM["/dev/kvm设备"] end subgraph "内核空间" DevKVM --> KVM["KVM内核模块"] KVM --> |硬件虚拟化| CPU["物理CPU (VT-x/AMD-V)"] end subgraph "虚拟机" VM["虚拟机进程"] --> VCPU["vCPU"] VM --> VMem["虚拟内存"] VM --> VDev["虚拟设备"] end QEMU --> |I/O模拟| VM KVM --> |资源管理| VM

我读这张图会先找边界——ioctl是用户态和内核态的分界，虚机那块的资源其实由KVM模块在管。

2.2 三种执行模式：客户、用户与内核态¶

使用KVM后，系统有三种执行模式：

  1. 客户模式：执行Guest OS的非I/O指令
  2. 用户模式：执行I/O指令，QEMU运行于此模式
  3. 内核模式：实现客户模式切换，处理VM Exit事件，KVM模块运行于此模式

2.3 工作流程：VMLAUNCH进去，VM Exit出来¶

KVM的虚拟化工作流程如下：

sequenceDiagram participant User as 用户空间(QEMU) participant KVM as 内核空间(KVM模块) participant VMCS as VMCS participant CPU as 物理CPU User->>KVM: 通过ioctl创建VM和VCPU KVM->>KVM: 初始化数据结构 KVM->>User: 返回VM/VCPU描述符 User->>KVM: VCPU运行请求 KVM->>VMCS: 设置VMCS结构 KVM->>CPU: 执行VMLAUNCH指令 Note over CPU: VM Entry进入客户模式 CPU->>CPU: 执行Guest代码 alt 敏感指令或外部中断 CPU-->>VMCS: 记录退出信息 CPU->>KVM: VM Exit alt I/O操作 KVM->>User: 返回到QEMU处理I/O User->>KVM: 处理完成，继续运行 else 其他原因 KVM->>KVM: VMM自行处理 end KVM->>CPU: 继续执行(VMRESUME) end

3. CPU虚拟化：VT-x双模式加VMCS解决特权级压缩¶

3.1 VT-x：根模式与非根模式各有Ring 0到3¶

Intel的VT-x技术为CPU虚拟化提供了硬件支持，引入了两种操作模式：

  1. VMX根操作模式(Root Mode) - 用于运行VMM(即KVM)
  2. VMX非根操作模式(Non-Root Mode) - 用于运行客户操作系统

在每个模式下都有完整的Ring 0到Ring 3特权级，解决了传统虚拟化中的特权级压缩问题。

graph TD subgraph "根模式(KVM运行)" R0["Ring 0(KVM内核模块)"] R3["Ring 3(QEMU进程)"] R0 --- R3 end subgraph "非根模式(客户OS运行)" GR0["Ring 0(客户OS内核)"] GR3["Ring 3(客户OS用户程序)"] GR0 --- GR3 end R0 -->|VM Entry| GR0 GR0 -->|VM Exit| R0

踩过的坑是把根模式和非根模式的Ring 0搞混，理解成两套完整的0到3特权级之后，特权级压缩的问题就想通了。

3.2 VMCS：每个VCPU一份，存客户/主机状态与控制字段¶

VMCS(Virtual Machine Control Structure)是Intel VT-x引入的关键数据结构，每个VCPU都对应一个VMCS，用于存储:

  • 客户机状态(Guest-state area)
  • 宿主机状态(Host-state area)
  • VM执行控制字段(VM-execution control fields)
  • VM退出控制字段(VM-exit control fields)
  • VM进入控制字段(VM-entry control fields)

3.3 VCPU：kvm_vcpu与kvm_vcpu_arch的结构¶

KVM使用VCPU描述符来表示虚拟CPU，包含以下信息：

  • VCPU标识信息(ID、所属VM等)
  • 虚拟寄存器信息(保存在VMCS中)
  • VCPU状态信息(运行、阻塞、睡眠等)
  • 额外寄存器信息(浮点寄存器、虚拟APIC等)

4. 内存虚拟化：GVA到GPA再到HPA的两级转换¶

4.1 三层地址：GVA、GPA与HPA¶

在KVM虚拟化中，存在三种地址空间：

  1. 客户虚拟地址(GVA): Guest OS进程使用的虚拟地址
  2. 客户物理地址(GPA): Guest OS内核使用的”物理地址”
  3. 主机物理地址(HPA): 真实的物理内存地址

这三种地址空间的转换关系如下：

flowchart LR GVA["客户虚拟地址(GVA)"] -->|"Guest页表"| GPA["客户物理地址(GPA)"] GPA -->|"EPT/影子页表"| HPA["主机物理地址(HPA)"]

4.2 影子页表：软件直连GVA到HPA，同步开销大¶

影子页表是KVM早期使用的内存虚拟化技术，原理是VMM为每个Guest进程维护一套影子页表，直接将GVA映射到HPA。

flowchart TD GCR3["Guest CR3"] --> GPT["Guest页表"] GPT --> SPT["影子页表"] SPT --> HCR3["物理CR3"] GVA["GVA"] --> |"Guest OS查询"| GPT GVA --> |"物理MMU查询"| SPT SPT --> |"直接映射"| HPA["HPA"]

优点：访问内存时无需额外地址转换。
缺点：实现复杂，内存开销大，同步开销高。

4.3 EPT：硬件两级转换，缺页不再触发VM Exit¶

EPT是Intel提供的硬件辅助内存虚拟化技术，通过硬件支持两级地址转换：

flowchart LR GVA["客户虚拟地址"] -->|"Guest页表(硬件)"| GPA["客户物理地址"] GPA -->|"EPT页表(硬件)"| HPA["主机物理地址"]

EPT地址转换流程：

flowchart TD gCR3["Guest CR3(GPA)"] --> GuestPD["Guest页目录(GPA)"] GuestPD --> GuestPT["Guest页表(GPA)"] gCR3 -.->|"EPT转换"| hgCR3["Guest CR3(HPA)"] GuestPD -.->|"EPT转换"| hGuestPD["Guest页目录(HPA)"] GuestPT -.->|"EPT转换"| hGuestPT["Guest页表(HPA)"] GVA["GVA"] --> |"分段"| Linear["线性地址"] Linear --> |"页表查询"| gCR3 hGuestPT --> |"直接访问"| HPA["HPA"]

优点：

  • 硬件自动进行地址转换，减轻软件负担
  • 只需维护一套EPT页表
  • Guest OS缺页异常不会导致VM Exit

实测下来EPT比影子页表省事很多，不用自己同步页表，Guest缺页也不会动不动就VM Exit。

5. 中断虚拟化：虚拟IO APIC到Local APIC再到VCPU¶

5.1 虚拟中断架构：从虚拟设备到VCPU的路径¶

KVM为每个虚拟机提供了完整的虚拟中断控制系统：

flowchart TD VDev["虚拟设备"] -->|"触发中断"| VIO_APIC["虚拟IO APIC"] VIO_APIC --> VLAPIC["虚拟Local APIC"] VLAPIC -->|"事件注入"| VCPU["VCPU"] subgraph "VMM中的软件实体" VIO_APIC VLAPIC end

5.2 中断注入：四步把中断送进VCPU¶

当虚拟设备需要发送中断时：

  1. 虚拟设备调用虚拟IO APIC接口发送中断
  2. 虚拟IO APIC选择合适的虚拟Local APIC
  3. 虚拟Local APIC利用事件注入机制将中断注入VCPU
  4. VCPU获得调度时处理相应中断

我看中断注入会顺着虚拟设备→IO APIC→Local APIC→VCPU这条链走一遍，注入时机卡在VCPU获得调度那一刻。

6. KVM API：/dev/kvm上的三类ioctl调用¶

KVM通过/dev/kvm设备提供API接口，主要使用ioctl进行操作。API分为三类：

6.1 System API：全局参数与能力检查¶

针对虚拟化系统的全局性参数设置和控制：

  • KVM_CREATE_VM: 创建虚拟机
  • KVM_GET_API_VERSION: 获取API版本
  • KVM_CHECK_EXTENSION: 检查扩展功能支持情况

6.2 VM API：建VM、VCPU与内存区域¶

针对特定虚拟机的操作：

  • KVM_CREATE_VCPU: 创建虚拟CPU
  • KVM_SET_USER_MEMORY_REGION: 设置内存区域
  • KVM_CREATE_IRQCHIP: 创建中断控制器
  • KVM_RUN: 运行虚拟机

6.3 VCPU API：寄存器读写与中断注入¶

针对特定VCPU的操作：

  • KVM_GET/SET_REGS: 获取/设置通用寄存器
  • KVM_GET/SET_SREGS: 获取/设置特殊寄存器
  • KVM_INTERRUPT: 注入中断

一个典型的KVM API使用流程：

sequenceDiagram participant App as 应用程序 participant Dev as /dev/kvm App->>Dev: open("/dev/kvm") Dev-->>App: 返回kvmfd App->>Dev: ioctl(kvmfd, KVM_CREATE_VM) Dev-->>App: 返回vmfd App->>Dev: ioctl(vmfd, KVM_CREATE_VCPU, 0) Dev-->>App: 返回vcpufd App->>Dev: ioctl(vmfd, KVM_SET_USER_MEMORY_REGION, &region) App->>Dev: mmap(vcpufd, ...) Dev-->>App: 返回kvm_run结构体地址 loop 虚拟机运行 App->>Dev: ioctl(vcpufd, KVM_RUN) alt I/O操作 Dev-->>App: 返回I/O请求 App->>App: 模拟I/O设备 else 其他退出原因 App->>App: 处理其他VM Exit end end

我一般先调KVM_GET_API_VERSION和KVM_CHECK_EXTENSION探能力，再走CREATE_VM那串ioctl，顺序反了容易踩空。

7. 内核模块：kvm.ko加intel/amd两个架构后端¶

KVM由以下三个主要内核模块组成：

  1. kvm.ko: 提供核心虚拟化功能的通用模块
  2. kvm-intel.ko: 针对Intel处理器的特定实现
  3. kvm-amd.ko: 针对AMD处理器的特定实现

主要数据结构包括：

  • struct kvm: 表示一个虚拟机实例
  • struct kvm_vcpu: 表示一个虚拟CPU
  • struct kvm_run: 保存虚拟机运行状态
  • struct kvm_userspace_memory_region: 定义客户机内存区域
