17-感知模块-雷达感知

毫米波雷达怎么测距测速、CAN 消息怎么解析、运动补偿怎么做，以及它在融合里的测速和补盲角色。顺带说下超声波雷达的泊车用途。
📅 2026-11-03· 更新于 2026-11-03 · 3929 字 · 约 10 分钟 ✍ zeek.zhao #实战#apollo

相机怕黑，激光怕雾，雷达正好把这两块补上。这篇顺着 Apollo 的雷达链路走一遍：驱动怎么拆 CAN 消息，运动补偿怎么回灌，融合里它又干什么活。接着 16-感知模块-视觉感知 往下看，感知三源就齐了。

1. 雷达主打测速和补盲¶

毫米波雷达发射毫米波、收反射回波来探障碍，雨雾和夜间都稳。它的长处有三条：

  • 全天候工作，光照、雨雪、雾霾都不影响；
  • 靠多普勒效应直接给出目标距离和相对速度；
  • 探测距离远，200m 以上，穿透能力强。

短板也实在：角度分辨率低，认不出目标的形状和尺寸；行人这类非金属目标检测偏弱；多径效应还会添乱。我的判断是，别指望雷达去认目标，它真正的活是测速与补盲——和 15-感知模块总览与点云感知、16-感知模块-视觉感知 凑成感知三源，各管一段。

2. 雷达输出：稀疏、没有高度的点¶

特性 说明
测距 数十至数百米
测速 径向速度直接测量
角度 方位角分辨率较低
点云 稀疏、无高度信息

Apollo 的雷达驱动分三类：

  • modules/drivers/radar/conti_radar：大陆(Continental)毫米波雷达；
  • modules/drivers/radar/racobit_radar：理工雷科(Racobit)毫米波雷达；
  • modules/drivers/radar/ultrasonic_radar：超声波雷达（短距 0.3~5m，用于泊车场景）。

输出分两种模式。目标列表模式由雷达芯片内部完成检测和跟踪，直接吐出距离、速度和角度；点云模式给的是原始反射点，聚类和跟踪得自己做。驱动这层的活，就是把厂商协议解析出来，统一转成标准雷达消息发布出去。

3. 驱动架构：三层组件¶

graph TD A[雷达硬件 CAN 总线] --> B[ContiRadarCanbusComponent] B --> C[ContiRadarMessageManager 消息解析] C --> D[标准 ContiRadar 消息] D --> E[感知融合模块] L[定位模块] -->|车速/航向角| B B -->|运动补偿参数| A

核心组件三个：

  • ContiRadarCanbusComponent：模块入口，初始化 CAN 客户端和消息管理器，订阅定位做运动补偿；
  • ContiRadarMessageManager：按 CAN ID 解析消息，填充 ContiRadar 协议数据；
  • CanReceiver：独立线程接收 CAN 帧，转给消息管理器。

4. 运动补偿：把车速和角速度回灌给雷达¶

雷达测的是相对位置，自车一动就跟着变。补偿的做法是把车速和航向角速度经 CAN 发给雷达，让雷达内部算掉这部分。

串起来就是：定位给车速和航向角 → 转到雷达坐标系 → 走 MotionInputSpeed300/MotionInputYawRate301 发给雷达 → 雷达吐出补偿后的绝对位置和速度。

5. 消息解析：按 CAN ID 拆包¶

大陆雷达在 CAN 总线上发好几种消息，各自带不同的东西：

消息 内容
RadarState201 雷达工作状态与配置
ClusterListStatus600 / ClusterGeneralInfo701 / ClusterQualityInfo702 聚类障碍物数量、位置速度、质量(RCS)
ObjectListStatus60A / ObjectGeneralInfo60B / ObjectQualityInfo60C / ObjectExtendedInfo60D 目标障碍物数量、位置速度、质量、扩展信息(加速度)

7. 感知处理：滤波、聚类、跟踪¶

驱动吐出的雷达目标进到感知层，走四步：

  1. 预处理：滤掉静态杂波、地面反射这些噪声；
  2. 检测/聚类：按反射强度阈值过滤、聚类，再用运动特征检测；
  3. 跟踪：卡尔曼滤波加状态预测，多假设跟踪(MHT)处理目标交互；
  4. 输出：把障碍物候选交给融合。

8. 融合里雷达干什么¶

雷达在融合框架里有三处替代不了：直接测径向速度，修正相机和激光估出来的目标速度；远距离和恶劣天气下维持观测，补视觉和激光的短板；对金属车辆目标检测好，跟视觉的类别信息互补。

关联靠时间对齐加空间对齐，把雷达目标跟相机、激光目标配对（关联与坐标系见 15-感知模块总览与点云感知 与 18-传感器标定与坐标转换），最后输出统一的速度和类别。

接入调试有个顺序值得照着来：先确认驱动解析正常、话题频率到 50Hz 级；再看原始数据、比对 DreamView，先排除硬件和驱动，回头才动算法配置。网络丢包会让数据断续，协议不匹配会吐乱码，安装位置不对会留盲区，这三个最常见。参数上，RCS 阈值影响检测灵敏度，输出类型在目标和聚类之间挑一个。

9. 误报、漏检和多目标¶

真跑起来，麻烦集中在三处：护栏、路牌这类静态物体容易误报；行人这种低反射目标容易漏；多个目标靠近时分不清。办法是拿多传感器融合互补，用卡尔曼或粒子滤波改善跟踪，调 RCS 阈值和输出类型，再上 CFAR 恒虚警检测和 DOA 到达方向估计；分类和跟踪也可以交给深度学习。

雷达本身在往 4D 成像雷达走：MIMO 虚拟阵列把角度分辨率和点云级输出做上来了，恶劣天气下也能识别目标轮廓。这是我最愿意盯的一条线——它把雷达从”只会测速补盲”往”能出轮廓”推了一步。Apollo 10.0 的多传感器持续融合框架进一步增强了雷达和相机、激光的特征级融合；”大感知”体系下，雷达数据进到联合训练的多任务网络，模型个数和计算量都往下走（见 15-感知模块总览与点云感知）。超声波雷达则继续守着泊车这类低速近距场景，配合 24-仿真平台与场景数据 里的泊车场景验证。

操作步骤¶

接一路雷达，按这个顺序来：

  1. 确认 CAN 卡硬件在位，加载驱动，看 /apollo/sensor/radar/front 有没有数据
  2. 用 cyber_monitor 看话题频率，目标是 50Hz 级（对应 input_send_interval: 20000000，即 20ms）
  3. 核对 CAN 配置：brand/type/channel_id 要和硬件一致，enable_debug_mode 先关掉
  4. 核对雷达参数：max_distance、output_type（目标列表还是聚类）、rcs_threshold、是否发扩展信息
  5. 启动定位模块，确认 PoseCallback 的速度/角速度确实发到了雷达（抓 CAN 帧看 300/301 报文）
  6. 打开 DreamView 看雷达目标叠加，比对实际车辆位置：静止目标不该跟着自车动
  7. 录一段包含护栏、行人、相邻车辆的数据包，调 RCS 阈值和输出类型
  8. 接融合：先确认时间对齐（雷达时间戳与相机/激光同步），再看空间对齐（外参见 18-传感器标定与坐标转换）
  9. 最后用恶劣天气/夜间数据回归，确认雷达补盲效果

使用流程¶

雷达数据从硬件到融合的链路：

关键分支在驱动层：Parse 收到 ClusterListStatus600 或 ObjectListStatus60A 才写满一帧。如果这两个 ID 没出现，下游永远收不到完整消息——排查时先看原始 CAN 帧里有没有这两个 ID。

运动补偿是独立的一支：定位模块 → PoseCallback → CAN 报文 300/301 → 雷达内部补偿 → 输出的才是绝对速度。少了这一支，静止目标会随车运动”漂移”。

注意事项与常见坑¶

  1. CAN 通道号写错：channel_id 与实际 CAN 卡通道不符，收不到任何帧
  2. CAN 波特率不匹配：雷达侧和 CAN 卡侧波特率不一致，解析出乱码
  3. 列表状态 ID 缺失：没收到 600/60A，驱动不发布完整帧，下游一直空
  4. 运动补偿没接定位：PoseCallback 没数据，静止物体速度跟着自车变
  5. 速度取错分量：(rotation_matrix * speed_v).y() 写成 x 或 z，补偿方向错
  6. 角速度单位错：雷达要度/秒，定位给的是弧度/秒，忘了乘 180/M_PI
  7. 发送间隔过短：input_send_interval 设太小，CAN 总线过载、丢帧
  8. RCS 阈值太低：护栏、路牌大量误报；太高则行人、自行车漏检
  9. 多雷达通道混淆：前后雷达用了同一个 radar_channel，数据串台
  10. 输出类型选错：需要跟踪 ID 却配了点云模式，聚类得自己做
  11. 时间戳没同步：雷达与相机/激光时间对不上，关联错配（见 18-传感器标定与坐标转换）
  12. 安装角没标定：雷达俯仰角偏差导致距离-高度映射错，远处的目标位置偏移
  13. 超声波误当远距用：USS 只有 0.3~5m，别拿它做行车避障
