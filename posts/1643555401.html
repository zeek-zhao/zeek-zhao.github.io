14-调试与可视化工具（DreamView）

DreamView 看现象，cyber 命令行看数据，录制回放留现场。这套工具怎么配合、排查路径怎么走，附五种常见可视化现象的对照表。
📅 2026-11-06· 更新于 2026-11-06 · 4070 字 · 约 11 分钟 ✍ zeek.zhao #排障#apollo

调试 Apollo 光盯着代码没用，得看着数据跑起来才知道哪一段断了。这篇把 DreamView 和 cyber 那套命令行工具过一遍，最后给一条能照着走的排查路径。上一篇的配置参数见 13-Apollo配置文件与参数。

1. DreamView：把数据画在浏览器里¶

DreamView 是 Apollo 的 Web 可视化工具，实时显示车辆位姿、感知结果、规划轨迹和控制状态，还能叠高精地图。它本身就是一个 Cyber 模块，订阅各模块的输出消息，在浏览器里渲染。调试基本离不开它。

2. 七个功能面板¶

功能 说明
场景地图 叠加显示高精地图、车辆位置与朝向、障碍物
感知可视化 障碍物检测框、类别与速度、车道线、信号灯状态

几个常用操作：

  • 地图与车辆选择：右上角选当前加载的地图（对应 --map_dir）和车辆配置。地图不一致，可视化就会错位
  • 图层开关：只保留怀疑链路的相关图层，避免信息淹没
  • 多视角：俯视看规划和感知的整体形态，跟随视角查局部细节

4. 录制回放复现偶发问题¶

偶发场景最难调，因为复现不了。录制回放就是干这个的，也是做算法对比的常用手段：

回放会按原来的时序重发数据，模块像在实时运行一样被”喂”历史数据。配合断点或日志能逐帧看根因。偶发问题一旦录下来，就有了一个可重复的复现环境。

要说最省时间的调试习惯，我会先把现场录下来再动手改，改完回放对比，比反复上实车快得多。

5. 一条排查路径走到底¶

拿”规划轨迹异常”举例，完整排查路径：

  1. 模块面板确认运行状态（DreamView 模块状态 / cyber_node list）
  2. cyber_channel hz 检查输入通道频率：
    感知 /apollo/perception/obstacles 是否在发？
    定位 /apollo/localization/pose 频率是否 100Hz 稳定？
  3. 输入正常 → 打开轨迹可视化，观察异常形态：
    抖动？偏移？不贴合参考线？
  4. 结合日志（data/log/ 下模块日志）定位算法环节
  5. 录制现场数据，回放 + 调参迭代验证

几条通用原则：

  • 逐层检查数据流：从传感器 → 感知 → 定位 → 规划 → 控制，用模块开关与频率检查定位数据断裂点
  • 先输入后算法：确认输入数据质量正常再怀疑算法。输入问题多出在 09-传感器接入-相机激光雷达毫米波 的时间同步与 07-高精地图HD-Map 的地图对齐
  • 对比观察：规划轨迹对比实际轨迹、点云对比地图叠加、图像对比检测框
  • 记录形成问题库：场景模板加录制文件加日志关键字，把团队的调试经验沉淀下来

7. 日志与资源检查¶

日志分析有几个技巧：用模块名加时间戳对齐多模块日志，关键字搜 AWARN、AERROR 找告警。高频路径上少打日志，免得干扰实时性。

8. 五种常见现象的排查表¶

现象 可能原因 处理
车辆不动/位置错误 地图选择错误、定位未启动 核对 DreamView 地图选项与 --map_dir，用 cyber_monitor 查定位话题
看不到障碍物 感知模块未启动或传感器数据断流 检查 /apollo/perception/obstacles 频率与传感器链路
无规划轨迹 输入缺失（感知/定位/路由）或路由未设置 检查三路输入频率；确认已发送 Routing 请求
点云与地图错位 外参标定偏差或时间同步问题 检查标定文件与传感器时间戳，见 08-定位模块 排查
界面卡顿 消息流量过大或浏览器性能限制 关闭大流量图层（点云渲染），或换用 DreamView Plus

我的习惯是联调前先过一遍自检清单：各通道频率正常、模块状态全绿、地图和车辆配置正确。这一遍能滤掉大半低级问题，剩下的精力留给真正的算法缺陷。

补一个 9.0 之后的变化：DreamView Plus 换了套新的 Web 架构，渲染性能和大规模场景可视化都强了不少，还支持插件化扩展。经典 DreamView 没退场，轻量调试照样能用。配合包化模块开发，自己的模块也能写可视化插件了。

9. 让调试更快的四招¶

  • 场景模板：为高频复现的典型场景（路口、跟车、泊车）建立录制模板，快速重放
  • 离线分析优先：能在回放中定位的问题不上实车，节省场地与安全成本
  • 日志关键字沉淀：维护”问题现象 → 日志关键字 → 根因 → 修复”对照表，形成团队问题库
  • 工具链组合拳：DreamView 看形态、cyber_monitor 看频率、cyber_recorder 留现场、日志看细节——四件套覆盖绝大多数调试场景

配置参数怎么影响模块行为，回顾 13-Apollo配置文件与参数；Cyber 框架背景见 11-Apollo-Cyber-RT框架。

代码示例与实现细节¶

示例 1：启动整套调试环境 —— 解决「DreamView 怎么起、在哪看」。

常见坑：8888 端口被占用时 DreamView 起不来；用 lsof -i:8888（或 netstat）查占用进程；容器端口没映射到宿主机也会导致浏览器打不开。

示例 2：cyber_monitor 交互式监控 —— 解决「全局频率与延迟怎么看」。

实操：cyber_monitor 是排查数据断流的第一工具——通道频率为 0 就是数据没发出来，直接定位到发布模块。

示例 3：cyber_channel 通道诊断四连 —— 解决「某个通道到底有没有数据」。

常见坑：hz 显示 0Hz 不一定是没有发布者，也可能是发布者进程卡死；配合 cyber_node list 确认节点还活着。

示例 4：节点与服务探查 —— 解决「模块进程状态与服务接口怎么查」。

用途：规划模块收不到路由请求时，用 cyber_service list 查 Routing 服务是否存在，确认服务链路正常。

示例 5：录制全部通道留现场 —— 解决「偶发问题怎么复现」。

常见坑：-a 会把点云、图像等大流量通道全录下来，几十秒就可能几个 GB；磁盘空间不够时改用 -c 只录关注通道。

示例 6：按关注通道录制 —— 解决「录制文件太大怎么瘦身」。

调参：调试规划问题时只录定位、感知、规划三路通道，体积小、回放快；调试感知问题时加上传感器原始通道。

示例 7：按时间段与倍速回放 —— 解决「怎么只重放问题发生的那一段」。

常见坑：回放时若真实传感器也在发数据，会出现”两套数据打架”；回放前先停掉真实驱动或用独立容器。

示例 8：DreamView 回放模式加载录制数据 —— 解决「怎么在可视化界面里看历史数据」。

常见坑：录制时的地图必须与 DreamView 当前加载地图一致，否则车辆位置与地图错位——先看地图选项（--map_dir 对应配置见 13-Apollo配置文件与参数）。

示例 9：日志与资源联合排查 —— 解决「模块报错与系统瓶颈怎么同时看」。

实操：用时间戳对齐多模块日志（各模块日志同一时刻的行），还原故障发生时的完整链路；高频路径少打日志，避免拖慢实时性。

示例 10：规划轨迹异常的端到端排查脚本 —— 解决「排查路径怎么落地」。

排查心法：先确认输入正常再怀疑算法——输入问题多出在传感器时间同步（见 09-传感器接入-相机激光雷达毫米波）与地图对齐（见 07-高精地图HD-Map）。

操作步骤 / 使用流程¶

注意事项与常见坑¶

  1. 端口被占用：8888 端口被占则 DreamView 起不来；先查端口占用再启动。
  2. 地图选错：DreamView 地图与 --map_dir 不一致，车辆位置与地图错位。
  3. 容器端口未映射：8888 没映射到宿主机，浏览器打不开界面。
  4. hz=0 不等于没发布：可能是发布进程卡死；配合 cyber_node list 确认节点存活。
  5. 录制文件过大：record -a 会把点云/图像全录下来，磁盘瞬间吃满；改用 -c 选通道。
  6. 回放数据打架：真实传感器与回放数据同时发，出现两套数据冲突；回放前停真实驱动。
  7. 回放地图不一致：录制时的地图与当前加载地图不同，可视化错位；核对地图选项。
  8. 只看界面不看数据：DreamView 画的是加工后结果，原始问题要靠 cyber_channel echo 看。
  9. 高频路径打日志：日志过多拖慢实时性；只在关键分支打，排查完移除。
  10. 不录现场就改代码：偶发问题没录下来，改完无法验证；先留现场再动手。
  11. 多模块日志不对齐：不按时间戳对齐，无法还原链路；用同一时刻的行交叉比对。
  12. 忽视系统资源：GPU 温度过高降频、CPU 跑满都会造成”算法异常”假象；先看 nvidia-smi/top。
