56-自动驾驶云服务与基础设施

📅 2026-09-25· 更新于 2026-09-25 · 4642 字 · 约 12 分钟 ✍ zeek.zhao #apollo#教程

前面几篇讲标注、讲测试，真正把它们撑起来的是云。单车一天产生的数据，不是一台工作站能接住的；训练和万级场景仿真也得放到集群上。这篇把云平台的分层、数据底座、训算底座和车云协同过一遍；标注那头见 55-标注工具与数据闭环，测试策略见 54-自动驾驶测试方法。

1. 云在研发链路里干六件事¶

角色 功能 典型服务
数据中心 PB 级研发/运行数据管理 数据湖、对象存储
计算中心 大规模分布式训练 GPU 集群、训练平台
研发中台 全流程工具链 开发环境、CI/CD
仿真平台 虚拟测试与场景管理 云端仿真引擎
运营中心 车队监控与调度 监控系统
地图服务 高精地图分发与更新 地图云、增量更新

价值说白了就四条：突破本地算力限制、按需付费降低门槛、靠数据加速迭代、支撑多车协同。

2. 四层架构，混合云是主流¶

设计原则：分层解耦、横向扩展、微服务化、弹性伸缩、多租户隔离。

部署模式：公有云（初创/小规模）、私有云（核心研发数据可控）、混合云（主流选择：核心私有 + 弹性公有）、多云（避免锁定）、边缘云（低延迟车云协同）。多数自动驾驶企业最终采用混合/多云策略。

3. 单车每小时 60-130GB 怎么存¶

3.1 数据规模¶

数据来源 单车每小时 100 车队每日
摄像头 20-40 GB 50-100 TB
激光雷达 38-76 GB 90-180 TB
毫米波雷达 1-5 GB 2.4-12 TB
车辆状态/其他 1-13 GB 6-30 TB
合计 60-130 GB 150-320 TB

年增长 40-60%，倒逼 EB 级存储与冷热分层策略。

3.2 数据湖架构与存储选型¶

数据湖四层：接入层（车载/仿真/第三方）→ 存储层 → 处理层（批 Spark / 流 Flink）→ 服务层（查询/可视化/API），辅以元数据管理与数据治理。

数据类型 推荐存储 理由
传感器原始数据 对象存储（S3/OSS/COS） 高吞吐、冷热分层、生命周期管理
车辆状态数据 时序数据库（InfluxDB） 高写入、高压缩
标注数据 关系数据库（PostgreSQL） 事务与索引
高精地图 空间数据库 + 对象存储 空间索引、分区
训练数据集 分布式文件系统（HDFS/Ceph） 并行访问
模型参数 对象存储 + 版本库 版本回滚

数据处理管线：车端采集 → 传输（增量 + 断点续传）→ 清洗验证 → 标注（见 55-标注工具与数据闭环）→ 转换 → 索引 → 数据集版本化。

4. 训算底座：K8s 加分布式训练¶

4.1 AI 训练平台¶

核心能力要求：数百至数千 GPU 协同、端到端自动化训练流程、多任务混合调度、智能资源分配。

GPU 集群管理要点：Kubernetes + GPU 调度插件、GPU 虚拟化与共享、拓扑感知调度（NVLink/InfiniBand）、弹性训练与自动故障恢复。

分布式训练框架对比：

框架 特点 适用
PyTorch DDP 深度集成，NCCL 通信 数据并行主力（见 52-PyTorch与自动驾驶实践）
DeepSpeed / FSDP ZeRO 分片、3D 并行 超大模型（端到端/VLA）
Horovod Ring-AllReduce，轻量 跨框架数据并行

性能优化：梯度压缩、通信计算重叠、混合精度、拓扑感知通信。

4.2 实验与超参数管理¶

工具：MLflow（开源追踪）、Weight & Biases（可视化）、Optuna/Ray Tune（自动调参）。核心价值：实验可复现（代码/数据/配置三版本绑定）、早停策略节约算力。

5. 云端仿真万级并行¶

云端仿真平台支持 1000+ 并行仿真实例、仿真速度达实时的 10-100 倍：

组件 技术实现
任务编排 Kubernetes + Argo Workflows
资源调度 自定义调度器、GPU 共享
分布式存储 Ceph/S3，高吞吐
结果分析 Spark/Presto + Web 3D 可视化

与真实测试形成闭环：路测数据 → 场景挖掘 → 仿真重构 → 差异分析校准仿真模型 → 改进后再预测验证（测试策略详见 54-自动驾驶测试方法）。

6. 按延迟分四层算¶

6.1 分层计算¶

层级 位置 延迟 功能
L1 车载边缘 车内 <10ms 实时决策、数据筛选
L2 路侧边缘 道路设施 10-50ms 环境感知、车路协同
L3 区域边缘 基站/边缘 IDC 50-100ms 多车协调
L4 中心云 数据中心 >100ms 训练、大数据分析

6.2 数据同步与端云推理¶

  • 同步策略：紧急事件实时推送、传感器数据批量筛选上传、OTA 分块下载；多通道（4G/5G/WiFi）+ 断点续传
  • 端云推理协同：安全关键功能车端为主（低延迟、离线可用）；复杂非实时决策可上云；模型经量化/裁剪/蒸馏后下沉车端，模型分割可在带宽与算力间取平衡

7. 合规要设计进去，不是补上去¶

环节 措施
车端 安全启动、本地加密、数据脱敏（人脸/车牌）
传输 TLS 加密、双向认证
云端 静态加密、多租户隔离、备份容灾
访问 RBAC、最小权限、审计
隐私技术 匿名化、差分隐私、联邦学习（数据不出域联合训练）

主要法规：GDPR（欧盟）、CCPA（加州）、中国《个人信息保护法》《数据安全法》——车外环境图像属高敏感数据，位置轨迹极敏感，跨境传输受限。合规必须”设计即合规”，而非事后补救。

8. 开源代码做研发，云上做闭环¶

Apollo 官方云端能力一直在扩大，也划清了和开源代码的边界：云端仿真（Cloud Sim）提供免安装的浏览器仿真体验与大规模并行验证；Fuel 研发云平台提供全云端工具链；数据管线与模型增量训练平台支撑量产迭代。Apollo 10.0/11.0 代际的部分感知模型训练已依赖百度云平台——开源社区拿到的是模型与代码，规模化训练能力在云端。

选型上可以按”开源代码做研发验证 + 云平台做数据闭环”双轨规划（资源入口见 59-自动驾驶学习资源与链接）。我的看法是，双轨几乎是唯一现实的走法：单机复现不了云端的训练规模，硬要复现只会浪费时间。

代码示例与实现细节¶

下面这组配置把「数据湖 + 训练平台 + 云仿真」这条链路上最关键的实现点串起来，均来自源文档的架构与选型章节，按工程落地的顺序排列。

1. 计算配额：给关键任务留 80% CPU（cgroups v1）¶

这段解决同城混合负载下关键任务被普通任务抢占的问题，是 L4 训算底座资源隔离的原型；车载侧的同款做法见 57-自动驾驶操作系统。

参数怎么调：cfs_quota_us / cfs_period_us 就是核心数上限，800000/1000000 表示 0.8 核；要按整机核数成比例放大。常见坑：cgroups v2 的路径与接口完全不同（改为 cpu.max），上面这段不能照搬。

2. 设置 CPU 亲和性（C 语言）¶

这段解决进程在核心间迁移导致缓存失效的问题，是拓扑感知调度的底层手段。

参数怎么调：控制/规划/感知可分别绑到 CPU0 / CPU1 / CPU2-3。常见坑：sched_setaffinity 传的是线程 ID（tid）而不是进程组，绑错对象等于没绑。

3. 存储选型速查（从源文档表提炼）¶

这段解决「什么数据放哪种存储」的决策问题，可用作架构评审 check list。

参数怎么调：数据分片、多级缓存、并行访问与数据压缩是四种通用性能优化手段；成本侧则靠冷热分离、生命周期管理与复制因子优化。常见坑：把原始点云塞进关系库，查询慢且存储贵。

4. 车云同步优先级表¶

这段解决带宽受限时「先传什么」的问题，是数据闭环设计的核心策略。

紧急异常事件 最高优先级 实时立即推送 KB/event
车辆状态数据 高 实时/准实时增量 KB-MB/min
地图数据 中-高 区域优先增量 MB-GB/update
模型更新 中 版本发布差异 MB-GB/model
OTA 更新包 中 计划性分块 MB-GB/update
传感器原始数据 低-中 筛选 + 压缩批量 GB-TB/day

参数怎么调：带宽不够时按优先级从低到高停传。常见坑：原始数据不分优先级全量上传，直接把链路打死，正确做法是先边缘筛选压缩。

5. 端云推理四种协同模式¶

这段解决推理任务在车端与云端之间怎么切分的问题。

车端为主 ：低延迟、离线可用；基础驾驶 / 安全关键功能
云端为主 ：算力足、模型复杂；复杂决策 / 非实时场景
模型分割 ：车端提特征 + 云端做推理；网络较稳定场景
自适应协同 ：按场景 / 负载 / 网络动态切换；高级自动驾驶

参数怎么调：模型量化 INT8 可让体积缩小 2-4 倍、推理快 2-3 倍；结构裁剪可减 30-70% 体积；知识蒸馏保留 80-90% 性能、体积缩小 5-10 倍。常见坑：把安全关键的制动决策放云端，网络抖动就是事故。

6. 云仿真平台技术栈¶

这段解决万级并行仿真的组件选型问题。

任务编排 ： Kubernetes + Argo Workflows
资源调度 ： 自定义调度器 + GPU 共享
分布式存储 ： Ceph / S3（高吞吐）
结果分析 ： Spark / Presto + Web 3D 可视化
规模目标 ： 1000+ 并行实例，10-100 倍实时速度

参数怎么调：场景优先级决定谁先跑。常见坑：只堆实例数不做差异分析校准，仿真与真实偏差越来越大，跑得越多错得越多。

7. 分布式训练框架与优化手段¶

这段解决大规模训练框架选型与通信优化问题。

PyTorch DDP ： NCCL 通信，数据并行主力（详见 52-PyTorch与自动驾驶实践）
DeepSpeed ： ZeRO 分片 + 3D 并行，超大模型
Horovod ： Ring-AllReduce，轻量跨框架
优化五件套 ： 梯度压缩 / 通信计算重叠 / 混合精度 / 智能批处理 / 拓扑感知通信

参数怎么调：FP16 混合精度能同时省显存与通信量。常见坑：多机训练不配 NCCL 拓扑，带宽浪费在跨 NUMA 节点上。

8. 成本优化收益对照¶

这段解决「先省哪里」的成本决策问题，数字取自源文档成本优化表。

竞价/抢占式实例 50-80% 节省 容错任务 实施难度 中-高
冷热数据分层 40-70% 节省 大规模数据 实施难度 中
预留承诺折扣 30-60% 节省 稳定负载 实施难度 低
数据生命周期管理 30-60% 节省 大量历史数据 实施难度 低-中
自动扩缩容 20-40% 节省 波动负载 实施难度 中

参数怎么调：训练计算成本占总体 30-50%，优先优化 GPU 选择。常见坑：把不能中断的训练放竞价实例，被回收后前功尽弃。

9. 数据湖五层架构¶

这段解决数据孤岛问题，给出统一数据平台的完整分层。

接入层：车载 / 仿真 / 第三方 / 标注数据
存储层：对象存储 / 分布式 FS / 时序库 / 关系库
处理层：Spark 批 / Flink 流 / AI 训练平台
服务层：探索查询 / 可视化 / 数据 API
治理层：元数据 / 质量 / 生命周期 / 安全权限

参数怎么调：治理层要贯穿其余四层，而非事后补。常见坑：先建存储后补元数据，最后连有哪些数据集都说不清。

操作步骤 / 使用流程¶

下面是从源文档提炼的云平台搭建 checklist，按顺序做完即可拿到一条最小可用的数据闭环。

注意事项与常见坑¶

  1. 原始数据不做边缘筛选就全量上传：带宽会被瞬间打满，必须先筛选压缩、按优先级分批传。
  2. 把安全关键决策放云端：网络延迟不稳定，制动等安全功能必须车端闭环。
  3. 仿真只堆实例不做差异校准：仿真模型与真实偏差会累积，越跑越偏。
  4. 元数据治理事后补：数据湖没有元数据就等于数据沼泽，治理层必须从第一天就建。
  5. 多机训练忽略 NCCL 拓扑：跨 NUMA 通信会吃掉大部分加速收益，要做拓扑感知调度。
  6. 竞价实例跑不可中断训练：节点被回收后若没检查点恢复机制，训练直接归零。
  7. 合规当事后补丁：车外图像与位置轨迹属高敏感数据，跨境传输受限，必须”设计即合规”。
  8. 只依赖 GitHub release tag 复现环境：Apollo 10.0/11.0 通过开放平台发布在 master 上，应 pin commit。
  9. 冷热数据同价存储：历史数据不分层，存储成本会失控，要用生命周期管理自动迁移。
  10. 忽略多租户隔离：研发与运营共用集群不隔离，一个团队的失控任务能拖垮全平台。
