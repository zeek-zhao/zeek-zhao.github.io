1. 需求背景¶

1.1 目标¶

让本地 AI 助手能够直接用自然语言查询、操作内部 Jira 与 Confluence：

  • 查询 / 搜索 Jira Issue（JQL）、项目、看板、Sprint、工作日志
  • 创建 / 更新 / 流转 / 评论 / 删除 Issue
  • 搜索 / 读取 / 创建 / 更新 Confluence 页面、评论、附件、标签
  • 查看 Space 页面树、页面历史与差异、权限

1.2 约束条件¶

约束 说明
实例类型 Atlassian Server / Data Center（非 Cloud，域名非 *.atlassian.net）

2. 环节一：方案调研¶

联网调研 Jira × Confluence × MCP 的主流接入方案，确定采用社区维护、官方文档完备的 **mcp-atlassian**（GitHub：sooperset/mcp-atlassian）。

2.1 为什么选 mcp-atlassian¶

  • 单一 Python 包，同时覆盖 Jira + Confluence，一个进程暴露全部工具（实测 98 个）
  • 原生支持 Server/Data Center 的 PAT 认证（JIRA_PERSONAL_TOKEN / CONFLUENCE_PERSONAL_TOKEN），正好匹配本次凭据
  • 支持 Cloud（邮箱 + API Token）、PAT、OAuth 2.0、mTLS 多种认证
  • 提供 uvx / pip / Docker / 源码四种运行方式

2.2 运行方式取舍¶

方式 是否采用 说明
uvx mcp-atlassian 否 本机未安装 uv，且 uvx 缓存不在目标目录
pip 安装到 venv 是 把包装进 D:\zeek\WorkBuddy\MCP\venv，满足「文件落在该目录」的要求
Docker 否 本机无 Docker 需求，且 stdio 本地进程更简单
源码 否 没必要
🔥决策
用本机自带 Python 3.13 建一个 venv，把 mcp-atlassian 装进去，再用 venv 内的 mcp-atlassian.exe 作为 MCP Server 的 command。既零侵入（实例侧无改动），又把下载物集中在 D:\zeek\WorkBuddy\MCP\。

5. 环节四：PAT 认证配置（含踩坑）¶

5.1 环境变量映射¶

Server/DC 的 PAT 认证只需「实例地址 + PAT」，无需用户名 / 邮箱：

变量 值
JIRA_URL https://issues.rollingwireless.com

CONFLUENCE_URL https://confluence.rollingwireless.com
CONFLUENCE_PERSONAL_TOKEN <confluence-pat>（占位符，真实值见 mcp.json）
⚠️第一次 401 的根因（重要踩坑）
用户给出的两行是 CONFLUENCE_PAT=... 在前、JIRA_PAT=... 在后。初次联调时把两个 token 张冠李戴（Jira 用了 Confluence 的 token，反之亦然），两端均返回 401。
通过响应头定位：X-Seraph-LoginReason: OK 表示该 token 在其对应系统登录成功；WWW-Authenticate: OAuth realm=... 表示 token 用错系统被拒。据此纠正映射后两端均 200。

9. 经验教训与后续建议¶

9.1 经验教训¶

🔥关键经验
  1. PAT 严格绑定系统：Jira 的 PAT 只能用于 Jira，Confluence 的 PAT 只能用于 Confluence；用错系统会 401（响应头 WWW-Authenticate 可识别）。
  2. 先 curl 后配置：用 GET /rest/api/2/myself 与 /rest/api/user/current 验证 PAT，比直接调 MCP 更快二分问题。
  3. venv 落盘满足「文件归位」：用 pip + 项目内 venv 替代 uvx，既能集中存放下载物，又避免额外装 uv。
  4. TOOLSETS=all 早设：新版默认工具集会缩减，提前显式声明避免「工具变少」困惑。
  5. 凭据只在本地启动脚本：文档与脚本一律占位符，PAT 不进 Git / 聊天 / 共享文档。

9.2 后续建议¶

  • 信任并启用：在 WorkBuddy 连接器管理页面对 atlassian-rw 点击 Trust 启用（写入 mcp.json 不会自动激活）。
  • PAT 轮换：PAT 有有效期，到期前在用户中心重新生成并更新 mcp.json。
  • 最小权限：如仅需只读，可在 Atlassian 侧为 PAT 限定权限范围。
  • 多实例扩展：若另有 Cloud 实例，可再加一个 server 用 JIRA_USERNAME + JIRA_API_TOKEN 认证。

10. 环节七：连接失败排查 → 改造为 HTTP 常驻（2026-10-30）¶

10.1 现象¶

连接器列表里已经能看到 atlassian-rw，但点连接就失败；.workbuddy 那个 App 里每次必失败，.workbuddy-ai 里时好时坏。

10.2 定位过程¶

第 1 步：看 daemon 日志，直接拿到失败事件：

判读：pidSpawned 有值 → 进程起来了；stderrChunks: 0 → 没崩没报错；elapsedMs 31568 > timeoutMs 30000 → 握手超时。所以不是路径错、不是崩溃，是启动太慢。

第 2 步：量启动耗时（同一台机器，连测三次）

测量项 结果
python -c "pass" 576 ms
import fastmcp 2.5–4.8 s
import mcp_atlassian.servers.main 8.5–13 s
完整 stdio 握手 10.7 / 13.7 / 12.3 s
遍历 site-packages（12,156 文件 / 158 MB） 118 s → 1.3 MB/s
CPU 基准（1e7 次循环） 1.5 s（正常约 0.3 s）

第 3 步：排除错误方向

  • 裁减工具集：all 8.5s / default 7.0s / 精选 6 个 11.1s → 无稳定收益，导入开销固定。
  • 换盘：C: 与 D: 小文件延迟无本质差异 → 瓶颈是 Defender 实时扫描，不是磁盘型号。
  • 探活超时可配？读 bundle 确认 normalizeTimeout 有硬编码上下限，应用层不可配。

第 4 步：确认之前的判断错了

曾认为「本版不读全局 mcp.json」。实际 CODEBUDDY_MCP_CONFIG 环境变量里明确有
"atlassian-rw":{"type":"stdio",...,"_workbuddyMcpOrigin":"custom"}，daemon 也有 wb:mcp:connect arg="custom-mcp:atlassian-rw" —— 条目确实被注册并尝试连接了，只是卡在超时。原结论作废。

10.3 改造方案：HTTP 常驻¶

思路：冷启动那 9–13 秒只付一次，之后连接毫秒级。

改造中又踩两个坑：

  1. 401：HTTP 模式默认按「每用户令牌」鉴权，服务端日志
    UserTokenMiddleware: rejecting unauthenticated MCP request (no user identity and ALLOW_GLOBAL_CRED_FALLBACK is off)
    → 启动脚本加 set "ALLOW_GLOBAL_CRED_FALLBACK=true"。
  2. .cmd 中文注释把脚本解析崩了：报「此时不应有 常驻。」→ .cmd 全部改 ASCII 注释。

另有两个环境性坑：--path /mcp 在 Git Bash 里被 MSYS 改写成 Windows 路径；http_proxy=127.0.0.1:9979 会干扰本地探测，需 NO_PROXY。

10.4 结果¶

指标 stdio（改造前） HTTP 常驻（改造后）
连接耗时 9–13 s（探活上限 30 s） 0.35 s
稳定性 并发时必超时 稳定
工具数 98 98（Jira 63 + Confluence 35）
真实调用 — jira_get_all_projects 返回 46,993 字节
mcp.json 是否含令牌 是（明文） 否，只剩 URL

10.5 自启动的约束¶

schtasks.exe、wscript.exe 都在本机工具黑名单里，AI 侧无法创建计划任务 → 改用启动文件夹放隐藏启动器（WorkBuddy-AtlassianMCP.vbs）。代价是只在登录时启动，重启 App 后需手动双击一次 ensure-mcp-http.cmd。
