29-Cyber数据系统详解

一条消息从进进程到触发 Proc，中间发生了什么。DataDispatcher、CacheBuffer、DataNotifier 和 AllLatest 怎么配合。
📅 2026-10-22· 更新于 2026-10-22 · 5164 字 · 约 13 分钟 ✍ zeek.zhao #概念#apollo

消息从网卡进来，到组件 Proc 真正拿到手，中间这段以前我一直当黑盒。这篇专门拆这段路：数据怎么分发、怎么缓存、怎么唤醒协程，以及多路输入怎么揉成一组。使用层怎么建 Reader/Writer 见 12-Cyber消息通信与组件开发；唤醒之后协程怎么跑，是 26-Cyber调度系统详解 那一侧的事。

1. 一条消息的六步旅程¶

一条消息的生命周期（本进程视角）可归纳为六步：

sequenceDiagram participant W as Writer participant TR as Transmitter participant RE as Receiver participant DD as DataDispatcher participant CB as CacheBuffer participant DN as DataNotifier participant DV as DataVisitor participant CR as 协程 W->>TR: 写入通道 TR->>RE: 传输（进程内引用/共享内存/网络） RE->>DD: 触发回调分发 DD->>CB: Fill 进每个订阅者的环形缓存 DD->>DN: Notify(channel_id) DN->>DV: 调用注册的唤醒回调 DV->>CB: TryFetch 取数据/融合 DV->>CR: 唤醒协程执行 Proc

设计目标：高吞吐、低延迟、灵活融合、无锁热路径、故障隔离。

2. DataVisitor 是接线员¶

2.1 构造时干三件事¶

DataVisitor 是”组件与数据系统”的接线员，构造时完成三件事（回看 25-Cyber启动系统详解 中组件 Initialize 第 5 步）：

  1. 向 DataDispatcher<M> 注册自己的 ChannelBuffer
  2. 向 DataNotifier 注册唤醒回调
  3. 多输入场景创建数据融合器

2.2 TryFetch：协程取数入口¶

协程被唤醒后通过 TryFetch 拉取数据；这正是组件 Proc 的数据来源：

返回 false 时协程进入 DATA_WAIT（状态机见 26-Cyber调度系统详解）。

3. 分发中心按消息类型分¶

每种消息类型 M 对应一个 DataDispatcher<M> 单例。它内部维护一张原子哈希表，键是通道 ID，值是一串订阅者缓存：

关键设计：

  • std::shared_ptr<M> 贯穿全链：从 Receiver 到 CacheBuffer 到回调，传递的是同一个对象引用——这就是 Cyber 进程内”零拷贝”的真正实现层（真正的内存级零拷贝传输见 30-Cyber网络IO详解）
  • weak_ptr 存储订阅者：组件销毁后残留 buffer 自动失效，不阻塞分发
  • AtomicHashMap 使热路径免锁

4. 每个订阅者一份环形缓存¶

每个”订阅者 × 通道”持有独立的 CacheBuffer，容量由 DAG 中的 queue_size/history_depth 决定：

classDiagram class CacheBuffer~T~ { -vector<T> buffer_ -uint64_t head_ -uint64_t tail_ -uint64_t capacity_ -std::mutex mutex_ +Fill(value) +Fetch(index, msg) bool +Latest(msg) bool +Empty() bool +Full() bool +SetFusionCallback(cb) }

填充策略（满则覆盖最旧数据）：

缓存满就覆盖最旧数据，这是刻意的自动驾驶语义：处理最新观测比补历史更重要。queue_size 给小了，多输入组件更容易对不齐；给大了，内存和延迟又跟着涨。这个参数没有通用最优值，得看下游消费速度。

5. Notifier 把分发和访问解开¶

DataNotifier 单例维护”通道 ID → Notifier 列表”，把分发器与具体的 DataVisitor 解耦：

classDiagram class Notifier { +std::function<void()> callback } class DataNotifier { <<singleton>> -AtomicHashMap<uint64_t, vector<Notifier>> notifies_map_ +AddNotifier(channel_id, notifier) +Notify(channel_id) }

Notify(channel_id) 遍历该通道所有 Notifier 并执行回调——即 26-Cyber调度系统详解 中 Scheduler::NotifyProcessor 的起点：

6. AllLatest 只保证都尽量新¶

多输入组件靠融合策略保证”取到一组互相匹配的数据”。Planning 就是典型，预测、定位、底盘三路数据一起吃。

6.1 AllLatest 语义¶

以第一个通道的新消息为基准，搭配其余通道各自的最新消息：

graph LR A[通道A: 1, 2, 3, 4] --> C{AllLatest} B[通道B: a, b] --> C C --> D["输出: (1,null), (2,a), (3,a), (4,b)"]

6.2 实现¶

融合回调挂在主通道的 CacheBuffer 上。主通道一来新消息，就把其余通道的最新值取出来打包：

Fusion(index, m0, m1) 随后从融合缓存按游标取出成对数据。

有个边界得说清楚：AllLatest 只保证”都尽量新”，不保证时间戳严格对齐。要时间对齐的融合（比如感知多传感器），得在业务层做时间窗口校验——配合 27-Cyber时间系统与定时器 的时间戳体系和 31-Cyber-Transform与坐标变换 的时空插值。真要按时间戳配对，照这个模式自己写一个融合器就行。

7. 从消息到回调的完整闭环¶

把本篇与调度篇串起来，一次完整的”消息→回调”闭环：

graph TB A[消息到达 Receiver] --> B[DataDispatcher.Dispatch] B --> C[CacheBuffer.Fill 共享指针入环形缓存] B --> D[DataNotifier.Notify] D --> E[Scheduler.NotifyProcessor task_id] E --> F[CRoutine SetUpdateFlag → READY] F --> G[Processor 取协程执行] G --> H[DataVisitor.TryFetch] H -- 无数据 --> I[协程进入 DATA_WAIT] H -- 有数据 --> J[组件 Proc 执行] J --> K[处理完成，协程再次等待]

8. 四个工程取舍¶

  1. 无锁/低锁热路径：AtomicHashMap、AtomicRWLock、原子状态机将锁压缩到临界区极小的位置
  2. shared_ptr 全链传递：杜绝大消息拷贝；引用计数的原子性保证跨线程安全
  3. 每订阅者独立缓存：慢消费者只覆盖自己的旧数据，不拖累其他订阅者
  4. 通道 ID 体系：通道名经 GlobalData::RegisterChannel 哈希为 uint64，哈希表查找 O(1)

9. 常见问题诊断¶

现象 可能原因 排查
Proc 永不触发 通道名不匹配 / 上游未发布 / DataNotifier 未注册 cyber_channel hz 验证上游；cyber_node info 验证订阅
多输入组件频繁跳拍 下游消费慢，环形缓存覆盖旧数据 增大 queue_size；检查 Proc 耗时（SysMo）
多输入数据”对不齐” AllLatest 天然不对齐 业务层时间窗口校验
内存持续增长 shared_ptr 循环引用（回调捕获自身） 回调改捕获 weak_ptr
同名任务/通道冲突 哈希碰撞或重复注册 检查 DAG 中组件名唯一性

补一个时间背景。Cyber RT 从 Apollo 3.5（2019）引入起，就用 DAG 图组织组件依赖、运行时生成轻量任务、支持零拷贝消息通信。官方说 10.0 代际传输性能提升约 10 倍，主要贡献就是进程内 shared_ptr 引用传递、进程间共享内存和无锁数据系统。这套六步链路到 10.0/11.0 代际都没变，算是稳住了。

10. 四件套撑起数据链路¶

把这一路收个口：数据系统就是分发（DataDispatcher）+ 缓存（CacheBuffer 环形覆盖）+ 通知（DataNotifier）+ 访问与融合（DataVisitor + AllLatest） 四件套。底色是 shared_ptr 全链零拷贝，默认 QoS 是”满则覆盖旧数据”。我比较认可这个取舍——车载场景下，最新一帧永远比补历史值钱。它往下通过 Notify 钩住调度器（26-Cyber调度系统详解），往上承接组件的 Reader/Proc（25-Cyber启动系统详解）；跨进程那一程（Transmitter/Receiver 之下）交给 30-Cyber网络IO详解。

代码示例与实现细节¶

下面这组代码片段与图表把数据系统再往细里拆一层：从组件全景、访问器类结构、分发流程、融合策略，到 Planning 实际 Proc、自定义时间窗口融合与调试工具用法。它们回答的是「消息进缓存到 Proc 之间究竟怎么实现」。

1. 数据系统核心组件全景¶

这段解决「从 Writer 到回调的完整组件链长什么样」的问题：发布端与订阅端两大子图呈现数据流转。

graph TD subgraph 数据发布端 Writer --> Transmitter Transmitter --> Channel end subgraph 数据订阅端 Channel --> Receiver Receiver --> DataDispatcher DataDispatcher --> CacheBuffer DataDispatcher --> DataNotifier DataNotifier --> DataVisitor CacheBuffer --> DataVisitor DataVisitor --> Routine[协程] Routine --> Callback[回调处理] end

参数怎么调：设计目标为高性能、低延迟、灵活融合、可靠、隔离；常见坑是把进程内 shared_ptr 传递当成内存级零拷贝，后者由 30-Cyber网络IO详解 的共享内存传输负责。

2. DataVisitor 类结构¶

这段解决「单输入与多输入 DataVisitor 有什么区别」的问题：基类提供注册回调与游标，子类按 1 个或 2 个通道特化。

classDiagram class DataVisitorBase { +RegisterNotifyCallback(callback) #next_msg_index_ #data_notifier_ #notifier_ } class DataVisitor~M0~ { +DataVisitor(config) +TryFetch(msg) -buffer_ } class DataVisitor~M0,M1~ { +DataVisitor(config) +TryFetch(msg0, msg1) -data_fusion_ -buffer_m0_ -buffer_m1_ } DataVisitorBase <|-- DataVisitor~M0~ DataVisitorBase <|-- DataVisitor~M0,M1~

参数怎么调：每个数据处理流程对应一个 DataVisitor 实例；常见坑是手工 new 多个 Visitor 指向同一通道，造成重复注册与重复唤醒。

3. TryFetch 取数流程¶

这段解决「协程调用 TryFetch 时如何决定单取还是融合」的问题：单通道直接取，多通道走 DataFusion。

graph TB A[协程调用TryFetch] --> B{是单个通道?} B -- 是 --> C[从Buffer直接获取] B -- 否 --> D[调用DataFusion融合数据] C --> E{获取成功?} D --> E E -- 是 --> F[递增消息索引] E -- 否 --> G[返回失败] F --> H[返回数据]

参数怎么调：返回 false 时协程进入 DATA_WAIT 等待下次唤醒；常见坑是融合器一直不产出导致组件”假死”，通常是副通道迟迟无数据。

4. DataDispatcher 分发流程¶

这段解决「一条消息如何找到所有订阅者」的问题：按通道 ID 查 AtomicHashMap，遍历弱引用缓存填充并通知。

flowchart TB A[收到消息] --> B[查找通道对应的BufferVector] B --> C{找到订阅者?} C -- 是 --> D[遍历所有订阅Buffer] C -- 否 --> E[无需分发] D --> F[向每个Buffer填充消息] F --> G[通过DataNotifier通知消息到达]

参数怎么调：订阅者用 weak_ptr 存储，销毁后自动失效；常见坑是订阅者生命周期管理混乱导致弱引用频繁失效，消息看似丢失。

5. DataNotifier 通知流程¶

这段解决「分发器如何把’数据到了’传给 Visitor」的问题：按通道查 Notifier 列表并逐个回调。

flowchart TB A[DataDispatcher调用Notify] --> B[查找通道对应的NotifyVector] B --> C{找到Notifier列表?} C -- 是 --> D[遍历所有Notifier] C -- 否 --> E[结束流程] D --> F[调用每个Notifier的回调]

参数怎么调：回调最终表现为 Scheduler::NotifyProcessor(crid)；常见坑是 Notifier 注册遗漏导致 Proc 永不触发，排查见第 9 节诊断表。

操作步骤 / 使用流程¶

下面是一套「数据链路异常」的标准排查 runbook，从确认通道、检查订阅、观测缓存覆盖到验证融合时序。

关键检查点：先确认上游发布与订阅注册，再判断是缓存覆盖还是融合不对齐，最后排查内存与引用问题。

注意事项与常见坑¶

  1. 把 shared_ptr 传递当内存零拷贝：进程内只是对象引用共享，真正的内存级零拷贝由共享内存传输实现，见 30-Cyber网络IO详解。
  2. AllLatest 不做时间对齐：只保证”都尽量新”，严格时间同步须业务层校验，见 27-Cyber时间系统与定时器。
  3. queue_size 设置不当：给小了多输入易对不齐，给大了内存和延迟上涨，需按消费速度实测。
  4. 缓存满静默覆盖：默认覆盖最旧数据，慢消费者可能一直丢帧，需监控覆盖情况。
  5. shared_ptr 循环引用：回调捕获自身 shared_ptr 导致泄漏，应改捕获 weak_ptr。
  6. 订阅者弱引用失效：组件销毁后 buffer 自动失效，生命周期混乱会造成消息”丢失”假象。
  7. Notifier 未注册：DataVisitor 构造时漏注册会导致 Proc 永不触发，按诊断表用 cyber_node info 排查。
  8. 多 Visitor 重复注册：多个实例指向同一通道会重复唤醒和竞争，应保证组件与 Visitor 一一对应。
  9. 消息乱序未处理：各通道到达时间不同步，需基于时间戳排序/同步，不能假设顺序一致。
  10. 时间戳未填或基准不一致：漏填 header 导致下游按 0 时间处理，混用系统时间函数与 Time API 会乱序。
  11. 录制全部通道：调试录制应只选关键通道，否则产生超大文件且回放失真。
  12. 融合查找无界扫描：自定义融合器按时间窗口查找副通道消息时须限制范围，避免 O(n) 退化。
